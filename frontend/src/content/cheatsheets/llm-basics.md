## Токены и контекстное окно

**Токен** — элемент словаря токенизатора: слово, часть слова или знак; единица цены и лимитов, не JWT-токен. «Около четырёх символов на токен» — грубый ориентир для английского; для русского и кода соотношение другое. Считайте токенизатором модели.

**Окно контекста** — бюджет одного вызова: инструкции + история + документы RAG + вопрос + место под генерацию. У API бывают отдельные пределы входа и выхода, а у reasoning-моделей учитывается и бюджет рассуждений. Длинный контекст дороже; детали в середине могут теряться.

Превышение бюджета входа вызывает ошибку или обрезку истории; лимит генерации — обрыв ответа. Проверяйте причину завершения.

## Как модель пишет и почему галлюцинирует

Модель вычисляет распределение **следующего токена**, выбирает токен, добавляет его к тексту и повторяет до остановки или лимита. После «Столица Франции —» вероятным продолжением будет «Париж».

Обучение продолжать текст не означает проверку фактов. Модель может не знать свежих данных и выбирать правдоподобную выдумку вместо «не знаю». Веса не заменяют проверяемые источники.

Снижают риск: **RAG со ссылками**, разрешённое «не знаю», инструменты для актуальных данных, проверка опоры ответа. Низкая temperature уменьшает случайность, но не гарантирует истинность.

## Temperature, top-p и top-k

| Параметр | Что меняет |
|---|---|
| Temperature | Остроту распределения: ниже — вероятные варианты сильнее, выше — больше разнообразия |
| Top-k | Оставляет k наиболее вероятных токенов |
| Top-p | Оставляет небольшой набор с суммарной вероятностью не ниже p |

Для фактов, кода и JSON нужна стабильность, для вариантов — разнообразие. **Temperature = 0 не означает «без ошибок»** и не всегда обеспечивает побитовую повторяемость. Настраивайте один механизм за раз; поддержка зависит от API.

## Роли и история в API

Пример обмена:

```text
system: Ты — поддержка магазина. Отвечай кратко.
user: Где заказ 123?
assistant: tool_call get_order(id=123)
tool: {"status": "в пути"}
assistant: Заказ в пути.
```

Инструкции system/developer задаёт приложение, user — пользовательский запрос в этих рамках. Assistant содержит ответы и запросы инструментов; tool — результат выполнения приложением. Роли и приоритеты зависят от API.

В stateless-вызове историю передаёт приложение; другие API могут хранить её отдельно. Окно всё равно ограничено. **System-промпт не является защитой прав:** документы и результаты инструментов — недоверенные данные, доступ проверяет серверный код.

## Zero-shot, few-shot и рассуждение

**Zero-shot** — задача без примеров: «Определи тональность отзыва». **Few-shot** — несколько пар «вход → выход», задающих формат и границы:

```text
«Курьер опоздал» → негатив
«Всё пришло целым» → позитив
«Доставили за час!» → ?
```

Давайте примеры границ задачи без противоречий. Это контекст, а не дообучение.

**Chain of thought** — промежуточное рассуждение. Может помочь сложным задачам, но стоит времени и токенов. Reasoning-модели рассуждают сами; запрос внутренней цепочки не универсально полезен. Просите итог, необходимые вычисления и проверяемое объяснение.

## Стриминг ответа

Без стриминга пользователь ждёт готовый ответ; со стримингом получает части по мере генерации. **TTFT** — время до первого токена; полная длительность может почти не измениться, но ожидание ощущается короче.

```text
data: {"delta": "Заказ"}
data: {"delta": " в пути"}
data: [DONE]
```

Упрощённый SSE; события зависят от API. Обрабатывайте обрыв, отмену и ошибки. JSON валидируйте после сборки полного результата; неполный фрагмент не означает валидный объект.

## Валидный JSON и проверка ответа

**Просьба «верни JSON»** не даёт гарантии. **JSON mode** обеспечивает синтаксис в поддерживаемом режиме, но не обязательные поля. **Structured outputs** ограничивают генерацию поддерживаемой схемой; отказы и обрывы обрабатываются отдельно.

```python
from typing import Literal
from pydantic import BaseModel, Field

class Ticket(BaseModel):
    category: Literal["оплата", "доставка", "другое"]
    priority: Literal["low", "high"]
    summary: str = Field(max_length=200)
```

Поток: **проверить завершение → разобрать → Pydantic → бизнес-правила → использовать**. Схема гарантирует допустимую форму при успешном структурированном ответе, но не истинность summary или правильность категории. Ошибка → ограниченный повтор с безопасным описанием ошибки → fallback или ручной разбор. Бесконечные повторы недопустимы.

## Как снизить стоимость

Стоимость ≈ **входные токены × тариф входа + выходные × тариф выхода**, суммируется по всем вызовам. Учитывайте кэш, рассуждения и повторы.

- Выбирать модель по задаче; каскад дешёвая → сильная при необходимости.
- Сокращать вход: релевантные чанки RAG, компактные инструкции, сжатая история.
- Сокращать выход: нужный формат и разумный лимит без обрыва полезного ответа.
- Кэшировать разрешённые ответы и промпты; семантический кэш требует проверки уместности и изоляции пользователей.
- Для несрочного — пакетная обработка; для агентов — бюджеты шагов, токенов и ретраев.

## API или открытые веса

| Критерий | Управляемый API | Собственный запуск открытых весов |
|---|---|---|
| Старт | Без своей GPU-инфраструктуры | Нужны вычисления и обслуживание |
| Цена | Обычно за использование | Инфраструктура и эксплуатация |
| Данные | Обрабатывает выбранный провайдер | Остаются в контролируемом контуре при локальном размещении |
| Контроль | Версии и доступность зависят от сервиса | Выбираете версию, настройки, дообучение |

Качество сравнивайте на своей задаче; открытые веса не означают свободную лицензию. Модель можно вынести за адаптер, чтобы менять провайдера. Свой запуск не гарантирует безопасность.
