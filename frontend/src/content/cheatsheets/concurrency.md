## Конкурентность и параллелизм

**Конкурентность** — несколько задач продвигаются за один период. **Параллелизм** — задачи выполняются одновременно. На одном ядре A и B могут чередоваться; на двух — работать одновременно.

**CPU-bound** долго считает; **I/O-bound** ждёт сеть, БД или диск. Конкурентность перекрывает ожидание I/O, но сама по себе не ускоряет вычисления. Сначала измерьте узкое место: запуск работников и передача данных тоже стоят времени.

## Процессы, потоки и GIL

| Свойство | Потоки | Процессы |
|---|---|---|
| Память | Общая | Изолирована |
| Обмен | Общие объекты | IPC, сериализация |
| Запуск | Обычно дешевле | Обычно дороже |

В обычной сборке CPython **GIL** позволяет одному потоку интерпретатора выполнять Python-байткод за раз. При блокирующем I/O GIL обычно освобождается; некоторые нативные библиотеки освобождают его и при вычислениях. У процессов отдельные интерпретаторы.

С Python 3.13 доступны отдельные **free-threaded** сборки без GIL; поведение зависит от сборки и расширений. GIL не заменяет синхронизацию общего состояния.

## Что выбрать под задачу

| Нагрузка | Инструмент |
|---|---|
| I/O с async-библиотекой | asyncio |
| I/O с sync-библиотекой | ThreadPoolExecutor |
| CPU на чистом Python в обычном CPython | ProcessPoolExecutor |

**100 сетевых запросов:** asyncio + лимит конкурентности + таймауты. **Частоты слов в корпусе:** процессы и достаточно крупные порции данных. Для маленького объёма последовательный вариант может быть быстрее. CPU-библиотека, отпускающая GIL, — отдельный случай: проверьте потоки измерением.

## Race condition и Lock

Два работника читают 5 и оба пишут 6: ожидали 7, потеряли одно увеличение (**lost update**). Даже короткая операция изменения общего состояния не должна считаться атомарной без гарантии.

```python
import threading

lock = threading.Lock()  # один для всех работников
with lock:
    counter += 1
```

Защищайте **всю последовательность чтение → вычисление → запись**, включая проверки, от которых зависит изменение. Все участники используют один lock.

**Deadlock:** A держит L1 и ждёт L2, B держит L2 и ждёт L1. Захватывайте несколько блокировок в одном согласованном порядке. В asyncio гонки тоже возможны, если между чтением и записью есть await; для задач одного loop используют asyncio.Lock.

## async, await и event loop

| Запись | Что происходит |
|---|---|
| async def f() | Описывает корутинную функцию |
| f() | Создаёт объект корутины, обычно ещё не выполняет её |
| await f() | Выполняет корутину и получает результат |
| asyncio.run(main()) | Запускает верхнюю корутину в обычном скрипте |

Event loop выполняет задачи кооперативно: **готова → выполняется → ждёт I/O → снова готова**. В одном loop Python-код одной задачи работает за раз. Await отдаёт управление, когда приходится ждать; уже готовый результат может вернуться без переключения. Само слово async не превращает код в неблокирующий.

## Task, create_task и gather

Task организует выполнение корутины через event loop. Сначала создайте обе задачи, затем ждите результаты:

```python
a = asyncio.create_task(job("A"))
b = asyncio.create_task(job("B"))
x = await a
y = await b
```

Если каждая job ждёт секунду, последовательные await двух **корутин** займут около двух секунд. Обе Task созданы заранее — около секунды.

**gather(*aws)** планирует переданные корутины и возвращает результаты **в порядке аргументов**. По умолчанию первая обычная ошибка передаётся вызывающему коду, остальные задачи автоматически не отменяются. Если нужен принцип «ошибка одного отменяет остальных», рассмотрите TaskGroup.

## Блокирующий код в async

| Блокирует поток loop | Даёт другим задачам работать |
|---|---|
| time.sleep(2) | await asyncio.sleep(2) |
| Синхронный HTTP/БД | Async-клиент или вынос в поток |

Файловое I/O и длинный CPU-цикл также занимают поток event loop. Синхронное I/O можно вынести:

```python
result = await asyncio.to_thread(blocking_io, arg)
```

to_thread прежде всего подходит для **sync I/O**. Для CPU на чистом Python в обычном CPython нужен пул процессов. Отмена ожидания потока не гарантирует остановку уже запущенной функции.

## Лимит запросов и ошибки

```python
sem = asyncio.Semaphore(10)

async def one(url):
    async with sem:
        return await asyncio.wait_for(fetch(url), timeout=3)

results = await asyncio.gather(
    *(one(url) for url in urls),
    return_exceptions=True,
)
```

Не больше **10 запросов внутри семафора** одновременно; слот освободится и при ошибке. Таймаут здесь **не включает ожидание слота**. wait_for отменяет ожидание при превышении лимита, но завершение отмены может занять дополнительное время.

В results будут ответы или исключения: проверяйте каждый элемент. **CancelledError обычно передавайте выше**, не скрывайте отмену. Лимит конкурентности не равен запросам в секунду; для rate limit нужен отдельный механизм.

## Результаты без общего счётчика

Каждый работник возвращает локальный результат, сборщик объединяет:

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor() as pool:
    total = sum(pool.map(count, chunks))
```

Это схема агрегации; для CPU-функции count в обычном CPython выбирайте ProcessPoolExecutor. Для потока результатов между потоками подходит **queue.Queue**: общий изменяемый счётчик не нужен.

**Ментору:** потерянный +1 → lock на всю операцию; сбор результатов → return и sum; time.sleep внутри async → блокировка loop; лимит с частичными ошибками → Semaphore и разбор результатов gather. job, fetch, count — прикладные функции фрагментов.

Документация: [asyncio: задачи и отмена](https://docs.python.org/3/library/asyncio-task.html), [threading](https://docs.python.org/3/library/threading.html), [пулы исполнителей](https://docs.python.org/3/library/concurrent.futures.html).
