## RAG-пайплайн по шагам

**Retrieval-Augmented Generation** — сначала найти релевантные документы, затем дать модели найденный контекст для ответа. **Веса модели не меняются.** RAG помогает работать с частными и свежими знаниями, приводить источники и учитывать права. Вся база в промпте упирается в окно, цену и качество.

**Индексация заранее:**

1. Загрузить и очистить документы: PDF, wiki, тикеты.
2. Разбить по структуре на чанки.
3. Получить эмбеддинг каждого чанка.
4. Сохранить вектор, текст и метаданные: источник, версия, права.

**На каждом запросе:** вопрос → совместимый эмбеддинг → поиск top-k с фильтрами доступа → при необходимости реранкинг → промпт с чанками и id → ответ со ссылками. Если доказательств нет — сообщить об этом, а не заполнять пробел выдумкой.

## Эмбеддинги

**Эмбеддинг** — вектор фиксированной размерности, обычно сотни или тысячи чисел, построенный отдельной моделью. Близкие смыслы могут получить близкие векторы даже без общих слов: «питомец», «кот», «кошка». Это свойство модели, а не гарантия для любых текстов.

**Косинусное сходство = (a · b) / (‖a‖ × ‖b‖).** Для ненулевых векторов близость к 1 означает сходное направление; 0 — ортогональность, −1 — противоположное направление. Это не вероятность правильного ответа.

Вопросы и документы кодируют совместимой моделью и её режимами query/document. При смене пространства эмбеддингов документы обычно переиндексируют. Применения: семантический поиск, RAG, кластеризация, рекомендации. **Эмбеддинг не равен токену.**

## Векторные базы данных

Хранят векторы вместе с текстом и метаданными, ищут ближайших соседей. **ANN** — приближённый поиск; HNSW ускоряет его ценой памяти и компромисса полноты/скорости, а не обещает всегда точный top-k.

| Инструмент | Типичный выбор |
|---|---|
| pgvector | Векторы рядом с данными Postgres, SQL и транзакции |
| Qdrant | Отдельный сервис поиска с фильтрами |
| Chroma | Быстрый старт, встраиваемый или серверный режим |

```sql
CREATE INDEX ON chunks
USING hnsw (embedding vector_cosine_ops);

SELECT id, text FROM chunks
WHERE team_id = $2
ORDER BY embedding <=> $1
LIMIT 5;
```

Для pgvector **<=> — косинусное расстояние**, 1 − сходство: меньше — ближе. Пример предполагает готовую таблицу и параметры запроса. team_id сервер получает из авторизованного контекста; пользователь не выбирает чужую команду. Права ограничивают поиск **до передачи текста модели**. При ANN фильтры могут сократить выдачу — проверяйте recall с ними. HNSW в pgvector поддерживает vector до 2000 измерений и halfvec до 4000; ограничения проверяйте для используемой версии.

## Чанкинг: размер и перекрытие

Один вектор длинного документа размывает темы. Режьте по заголовкам, абзацам и смысловым границам; сохраняйте источник и заголовок. **300–800 токенов и 10–20% overlap** — отправная гипотеза из исходной памятки, а не универсальный оптимум.

| Чанки | Последствия |
|---|---|
| Слишком крупные | Шум, цена, в окно помещается мало разных фрагментов |
| Слишком мелкие | Теряется контекст, ответ собирается из обрывков |
| С перекрытием | Мысль на границе попадает в соседние фрагменты, но растут дубли |

Размер подбирают по корпусу, модели и контрольным вопросам. Таблицу или пример кода полезно сохранить целиком. Overlap помогает границам, но не заменяет структурное разбиение и удаление дублей.

## Гибридный поиск и реранкинг

**BM25** ищет по словам: полезен для кодов, артикулов и имён. **Векторный поиск** — по смыслу: синонимы, перефразы. Гибридный поиск объединяет оба списка, например **RRF** по позициям, без прямого сложения несопоставимых scores.

Пример: два поиска → объединение → около 50 кандидатов → **cross-encoder реранкер**, читающий вопрос и каждый чанк вместе → 5 лучших в LLM. Числа подбирают по качеству и задержке.

Реранкер обычно точнее сортирует кандидатов, но дороже; он **не вернёт документ, который не попал в кандидаты**. Встроенный ts_rank PostgreSQL не является BM25. Больше чанков не всегда лучше: шум отвлекает и расходует окно.

## RAG или fine-tuning

| Задача | Подход |
|---|---|
| Свежие факты, частные документы, ссылки и права | RAG |
| Устойчивый стиль, формат, специализация поведения | Fine-tuning |

RAG подставляет знания при запросе; fine-tuning меняет веса на примерах. Заучивание меняющейся базы через дообучение плохо решает обновление, удаление и проверку источников. Подходы можно сочетать.

Практический порядок: **ясный промпт и baseline → RAG, если нужны знания → дообучение, если подтверждена проблема поведения или эффективности**. Это порядок проверки гипотез, а не обязательный маршрут каждого приложения.

## Оценка качества RAG

Начните с набора характерных вопросов, эталонных ответов и релевантных источников. Например, 50–200 вопросов — стартовая выборка; добавляйте отказы, отсутствующие ответы, права и сложные случаи.

| Участок | Что проверять |
|---|---|
| Retrieval | Hit rate@k: есть ли хотя бы один нужный документ; Recall@k: какая доля всех нужных найдена |
| Порядок | MRR: среднее обратного ранга первого релевантного результата |
| Generation | Faithfulness: подтверждаются ли утверждения контекстом; relevance: ответ по вопросу; correctness: верен ли он |

**Поиск и ответ измеряйте отдельно:** так видно, потерян источник или искажён ответ. Ссылка сама по себе не доказывает опору. LLM-as-a-judge работает по явной рубрике и проверяется человеком на выборке. После изменения чанкинга, модели или промпта прогоняйте тот же набор; в работе следите за фидбэком, отказами, задержкой и ценой.

**Ментору:** эмбеддинг → смысловой вектор; векторная БД → поиск соседей; RAG → найти и подставить; чанкинг → компромисс контекста и точности; fine-tuning → поведение; оценка → retrieval отдельно от generation. Связка с инструментами — [Tool calling и агенты](/cheatsheets/agents).

Детали индексов и фильтров: [pgvector](https://github.com/pgvector/pgvector).
