## Tool calling: модель просит, приложение выполняет

**Tool calling** — структурированный запрос модели на вызов инструмента: имя функции и аргументы. Код выполняет приложение, а не сама языковая модель. Описание инструмента задаёт назначение и схему аргументов; это не разрешение выполнить всё, что попросит модель.

1. Приложение передаёт вопрос и описания доступных функций.
2. Модель возвращает запрос, например get_order с id = 123.
3. Приложение проверяет разрешённое имя, аргументы по схеме, права пользователя и принадлежность заказа.
4. Вызывает функцию/API с таймаутом и ограничениями.
5. Возвращает результат модели, связывая его с конкретным запросом инструмента.
6. Модель отвечает по результату либо запрашивает следующий инструмент.

```text
user: Где заказ 123?
assistant: tool_call get_order(id=123)
приложение: проверка → вызов API
tool: {"status": "в пути"}
assistant: Заказ в пути.
```

Ответ может содержать несколько запросов инструментов; независимые можно выполнять параллельно при допустимых правах и лимитах. Названия ролей и формат результата зависят от API. **Не обещайте «будет завтра», если инструмент не вернул срок.**

## Агент, ReAct и Plan-and-Execute

**Обычный вызов:** вход → ответ, следующий шаг задаёт код. **Агентный сценарий:** модель выбирает следующие шаги и инструменты, получает результаты и продолжает до цели или ограничения. Не каждый чат-бот является агентом; один tool call сам по себе тоже не требует сложной агентной системы.

| Подход | Цикл | Когда удобен |
|---|---|---|
| ReAct | Решение → действие → наблюдение → новое решение или ответ | Следующий шаг зависит от результата предыдущего |
| Plan-and-Execute | План → выполнение шагов → проверка → при необходимости новый план | Длинная задача с явными этапами |

Пример ReAct: «нужен статус» → запрос get_order → «в пути» → краткий ответ. Сохранять полезные решения и наблюдения можно без раскрытия внутренней цепочки рассуждений модели.

План облегчает проверку намерений, но не гарантирует результат: данные меняются, инструменты ошибаются. Выполнение каждого шага всё равно проходит серверные проверки. Если сценарий заранее известен, линейный код часто проще и надёжнее автономного выбора.

## LangChain и LangGraph

**LangChain** предоставляет интеграции и блоки для моделей, промптов, загрузчиков, разбиения документов, поиска и цепочек. Экосистема помогает собрать RAG; современные агентные API дают готовый цикл поверх LangGraph. Абстракции не отменяют различий провайдеров.

**LangGraph** описывает выполнение как граф: узлы, состояние, условные переходы, циклы, сохранение контрольных точек и паузы для участия человека. Удобен для долгих сценариев с возобновлением.

```text
START → retrieve → grade → generate → END
                    ↓
                  rewrite
                    ↓
                 retrieve
```

Если документы нерелевантны, запрос переписывается и поиск повторяется **до заданного лимита**, затем — отказ или другой fallback. Состояние содержит вопрос, документы, ответ и число попыток; поток данных и изоляция сессий задаются приложением.

Для короткого линейного сценария достаточно обычного кода. Граф нужен, когда ветвления, циклы и возобновление действительно полезны; наличие фреймворка не делает систему качественной автоматически.

## Ассистент по документам и живым данным

Вопрос: «Когда придут деньги по возврату 123?» Регламент отвечает об общих сроках, а актуальный статус конкретного возврата находится в сервисе.

1. **Бюджет окна:** инструкции + нужная история + вопрос + резерв генерации. Всю базу не отправляем.
2. **RAG:** найти top-k релевантных фрагментов регламента, доступных пользователю; передать текст и id источников.
3. **Tool calling:** модель просит get_refund(id=123); сервер проверяет владельца и вызывает сервис за текущим статусом.
4. **Ответ:** отдельно сообщить правило и статус. «По пункту 7 регламента — до 10 рабочих дней» допустимо только при наличии такого источника.
5. **Проверка опоры:** каждое фактическое утверждение подтверждается чанком или результатом инструмента; иначе — «не нашёл подтверждения».
6. **Офлайн-оценка:** контрольные вопросы, качество поиска, faithfulness и корректность ответа; человек проверяет выборку оценок.

Ссылка [id] должна вести именно к переданному источнику. Цитирование не доказывает, что вывод поддерживается текстом. **Документы — знания, инструмент — актуальное состояние; доступ к обоим ограничивает приложение.** Подробнее: [LLM: основы работы](/cheatsheets/llm-basics) и [RAG](/cheatsheets/rag).

## Ограничители, ошибки и ответы ментору

Задайте **лимит шагов и токенов, общий deadline, таймаут инструмента, ограниченные ретраи и условие остановки**. Повтор записи после таймаута опасен: используйте идемпотентность и проверку результата. Подтверждение человеком нужно для действий с существенными последствиями, например оплаты или удаления, согласно политике приложения.

Логируйте безопасные сведения о шаге, результате и стоимости, не секреты и полный чувствительный контекст. Результаты инструментов и документы могут содержать prompt injection: их нельзя превращать в инструкции, выдающие новые полномочия.

| Ошибка в ответе | Как сказать точно |
|---|---|
| «Модель сама вызвала функцию» | Модель запросила; приложение проверило и вызвало |
| «Агент — любой чат-бот» | Здесь модель управляет шагами цикла с инструментами |
| «RAG — дообучение» | RAG подставляет найденное в контекст |
| «Чем больше чанков, тем лучше» | Нужен баланс полноты, шума, окна и стоимости |
| «Проверили на пяти вопросах» | Нужны представительный набор, метрики и разбор ошибок |

**Ментору:** tool calling — контракт и ответственность приложения; агент против одного вызова — выбор следующих шагов; LangChain против LangGraph — блоки против управления графом; ассистент — окно → RAG → живые данные → ответ с проверяемой опорой.

Границы фреймворков: [LangChain](https://docs.langchain.com/oss/python/langchain/overview), [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview).
