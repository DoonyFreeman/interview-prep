# Offsite-бэкап БД: страховка от потери сервера

**Дата:** 2026-06-20
**Статус:** дизайн утверждён, готов к плану

## Проблема

Приложение хранит SQLite-базу (`data/app.db`) на named-volume сервера. В ней —
вся пользовательская стейт-часть: аккаунты (email + bcrypt-хэши), попытки,
прогресс/SM-2, статистика по глоссарию и тестам. Контент пересеивается из
репозитория при старте, но **пользовательские данные не воспроизводимы**.

Существующий `scripts/backup.sh` делает консистентные онлайн-снапшоты, но кладёт
их в `./backups/` **на том же сервере**. Если сервер выключат и сотрут (например,
забыли оплатить → хостинг удалил инстанс), локальные снапшоты исчезнут вместе с
базой. Нужна **offsite-копия** — бэкап, который живёт вне этого сервера.

## Решение

Заливать снапшоты в **отдельную orphan-ветку `backups`** того же приватного
GitHub-репозитория (`DoonyFreeman/interview-prep`).

### Почему orphan-ветка + force-push

Если коммитить бинарный `.db` в обычную накопительную ветку, каждый снапшот
**навсегда** оседает в истории git — `.git` пухнет на десятки/сотни МБ за год.

Вместо этого ветка `backups` каждый запуск **пересобирается с нуля как один
orphan-коммит** и заливается `git push --force`. Свойства:

- история git **не растёт** — предыдущий коммит становится недостижимым, GitHub
  его со временем GC-ит; бинарники не копятся;
- в ветке всегда лежат N последних снапшотов как обычные файлы — любой можно
  скачать;
- ветка полностью изолирована от `master`: не мёржится, не мешает коду.

### Решения по параметрам

- **Частота:** ежедневно (та же cron-строка, что и локальный бэкап).
- **Глубина (N):** 7 последних снапшотов (неделя). База маленькая → ветка лёгкая.
- **Шифрование:** нет. Репозиторий приватный; проект приватный (автор + друг).
  (Осознанный компромисс: доступ к репозиторию = доступ к email'ам + хэшам.)

## Компоненты

### 1. `scripts/backup-offsite.sh` (новый)

Запускается **после** `backup.sh` (который уже создал свежий снапшот и подчистил
`./backups/` до `KEEP`). Логика:

1. Собрать список последних N (`KEEP_OFFSITE`, default 7) файлов `app-*.db` из
   `./backups/`. Если снапшотов нет — выйти с ошибкой (нечего заливать).
2. Во временном каталоге (`mktemp -d`, удаляется через `trap`):
   - `git init -q`, скопировать N снапшотов + короткий `README.md`
     (что это, как восстановить);
   - закоммитить от имени бэкап-бота (`git -c user.name=... -c user.email=...`);
   - `git push --force <remote> HEAD:backups`.
3. Remote берём из основного репозитория (`git -C <repo> remote get-url origin`),
   чтобы не хардкодить.

Env-overrides по образцу `backup.sh`: `KEEP_OFFSITE` (7), `OUT_DIR` (`./backups`),
`BRANCH` (`backups`), `REMOTE` (автоопределение из origin).

`set -euo pipefail`, portable под bash 3.2 (как существующие скрипты).

### 2. `scripts/restore-offsite.sh` (новый, тонкая обёртка)

Для восстановления на чистом сервере, когда локальных снапшотов нет:

1. `git fetch <remote> backups` в временный каталог (или
   `git archive`/`git show`), достать **новейший** `app-*.db`.
2. Передать его существующему `scripts/restore.sh` (который останавливает app,
   подменяет файл на volume, чистит WAL-сайдкары, стартует обратно).

Не дублируем логику restore — переиспользуем `restore.sh`.

### 3. Предусловие: push-доступ сервера к репозиторию

Сейчас origin по SSH (`git@github.com:DoonyFreeman/interview-prep.git`). Для
push нужен ключ/токен **с правом записи**:

- вариант A: GitHub **deploy key с write-доступом** на этом репозитории;
- вариант B: fine-grained **PAT**, ограниченный одним репозиторием (Contents:
  write), прописанный в https-remote или credential helper.

Скрипт делает раннюю проверку (`git ls-remote` / пробный push) и падает с
понятным сообщением, если доступа нет.

### 4. Cron / документация

В `DEPLOY.md` обновить раздел бэкапов:

```cron
0 3 * * *  cd /opt/interview-prep && scripts/backup.sh && scripts/backup-offsite.sh >> backups/backup.log 2>&1
```

Плюс runbook: как настроить deploy key/PAT, как восстановиться с нуля через
`restore-offsite.sh`.

## Поток данных

```
cron (ежедневно)
  └─ backup.sh
       ├─ online snapshot из контейнера → ./backups/app-<ts>.db
       └─ прунинг до KEEP (14)
  └─ backup-offsite.sh
       ├─ взять 7 новейших ./backups/app-*.db
       ├─ orphan-коммит во временном каталоге
       └─ git push --force origin HEAD:backups   ← offsite-копия

восстановление на новом сервере
  └─ restore-offsite.sh
       ├─ git fetch origin backups → новейший app-*.db
       └─ restore.sh <file>  → подмена БД на volume → app up
```

## Обработка ошибок

- Нет снапшотов в `./backups/` → exit с сообщением (не пушим пустоту).
- Нет push-доступа → ранний выход с инструкцией (предусловие).
- Сбой push (сеть/GitHub down) → ненулевой код возврата; cron-лог это покажет.
  Локальные снапшоты при этом уже есть — единичный пропуск offsite не критичен.
- Временный каталог чистится через `trap ... EXIT` при любом исходе.

## Тестирование / верификация

Скрипты на bash, инфраструктурные — юнит-тестов нет. Верификация фактами:

1. Прогнать `backup-offsite.sh` локально против тестовой ветки → убедиться, что
   `backups` содержит ровно один коммит с N файлами.
2. Прогнать дважды → убедиться, что число коммитов в ветке остаётся 1 (история
   не растёт), `git count-objects` не пухнет линейно.
3. `restore-offsite.sh` на пустом volume → app поднимается, пользователь из
   снапшота логинится.

## Вне области (YAGNI)

- Шифрование дампа (репозиторий приватный).
- Напоминание об оплате сервера (это про биллинг хостинга, не про данные).
- S3/прочие хранилища — выбран git-branch.
