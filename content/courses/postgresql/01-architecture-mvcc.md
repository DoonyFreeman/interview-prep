# Архитектура PostgreSQL: MVCC, WAL, VACUUM

> Цель урока: понять, как PostgreSQL обеспечивает надёжность и конкурентность —
> через MVCC, журнал WAL и очистку VACUUM. Это объясняет «почему таблица
> раздувается» и «как работает изоляция в PG» — частые вопросы про эксплуатацию
> PostgreSQL.

## MVCC: версии строк

PostgreSQL использует **MVCC (Multi-Version Concurrency Control)**: при изменении
строки он **не перезаписывает её на месте**, а создаёт **новую версию**, оставляя
старую для транзакций, которые её ещё видят. Каждая транзакция работает со своим
**согласованным снимком** данных.

Главное следствие: **читатели не блокируют писателей, а писатели — читателей**.
`SELECT` не ждёт `UPDATE` той же строки (видит старую версию), а `UPDATE` не ждёт
`SELECT`. Это даёт высокую конкурентность без массовых блокировок.

```sql
-- транзакция A читает старую версию строки,
-- пока транзакция B её обновляет (создаёт новую версию) — никто не ждёт
```

У каждой версии строки есть служебные поля (`xmin`/`xmax` — какие транзакции её
создали/удалили), по которым PG решает, видна ли версия данной транзакции. Это
основа уровней изоляции в PostgreSQL.

**Аналогия.** MVCC — как система версий документа: пока один читает версию 5,
редактор создаёт версию 6. Каждый видит целостную версию на свой момент, и никому
не приходится ждать, пока другой допишет.

## WAL: журнал упреждающей записи

**WAL (Write-Ahead Log)** обеспечивает **долговечность (Durability из ACID)**:
прежде чем применить изменение к файлам данных, PostgreSQL **сначала записывает
его в журнал WAL** (последовательно, на диск). Правило «сначала журнал, потом
данные».

Зачем: если сервер упадёт, при перезапуске PostgreSQL **проиграет WAL** и
восстановит все подтверждённые (закоммиченные) транзакции — данные не потеряются,
даже если не успели попасть в основные файлы. Запись в журнал последовательна и
быстра (не нужно сразу писать вразброс по файлам данных).

WAL — не только про восстановление: на нём построены **репликация** (реплика
применяет WAL мастера), **point-in-time recovery** (откат на любой момент),
**бэкапы**. Это центральный механизм надёжности.

**Аналогия.** WAL — как сначала записать операцию в бухгалтерский журнал, а уже
потом разнести по счетам. Если по дороге свет выключился, по журналу всегда можно
восстановить, что было сделано, и довести до конца.

## VACUUM и bloat

У MVCC есть цена: старые версии строк (**dead tuples**) **накапливаются** — после
`UPDATE`/`DELETE` устаревшие версии остаются физически в таблице, пока их кто-то
может видеть. Без очистки таблицы и индексы **раздуваются** (**bloat**), занимая
место и замедляя сканирование.

**`VACUUM`** помечает мёртвые версии как свободное место для переиспользования (а
`VACUUM FULL` физически сжимает таблицу, но блокирует её). На практике работает
**autovacuum** — фоновый процесс, который автоматически чистит таблицы по порогам.
Дополнительно VACUUM обновляет статистику для планировщика и предотвращает
**transaction ID wraparound** (исчерпание счётчика транзакций — критичная
проблема).

```sql
VACUUM ANALYZE my_table;     -- очистить мёртвые версии + обновить статистику
```

Типичные проблемы эксплуатации: «таблица растёт, хотя строк столько же» — это
bloat от частых обновлений и отстающего autovacuum; лечится тюнингом autovacuum.
Понимание связки «MVCC создаёт мёртвые версии → VACUUM их чистит» — ключ к
ответу про раздувание.

**Аналогия.** VACUUM — как уборщик, выносящий старые черновики (мёртвые версии),
которые MVCC оставляет после правок. Если уборщик не успевает (autovacuum отстаёт),
кабинет (таблица) заваливается макулатурой и работать в нём медленнее.

## Памятка для собеседования

- **MVCC**: изменение создаёт **новую версию** строки, старая остаётся для тех, кто
  её видит → **читатели не блокируют писателей** и наоборот. Видимость по
  `xmin`/`xmax`.
- **WAL** (write-ahead log): **сначала журнал, потом данные** → долговечность
  (восстановление после сбоя проигрыванием WAL); основа **репликации**, PITR,
  бэкапов.
- **VACUUM**: MVCC оставляет **мёртвые версии** → без очистки **bloat** (раздувание);
  **autovacuum** чистит автоматически, обновляет статистику, предотвращает ID
  wraparound.

## Частые ошибки в ответах

- Не знать, что MVCC создаёт новые версии строк (думать, что UPDATE пишет на месте).
- Не связывать раздувание таблиц (bloat) с MVCC и отстающим VACUUM.
- Не понимать роль WAL (долговечность + основа репликации/бэкапов).
- Считать, что VACUUM сразу возвращает место ОС (обычное VACUUM — нет, только
  VACUUM FULL).
