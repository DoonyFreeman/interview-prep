# Конкурентность, блокировки и продвинутый SQL

> Цель урока: разобрать конкурентный доступ в PostgreSQL — `SELECT ... FOR
> UPDATE`, `SKIP LOCKED`, advisory locks — и продвинутые возможности (оконные
> функции, рекурсивные CTE, материализованные представления, партиционирование).
> Это вопросы уровня «как сделать очередь задач в PG» и «как не словить гонку».

## Явные блокировки строк

MVCC спасает читателей от ожидания, но иногда нужно **намеренно заблокировать**
строку, чтобы безопасно её прочитать-изменить (избежать **lost update** — гонки на
`read-modify-write`). Для этого — **`SELECT ... FOR UPDATE`**: блокирует выбранные
строки до конца транзакции, другие транзакции на тех же строках ждут.

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- блок строки
-- никакая другая транзакция не изменит её, пока мы не закоммитим
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

Это классический способ безопасно реализовать «списать со счёта»: между чтением и
записью никто не вклинится. Варианты: `FOR SHARE` (разделяемая, для чтения),
`FOR NO KEY UPDATE`. Без явной блокировки два параллельных `read-modify-write`
могут затереть друг друга.

**Аналогия.** `FOR UPDATE` — повесить табличку «занято» на конкретную строку: пока
ты с ней работаешь, остальные ждут у двери, и никто не перепишет данные у тебя
из-под рук.

## SKIP LOCKED и очереди

**`SKIP LOCKED`** — мощное дополнение: вместо ожидания заблокированных строк
**пропустить** их и взять следующие свободные. Это позволяет строить **очереди
задач прямо в PostgreSQL** без отдельного брокера: несколько воркеров берут разные
задачи, не мешая друг другу.

```sql
-- воркер берёт одну необработанную задачу, пропуская занятые другими воркерами
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

Каждый воркер получает **свою** задачу (заблокированные другими — пропускаются),
без дублирования и блокировок-ожиданий. Это популярный паттерн «БД как очередь»
для умеренных нагрузок (когда не хочется тащить Redis/RabbitMQ).

Отдельно — **advisory locks** (рекомендательные блокировки): блокировки по
**произвольному числу-ключу**, не привязанные к строкам. Полезны для координации на
уровне приложения: «только один процесс выполняет эту джобу» (распределённый
mutex), защита от параллельного запуска миграций/крон-задач.

**Аналогия.** `SKIP LOCKED` — как разбор заявок из общей стопки: каждый сотрудник
берёт верхнюю свободную, а занятую коллегой пропускает, не стоя над душой. Advisory
lock — общий «ключ от комнаты»: кто взял по номеру, тот и работает, остальные ждут.

## Оконные функции и рекурсивные CTE

PostgreSQL (как и стандарт SQL) даёт мощные средства аналитики:

- **Оконные функции** (`OVER (PARTITION BY ... ORDER BY ...)`) — считают по группе
  строк, **не схлопывая** их (ранги, накопительные суммы, `LAG`/`LEAD`); см. курс
  по SQL.
- **Рекурсивные CTE** (`WITH RECURSIVE`) — обход **иерархий и графов** в SQL:
  дерево комментариев, оргструктура, граф связей.

```sql
WITH RECURSIVE subordinates AS (
    SELECT id, manager_id FROM employees WHERE id = 1   -- якорь
    UNION ALL
    SELECT e.id, e.manager_id FROM employees e
    JOIN subordinates s ON e.manager_id = s.id          -- рекурсивный шаг
)
SELECT * FROM subordinates;     -- все подчинённые по дереву
```

Это позволяет решать «развернуть иерархию» прямо в БД, не вытаскивая всё в
приложение и не делая N запросов.

**Аналогия.** Рекурсивный CTE — как разворачивать генеалогическое древо: начинаешь с
человека (якорь) и шаг за шагом добавляешь потомков потомков, пока не обойдёшь всю
ветвь.

## Материализованные представления и партиционирование

Два инструмента для масштаба:

- **Материализованное представление (materialized view)** — **сохранённый
  результат** тяжёлого запроса (агрегата, отчёта). В отличие от обычного view
  (виртуального), оно физически хранит данные и **обновляется по команде**
  (`REFRESH`). Подходит для дорогих аналитических запросов, которые не нужны
  «секунда-в-секунду».
- **Партиционирование** — разбиение большой таблицы на **части (партиции)** по
  ключу (по дате, по диапазону id). Запросы и обслуживание идут по нужным партициям;
  старые данные легко удалять целой партицией. Помогает гигантским таблицам
  (логи, события).

```sql
REFRESH MATERIALIZED VIEW daily_stats;       -- пересчитать сохранённый отчёт
-- партиции: таблица events_2024_01, events_2024_02, ... по месяцу
```

Это инструменты, когда обычных индексов уже мало: предвычислить отчёт
(materialized view) или физически разделить огромную таблицу (партиционирование).

**Аналогия.** Материализованное представление — как заранее свёрстанный ежемесячный
отчёт: не пересчитываешь при каждом запросе, а берёшь готовый и иногда обновляешь.
Партиционирование — разложить огромный архив по годам в отдельные ящики: ищешь и
выбрасываешь нужный ящик целиком, не перебирая весь архив.

## Памятка для собеседования

- **`SELECT ... FOR UPDATE`** — явная блокировка строк до конца транзакции (против
  lost update в read-modify-write); `FOR SHARE` — разделяемая.
- **`SKIP LOCKED`** — пропускать занятые строки → **очередь задач в PostgreSQL**
  (воркеры берут разные задачи). **Advisory locks** — блокировки по ключу
  (распределённый mutex, защита крон/миграций).
- **Оконные функции** (не схлопывают строки), **рекурсивные CTE** (`WITH
  RECURSIVE`) — иерархии/графы в SQL.
- **Материализованное представление** — сохранённый результат тяжёлого запроса
  (`REFRESH`); **партиционирование** — разбиение огромной таблицы по ключу.

## Частые ошибки в ответах

- Делать read-modify-write без `FOR UPDATE` и ловить lost update.
- Не знать про `SKIP LOCKED` для очередей в БД (тащить брокер там, где не нужно).
- Путать обычное view (виртуальное) и материализованное (физически хранит,
  REFRESH).
- Не знать про рекурсивные CTE для иерархий (делать N запросов из приложения).
