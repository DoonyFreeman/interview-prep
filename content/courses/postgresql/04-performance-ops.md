# Производительность и эксплуатация PostgreSQL

> Цель урока: научиться диагностировать производительность через `EXPLAIN
> ANALYZE`, понять роль пула соединений (PgBouncer) и базовые понятия эксплуатации
> — репликацию и бэкапы. Это «продакшен-сторона» PostgreSQL, которую спрашивают у
> тех, кто эксплуатирует БД.

## EXPLAIN ANALYZE

**`EXPLAIN`** показывает **план выполнения** запроса (как планировщик собирается
доставать данные), **`EXPLAIN ANALYZE`** — реально выполняет запрос и показывает
**фактическое время и число строк**. Это главный инструмент диагностики медленных
запросов.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42 AND created_at > '2024-01-01';
```

Что искать:

- **Seq Scan** по большой таблице на селективном условии → не хватает индекса.
- **тип соединения** (Nested Loop / Hash Join / Merge Join) — Nested Loop без
  индекса на больших данных медленный.
- **расхождение `rows` (estimated) и `actual`** — устаревшая статистика, лечится
  `ANALYZE`.
- **самые дорогие узлы** (где основное время) — туда и смотреть.

Принцип тот же, что в курсе по SQL: **сначала измерь план, потом оптимизируй**. В
PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` ещё покажет, сколько читалось с диска/кэша.

**Аналогия.** `EXPLAIN ANALYZE` — как разбор записи гонки: видно не только
запланированный маршрут (план), но и реальное время на каждом участке — сразу ясно,
где машина застряла.

## Пул соединений (PgBouncer)

Каждое соединение с PostgreSQL — это **отдельный процесс** на сервере (PG —
process-per-connection), что дорого по памяти. Если приложение открывает сотни/
тысячи соединений (особенно serverless, много инстансов), сервер задыхается.

**PgBouncer** — лёгкий **пул соединений** перед PostgreSQL: приложение
подключается к нему, а он держит небольшой пул реальных соединений к БД и
**переиспользует** их между клиентами. Так тысячи клиентских подключений
обслуживаются десятком реальных.

```text
1000 клиентов → PgBouncer (пул из 20 соединений) → PostgreSQL
```

Режимы: **session** (соединение закреплено за клиентом на сессию), **transaction**
(на транзакцию — самый эффективный, но нельзя использовать сессионные фичи вроде
prepared statements без оговорок). Пул соединений критичен для масштабирования
PostgreSQL под многими клиентами; сам драйвер (SQLAlchemy) тоже пулит, но PgBouncer
решает проблему на уровне инфраструктуры.

**Аналогия.** PgBouncer — как ресепшен с ограниченным числом переговорных:
посетителей (клиентов) много, но переговорных (соединений) мало, и ресепшен
эффективно распределяет их между гостями, вместо того чтобы строить переговорную
под каждого.

## Репликация и бэкапы

Базовые понятия эксплуатации (обзорно):

- **Репликация** — копия БД на другом сервере, поддерживаемая в актуальном
  состоянии **через WAL** (реплика проигрывает журнал мастера). Даёт
  **отказоустойчивость** (упал мастер — переключаемся на реплику) и
  **масштабирование чтения** (read-реплики разгружают мастер). Бывает
  **синхронная** (мастер ждёт подтверждения реплики — надёжнее, но медленнее) и
  **асинхронная** (быстрее, но возможна потеря последних транзакций при сбое).
- **Бэкапы**: **логические** (`pg_dump` — SQL-дамп, гибко, медленно для больших) и
  **физические** (копия файлов + WAL, для **point-in-time recovery** — откат на
  любой момент). Бэкап без проверки восстановления — не бэкап.

```text
Мастер --WAL--> Реплика (read-only): чтение разгружается, при сбое — failover
```

Понимание «репликация на WAL, read-реплики для масштабирования чтения, PITR через
WAL+бэкап» — достаточный обзорный уровень для бэкенд-собеса.

**Аналогия.** Репликация — как вести синхронную копию журнала в соседнем здании:
если основной сгорит, копия продолжит работу. Бэкап — как сейф с копией на случай,
если потеряются оба; а PITR — возможность «отмотать» состояние к нужной минуте.

## Памятка для собеседования

- **`EXPLAIN ANALYZE`** — план + фактическое время/строки; искать Seq Scan на
  селективных условиях, тип JOIN, расхождение estimated/actual (→ `ANALYZE`),
  дорогие узлы. Сначала измерь, потом оптимизируй.
- PostgreSQL — **процесс на соединение** → дорого; **PgBouncer** пулит соединения
  (тысячи клиентов → десятки реальных); режимы session/transaction.
- **Репликация** через **WAL**: отказоустойчивость + масштабирование чтения
  (read-реплики); синхронная/асинхронная. **Бэкапы**: `pg_dump` (логический) и
  физический + WAL (**PITR**).

## Частые ошибки в ответах

- Оптимизировать запросы без `EXPLAIN ANALYZE`.
- Не знать, что PG — процесс на соединение, и зачем нужен PgBouncer.
- Считать асинхронную репликацию гарантией нулевой потери данных.
- Называть «бэкапом» дамп, который никогда не проверяли восстановлением.
