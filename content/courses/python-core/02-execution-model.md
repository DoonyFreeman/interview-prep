# Модель выполнения: как CPython исполняет код

> Цель урока: построить в голове честную картину того, что происходит, когда вы
> запускаете `python script.py`. Это фундамент: без него ответы про GIL, импорты,
> производительность и `is` vs `==` звучат как заученные факты, а не как
> понимание. На собеседовании очень ценится умение отделить **язык Python** от
> его **реализации CPython**.

## Язык против реализации: Python и CPython

Первое, что отличает джуна от мидла в этом вопросе, — понимание, что **«Python» —
это спецификация языка**, а **CPython — её конкретная реализация** на C. Есть и
другие реализации: **PyPy** (с JIT-компиляцией, часто в разы быстрее на чистом
Python), **Jython** (на JVM), **IronPython** (на .NET), **GraalPy**. Когда вы
пишете «питон тормозит» или «в питоне есть GIL» — почти всегда речь именно про
**CPython**, потому что это эталонная и самая распространённая реализация.

**Аналогия.** Python — это как стандарт языка (грамматика), а CPython, PyPy,
Jython — разные «дикторы», которые этот стандарт произносят. Грамматика одна,
произношение и скорость — разные.

Практический вывод для собеседования: формулировки вроде «в CPython счётчик
ссылок...», «в CPython байткод...» сразу показывают, что вы не путаете язык с
реализацией. Это маркер зрелого ответа.

## Компиляция в байткод и виртуальная машина

Расхожий миф — что Python «чисто интерпретируемый». На самом деле CPython
работает в два шага: сначала **компилирует** исходный код в **байткод**
(промежуточное представление), а потом этот байткод **исполняет виртуальная
машина** (Python Virtual Machine, PVM) — большой цикл, который по очереди
выполняет инструкции байткода.

Увидеть байткод можно модулем `dis`:

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
# LOAD_FAST   a
# LOAD_FAST   b
# BINARY_OP   + (add)
# RETURN_VALUE
```

Это не машинный код процессора, а инструкции для PVM. Поэтому Python — **и
компилируемый, и интерпретируемый**: компиляция в байткод + интерпретация
байткода. Сравнение с Java полезно: там тоже исходник → байткод (`.class`) →
JVM. Разница в том, что JVM агрессивно JIT-компилирует горячие места в машинный
код, а классический CPython просто интерпретирует байткод инструкция за
инструкцией (JIT появляется в CPython только начиная с 3.13, экспериментально).

**Аналогия.** Байткод — это как ноты для музыканта: не сам звук (машинный код),
но и не текст песни словами (исходник). Промежуточная запись, которую «играет»
виртуальная машина.

## Зачем нужны .pyc и папка __pycache__

Компиляция в байткод стоит времени, и было бы расточительно делать её при каждом
запуске. Поэтому CPython **кэширует** результат компиляции модулей в файлы `.pyc`
внутри папки `__pycache__/`. При следующем импорте, если исходник не менялся,
интерпретатор берёт готовый байткод из кэша и пропускает шаг компиляции.

Ключевые нюансы для ответа:

- `.pyc` создаётся **только для импортируемых модулей**, а не для скрипта,
  который вы запускаете напрямую (`python script.py` сам по себе `.pyc` не
  оставляет, но импортированные им модули — оставляют).
- Актуальность кэша определяется по времени модификации исходника (или по хэшу в
  hash-based `.pyc`), а не «на глаз».
- `.pyc` — это **ускорение загрузки, а не защита кода и не ускорение
  выполнения**: сам байткод исполняется с той же скоростью.

**Аналогия.** `__pycache__` — это как заранее нарезанные овощи в холодильнике:
готовка (запуск) идёт быстрее, потому что часть подготовки (компиляция) уже
сделана и сохранена.

## Имена и объекты: переменная — это ярлык

Самая важная ментальная модель Python: **переменная — это не коробка со
значением, а имя (ярлык), привязанное к объекту**. Присваивание `x = [1, 2]` не
«кладёт список в x», а создаёт объект-список и привязывает к нему имя `x`. Когда
вы пишете `y = x`, вы вешаете **второй ярлык на тот же объект** — копии не
происходит.

```python
x = [1, 2, 3]
y = x          # y и x — два имени одного списка
y.append(4)
print(x)       # [1, 2, 3, 4] — изменили через y, видно через x
```

Отсюда растёт половина «загадок» Python: мутабельные аргументы по умолчанию,
неожиданные изменения «копии», поведение в циклах. Всё это объясняется одним
принципом: **имена ссылаются на объекты, присваивание перепривязывает имя, а не
меняет объект**.

**Аналогия.** Объект — это человек, а имена — прозвища. У одного человека может
быть несколько прозвищ (`x`, `y`); окликнув любым, вы обращаетесь к тому же
человеку. «Переименовать» прозвище (`y = ...`) не создаёт нового человека.

## is против ==: идентичность и равенство

Из модели «имена и объекты» прямо следует разница двух операторов:

- `==` спрашивает: **равны ли значения** (вызывает `__eq__`).
- `is` спрашивает: **это один и тот же объект** (сравнивает `id()` — адрес в
  памяти).

```python
a = [1, 2]
b = [1, 2]
a == b   # True  — значения равны
a is b   # False — это два разных списка
```

Правило: **`is` используйте только для синглтонов** — `None`, `True`, `False`
(`if x is None`). Для сравнения значений всегда `==`.

Коварство — **интернирование (кэширование) малых объектов**. CPython заранее
создаёт и переиспользует объекты для малых целых чисел (от −5 до 256) и
некоторых коротких строк. Поэтому:

```python
a = 256; b = 256
a is b      # True  — взяты из кэша малых int
a = 257; b = 257
a is b      # False (в REPL построчно) — разные объекты
```

Это **деталь реализации CPython**, а не гарантия языка. На собеседовании
правильный вывод: «никогда не полагайтесь на `is` для чисел и строк — это
оптимизация интернирования, она не гарантирована». Интернирование существует для
экономии памяти и ускорения сравнений часто используемых значений.

**Аналогия.** `==` — «у нас одинаковые паспортные данные?»; `is` — «мы буквально
один и тот же человек?». Двойняшки равны по виду (`==`), но это разные люди
(`is` → False).

## Памятка для собеседования

- Python = язык (спецификация); **CPython** = эталонная реализация на C. Есть
  PyPy/Jython/IronPython.
- CPython: исходник → **компиляция в байткод** → исполнение **виртуальной
  машиной (PVM)**. И компилируемый, и интерпретируемый.
- `__pycache__/*.pyc` — **кэш байткода** для импортируемых модулей; ускоряет
  загрузку, не выполнение; не защита кода.
- Переменная — **имя (ярлык) на объект**; присваивание перепривязывает имя, не
  копирует объект.
- `==` — равенство значений (`__eq__`); `is` — идентичность (`id()`). `is`
  только для `None`/синглтонов.
- Интернирование малых int (−5..256) и строк — оптимизация CPython, **не
  полагаться** на неё через `is`.

## Частые ошибки в ответах

- «Python — интерпретируемый язык» без оговорок: на деле есть компиляция в
  байткод; и это про **реализацию**, не про язык.
- Думать, что `.pyc` ускоряет **выполнение** (он ускоряет только загрузку) или
  «защищает» код.
- Использовать `x is 256` / `name is "admin"` в коде — работает «случайно» из-за
  интернирования и ломается на других значениях/реализациях.
- Считать, что `y = x` копирует объект (для мутабельных это один и тот же объект,
  два имени).
- Путать «Python» и «CPython» в утверждениях про GIL, счётчик ссылок, байткод.
