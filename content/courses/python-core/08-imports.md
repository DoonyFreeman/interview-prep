# Импорты и модули

> Цель урока: понять, что `import` — это не «вставить файл», а выполнить модуль
> один раз и закэшировать. Из этой модели объясняются циклические импорты, идиома
> `if __name__ == "__main__"`, роль `__init__.py` и `sys.path`. Тема прикладная:
> почти в любом проекте кто-то ловил `ImportError` от кольцевых зависимостей.

## Как работает система импорта

Когда вы пишете `import mymodule`, Python делает несколько шагов:

1. **Проверяет кэш `sys.modules`** — словарь уже импортированных модулей. Если
   модуль там есть, берёт готовый объект и **не выполняет файл заново**.
2. Если нет — **ищет** модуль по `sys.path` (список папок: текущая, стоящие в
   `PYTHONPATH`, стандартная библиотека, `site-packages`).
3. **Создаёт объект модуля, выполняет его код сверху вниз** (один раз) и кладёт в
   `sys.modules`.
4. Привязывает имя в вашем пространстве имён.

Ключевой вывод: **модуль выполняется ровно один раз за процесс**, при первом
импорте. Все последующие `import` берут тот же объект из кэша. Поэтому код
верхнего уровня модуля (создание констант, подключения) выполнится единожды — это
и удобно (синглтон-эффект), и опасно (побочные эффекты при импорте).

**Аналогия.** Импорт — это как пригласить эксперта в офис: в первый раз он
приходит и разворачивает рабочее место (выполняется код модуля), а дальше все
просто заходят к уже сидящему на месте человеку (`sys.modules`), а не вызывают
нового.

## Пакеты и __init__.py

**Модуль** — это файл `.py`. **Пакет** — это папка с модулями. Исторически папка
становилась пакетом благодаря файлу **`__init__.py`** (даже пустому). Он
выполняется при импорте пакета и определяет, что «экспортируется» наружу.

```
myapp/
├── __init__.py        # делает myapp пакетом; код выполняется при import myapp
├── models.py
└── db/
    ├── __init__.py
    └── session.py      # import myapp.db.session
```

Нюансы:

- `__init__.py` удобно использовать, чтобы «поднять» имена наверх:
  `from .models import User` внутри него позволит писать `from myapp import User`.
- С Python 3.3+ существуют **namespace packages** — папки **без** `__init__.py`
  тоже могут быть пакетами (для разнесённых по разным местам частей одного
  пакета). Но для обычного приложения `__init__.py` по-прежнему стандарт и
  делает поведение явным.
- **Абсолютные импорты** (`from myapp.db import session`) предпочтительнее
  **относительных** (`from ..db import session`) для читаемости, хотя
  относительные удобны внутри пакета.

**Аналогия.** Пакет — это шкаф (папка), модули — полки (файлы), а `__init__.py` —
табличка на дверце шкафа, которая говорит «это шкаф» и может выставить часть
содержимого в витрину.

## Циклические импорты

**Циклический импорт** возникает, когда модуль A импортирует B, а B (прямо или
через цепочку) импортирует A. Поскольку модуль выполняется сверху вниз и кладётся
в `sys.modules` **частично готовым**, второй модуль может увидеть A ещё
недозаполненным и упасть на `ImportError: cannot import name ...` или
`AttributeError`.

```python
# a.py
from b import helper      # выполняется при импорте a
def greet(): ...

# b.py
from a import greet       # если a ещё не дозагрузился — ошибка
def helper(): ...
```

Как чинят:

- **Перепроектировать зависимости** (лучший способ): вынести общий код в третий
  модуль, чтобы убрать кольцо. Цикл часто сигнал о проблеме архитектуры.
- **Импорт внутри функции** (отложенный) — импортировать не на верхнем уровне, а
  в теле функции, где имя реально нужно: к моменту вызова оба модуля загружены.
- **`import module` вместо `from module import name`** — обращаться через
  `module.name` лениво, а не «выдёргивать» имя в момент импорта.

**Аналогия.** Два мастера, каждый ждёт деталь от другого, чтобы начать работу, —
дедлок. Решение: либо вынести общую деталь третьему поставщику, либо взять её
позже, когда оба уже на месте (импорт внутри функции).

## if __name__ == "__main__"

Каждый модуль имеет переменную `__name__`. Если файл **запущен напрямую**
(`python script.py`), его `__name__ == "__main__"`. Если **импортирован**,
`__name__` равно имени модуля (`"script"`). Идиома позволяет одному файлу быть и
импортируемой библиотекой, и запускаемым скриптом:

```python
def main():
    print("running")

if __name__ == "__main__":
    main()          # выполнится только при прямом запуске, не при импорте
```

Зачем: при импорте модуля вы **не хотите**, чтобы его «скриптовая» часть
(парсинг аргументов, запуск сервера) выполнилась автоматически. Эта проверка
отделяет «код библиотеки» от «кода точки входа». Особенно важно для
`multiprocessing` на Windows/macOS (spawn) — без этой защиты дочерние процессы
повторно выполнили бы запуск и вошли в рекурсию.

**Аналогия.** `if __name__ == "__main__"` — это как раздел инструкции «если вы
читаете это как самостоятельную брошюру — начните отсюда; если это глава внутри
книги — пропустите». Один текст, два режима использования.

## Памятка для собеседования

- `import` = найти по `sys.path` → выполнить модуль **один раз** → положить в
  `sys.modules` (кэш) → привязать имя. Повторный импорт берёт из кэша.
- Код верхнего уровня модуля выполняется единожды за процесс (синглтон-эффект и
  побочные эффекты).
- **Пакет** — папка; `__init__.py` выполняется при импорте, поднимает имена.
  3.3+ — namespace packages без `__init__.py`.
- **Циклический импорт**: модуль виден частично готовым → ошибка. Фикс:
  переархитектура, импорт внутри функции, `import module` вместо `from ... import`.
- `if __name__ == "__main__"`: код точки входа, не выполняется при импорте; важно
  для `multiprocessing` (spawn).

## Частые ошибки в ответах

- «Импорт вставляет код файла» — на деле выполняет модуль один раз и кэширует.
- Не знать про `sys.modules` и думать, что повторный импорт перевыполняет модуль.
- Лечить циклический импорт только «импортом внутри функции», не упоминая, что это
  обычно признак плохой структуры зависимостей.
- Считать `if __name__ == "__main__"` «необязательной формальностью» — без неё
  скриптовый код выполнится при импорте и сломает `multiprocessing`.
- Путать, чему равен `__name__` при импорте (имя модуля) и при запуске
  (`"__main__"`).
