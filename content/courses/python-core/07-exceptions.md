# Исключения: обработка, иерархия, EAFP

> Цель урока: научиться говорить про исключения как про инструмент управления
> потоком, а не только «обработку ошибок». Разобрать полный синтаксис
> `try/except/else/finally`, иерархию исключений, цепочки (`raise from`) и
> питоническую философию **EAFP против LBYL**. Это база, по которой видно,
> писал ли человек надёжный код.

## try / except / else / finally

Полная форма обработки исключений состоит из четырёх частей, и важно понимать
роль каждой:

```python
try:
    data = fetch(url)          # код, который может бросить исключение
except TimeoutError as e:
    log.warning("retrying: %s", e)
    data = fetch(url)
except (ValueError, KeyError):  # несколько типов одним блоком
    data = default()
else:
    cache.store(data)           # выполнится, ТОЛЬКО если try прошёл без исключений
finally:
    conn.close()                # выполнится ВСЕГДА: и при успехе, и при ошибке
```

- **`except`** ловит конкретный тип (и его подклассы). Несколько блоков
  проверяются сверху вниз — первый подходящий побеждает, поэтому **специфичные
  типы идут раньше общих**.
- **`else`** выполняется, только если в `try` **не было** исключения. Зачем:
  чётко отделить «опасный» код в `try` от «кода после успеха», чтобы случайно не
  поймать исключение из последнего.
- **`finally`** выполняется **всегда** — для гарантированной очистки (закрыть
  файл, соединение, освободить блокировку), даже если внутри был `return` или
  новое исключение.

**Аналогия.** `try` — рискованный манёвр; `except` — план Б на случай аварии;
`else` — что делать, если всё прошло гладко; `finally` — обязательная уборка
рабочего места независимо от исхода.

## Иерархия исключений

Все исключения — объекты-классы, наследующиеся от **`BaseException`**. Ключевая
ветка для прикладного кода — **`Exception`**; от неё наследуются `ValueError`,
`KeyError`, `TypeError`, `OSError` и т. д. Отдельно стоят
`KeyboardInterrupt`, `SystemExit`, `GeneratorExit` — они наследуются от
`BaseException`, но **не** от `Exception`, чтобы их случайно не проглотил
`except Exception`.

Практические правила:

- **Ловите как можно конкретнее.** `except Exception` — широкая сеть; `except
  KeyError` сообщает намерение и не маскирует чужие баги.
- **`except:` без типа — почти всегда ошибка**: ловит даже `KeyboardInterrupt` и
  `SystemExit`, мешая остановить программу. Если нужна «вся прикладная ветка» —
  `except Exception`.
- Порядок `except`-блоков: от частного к общему (подкласс раньше суперкласса),
  иначе общий блок перехватит раньше и частный никогда не сработает.

**Аналогия.** Иерархия — как медицинские диагнозы: `Exception` — «болезнь
вообще», `ValueError` — конкретный диагноз. Ловить `except Exception` — лечить
«вообще от всего»; лучше точный диагноз, чтобы не залечить здорового.

## Свои исключения и цепочки (raise from)

**Свои классы исключений** делают ошибки доменно осмысленными и позволяют их
ловить выборочно. Минимально — наследование от `Exception`:

```python
class PaymentError(Exception):
    """Базовое для платёжного модуля."""

class InsufficientFunds(PaymentError):
    def __init__(self, needed, available):
        super().__init__(f"need {needed}, have {available}")
        self.needed = needed
        self.available = available
```

**Цепочки исключений (`raise ... from ...`)** сохраняют первопричину. Когда вы
ловите низкоуровневое исключение и бросаете своё, доменное, `from` связывает их:

```python
try:
    row = db.execute(query)
except OperationalError as e:
    raise PaymentError("payment lookup failed") from e
```

В трейсбеке появится «The above exception was the direct cause of the following»,
и видно обе ошибки. Без `from` Python всё равно покажет «During handling of the
above exception...» (неявная цепочка), но `from` выражает намерение явно. Чтобы
**скрыть** первопричину, используют `raise ... from None`.

**Аналогия.** `raise from` — это как, передавая жалобу выше по инстанции,
прикладывать оригинал: начальник видит и вашу формулировку, и исходный документ,
а не только «что-то пошло не так».

## EAFP против LBYL

Две философии работы с возможными ошибками:

- **LBYL (Look Before You Leap)** — «семь раз проверь»: заранее проверяем условия
  перед действием.
- **EAFP (Easier to Ask Forgiveness than Permission)** — «проще извиниться, чем
  спрашивать»: пробуем действие и ловим исключение, если не вышло. Это
  **питонический** стиль по умолчанию.

```python
# LBYL — проверки заранее (риск гонки: между проверкой и доступом всё изменится)
if "key" in config and isinstance(config["key"], int):
    value = config["key"]

# EAFP — пробуем и ловим (идиоматично для Python)
try:
    value = int(config["key"])
except (KeyError, ValueError):
    value = default
```

Почему EAFP часто лучше: меньше дублирующих проверок, нет **гонки** между
проверкой и использованием (в LBYL состояние может измениться в промежутке), и в
«счастливом пути» нет накладных расходов на проверки. Но EAFP не догма: если
исключение — это норма, а не редкость (например, в горячем цикле срабатывает
постоянно), проверка может быть и дешевле, и читаемее.

**Аналогия.** LBYL — проверять рукой, заперта ли дверь, прежде чем толкнуть. EAFP
— просто толкнуть и, если заперто, достать ключ. В Python «толкать» дёшево, а
двойные проверки засоряют код.

## Памятка для собеседования

- `try/except/else/finally`: `else` — только при успехе `try`; `finally` —
  **всегда** (очистка). Несколько типов: `except (A, B)`.
- Иерархия: всё от `BaseException`; прикладное — от `Exception`.
  `KeyboardInterrupt`/`SystemExit` — мимо `Exception` намеренно.
- Ловить **конкретно**; `except:` без типа — антипаттерн; блоки от частного к
  общему.
- Свои исключения — наследники `Exception`; `raise NewError(...) from original`
  сохраняет первопричину (а `from None` — скрывает).
- **EAFP** (пробуй и лови) — питонический стиль; избегает гонок проверки/доступа.
  **LBYL** уместен, когда «ошибка» — частый ожидаемый случай.

## Частые ошибки в ответах

- Голый `except:` или `except Exception: pass` — глушит баги и сигналы остановки.
- Ставить общий `except Exception` раньше специфичных — частные блоки не
  сработают.
- Путать `else` и `finally`: `else` — при успехе, `finally` — всегда.
- Не знать про `raise from` и терять первопричину при «перезаворачивании» ошибки.
- Считать LBYL единственно правильным; не уметь объяснить, почему Python склоняется
  к EAFP (гонки, читаемость).
