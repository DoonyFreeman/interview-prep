# GIL — Global Interpreter Lock

> Цель урока: понять, что такое GIL, *почему* он есть, как он влияет на потоки и
> производительность, и как осознанно обходить его ограничения. Это один из
> самых частых вопросов на собеседованиях по Python — и хорошо отвечают на него
> единицы, потому что путают «Python» и «CPython», потоки и процессы, конкурентность
> и параллелизм.

## Что такое GIL

**GIL (Global Interpreter Lock)** — это мьютекс (взаимное исключение) внутри
интерпретатора **CPython**, который гарантирует, что в любой момент времени
**байткод Python исполняет только один поток операционной системы**. Даже если у
вас 8 ядер и 8 потоков, инструкции Python в рамках одного процесса выполняются
строго по одному — потоки «передают друг другу» этот единственный замок.

Критично понимать формулировку: GIL — это деталь реализации **CPython**, а не
часть языка Python. В альтернативных интерпретаторах (Jython на JVM, IronPython
на .NET) GIL нет вовсе. Когда вас спрашивают про GIL, корректно начинать ответ с
«в CPython…», а не «в Python…» — это сразу показывает глубину понимания.

Зачем он нужен в одном предложении: **GIL защищает внутреннее состояние
интерпретатора** (в первую очередь подсчёт ссылок у объектов) от гонок данных,
делая саму реализацию проще и быстрее для однопоточного кода.

## GIL и потоки: CPU-bound vs IO-bound

Главное практическое следствие: эффект GIL **зависит от типа нагрузки**.

- **CPU-bound** задачи (вычисления: перемножение матриц, парсинг, сжатие) почти
  всё время держат GIL, потому что активно исполняют байткод. Поэтому несколько
  Python-потоков на CPU-bound коде **не дают ускорения** — они конкурируют за
  один замок и в сумме работают как один поток (а иногда даже медленнее из-за
  накладных расходов на переключение). Это и есть «GIL мешает многопоточности».

- **IO-bound** задачи (сеть, диск, ожидание ответа БД) бóльшую часть времени
  **ждут**, а не считают. На время блокирующей операции ввода-вывода поток
  **отпускает GIL**, и другой поток может работать. Поэтому для IO-bound нагрузки
  потоки в Python **дают реальный выигрыш**, несмотря на GIL.

Отсюда мостик к терминам: GIL ограничивает **параллелизм** (одновременное
исполнение байткода на нескольких ядрах), но **не** ограничивает
**конкурентность** (чередование задач, в т.ч. ожидающих IO). Потоки и `asyncio`
в Python — это про конкурентность; настоящий параллелизм для CPU-bary даёт только
много процессов.

## Когда GIL освобождается

Поток отдаёт GIL в нескольких ситуациях — знать их полезно, чтобы объяснить, *как*
вообще возможна многопоточность в Python:

1. **На блокирующих операциях ввода-вывода.** Перед системным вызовом (чтение
   сокета, файла) интерпретатор освобождает GIL и берёт его обратно после.
2. **Периодически между инструкциями.** В современном CPython (3.x) поток,
   удерживающий GIL, обязан «по тайм-ауту» (по умолчанию каждые ~5 мс,
   настраивается через `sys.setswitchinterval()`) дать шанс другим потокам
   захватить замок. В Python 2 механизм был другим — счётчик из 100 «тиков»
   байткода; называть актуальным именно «тики» на собеседовании — частая ошибка.
3. **В C-расширениях**, которые явно отпускают GIL макросами
   `Py_BEGIN_ALLOW_THREADS` / `Py_END_ALLOW_THREADS`. Именно так numpy, сжатие,
   многие криптобиблиотеки считают тяжёлые блоки **параллельно** на нескольких
   ядрах — пока они в C-коде и не трогают Python-объекты, GIL им не нужен.

## Как обойти ограничения GIL

Когда CPU-bound код упирается в GIL, есть несколько проверенных стратегий:

- **`multiprocessing` / `ProcessPoolExecutor`** — запускаем несколько *процессов*,
  у каждого свой интерпретатор и свой GIL. Это даёт настоящий параллелизм на
  ядрах. Цена — изоляция памяти и накладные расходы на сериализацию данных между
  процессами (pickling), поэтому хорошо подходит для «тяжёлый расчёт, мало данных
  на входе/выходе».
- **C-расширения / нативные библиотеки** (numpy, pandas, Cython, numba) — выносим
  горячий цикл в нативный код, который отпускает GIL и параллелит вычисления
  внутри. Часто это эффективнее, чем городить процессы.
- **Другой интерпретатор** — PyPy (есть свой GIL, но быстрее) или окружения без
  GIL. С Python 3.13 появилась **экспериментальная сборка `free-threaded`
  (PEP 703)** без GIL — это будущее, но пока опционально и не везде стабильно.
- **Для IO-bound** GIL обходить не нужно: берём потоки (`ThreadPoolExecutor`) или
  `asyncio` — они и так дают выигрыш, потому что задачи ждут, а не считают.

Правило выбора одним предложением: **IO-bound → потоки/asyncio; CPU-bound →
процессы или нативный код.**

## Почему GIL существует и его будущее

GIL — не «недосмотр», а инженерный компромисс. Причины:

- **Управление памятью через подсчёт ссылок.** У каждого объекта CPython есть
  счётчик ссылок; он меняется крайне часто. Без глобального замка каждое такое
  изменение требовало бы своей атомарной синхронизации, что замедлило бы
  **однопоточный** код (а это большинство программ). GIL делает счётчик
  безопасным «бесплатно».
- **Простота и совместимость C-API.** Огромная экосистема C-расширений написана в
  предположении, что GIL их защищает. Убрать GIL — значит сломать или переписать
  эту совместимость.

Исторически попытки убрать GIL (например, патч Грега Стайна ещё в 1990-х)
замедляли однопоточные программы в ~2 раза, поэтому их отвергали. Сейчас
**PEP 703** аккуратно ведёт CPython к опциональной сборке без GIL: ссылки делают
атомарными/смещёнными, добавляют пер-объектные блокировки. Это долгий путь с
сохранением обратной совместимости, и в обозримом будущем GIL-сборка остаётся
дефолтной.

## Памятка для собеседования

- Начинай с «в **CPython**…»: GIL — деталь реализации, не язык.
- GIL = один поток исполняет байткод одновременно; защищает подсчёт ссылок.
- CPU-bound: потоки **не** ускоряют (упор в GIL). IO-bound: потоки помогают
  (GIL отпускается на ожидании).
- GIL отпускается: на IO, периодически по `switchinterval` (~5 мс), в C-коде
  через `Py_BEGIN_ALLOW_THREADS`.
- Обход: процессы (свой GIL у каждого), нативные либы, free-threaded сборка
  (PEP 703, 3.13+).
- Конкурентность ≠ параллелизм: GIL бьёт по параллелизму, не по конкурентности.

## Частые ошибки в ответах

- «В Python нельзя в многопоточность» — неверно: для IO-bound потоки полезны.
- Путать потоки и процессы; думать, что `multiprocessing` тоже под GIL (нет, у
  каждого процесса свой интерпретатор).
- Называть актуальным механизм «100 тиков» (это Python 2; в 3.x — временной
  интервал).
- Говорить, что GIL делает код потокобезопасным «полностью» — нет: GIL защищает
  интерпретатор, но **ваши** составные операции (`x += 1` над общим объектом)
  всё равно не атомарны на уровне логики и требуют своих блокировок.
