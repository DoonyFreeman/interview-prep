# Управление памятью: подсчёт ссылок и сборка мусора

> Цель урока: понять, как CPython решает, когда удалять объект из памяти. Это
> прямое продолжение разговора про GIL (который существует ради потокобезопасности
> счётчика ссылок) и частый вопрос на собесе: «как в Python работает сборщик
> мусора?». Сильный ответ называет **два механизма** — подсчёт ссылок и
> поколенческий GC для циклов — и понимает, зачем нужен второй.

## Подсчёт ссылок: основной механизм

Базовый способ управления памятью в CPython — **подсчёт ссылок (reference
counting)**. У каждого объекта есть счётчик: сколько имён и контейнеров на него
ссылаются. Счётчик растёт при новой ссылке и падает при её исчезновении. Как
только он достигает **нуля — объект немедленно удаляется**, память
освобождается.

```python
import sys

x = []
print(sys.getrefcount(x))   # например 2: имя x + временный аргумент getrefcount
y = x
print(sys.getrefcount(x))   # 3: добавился y
del y
print(sys.getrefcount(x))   # снова 2
```

Плюс этого подхода — **детерминированность**: объект освобождается сразу, как
только стал не нужен, без пауз «на потом». Минус — накладные расходы (счётчик
постоянно меняется) и **главная причина существования GIL**: без глобального
замка каждое изменение счётчика в многопоточной программе требовало бы
дорогой атомарной синхронизации.

**Аналогия.** Подсчёт ссылок — как библиотека, считающая, сколько читателей
сейчас держат книгу. Вернул последний читатель (счётчик = 0) — книгу тут же
списывают и убирают с полки. Пока хоть один держит — книга живёт.

## Проблема циклических ссылок

У подсчёта ссылок есть фундаментальная дыра: **циклы**. Если два объекта
ссылаются друг на друга, их счётчики никогда не упадут до нуля, даже когда на них
больше никто не ссылается извне.

```python
a = {}
b = {}
a["b"] = b      # a ссылается на b
b["a"] = a      # b ссылается на a — цикл
del a, b        # внешние имена удалены, но счётчики всё ещё 1 (друг на друга)
# без второго механизма эта память утекла бы навсегда
```

Чтобы это чинить, в CPython есть **второй механизм — поколенческий сборщик
мусора** (модуль `gc`), который специально ищет и собирает **недостижимые
циклы**.

**Аналогия.** Две книги, каждая из которых «отмечена как нужная другой книге».
Читателей-людей нет, но они держат друг друга — и система подсчёта думает, что
обе нужны. Нужен отдельный обходчик, который заметит: «эта пара ссылается только
сама на себя, снаружи никому не нужна» — и спишет обе.

## Поколенческий сборщик мусора

Сборщик циклов в CPython — **поколенческий (generational)**. Идея опирается на
**гипотезу о поколениях**: большинство объектов умирают молодыми, а пережившие
несколько сборок живут долго. Поэтому объекты делят на **три поколения** (0, 1,
2). Новые попадают в поколение 0; пережившие сборку «повышаются» в следующее.

GC чаще всего проверяет **поколение 0** (там больше всего мусора, дёшево), реже —
старшие. Это снижает накладные расходы: не нужно каждый раз обходить все
долгоживущие объекты. Сам поиск циклов работает методом «mark-and-sweep» по
объектам, которые **могут** содержать ссылки (контейнеры); простые `int`/`str`
GC не трогает — они освобождаются только подсчётом ссылок.

Управление через модуль `gc`:

```python
import gc
gc.collect()        # запустить сборку циклов вручную
gc.disable()        # отключить (например, в коротком батч-скрипте ради скорости)
gc.get_threshold()  # пороги срабатывания по поколениям
```

**Аналогия.** Это уборка по зонам: «горячую» прихожую (поколение 0), где мусора
больше всего, подметают часто; дальние кладовки (поколение 2) с давно лежащими
вещами — редко. Так тратишь меньше сил на то, что и так стабильно.

## __del__, слабые ссылки и утечки

Несколько практичных тем, которые любят на собесе:

**`__del__` (финализатор)** вызывается при удалении объекта. Опасности: момент
вызова не гарантирован (особенно если объект в цикле), исключения в `__del__`
проглатываются, а сам `__del__` исторически **мешал** сборке циклов (до Python
3.4 / PEP 442). Вывод: для освобождения ресурсов (файлы, соединения) используйте
не `__del__`, а **контекст-менеджеры** (`with`) — детерминированно и явно.

**Слабые ссылки (`weakref`)** — ссылка, которая **не увеличивает счётчик** и не
мешает удалить объект. Нужны, чтобы разрывать циклы и строить кэши, которые не
держат объекты «насильно» (родитель↔ребёнок, наблюдатели, `WeakValueDictionary`).

```python
import weakref

class Node: ...
n = Node()
r = weakref.ref(n)
print(r())     # <Node> — объект жив
del n
print(r())     # None — объект собран, слабая ссылка «обнулилась»
```

**Утечки памяти в Python** возможны, несмотря на GC: глобальные списки/словари,
которые бесконечно растут; кэши без ограничения; зарегистрированные колбэки,
которые никто не снимает; ссылки в замыканиях. Инструменты диагностики:
`sys.getsizeof`, `tracemalloc`, `gc.get_objects()`.

**Аналогия.** Слабая ссылка — это записка «если увидишь Васю, передай привет», а
не «держи Васю здесь силой». Если Вася ушёл (объект собран), записка просто
становится пустой (`None`), а не удерживает его в комнате.

## Памятка для собеседования

- Два механизма: **подсчёт ссылок** (основной, мгновенный при счётчике = 0) +
  **поколенческий GC** (для циклов).
- Подсчёт ссылок — детерминированный, но требует синхронизации → **причина
  существования GIL**.
- Циклические ссылки счётчик не освобождает; их собирает `gc` (mark-and-sweep по
  контейнерам).
- GC **поколенческий** (0/1/2): молодые проверяются чаще; гипотеза «объекты
  умирают молодыми».
- `__del__` ненадёжен по времени → для ресурсов используй `with`
  (контекст-менеджеры).
- `weakref` — ссылка без увеличения счётчика; разрывает циклы, кэши. Утечки
  возможны: растущие глобальные структуры, незакрытые кэши.

## Частые ошибки в ответах

- «В Python сборщик мусора как в Java» — упускают, что **основной** механизм
  именно подсчёт ссылок, а GC — лишь для циклов.
- Не уметь объяснить, **зачем** нужен GC, если есть подсчёт ссылок (ответ:
  циклы).
- Считать `__del__` надёжным деструктором для закрытия файлов/соединений (нет —
  `with`).
- «В Python не бывает утечек» — бывают: бесконечно растущие структуры, кэши,
  висящие ссылки.
- Путать поколения GC с управлением кучей у простых объектов (`int`/`str` GC не
  трогает — только подсчёт ссылок).
