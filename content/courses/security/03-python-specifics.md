# Безопасность в Python: pickle, eval, зависимости

> Цель урока: разобрать специфичные для Python риски — опасную десериализацию
> (`pickle`), `eval`/`exec`, и угрозы цепочки поставок (supply chain). Эти вопросы
> отличают тех, кто думает о безопасности в Python-коде, а не только в вебе вообще.

## Опасность pickle и десериализации

**`pickle`** — стандартная сериализация Python — **небезопасна для недоверенных
данных**. При распаковке (`pickle.loads`) она может **выполнить произвольный код**:
формат позволяет описать «как воссоздать объект», и злоумышленник встраивает туда
выполнение команд.

```python
# ОПАСНО: распаковка pickle из недоверенного источника = выполнение чужого кода
data = pickle.loads(untrusted_bytes)    # может запустить произвольную команду!
```

Правило: **никогда не `pickle.loads` данные из недоверенного источника** (запрос,
внешний файл, сеть, кэш, доступный извне). Это касается всего на pickle: некоторые
конфигурации кэшей/очередей, `__reduce__`. Безопасная альтернатива для обмена
данными — **JSON** (он только данные, не код), а для схем — Pydantic/спецформаты.
Та же проблема у других «исполняющих» десериализаторов (YAML с `yaml.load` без
`SafeLoader`, marshal).

**Аналогия.** `pickle.loads` недоверенных данных — как собрать мебель по инструкции
от незнакомца, где шаг 5 — «подожги дом». Формат позволяет вписать в «инструкцию
сборки» любые действия. JSON — это просто список деталей без инструкций-действий,
поэтому безопасен.

## eval, exec и динамическое выполнение

**`eval()`** и **`exec()`** выполняют **строку как код Python**. Если в них попадёт
пользовательский ввод — это **прямое выполнение произвольного кода (RCE)**, тяжелейшая
уязвимость.

```python
# КАТАСТРОФА: пользователь контролирует, что выполнится
result = eval(user_input)     # user_input = "__import__('os').system('rm -rf /')"
```

Правило: **не использовать `eval`/`exec`/`compile` на пользовательском вводе**.
Почти всегда есть безопасная альтернатива:

- Нужно разобрать число/литерал → `int()`, `float()`, **`ast.literal_eval`** (только
  литералы, не код).
- Нужна «формула»/выражение → специализированный безопасный парсер, не `eval`.
- Нужен выбор функции по имени → **словарь** `{"sum": sum, ...}`, не `eval(name)`.

То же про `os.system`/`subprocess` с `shell=True` и пользовательским вводом —
**инъекция команд**; использовать `subprocess` со **списком аргументов** и без
`shell=True`.

**Аналогия.** `eval(user_input)` — дать незнакомцу микрофон, подключённый к системе
управления зданием: что скажет — то и выполнится. `ast.literal_eval` — микрофон,
который понимает только «число» или «список», но не команды.

## Supply chain и зависимости

Современный проект тянет **сотни сторонних пакетов** — и каждый это **доверие** к
чужому коду, выполняющемуся с вашими правами. Угрозы **цепочки поставок (supply
chain)**:

- **Скомпрометированный/вредоносный пакет** — украденный аккаунт мейнтейнера,
  вредонос в обновлении, **typosquatting** (пакет `reqeusts` вместо `requests`).
- **Уязвимости в зависимостях** — известные CVE в используемых версиях.

Защита:

- **Фиксировать версии** (lock-файлы: `requirements.txt` с хэшами,
  `poetry.lock`) — воспроизводимость, не подтянуть внезапно вредоносное обновление.
- **Сканеры уязвимостей** — `pip-audit`, Safety, Dependabot/Snyk — проверяют
  зависимости на известные CVE.
- **Проверять, что ставишь** — имя пакета (typosquatting), репутацию, не ставить
  лишнего.
- **Минимизировать зависимости** — меньше пакетов = меньше поверхность атаки.

**Аналогия.** Зависимости — как ингредиенты от множества поставщиков в вашем блюде:
один испорченный продукт (вредоносный пакет) отравит всё. Фиксация версий — брать
проверенную партию; сканеры — проверка на свежесть; внимание к имени — не перепутать
поставщика с подделкой.

## Принципы безопасной разработки

Сводка установок, которые проявляются в коде:

- **Валидация и санитизация ввода** на границе (Pydantic) — «не доверяй
  пользователю»; всё внешнее считается враждебным, пока не проверено.
- **Принцип наименьших привилегий** — у процесса, ключа, пользователя БД минимум
  прав (non-root контейнер, отдельные ключи, read-only где можно).
- **Defense in depth** — несколько слоёв защиты, не один (валидация + параметризация
  + права + WAF).
- **Fail securely** — при ошибке отказывать в доступе, а не открывать; не сливать
  детали (стектрейсы, версии) наружу.
- **Не изобретать криптографию** — использовать проверенные библиотеки (bcrypt,
  `secrets` для токенов, не `random`).
- **`secrets` вместо `random`** для токенов/паролей — `random` предсказуем, не
  криптостойкий.

**Аналогия.** Безопасная разработка — как охрана банка: не одна дверь, а слои
(валидация, права, шифрование); сотрудникам — доступ только к нужному (наименьшие
привилегии); при сбое сигнализации двери **запираются**, а не открываются (fail
securely); и не строят свой сейф, а ставят сертифицированный (не своя криптография).

## Памятка для собеседования

- **`pickle.loads` недоверенных данных = выполнение кода** → никогда; для обмена —
  **JSON**. То же у небезопасного YAML/marshal.
- **`eval`/`exec` на вводе = RCE** → не использовать; альтернативы:
  **`ast.literal_eval`**, `int()`, словарь функций. `subprocess` без `shell=True`,
  списком аргументов.
- **Supply chain**: вредоносные пакеты/typosquatting, CVE в зависимостях → **лок-
  файлы**, сканеры (`pip-audit`/Dependabot), проверять имена, меньше зависимостей.
- Принципы: **валидация ввода** (Pydantic), **наименьшие привилегии**, defense in
  depth, **fail securely**, не своя крипта, **`secrets`** вместо `random`.

## Частые ошибки в ответах

- Не знать, что `pickle.loads` недоверенных данных позволяет выполнить код.
- Использовать `eval`/`exec` на вводе или `ast.literal_eval` путать с `eval`.
- Не упоминать supply chain (typosquatting, CVE) и лок-файлы/сканеры.
- Брать `random` вместо `secrets` для токенов; «изобретать» криптографию.
