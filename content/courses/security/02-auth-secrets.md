# Хэширование паролей, JWT и секреты

> Цель урока: понять, как **правильно** хранить пароли (bcrypt/argon2 + соль),
> безопасно работать с JWT и управлять секретами. «Как вы храните пароли» — частый
> вопрос, и неверный ответ («MD5», «шифруем») сразу выдаёт пробел в безопасности.

## Хэширование паролей

Пароли **никогда не хранят в открытом виде** и **не шифруют** (шифрование
обратимо — утёк ключ, утекли пароли). Их **хэшируют** — необратимо. Но обычные
хэши (MD5, SHA-256) **не годятся** для паролей: они **слишком быстрые**, и атакующий
перебирает миллиарды вариантов в секунду (брутфорс, радужные таблицы).

Нужны **специальные медленные хэши для паролей**:

- **bcrypt** — проверенный временем, с настраиваемой «стоимостью» (work factor).
- **argon2** — современный победитель конкурса, устойчив к GPU/ASIC-атакам
  (рекомендуется для нового кода).
- **scrypt**, **PBKDF2** — тоже приемлемы.

```python
# bcrypt: медленно намеренно, со встроенной солью
import bcrypt
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt())
bcrypt.checkpw(attempt.encode(), hashed)     # проверка
```

Их **намеренная медленность** (можно усиливать с ростом железа) делает перебор
дорогим. В этом проекте bcrypt используется напрямую (пароли усекаются до 72 байт —
его лимит).

**Аналогия.** Обычный хэш — быстрый замок, который вор открывает миллионами
отмычек в секунду. bcrypt/argon2 — сейф с замедленным механизмом: каждая попытка
занимает время, и перебрать все комбинации становится непрактично долго.

## Соль и перец

Даже медленный хэш недостаточен без **соли**:

- **Соль (salt)** — случайная строка, **уникальная для каждого пароля**, которая
  добавляется перед хэшированием и хранится рядом с хэшем. Зачем: без соли два
  одинаковых пароля дают одинаковый хэш (видно, у кого пароли совпадают, и работают
  **радужные таблицы** — предпосчитанные хэши). Соль делает каждый хэш уникальным и
  убивает предпосчёт.

```text
Без соли:  hash("password123") всегда одинаков → радужная таблица сработает
С солью:   hash(salt + "password123"), salt уникальна → таблицы бесполезны
```

Важно: **bcrypt/argon2 генерируют и встраивают соль автоматически** — она внутри
итогового хэша, отдельно хранить не нужно. **Перец (pepper)** — дополнительный
секрет (не в БД, а в конфиге/HSM), добавляемый ко всем паролям; защищает, если
утекла только БД. Соль — обязательна, перец — опционален.

**Аналогия.** Соль — как добавлять каждому блюду уникальную приправу перед готовкой:
даже два одинаковых рецепта дадут разный «отпечаток вкуса», и заранее заготовленная
шпаргалка вкусов (радужная таблица) не подойдёт ни к одному.

## Безопасность JWT

JWT (см. курсы Web/HTTP и FastAPI) удобен, но требует аккуратности:

- **Подпись обязательна и проверяется** — алгоритм фиксируется на сервере; **не
  доверять `alg` из токена** (классическая атака — подменить `alg` на `none` или
  RS256→HS256). Указывать допустимые алгоритмы явно при декодировании.
- **Payload не секретен** — он только закодирован (base64), читается любым → **не
  класть туда секреты/чувствительные данные**.
- **Короткий срок жизни** access-токена + **refresh-токен** для продления; так
  ограничивается окно при утечке.
- **Отзыв** — JWT трудно отозвать до истечения (stateless); для logout/бана ведут
  blacklist или версию токена, либо делают access-токены очень короткими.
- **Секрет подписи** — длинный, случайный, в конфиге/секретах, не в коде.

```python
jwt.decode(token, SECRET, algorithms=["HS256"])   # явный список алгоритмов!
```

**Аналогия.** JWT — подписанный пропуск. Опасности: не дать подделать печать
(фиксировать алгоритм), не писать на пропуске секретов (payload читаем), делать
пропуск краткосрочным (короткий TTL), чтобы потерянный быстро устаревал.

## Управление секретами

**Секреты** (пароли БД, API-ключи, JWT-секрет, токены) — самое ценное; их утечка =
компрометация. Правила:

- **Никогда в коде/репозитории** — секрет в git утекает навсегда (даже после
  удаления остаётся в истории). Сканеры находят их в публичных репо за минуты.
- **Конфиг из окружения** (env / `.env` вне git, как `GEMINI_API_KEY`,
  `JWT_SECRET` здесь) — 12-factor.
- **Хранилища секретов** для прода — Vault, AWS Secrets Manager, K8s Secrets:
  централизованно, с ротацией и аудитом.
- **Ротация** — периодически менять секреты; уметь сменить быстро при утечке.
- **TLS везде** — секреты и данные не должны ходить по сети в открытом виде
  (HTTPS, шифрованные соединения к БД).
- **Принцип наименьших привилегий** — у каждого ключа минимум прав (отдельный
  ключ на сервис, read-only где можно).

**Аналогия.** Секреты — как ключи от сейфа: не пишут на стене (в коде), хранят в
защищённой связке (vault), периодически меняют замки (ротация), и передают только
по защищённому каналу (TLS), давая каждому сотруднику ключ лишь от нужных дверей.

## Памятка для собеседования

- Пароли — **хэшировать** (не шифровать, не plaintext) **медленными** хэшами:
  **bcrypt/argon2** (не MD5/SHA — они быстрые). Медленность = дорогой брутфорс.
- **Соль** (уникальная на пароль) убивает радужные таблицы и одинаковые хэши;
  bcrypt/argon2 встраивают её сами. **Перец** — опциональный секрет вне БД.
- **JWT**: фиксировать **алгоритм** (не доверять `alg` из токена), payload не
  секретен, короткий TTL + refresh, продумать отзыв, секрет в конфиге.
- **Секреты**: **не в коде/git**, из env/vault, **ротация**, **TLS везде**,
  наименьшие привилегии.

## Частые ошибки в ответах

- «Храним пароли в MD5/SHA-256» или «шифруем» — нужны bcrypt/argon2 + соль,
  хэширование необратимо.
- Не знать про соль и радужные таблицы.
- Декодировать JWT, доверяя `alg` из токена; класть секреты в payload.
- Хранить секреты в коде/репозитории вместо env/vault.
