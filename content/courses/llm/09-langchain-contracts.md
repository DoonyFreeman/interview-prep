# LangChain, день 2: контракты и инструменты

> **30 минут чтения с разбором + 30 минут практики.** API и установка пакетов не нужны. Остановитесь, когда можете объяснить полный путь от запроса инструмента до ответа пользователю.

Вспомните вчера: что выходит из модели и что делает parser? Маршрут сегодня: форма ответа → контракт инструмента → полный обмен сообщениями → ошибки.
В «Маяке» вопрос прежний: «Можно вернуть заказ 42?». Правило — **45 дней и неиспользованный товар**; данные заказа — **40 дней, не использован**. Все ответы модели ниже заранее зафиксированы для обучения.

## Структура ответа и правильность фактов

**Structured output**, структурированный вывод, — ответ по заданной схеме полей. **Pydantic** — Python-библиотека, которая проверяет значения по описанию модели данных. Например, приложению нужен не произвольный абзац, а решение с основанием:

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict

class Decision(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    status: Literal["allowed", "denied", "unknown"]
    reason: str
    sources: list[str]

raw = {"status": "allowed", "reason": "40 ≤ 45, товар не использован",
       "sources": ["policy-v2", "order-42"]}
decision = Decision.model_validate(raw)
```

`Literal` ограничивает допустимые строки. `strict=True` запрещает неявное приведение типов; `extra="forbid"` запрещает лишние поля. Но даже строгая схема не проверяет, существует ли источник `policy-v2` и подтверждает ли он причину.

Сравните три уровня: JSON разбирается → поля соответствуют схеме → утверждение подтверждено данными. Успех первых двух не гарантирует третий. Вчерашний `StrOutputParser` лишь извлекал текст; JSON-parser разбирает запись; Pydantic проверяет поля и ограничения. Истинность сверяет приложение или отдельная проверка по источникам.

В LangChain модель может предоставлять `model.with_structured_output(Decision)`. Поддержка и способ ограничения вывода зависят от модели и интеграции. В агентном интерфейсе используют `response_format`; возможности поставщика или стратегия через tool calling помогают получить структуру, но не доказательство фактов.

### Практика — 5 минут

`status="allowed"`, `reason="Срок 60 дней"`, `sources=[]`. Пройдёт ли объект выше Pydantic? Достаточно ли его для ответа?

```solution
Да: все поля имеют разрешённые типы, а пустой список не запрещён схемой. Но причина противоречит регламенту 45 дней и не содержит оснований. Нужно отдельно проверять факты и требования к источникам; строгие типы не устанавливают истину.
```

## Контракт инструмента

**Tool**, инструмент, — разрешённая приложением операция, которую модель может запросить. **Контракт** описывает имя, назначение, вход и выход. Возьмём только чтение заказа:

| Часть | Значение |
| --- | --- |
| Имя | `get_order` |
| Назначение | получить разрешённые текущему пользователю сведения о заказе |
| Аргумент модели | `order_id: int`, положительное число |
| Успех | `{"order_id":42,"age_days":40,"unused":true}` |
| Ошибка | `{"error":"not_available"}` без чужих сведений |

В LangChain `@tool` может превратить Python-функцию с описанием и типами в инструмент. `model.bind_tools([get_order])` сообщает модели доступные инструменты. Это ещё не исполнение функции.

[Tool calling](/courses/llm/lessons/rag-agents#tool-calling "Модель запрашивает операцию по имени и аргументам; исполняет её приложение.") — выдача структурированного запроса операции. Модель не получает доступ к БД сама. Приложение проверяет известное имя, аргументы, текущего пользователя и принадлежность заказа. Идентификатор пользователя берут из доверенной сессии, не из слов модели.

### Практика — 5 минут

Модель запросила заказ 43 другого пользователя и передала `user_id="admin"`. Что делать?

```solution
Не доверять user_id из запроса модели. Контракт get_order принимает только order_id; лишний аргумент отклоняют. Приложение проверяет доступ по доверенной сессии и не возвращает сведения о чужом заказе. Сообщение об ошибке не должно раскрывать чужие данные.
```

## Полный цикл tool calling

**Runtime**, исполняющая часть приложения, организует обмен. **ToolMessage** — сообщение с результатом инструмента, связанное с запросом через `tool_call_id`. Рассмотрим все переходы, а не только строку `bind_tools`.

1. Приложение передаёт модели вопрос и действующий регламент 45 дней.
2. Модель возвращает `AIMessage` с `tool_calls=[{"name":"get_order","args":{"order_id":42},"id":"call_1"}]`.
3. Приложение добавляет это сообщение в историю, проверяет запрос и права, затем вызывает функцию.
4. Функция возвращает `{"order_id":42,"age_days":40,"unused":true}`.
5. Приложение добавляет `ToolMessage(content='{"order_id":42,"age_days":40,"unused":true}', tool_call_id="call_1")`.
6. Приложение снова вызывает модель с этой историей. Учебный финал: «Да: заказу 40 дней из допустимых 45, товар не использован».

История содержит и исходный запрос инструмента, и его результат. По `call_1` понятно, на какой запрос пришёл ответ; одного текста «40 дней» недостаточно для надёжного сопоставления нескольких операций.

![Обмен между моделью, приложением и инструментом](/lesson-media/llm/agents-tool-loop.svg#1200x720 "Модель просит get_order; приложение проверяет и исполняет; ToolMessage возвращает результат модели.")

### Практика — 10 минут

На бумаге воспроизведите шесть шагов. Где выполняется SQL? Где принимается решение, можно ли читать заказ? Кто пишет финальную фразу?

```solution
SQL выполняет код инструмента через доверенный слой доступа приложения, а не модель. Авторизацию проверяет приложение до выдачи данных. Модель формулирует финальный ответ после получения ToolMessage и регламента. Tool calling сам по себе не гарантирует автономный агентный цикл.
```

## Ошибки и отсутствие оснований

Неизвестный инструмент не запускаем; неверные аргументы не исправляем догадкой. При временном сбое чтения допустим ограниченный повтор. **Таймаут** — предельное время ожидания. Он завершает ожидание приложения, но не всегда отменяет уже начавшуюся внешнюю операцию.

Если заказ не найден или доступ запрещён, безопасный ответ: «Не могу получить доступные сведения об этом заказе». Если заказ известен, но регламент не найден, `status="unknown"`: «Не хватает действующего регламента». Пустой поиск не означает запрет возврата и не разрешает придумать срок.

В [оценке RAG](/courses/llm/lessons/rag-evaluation#набор-оценки-и-единица-релевантности "Полезность источника зависит от вопроса, действующей версии и разрешённой области данных.") уже разделяли наличие основания и качество формулировки. Здесь тот же принцип: результат инструмента — данные, а не инструкция изменить правила. Даже найденный документ может содержать вредоносную команду.

Установите предел числа обращений и общего времени. Для операций записи нужны отдельные права и защита от повторного исполнения; проверка возможности возврата не должна незаметно запускать возврат денег.

### Практика — 10 минут

Инструмент вернул возраст 40, но поле `unused` отсутствует. Можно ли ответить «возврат разрешён»?

```solution
Нет: подтверждено только условие срока. Нужно получить состояние товара разрешённым способом либо сообщить, что данных недостаточно. Отсутствующее поле нельзя считать true. Ограниченный повтор оправдан лишь при понятной исправимой ошибке, а не бесконечно.
```
