# Агенты, день 3: кто выбирает следующий шаг

> **30 минут чтения с разбором + 30 минут практики.** Никаких вызовов API. Остановитесь, когда можете выбрать между цепочкой, workflow и агентом и объяснить границы выбора.

Вспомните вчера: почему запрос инструмента не равен выполнению? Кто проверяет права?
Маршрут сегодня: три способа управления → ReAct → Plan-and-Execute → ограничения.
Данные «Маяка» прежние: вопрос **«Можно вернуть заказ 42?»**, срок **45 дней**, только неиспользованный товар; заказу **40 дней**, товар **не использован**. Результаты модели ниже зафиксированы для обучения.

## Chain, workflow и agent на одной задаче

**Chain**, цепочка, — заранее соединённые шаги. **Workflow**, рабочий процесс, — заранее определённые переходы, включая ветвления и повторы. **Agent**, агент, — система, где модель выбирает следующее действие в предоставленных приложением пределах. В этом уроке различаем их по управлению следующим шагом.

| Подход | Что происходит с заказом 42 | Кто выбирает переход |
| --- | --- | --- |
| Chain | подготовить факты → модель → parser | код задаёт последовательность |
| Workflow | получить заказ → если данных нет, уточнить; иначе проверить правило → ответить | условия в коде |
| Agent | модель запрашивает заказ, затем при необходимости регламент, затем завершает | модель выбирает из разрешённых действий; приложение исполняет |

Для этой простой проверки можно вообще обойтись без LLM:

```python
def eligible(age_days: int, unused: bool) -> bool:
    return age_days <= 45 and unused

eligible(40, True)  # True
```

Сначала валидируем входы и доступ; правило здесь уже известно. Модель полезна для понимания свободного вопроса или формулировки ответа, но сравнение чисел надёжнее выполнить кодом.

Границы понятий могут пересекаться: агентный цикл тоже можно представить графом, а workflow может содержать модель. Наличие LLM, графа или одного tool call ещё не означает, что модель управляет маршрутом.

### Практика — 5 минут

Код всегда вызывает `get_order`, затем одну LLM для текста. В ответе модель использует tool calling только для передачи структуры. Это агентный выбор маршрута?

```solution
Нет: следующий шаг заранее выбран кодом. Tool calling здесь — способ передать структурированные данные, а не самостоятельный выбор действий. Такую задачу достаточно описать как фиксированный workflow или цепочку с вызовом инструмента.
```

## ReAct как цикл действия и наблюдения

**ReAct** — паттерн, сочетающий выбор следующего действия и получение результата. **Наблюдение**, observation, — данные после выполненного действия. В реализации важен повторяемый цикл: модель выбирает действие → приложение проверяет и выполняет → результат возвращается модели → новый выбор или финал.

Для «Маяка» уже передан регламент; модели не хватает заказа:

| Шаг | Наблюдаемое событие | Новые данные |
| --- | --- | --- |
| 1 | модель запросила `get_order(42)` | только запрос операции |
| 2 | приложение проверило доступ и прочитало заказ | `age_days=40`, `unused=true` |
| 3 | результат передан как `ToolMessage` | у модели есть оба условия |
| 4 | модель завершила ответ | «Возврат допустим по этим данным» |

Это журнал внешних действий, а не раскрытие внутренних размышлений модели. Для обучения и отладки достаточно фиксировать выбранные инструменты, аргументы, результаты, ошибки и причину завершения в кратком операционном виде. Требовать скрытую цепочку рассуждений не нужно.

Если результат инструмента сообщает, что заказ недоступен, модель не должна «догадаться» о возрасте. Новый выбор может быть уточнением вопроса или безопасным завершением. Цикл обязан иметь предел.

### Практика — 10 минут

После `get_order` модель снова просит тот же заказ с теми же аргументами. Что добавить в управление?

```solution
Ограничение числа шагов и времени, обнаружение бесполезного повтора, завершение с понятным сообщением. При ошибке допускают ограниченное исправление запроса или повтор согласно политике приложения. Сам цикл не гарантирует прогресс.
```

## Plan-and-Execute

**Plan-and-Execute**, «спланируй и выполни», разделяет составление плана и исполнение шагов. **План** — явный список будущих операций, который можно проверить. **Executor**, исполнитель, выполняет шаги; при новых данных возможна проверка и корректировка плана.

Учебный план для заказа 42:

1. Получить доступные сведения о заказе.
2. Найти действующий регламент возврата.
3. Проверить возраст и состояние товара.
4. Сформулировать ответ с основаниями.

До исполнения это только намерения. После шага 1 есть `40 дней, unused=true`; после шага 2 — `45 дней, только unused`; после шага 3 — `40 <= 45 and true = true`. Исполнитель обязан передавать результаты дальше, а не просто отмечать пункты галочками.

Если на шаге 2 пришёл архивный срок 30 дней, план не делает его действующим. Проверяем версию, ищем разрешённый источник или завершаем с недостатком оснований. План не выдаёт дополнительных прав и не отменяет валидацию инструментов.

Отдельное планирование бывает полезно для длинных составных запросов. Но оно добавляет вызовы модели и объём контекста; перепланирование тоже стоит времени и денег. Plan-and-Execute не всегда дешевле ReAct и не гарантирует лучший ответ. Для четырёх известных шагов достаточно workflow.

### Практика — 10 минут

Планировщик предложил сначала оформить возврат денег, потом проверить условия. Как исправить план до запуска?

```solution
Убрать запись: пользователь спросил о возможности, а не поручил переводить деньги. Сначала получить разрешённые данные и действующий регламент, проверить оба условия, затем ответить. План проверяют по цели, правам и допустимым действиям до исполнения.
```

## Границы агента и выбор простого решения

**Бюджет** — заданный предел шагов, времени или стоимости. **Список разрешённых инструментов** ограничивает доступные операции; текст от модели не расширяет его. Права проверяются на каждом вызове. Ошибки инструментов, отсутствие источника и исчерпание бюджета — предусмотренные завершения.

В текущем LangChain есть `create_agent`, готовая организация модельного цикла на базе LangGraph. LangGraph помогает явно описывать управление и состояние. Это не означает, что каждый проект требует собственный граф или агент: [обзор LangChain и LangGraph](/courses/llm/lessons/rag-agents#langchain-и-langgraph "LangChain даёт компоненты и готовые агенты; LangGraph позволяет явно управлять состоянием и переходами.") связывает уровни.

После выбора подхода появляются пакеты: `langchain` для готового агента, интеграция провайдера для модели, `langgraph` для явно построенного графа. Установка не является задачей этого маршрута.

Для «Маяка» начните с workflow: чтение заказа, правило, ответ. Агент оправдан, если неизвестно заранее, какие сведения нужны, и модельный выбор даёт измеримую пользу. Сравнивайте на одинаковых вопросах точность, количество вызовов, время и корректные отказы при недостатке данных. Красивый журнал сам по себе не метрика качества.

### Практика — 5 минут

Из 100 запросов 95 требуют тех же двух чтений, пять — уточнения пользователя. Обязательно ли нужен агент?

```solution
Нет. Workflow может выполнять два чтения и иметь явную ветку уточнения. Агент стоит рассматривать, если фиксированные ветки перестают покрывать реальные задачи и измерения показывают пользу модельного выбора при приемлемой цене и рисках.
```
