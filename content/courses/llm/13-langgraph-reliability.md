# LangGraph, день 6: надёжность агента

> **30 минут вместе с практикой.** Разберём, кто исправляет сбой, сколько раз граф может попробовать снова и что увидит пользователь.

Продолжаем пример «Маяка» из [урока про подтверждение](/courses/llm/lessons/langgraph-persistence#interrupt-ждёт-решение-человека "Как граф ждёт ответ пользователя и продолжает тот же thread"). У заказа **№42** прошло **40 дней**, товар не использован. Действующий регламент даёт **45 дней**. Чтобы проверить условия, агенту нужны данные заказа и актуальный регламент.

## Как выбрать реакцию на сбой

Начни с вопроса **«Кто может исправить ситуацию?»** От ответа зависит следующий шаг:

| Ситуация | Действие графа | Что увидит пользователь |
| --- | --- | --- |
| Поисковый сервис временно не ответил | Повторить запрос чтения. При исчерпании попыток завершить с результатом `unavailable` | «Сейчас не могу проверить правила. Попробуйте позже» |
| Модель передала дату в `order_id`, хотя №42 есть в диалоге | Валидатор отклоняет аргумент до обращения к API. Модель получает `ToolMessage` с причиной и пробует новый вызов | Ответ по заказу, если исправление удалось |
| Номера заказа нет | `interrupt()` просит уточнение. API передаёт номер через `Command(resume=42)` с исходным `thread_id` | «Уточните номер заказа» |
| В узле опечатка и возник `NameError` | Исключение доходит до обработчика приложения. Причина доступна разработчику в логах или трейсе | Нейтральное сообщение о сбое |
| Сервис успешно вернул `[]` | Обычная ветка `not_found` | «По этому запросу правила не найдены» |

Проверка доступа тоже даёт отдельный исход. Если сессия не даёт права читать заказ, сервер останавливает чтение и возвращает допустимое для клиента сообщение. Право доступа проверяется на стороне приложения при вызове инструмента.

![Пять маршрутов обработки результата вызова](/lesson-media/llm/agents-reliability.svg#1200x720 "Успешный результат с пустым списком и ошибка после повторов ведут в разные ветки")

В `ToolMessage` для исправимой ошибки передавай конкретную подсказку: «`order_id` должен быть целым числом». Свяжи её с запросом через `tool_call_id`. Номер из сообщения модели всё равно проходит обычную проверку аргументов и доступа. Если номер может сообщить только человек, в нашем графе предусмотрена ветка уточнения.

## RetryPolicy повторяет попытку узла

Retry полезен, когда **тот же вызов может сработать чуть позже**. Например, библиотека клиента превратила таймаут чтения в исключение `TemporarySearchError`. Поставим политику на небольшой узел, который делает один запрос к поиску.

```python
from langgraph.types import RetryPolicy

# Учебный фрагмент. TemporarySearchError — исключение нашего адаптера API.
builder.add_node(
    "search_policy",
    search_policy,
    retry_policy=RetryPolicy(
        max_attempts=3,
        initial_interval=0.5,
        backoff_factor=2,
        jitter=True,
        retry_on=TemporarySearchError,
    ),
)
```

`max_attempts=3` — это **первый вызов и максимум два повтора**. Базовые интервалы в примере — 0,5 и 1 секунда. `jitter` добавляет случайный разброс, чтобы запросы после сбоя не возвращались все одновременно. Ограничение попыток работает вместе с таймаутом отдельного запроса и общим бюджетом времени. Если API-клиент уже делает повторы, считай суммарное число обращений. Для `429` отдельно проверяй причину лимита и подсказку сервиса о времени ожидания, если она есть.

Пройди запуск с тремя таймаутами. В снимках ниже `order_id` хранится в `State`, а номер попытки показан в подписи шага. Это информация о выполнении узла.


`RetryPolicy` сама по себе пробрасывает ошибку после последней попытки. Результат `unavailable` появится, если в приложении явно предусмотрен обработчик этой ошибки.

## Счётчик в State и предел графа

У каждого ограничения свой объект подсчёта:

| Где задано | Что считает | Что происходит на пределе |
| --- | --- | --- |
| `RetryPolicy(max_attempts=3)` | Попытки **одного выполнения узла** | Ошибка передаётся в обработку |
| `tool_calls_used` в `State` | Вызовы инструмента, которые агент инициирует для одной задачи | Роутер выбирает ожидаемый выход с понятным сообщением |
| `recursion_limit` в конфигурации запуска | Раунды исполнения графа (*supersteps*) | При превышении LangGraph выбрасывает `GraphRecursionError` |

В нашем примере узел валидации учитывает каждый полученный tool call, включая отклонённые аргументы. После выполнения или проверки инструмент возвращает результат. Если он успешен, идём дальше. Если модель может исправить ошибку и бюджет остался, отправляем ей `ToolMessage`. При исчерпании бюджета больше не вызываем инструмент. Один раунд исполнения может включать несколько параллельных узлов, поэтому из `recursion_limit` нельзя вывести число запросов к LLM.

```python
def route_after_tool(state):
    # Узел проверки уже записал результат и обновил счётчик.
    if state["tool_status"] == "ok":
        return "continue"
    if state["tool_status"] != "invalid_arguments":
        return "finish"
    if state["tool_calls_used"] >= 2:
        return "finish"
    return "ask_model_to_fix"  # Вернуть ToolMessage модели.
```

Имена веток связываются с узлами в `add_conditional_edges`. В этом фрагменте к модели возвращаемся только при исправимой ошибке и оставшемся бюджете. После успешной второй попытки граф продолжает работу. В агенте, который принимает несколько tool calls за сообщение, бюджет нужно проверять перед каждым фактическим вызовом.

## Практика по сбоям и повторам

Для каждой ситуации назови **действие графа** и **что увидит пользователь**. Затем сравни с разбором.

1. Поиск вернул `[]` после успешного запроса.
2. Сервис не ответил на первый вызов и на оба повтора.
3. Агент передал дату как ID, номер заказа есть в диалоге, бюджет остался.
4. Для проверки нужно узнать номер заказа, которого пользователь не указал.
5. В узле поиска возник неожиданный `NameError`.
6. Сотрудник одобрил черновик. Сервис записал заявку, но ответ потерялся. Что должно произойти при повторе?

```solution
1. Ветка `not_found`. Поиск отработал, совпадений нет.
2. Всего три вызова. Обработчик выбирает `unavailable`, пользователь узнаёт о временной недоступности.
3. Валидатор возвращает понятную ошибку в `ToolMessage` с исходным `tool_call_id`. Модель может исправить аргумент.
4. `interrupt()` запрашивает номер. API возобновляет граф с ответом и прежним `thread_id`.
5. Исключение доходит до обработчика приложения. Трейс содержит диагностические данные, пользователь получает нейтральное сообщение.
6. Повтор должен передать **тот же устойчивый ключ операции**. Хранилище или сервис атомарно обеспечивает уникальность ключа и возвращает результат существующей записи. Потерянный ответ сам по себе не доказывает, что запись не состоялась.
```
