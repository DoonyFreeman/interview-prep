## Состояние и обычные функции

**Граф** — схема шагов и переходов. **Узел, node**, — функция шага; **состояние, state**, — общие данные процесса. `StateGraph` описывает такой граф в LangGraph. Узел читает состояние и возвращает **обновление**, то есть только изменившиеся поля.

Это похоже на карточку заказа, которую передают сотрудникам. Один читает регламент, другой считает срок, третий пишет черновик. Не каждый сотрудник — LLM: проверка числа обычным Python надёжнее генерации. Граф с фиксированными правилами перехода вообще может не быть агентом.

```python
from typing import TypedDict

class State(TypedDict):
    order_id: int
    age_days: int
    unused: bool
    eligible: bool | None
    draft: str
    attempts: int
    valid: bool | None

def check(state: State):
    return {"eligible": state["age_days"] <= 45 and state["unused"]}
```

Вход `age_days=40, unused=True` даёт обновление `eligible=True`. Остальные поля сохраняются. `TypedDict` помогает статической проверке типов, но сам не проверяет вход во время выполнения. На внешней границе нужна отдельная валидация: отрицательный возраст нельзя принимать как корректный.

**Упражнение — 5 минут.** Какое обновление вернётся для 40 дней и использованного товара? Кто обязан отклонить `age_days=-2`?

```solution
**Решение.** Узел вернёт `{"eligible": False}`: срок подходит, состояние товара — нет. Остальные поля не меняются. Отрицательный возраст должна отклонить проверка входных данных до запуска графа; аннотация `int` этого не делает.
```

## Reducer объединяет обновления

**Reducer** — правило применения обновления к конкретному полю. Без специального reducer новое значение заменяет старое. Для истории иногда нужно объединение: например, складывать списки событий.

| Поле | Было | Обновление | Стало |
| --- | --- | --- | --- |
| `draft`, замена | «Срок 30» | «Срок 45» | «Срок 45» |
| `events`, сложение списков | `["check"]` | `["draft"]` | `["check", "draft"]` |

Для сообщений существует `add_messages`: он добавляет новые сообщения, а сообщение с уже существующим **ID**, идентификатором, обновляет на месте. Это не простое добавление в конец. История исправленной реплики не обязана расти.

```python
from typing import Annotated
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```

**Упражнение — 5 минут.** В истории сообщение `id="a"` с текстом «30 дней». Пришло `id="a"` с текстом «45 дней», затем новое `id="b"`. Сколько сообщений получится?

```solution
**Решение.** Два. Сообщение `a` обновится и будет содержать «45 дней»; `b` добавится. Простое сложение списков дало бы три элемента и сохранило устаревшую реплику.
```

## Условный маршрут и конечный цикл

**Ребро, edge**, задаёт следующий узел. **Условный переход** выбирает ребро по результату функции маршрутизации, router. Это обычный код, а не обязательный вызов модели.

Предположим, проверяющий узел выставляет `valid`: черновик содержит верный срок и условие. Разрешим не более двух попыток подготовки:

```python
def route(state):
    if state["valid"]:
        return "done"
    if state["attempts"] >= 2:
        return "stop"
    return "retry"
```

Узел подготовки увеличивает `attempts` на единицу. Тогда маршрут `draft → review → draft` конечен: после второй неудачи идём в `stop`, где возвращаем понятную ошибку без действия. Приоритет `valid` позволяет принять успешную вторую попытку.

`recursion_limit` ограничивает **supersteps**, раунды выполнения графа. Это не прямой счётчик LLM-вызовов: один раунд может запускать несколько узлов, некоторые не вызывают LLM вообще. Прикладной бюджет попыток хранится отдельно; технический предел остаётся дополнительной защитой.

**Упражнение — 5 минут.** `valid=False, attempts=1`, затем `False, 2`. Назови обе ветки. Что произойдёт при `True, 2`?

```solution
**Решение.** Сначала `retry`, потом `stop`. При `True, 2` получим `done`, потому что проверка успешности первая. Для гарантии остановки узел подготовки обязан увеличивать счётчик при каждой новой попытке.
```

## Сборка и ручная трасса

`compile()` собирает описание графа в запускаемый объект и проверяет его структуру. Сам запуск выполняет `invoke()`. `START` обозначает вход, `END` — завершение.

Минимальный граф ниже проверяет заказ; генерации и записи нет:

```python
from langgraph.graph import StateGraph, START, END

builder = StateGraph(State)
builder.add_node("check", check)
builder.add_edge(START, "check")
builder.add_edge("check", END)
graph = builder.compile()
result = graph.invoke({
    "order_id": 42, "age_days": 40, "unused": True, "eligible": None,
    "draft": "", "attempts": 0, "valid": None,
})
```

![Состояние проходит через узлы и обновления](/lesson-media/llm/agents-state.svg#1200x720 "Узел получает состояние, возвращает обновление; reducer применяет его перед следующим шагом")

Ниже расширенная **заранее заданная учебная трасса**, не выполнение кода и не живой ответ LLM. Каждый снимок показывает состояние после указанного шага. Первая заготовка намеренно ошибочна; проверка направляет её на исправление.

```execution
{

  "nodes": ["START", "check", "draft", "review", "END"],

    {"node":"START","explanation":"Получены учебные данные заказа 42.","state":{"order_id":42,"age_days":40,"unused":true,"attempts":0,"draft":"","eligible":null,"valid":null}},

```

Поля сохраняют те же имена, что в данных инструмента: `order_id` — номер заказа, `age_days` — дни с покупки. `None` (в JSON — `null`) означает, что проверка ещё не выполнена; это не отрицательный результат.

**Упражнение — 10 минут.** Вручную пройди трассу для `age_days=46`: назови обновление `check` и корректный черновик. Выполняет ли `compile()` проверку заказа?

```solution
**Решение.** `check` вернёт `eligible=False`. Корректный черновик: «Срок превышен: 46 > 45, условия возврата не соблюдены». Проверяющий узел должен принять такой ответ, а не требовать положительного решения. `compile()` только собирает граф; данные обрабатываются при `invoke()`.
```
