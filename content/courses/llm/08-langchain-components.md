# LangChain, день 1: данные между компонентами

> **30 минут чтения с разбором примеров + 25 минут практики.** Установка библиотек и API не нужны. Остановитесь, когда можете нарисовать вход и выход каждого шага, затем возвращайтесь к дню 2.

Маршрут: обычный Python → prompt/model/parser → Runnable и `|` → способы запуска.
Продолжаем синтетический магазин «Маяк»: вопрос **«Можно вернуть заказ 42?»**.
Действующий регламент разрешает возврат в течение **45 дней только неиспользованного товара**. Заказу 42 **40 дней**, товар **не использован**. Здесь проверяем возможность возврата, деньги не переводим.

## Сначала обычные шаги Python

Не начинайте с названий библиотек. Разложите задачу на операции: собрать известные данные, подготовить запрос, получить ответ, извлечь текст. Вчерашний [RAG-пайплайн](/courses/llm/lessons/rag-documents-embeddings#индексация-поиск-и-генерация "Поиск передаёт генератору найденные основания; генерация формулирует ответ по ним.") мог доставить регламент. Сегодня считаем, что основания уже переданы.

```python
question = "Можно вернуть заказ 42?"
facts = "Регламент: 45 дней, только неиспользованный товар. Заказ 42: 40 дней, не использован."

def prepare(question, facts):
    return [
        {"role": "system", "content": "Отвечай только по данным."},
        {"role": "user", "content": question + "\n" + facts},
    ]

def educational_model(messages):
    # Фиксированный учебный результат, не вызов LLM.
    return {"content": "Да: 40 ≤ 45, товар не использован."}

messages = prepare(question, facts)
message = educational_model(messages)
answer = message["content"]
```

`messages` — список сообщений; `message` — один ответ; `answer` — строка. Функция ничего не ищет и не проверяет: она намеренно возвращает заготовку. Настоящая модель может ошибиться даже при тех же входных данных.

### Практика — 5 минут

Замените возраст заказа на 46. Какой участок учебного кода перестал соответствовать данным?

```solution
Заготовленный ответ educational_model всё ещё утверждает «40 ≤ 45». Подготовка запроса получила новые данные, но функция их не анализирует. По регламенту 46 дней уже за пределами срока. Это демонстрация потока, а не работающий решатель возвратов.
```

## Prompt, model и parser

**Prompt** — подготовленный запрос к модели; **шаблон prompt** подставляет значения в сообщения. **Chat model** — компонент, принимающий сообщения и возвращающий сообщение ассистента. **Parser**, разборщик, превращает ответ в удобную приложению форму.

| Шаг | Тип входа → выхода | Значение в «Маяке» |
| --- | --- | --- |
| Шаблон | `dict → ChatPromptValue` | вопрос и основания → подготовленные сообщения |
| Модель | сообщения → `AIMessage` | ответ ассистента с текстом |
| `StrOutputParser` | `AIMessage → str` | «Да: 40 ≤ 45, товар не использован.» |

`ChatPromptValue` — объект с подготовленными сообщениями; `AIMessage` — объект ответа ассистента. У него могут быть дополнительные поля, например запросы инструментов. Разбор текста не устанавливает истинность ответа.

![Вход и выход шаблона, модели и разборщика](/lesson-media/llm/agents-components.svg#1200x720 "Словарь превращается в сообщения, затем в ответ модели и строку; проверка фактов остаётся отдельной задачей.")

Для реальной интеграции пригодятся `langchain-core` с базовыми компонентами и пакет выбранного провайдера — поставщика модели. Объединённый интерфейс уменьшает различия, но замена провайдера требует проверить доступные модели, настройки, инструменты и формат ответов.

### Практика — 5 минут

Модель вернула `AIMessage(content="Возврат разрешён через 60 дней")`. Что исправит `StrOutputParser`?

```solution
Он извлечёт строку из сообщения. Срок 60 дней останется ошибочным: разборщик не сверяет ответ с регламентом 45 дней. Форму ответа и соответствие основаниям проверяют отдельно.
```

## Runnable и соединение через LCEL

**Runnable** — объект с общим интерфейсом запуска. **LCEL**, LangChain Expression Language, — способ соединять такие объекты. Оператор `|` передаёт выход левого шага на вход правого. Он собирает последовательность, но сам её не запускает.

Ниже фрагмент с LangChain, который можно читать без запуска. `model` обозначает заранее настроенную chat model, а `question` и `facts` — строки из первого примера.

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    ("system", "Отвечай только по основаниям: {facts}"),
    ("human", "{question}"),
])
chain = prompt | model | StrOutputParser()
answer = chain.invoke({"question": question, "facts": facts})
```

Сначала словарь получает `prompt`, затем подготовленные сообщения получает `model`, затем сообщение получает parser. Здесь **chain**, цепочка, — последовательность с заранее выбранными шагами. Следующий шаг не выбирает модель.

Обычную функцию можно обернуть в `RunnableLambda`: это адаптер функции к интерфейсу Runnable. Обёртка не делает функцию моделью и не добавляет поиск. Ошибка типов между шагами остаётся ошибкой, даже если запись выглядит аккуратно.

### Практика — 5 минут

Что произойдёт, если после parser поставить функцию, ожидающую словарь с ключом `content`?

```solution
Она получит строку, а не словарь. Нужно либо изменить её входной контракт на строку, либо передать ей сообщение до parser. Символ | не преобразует любые типы автоматически.
```

## Invoke, batch и stream

Один Runnable предлагает несколько способов запуска:

| Метод | Что передаём | Что получаем |
| --- | --- | --- |
| `invoke(x)` | один вход | один полный результат |
| `batch([x, y])` | список независимых входов | список результатов в порядке входов |
| `stream(x)` | один вход | последовательность доступных частей результата |

`batch` может выполнять запросы параллельно: ограничивайте одновременность с учётом лимитов провайдера. Это не разговор, где второй вопрос помнит первый. Ошибку одного входа нужно обработать согласно выбранной политике.

`stream` полезен для постепенного показа ответа. Размер частей зависит от компонента; это не обязательно один токен. Поток всей цепочки зависит от поддержки промежуточных шагов: блокирующий разборщик может задержать выдачу. Вызов `stream` не гарантирует мгновенное появление текста.

![Три способа запуска одной последовательности](/lesson-media/llm/agents-invocations.svg#1200x720 "Invoke возвращает один результат, batch обрабатывает независимые входы, stream отдаёт доступные части одного результата.")

### Практика — 10 минут

Нужно одновременно проверить три независимых заказа, а пользователю одного заказа показывать ответ постепенно. Какие методы выбрать? Нарисуйте границы входов.

```solution
Для трёх независимых запросов подходит batch со списком трёх словарей и ограничением параллельности. Для постепенного ответа по одному заказу — stream при поддержке потока компонентами. Ни один метод сам не добавляет память разговора, проверку прав или фактов.
```
