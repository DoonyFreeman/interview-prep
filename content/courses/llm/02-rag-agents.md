# RAG и агенты

> Цель урока: понять, как научить модель отвечать по **своим** документам (эмбеддинги,
> векторные базы, RAG-пайплайн, чанкинг, гибридный поиск и реранкинг), как дать ей
> **действовать** (tool calling, агенты, LangChain и LangGraph) и как **измерить**
> качество. В конце — сквозной разбор ассистента по документам, который связывает оба
> урока.

## Эмбеддинги

**Эмбеддинг (embedding)** — представление текста в виде **вектора**: списка чисел
фиксированной длины (обычно сотни или тысячи чисел). Его строит отдельная **модель
эмбеддингов**: на один текст — один вектор. Главное свойство: **похожие по смыслу
тексты дают близкие векторы**, даже если в них разные слова.

![Текст превращается моделью эмбеддингов в вектор, на карте смысла похожие тексты лежат рядом](/lesson-media/llm/embeddings.png#1200x660 "Эмбеддинги — смысл текста в виде точки в пространстве")

1. На входе — текст: вопрос, абзац документа, название товара.
2. Модель эмбеддингов — не та модель, что пишет ответы. Она ничего не генерирует,
   только превращает текст в вектор.
3. На выходе — вектор фиксированной длины, например 384, 768, 1024 или 1536 чисел, в
   зависимости от модели.
4. На «карте смысла» тексты про возвраты собираются вместе, про базы данных — в
   другом месте. Запрос «Как вернуть деньги?» окажется рядом с «вернуть оплату», хотя
   общих слов почти нет. Это и есть **семантический поиск**.

Близость считают **косинусным сходством (cosine similarity)**: косинус угла между
векторами — чем ближе к 1, тем ближе смысл. Часто используют расстояние `1 − cos`: чем
меньше, тем ближе. Абсолютные значения зависят от модели: у одних даже несвязанные
тексты дают 0.7, поэтому результаты сравнивают между собой, а порог «релевантно»
подбирают на своих данных.

```python
import math

EMB_MODEL = "..."  # имя модели эмбеддингов у провайдера

def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))

resp = client.embeddings.create(model=EMB_MODEL, input=["Как вернуть деньги?", "возврат товара"])
q, doc = resp.data[0].embedding, resp.data[1].embedding
print(cosine(q, doc))  # чем больше, тем ближе по смыслу; порог подбирают на своих данных
```

**Модели эмбеддингов** бывают закрытые (например, `text-embedding-3-small` и
`text-embedding-3-large` у OpenAI) и открытые (BGE-M3, multilingual-e5 и другие — их
можно запустить у себя). Для русского текста нужна **мультиязычная** модель. Важное
правило: **документы и вопросы кодируются одной и той же моделью** — векторы разных
моделей несравнимы, и при смене модели всю базу переиндексируют.

**Аналогия.** Эмбеддинг — координаты на карте города, где районы — это темы. Тексты про
возвраты живут в одном районе, про базы данных — в другом. Чтобы найти похожее, не
нужно совпадение слов: достаточно посмотреть, кто живёт по соседству.

## Векторные базы данных: pgvector, Qdrant, Chroma

**Векторная база данных** хранит векторы вместе с исходным текстом и метаданными и
умеет быстро находить **ближайшие векторы** к запросу — top-k самых похожих.

Сравнить запрос со всеми миллионами векторов перебором долго. Поэтому векторные базы
строят **индекс приближённого поиска ближайших соседей (ANN, approximate nearest
neighbors)** — чаще всего **HNSW** (многоуровневый граф «соседей»). Он находит почти
лучших соседей в разы быстрее перебора, жертвуя небольшой долей точности.

| | pgvector | Qdrant | Chroma |
|---|---|---|---|
| Что это | расширение PostgreSQL | отдельный сервер векторного поиска | лёгкая встраиваемая база |
| Когда брать | уже есть Postgres, векторов до миллионов, нужны JOIN и транзакции с обычными данными | большие объёмы, сложная фильтрация, отдельный сервис поиска | прототип, обучение, локальные эксперименты |
| Плюсы | одна база, SQL, бэкапы и права как обычно | быстрый, фильтры по метаданным, масштабирование | ставится одной строкой, ничего не нужно поднимать |

pgvector на практике — то же PostgreSQL из курса по Postgres, плюс тип `vector` и
операторы расстояния:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
    id         bigserial PRIMARY KEY,
    doc_id     bigint NOT NULL,
    content    text NOT NULL,
    embedding  vector(1536) NOT NULL       -- размерность = размерность модели
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

-- 5 ближайших чанков к вектору вопроса ($1); <=> — косинусное расстояние
SELECT id, content, embedding <=> $1 AS distance
FROM chunks
WHERE doc_id = ANY($2)                     -- фильтр по метаданным, например по правам
ORDER BY embedding <=> $1
LIMIT 5;
```

Метаданные (источник, дата, отдел, права доступа) нужны, чтобы фильтровать поиск:
пользователь не должен получить кусок документа, к которому у него нет доступа.

Два подводных камня pgvector:
- **Фильтр применяется после обхода HNSW-индекса.** Индекс отдаёт ограниченное число
  ближайших кандидатов, и если права есть лишь на малую часть документов, после `WHERE`
  может остаться меньше 5 строк или ни одной. Лечится итеративным обходом индекса
  (`SET hnsw.iterative_scan = relaxed_order`, pgvector 0.8+), большим `hnsw.ef_search`
  или отдельным (частичным) индексом под частый фильтр.
- **HNSW-индекс по типу `vector` — до 2000 измерений.** Для модели на 3072 измерения
  используют тип `halfvec` (половинная точность) или модель с меньшей размерностью.

**Аналогия.** Обычная база — библиотечный каталог: ищет книгу по точному названию или
автору. Векторная — библиотекарь, которому описываешь, о чём хочешь почитать, и он
приносит книги «про это», даже если в названии нет твоих слов.

## RAG: какую проблему решает

У LLM две фундаментальные проблемы для бизнес-задач: она **не знает ваших данных**
(внутренние регламенты, база знаний, тикеты) и её знания **заканчиваются на дате
среза**. Спросишь — получишь уверенную галлюцинацию.

![Слева модель без RAG уверенно ошибается, справа с RAG отвечает по найденному фрагменту со ссылкой](/lesson-media/llm/rag-problem.png#1200x700 "Какую проблему решает RAG")

1. Без RAG модель отвечает «по памяти»: общие знания о магазинах, и ответ «14 дней»
   звучит правдоподобно — но в регламенте 30. Источника нет, проверить нельзя.
2. С RAG сначала **находим** нужный фрагмент документа, кладём его в промпт и просим
   отвечать **только по нему**. Ответ точный и со ссылкой на источник.

**RAG (Retrieval-Augmented Generation)** — генерация, дополненная поиском: сначала
**найти** релевантные куски документов (retrieval), потом **сгенерировать** ответ по
ним (generation). Что это даёт:

- ответы по **своим и свежим** данным без переобучения модели — обновил документ, и
  ответ изменился;
- **меньше галлюцинаций**: модель опирается на текст, а не на память;
- **ссылки на источники** — ответ можно проверить;
- **права доступа**: в поиск попадают только документы, которые можно этому
  пользователю.

Почему не положить всю базу знаний в промпт? Не влезет в контекстное окно, а если
влезет — будет дорого, медленно, и модель хуже найдёт нужное в середине огромного
текста. RAG кладёт только несколько самых полезных кусков.

**Аналогия.** Экзамен без RAG — отвечать по памяти. С RAG — экзамен с открытой книгой:
сначала находишь нужную страницу, потом отвечаешь своими словами и указываешь, откуда
взял.

## RAG-пайплайн по шагам

![Две дорожки: индексация документов заранее и ответ на запрос онлайн](/lesson-media/llm/rag-pipeline.png#1200x600 "RAG-пайплайн по шагам")

**Индексация** — заранее, в фоне (например, задачей Celery при изменении документа):

1. **Загрузка документов**: PDF, wiki, тикеты, записи из БД. Текст извлекают и чистят
   от мусора (колонтитулы, меню, дубли).
2. **Чанкинг**: режут на куски разумного размера с перекрытием (следующий раздел).
3. **Эмбеддинги**: каждый чанк превращают в вектор моделью эмбеддингов.
4. **Запись в векторную БД**: вектор + текст чанка + метаданные (источник, дата,
   права).

**Ответ на запрос** — онлайн, на каждый вопрос:

5. **Вопрос → вектор** той же моделью эмбеддингов. Иногда вопрос предварительно
   переписывают (например, превращают «а сколько дней?» с учётом истории диалога в
   полный вопрос).
6. **Поиск top-k** ближайших чанков (обычно 5–20) с фильтром по метаданным.
7. **Реранкинг** (по желанию): точнее пересортировать кандидатов и оставить лучшие.
8. **Сборка промпта**: инструкция («отвечай только по контексту, ставь ссылки [id],
   если ответа нет — так и скажи») + чанки с их id + вопрос. Затем **LLM**
   генерирует ответ, а приложение показывает его со ссылками на источники.

```python
def answer(question: str, user) -> str:
    q_vec = embed(question)                                   # шаг 5
    chunks = search(q_vec, k=20, allowed_docs=user.doc_ids)   # шаг 6
    chunks = rerank(question, chunks)[:5]                     # шаг 7
    context = "\n\n".join(f"[{c.id}] {c.text}" for c in chunks)
    messages = [                                               # шаг 8
        {"role": "system", "content": "Отвечай только по контексту. После каждого "
            "утверждения ставь [id] источника. Нет ответа в контексте — скажи об этом."},
        {"role": "user", "content": f"Контекст:\n{context}\n\nВопрос: {question}"},
    ]
    resp = client.chat.completions.create(model=MODEL, messages=messages, temperature=0)
    return resp.choices[0].message.content
```

**Аналогия.** Индексация — разложить документы по полкам и составить подробный
каталог. Запрос — консультант смотрит в каталог, приносит пять нужных страниц и
отвечает клиенту, показывая пальцем, откуда что взял.

## Чанкинг: размер и перекрытие

**Чанкинг (chunking)** — нарезка документов на куски (чанки). Нужен по двум причинам:
весь документ не влезает в контекст, а один вектор на огромный текст «усредняет» все
его темы, и поиск по нему становится неточным. Чанк должен быть **достаточно мал**,
чтобы быть про одно, и **достаточно велик**, чтобы быть понятным сам по себе.

![Регламент из семи абзацев нарезан на три чанка с общими абзацами на границах](/lesson-media/llm/chunking.png#1200x560 "Чанкинг: размер чанка и перекрытие")

1. Частая отправная точка: **300–800 токенов** на чанк и **перекрытие 10–20%**. Резать
   лучше по структуре документа — заголовкам, абзацам, пунктам, — а не посреди фразы.
   Дальше размер подбирают по оценке качества на своих данных.
2. **Слишком крупные** чанки: в одном куске несколько тем, вектор размыт и поиск
   промахивается; в окно влезает меньше чанков, в контексте больше шума, растут цена и
   задержка.
3. **Слишком мелкие** чанки: кусок теряет контекст. Найдётся «в течение 30 дней», но
   непонятно, о чём речь, и ответ собирается из обрывков.
4. **Перекрытие (overlap)** — соседние чанки делят общий кусок текста, чтобы мысль на
   границе целиком попала хотя бы в один из них. На схеме перекрытие крупное для
   наглядности; на практике это обычно 10–20% чанка.

Полезные приёмы: добавлять в чанк заголовок раздела и название документа; хранить в
метаданных, откуда чанк (для ссылок и фильтров); для таблиц и кода использовать свои
правила нарезки.

**Аналогия.** Чанкинг — как нарезать пиццу. Огромные куски неудобно брать и в них всё
вперемешку; крошечные кусочки — уже не понять, какая была начинка. А перекрытие —
чтобы начинка на линии разреза не досталась никому наполовину.

## Гибридный поиск и реранкинг

Векторный поиск хорошо понимает смысл и синонимы, но плохо — **точные совпадения**:
коды ошибок, артикулы, номера договоров, редкие термины. Поиск по словам (полнотекстовый,
чаще всего с ранжированием **BM25**) — наоборот: ловит точные термины, но не понимает
перефразы.

![Два поиска объединяются, реранкер отбирает пять лучших чанков из примерно пятидесяти](/lesson-media/llm/hybrid-rerank.png#1200x520 "Гибридный поиск и реранкинг")

1. **Поиск по словам (BM25)** находит чанк с «ERR-4031», если пользователь написал код
   ошибки.
2. **Векторный поиск** находит «ошибку авторизации» по запросу «не могу войти».
3. **Гибридный поиск** запускает оба и **объединяет** списки. Популярный способ —
   **RRF (Reciprocal Rank Fusion)**: каждому документу дают очки по его местам в
   каждом списке, так что результат, высоко стоящий в обоих, выигрывает. Набираем
   несколько десятков кандидатов.
4. **Реранкер (reranker)** — обычно модель-**cross-encoder**: читает вопрос и чанк
   **вместе** и выставляет точную оценку релевантности. Векторный поиск сравнивает
   заранее посчитанные векторы (быстро, но грубо), реранкер честно читает пару (точно,
   но медленно), поэтому его запускают только на коротком списке кандидатов. В
   промпт уходят 3–5 лучших.

В PostgreSQL гибрид можно собрать в одной базе: встроенный полнотекстовый поиск
(`tsvector` с GIN-индексом; GIN разбирается в курсе по Postgres) плюс pgvector. Учти:
встроенное ранжирование `ts_rank` — не BM25, оно проще; настоящий BM25 дают расширения
(например, ParadeDB) или Elasticsearch и OpenSearch. Qdrant и многие другие векторные
базы поддерживают гибридный поиск сами.

**Аналогия.** Найм: сначала два рекрутера быстро отбирают резюме — один по ключевым
словам, другой «по общему впечатлению», — и из двух стопок собирают 50 кандидатов.
Потом руководитель внимательно читает каждое и приглашает пятерых. Читать вдумчиво все
тысячи резюме он бы не успел.

## RAG или fine-tuning

**Fine-tuning (дообучение)** — дополнительное обучение модели на своих примерах.
Меняются веса модели (часто не все, а небольшая добавка — LoRA). RAG модель не меняет:
он подкладывает нужные знания в промпт во время запроса.

| | RAG | Fine-tuning |
|---|---|---|
| Что меняет | что модель **знает** в этом запросе | как модель **себя ведёт** |
| Подходит для | ответов по документам, фактов, свежих и часто меняющихся данных | стиля и тона, формата ответа, узкой задачи (классификация, извлечение), сокращения длинного промпта |
| Обновление данных | обновил документы — сразу работает | нужно собрать данные и дообучить заново |
| Источники и права | ссылки на документы, фильтр по доступу | факты «растворяются» в весах, источника нет |
| Цена | индексация и поиск, длиннее промпт | подготовка датасета и обучение; потом запросы короче и дешевле |

Правило: **знания — через RAG, поведение — через fine-tuning**. Дообучение плохо
подходит, чтобы «научить фактам»: модель всё равно может их перепутать, а при каждом
изменении документов придётся переобучать. Обычно начинают с промптинга, потом
добавляют RAG, и только если упираются в формат, стиль или цену — дообучают. Подходы
сочетаются: дообученная под формат модель + RAG для знаний.

**Аналогия.** RAG — дать сотруднику доступ к актуальной базе инструкций. Fine-tuning —
отправить его на курсы: он начнёт работать в нужном стиле и быстрее, но новые цены
после курсов он всё равно не узнает.

## Tool calling

**Tool calling (function calling)** — способность модели в ответ на запрос не писать
текст, а **попросить вызвать функцию**: вернуть её имя и аргументы в JSON. Так модель
получает доступ к живым данным и действиям: статус заказа, погода, поиск по базе,
создание заявки.

![Последовательность: пользователь, приложение, LLM и функция обмениваются сообщениями](/lesson-media/llm/tool-calling.png#1200x760 "Tool calling — модель просит, приложение выполняет")

1. Пользователь спрашивает о данных, которых нет ни в модели, ни в документах.
2. Приложение отправляет модели вопрос и **список инструментов**: имя, описание и
   JSON Schema аргументов. По описанию модель решает, нужен ли инструмент.
3. Модель отвечает не текстом, а **вызовом**: `get_order_status({"order_id": 1042})`.
4. **Приложение** проверяет аргументы и права пользователя и **само** вызывает функцию.
5. Функция возвращает результат.
6. Результат отправляют модели сообщением с ролью `tool`.
7. Модель возвращает приложению финальный ответ текстом — или просит ещё один вызов.
8. Приложение показывает ответ пользователю. Модель и пользователь напрямую не
   общаются: всё идёт через ваш код.

```python
import json
from pydantic import BaseModel, ValidationError

class OrderArgs(BaseModel):
    order_id: int

tools = [{
    "type": "function",
    "function": {
        "name": "get_order_status",
        "description": "Статус и срок доставки заказа по его номеру",
        "parameters": {
            "type": "object",
            "properties": {"order_id": {"type": "integer"}},
            "required": ["order_id"],
        },
    },
}]

for _ in range(5):                                        # лимит раундов
    resp = client.chat.completions.create(model=MODEL, messages=messages, tools=tools)
    msg = resp.choices[0].message
    if not msg.tool_calls:
        break                                             # финальный ответ текстом
    messages.append(msg)                                  # запрос модели на вызов
    for call in msg.tool_calls:
        if call.function.name != "get_order_status":
            result = {"error": "неизвестный инструмент"}
        else:
            try:
                args = OrderArgs.model_validate_json(call.function.arguments)
                result = get_order_status(user, args.order_id)  # НАШ код, внутри проверка прав
            except ValidationError as exc:
                result = {"error": f"неверные аргументы: {exc}"}
        messages.append({"role": "tool", "tool_call_id": call.id,
                         "content": json.dumps(result, ensure_ascii=False)})
else:                                                     # break не случился
    raise RuntimeError("модель не уложилась в лимит раундов")
print(msg.content)
```

Главное: **модель не выполняет код и не ходит в сеть** — она только просит. Поэтому
безопасность на приложении: валидировать аргументы (модель может ошибиться в типе или
выдумать id), проверять права (пользователь A не должен узнать заказ пользователя B),
ставить таймауты и ограничивать число вызовов. Опасные действия (оплата, удаление) —
только с подтверждением человека. Хорошее описание инструмента — это часть промпта:
от него зависит, вызовет ли модель нужную функцию.

**Аналогия.** Модель — диспетчер, у которого нет рук: он не может сам открыть склад,
но знает, кому позвонить, и диктует заявку по форме «склад, найди заказ 1042».
Заявку выполняет живой сотрудник — и проверяет, имеет ли диспетчер право её давать.

## Агенты: ReAct и Plan-and-Execute

Обычный вызов LLM — **один запрос, один ответ**: модель только пишет текст. **Агент** —
это LLM **в цикле с инструментами**: модель сама решает, какие шаги сделать, вызывает
инструменты, смотрит на результаты и продолжает, пока задача не решена. Отличие от
обычного вызова: **цель вместо одного вопроса, несколько шагов, действия во внешнем
мире и решения, которые модель принимает по ходу**.

![Обычный вызов, цикл ReAct и схема Plan-and-Execute для задачи оформить возврат](/lesson-media/llm/agent-patterns.png#1200x760 "Агент — LLM в цикле с инструментами")

1. **Обычный вызов**: на «Оформи возврат» модель ответит советом, как это сделать, но
   сама ничего не сделает.
2. **ReAct (Reasoning + Acting)** — подход из одноимённой статьи 2022 года. Модель
   чередует **мысль** («нужно найти заказ») → **действие** (вызов инструмента) →
   **наблюдение** (результат) и снова мысль — до ответа. Гибко: каждый шаг выбирается
   по свежим данным. Минусы: много вызовов модели, может ходить по кругу.
3. **Plan-and-Execute** — сначала **планировщик** (LLM) составляет план целиком, затем
   **исполнитель** проходит шаги по одному, вызывая инструменты; если шаг не удался —
   **перепланирование**. Предсказуемее и дешевле для длинных задач (план можно
   показать, проверить, выполнять шаги дешёвой моделью), но хуже реагирует на
   неожиданности.
4. **Ограничители обязательны**: лимит шагов и токенов, таймауты, только безопасные
   инструменты, подтверждение человеком перед необратимыми действиями, логирование
   каждого шага.

Не всё стоит делать агентом. Если шаги заранее известны («найди чанки → ответь»), это
**обычный пайплайн (workflow)**: он дешевле, быстрее, проще отлаживается. Агент нужен,
когда путь к цели заранее неизвестен.

**Аналогия.** Обычный вызов — справочное бюро: спросил — получил ответ. ReAct — опытный
мастер, который делает шаг, смотрит на результат и решает, что дальше. Plan-and-Execute
— прораб: сначала пишет план работ, бригада выполняет пункты по порядку, а если
что-то пошло не так — прораб правит план.

## LangChain и LangGraph

**LangChain** — Python-фреймворк с **готовыми блоками** для работы с LLM: единый
интерфейс к моделям разных провайдеров, шаблоны промптов, загрузчики документов,
сплиттеры (чанкинг), интеграции с векторными базами, **ретриверы** (поиск) и
**цепочки (chains)**, которые соединяют блоки в пайплайн. Плюс: быстро собрать RAG из
готовых деталей и легко сменить провайдера. Минус: много абстракций, сложнее
отлаживать и понимать, что именно уходит в модель.

**LangGraph** — библиотека из той же экосистемы для **агентов и сложных сценариев**:
приложение описывается как **граф** из узлов и переходов с общим **состоянием (state)**.

![Граф с узлами retrieve, grade, rewrite и generate, условным переходом, циклом и state](/lesson-media/llm/langgraph.png#1200x560 "LangGraph — агент как граф с состоянием")

1. **Узел (node)** — шаг, обычная функция: получает state и возвращает его изменения.
   Внутри может быть вызов LLM, поиск, вызов API.
2. **Условный переход (conditional edge)** — функция-маршрутизатор решает, куда идти
   дальше (например, по оценке релевантности).
3. **Цикл**: если чанки не подошли — переписать вопрос и искать снова, но не больше
   трёх раз. Обычные цепочки LangChain идут строго вперёд, а графу циклы разрешены.
4. **State** — общее состояние, которое узлы читают и дополняют. Его можно сохранять
   между шагами (checkpointing): продолжить после сбоя, дождаться подтверждения
   человека (human-in-the-loop), хранить историю диалога.

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    documents: list[str]
    answer: str
    attempts: int

def route(state: State) -> str:
    # grade уже оставил в documents только релевантные чанки
    if state["documents"] or state["attempts"] >= 3:
        return "generate"                 # попытки кончились — generate скажет «не нашёл»
    return "rewrite"

graph = StateGraph(State)
graph.add_node("retrieve", retrieve)   # каждая функция возвращает dict с изменениями state
graph.add_node("grade", grade)         # отбрасывает нерелевантные чанки
graph.add_node("rewrite", rewrite)     # переписывает вопрос и увеличивает attempts
graph.add_node("generate", generate)
graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "grade")
graph.add_conditional_edges("grade", route, {"generate": "generate", "rewrite": "rewrite"})
graph.add_edge("rewrite", "retrieve")  # цикл
graph.add_edge("generate", END)

app = graph.compile()
result = app.invoke({"question": "Сколько дней на возврат?", "documents": [], "attempts": 0})
```

**Когда что брать.** Простой вызов модели или линейный RAG — **обычный код** на SDK
провайдера: десятки строк, всё видно и легко тестировать. LangChain — когда нужно
быстро собрать пайплайн из готовых интеграций. LangGraph — когда есть **ветвления,
циклы, долгоживущее состояние, несколько агентов или подтверждение человеком**: писать
это руками — значит заново изобрести граф состояний.

**Аналогия.** LangChain — набор деталей конструктора: колёса, моторчик, провода, из
которых быстро собрать машинку. LangGraph — схема железной дороги со стрелками: поезд
(состояние) едет по путям, на стрелках выбирает направление, может сделать круг и
вернуться на станцию.

## Оценка качества RAG

Качество RAG нельзя оценивать «на глаз» по паре вопросов: поменял размер чанков или
модель — и не знаешь, стало лучше или хуже. Нужна **систематическая оценка (evals)**.

![Тестовый набор, прогон RAG, метрики поиска и ответа, LLM-судья и проверка человеком](/lesson-media/llm/rag-eval.png#1200x620 "Как оценить качество RAG")

1. **Тестовый набор** — 50–200 реальных вопросов пользователей с эталонным ответом и
   источником, где этот ответ лежит. Его собирают из логов и с экспертами, а потом
   пополняют неудачными случаями из продакшена.
2. **Прогон**: на каждый вопрос сохраняют найденные чанки и сгенерированный ответ.
3. **Метрики поиска (retrieval)**: **hit rate / recall@k** — попал ли нужный чанк в
   top-k; **MRR** — насколько высоко он оказался. Если поиск не нашёл нужное, хороший
   ответ невозможен — поэтому поиск оценивают отдельно.
4. **Метрики ответа (generation)**: **faithfulness (groundedness)** — каждое ли
   утверждение ответа подтверждается найденными чанками (нет ли выдумок); **answer
   relevance** — отвечает ли он на вопрос; **correctness** — совпадает ли с эталоном.
5. **LLM-as-a-judge** — оценки ставит другая модель по чёткой рубрике: «есть ли в ответе
   факты, которых нет в контексте? 0 или 1». Быстро и дёшево, но судья тоже ошибается,
   поэтому выборку проверяет **человек**, а рубрику делают узкой и однозначной.

```text
Ты проверяешь ответ ассистента. Контекст: <чанки>. Ответ: <ответ>.
Для каждого утверждения ответа выпиши, подтверждается ли оно контекстом.
Верни JSON: {"unsupported_claims": [...], "faithful": true/false}
```

Дальше это работает как тесты: любое изменение (чанкинг, модель эмбеддингов,
реранкер, промпт) прогоняют на том же наборе и сравнивают цифры. Готовые библиотеки
для таких метрик тоже есть, например RAGAS. В продакшене добавляют обратную связь
пользователей (лайки и дизлайки) и мониторинг: какие вопросы остались без ответа.

**Аналогия.** Оценка RAG — как экзамен по одним и тем же билетам после каждого
изменения учебной программы: отдельно проверяем, нашёл ли студент нужную страницу в
учебнике (поиск), и правильно ли он по ней ответил (генерация). Проверяет ассистент
преподавателя (LLM-судья), а преподаватель выборочно перепроверяет.

## Ассистент по документам: как всё связано

Сквозной сценарий из вопроса ментора: помощник должен ответить по вашим документам и
при необходимости вызвать функцию. Вот как связаны токены, контекст, RAG и tool calling.

![Вопрос, RAG-поиск, сборка контекста, LLM с вызовом функции, ответ со ссылками и проверка опоры](/lesson-media/llm/assistant-flow.png#1200x600 "Ассистент по документам — как всё связано")

1. Пользователь спрашивает: «Можно ещё вернуть мой заказ 1042?»
2. **RAG-поиск**: эмбеддинг вопроса → векторная БД (с фильтром по правам) → top-k →
   реранкинг. Находим пункт регламента о сроке возврата.
3. **Сборка контекста в бюджет окна**: system-инструкция («отвечай только по
   документам и данным инструментов, ставь [id]»), несколько лучших чанков с их id,
   сжатая история, вопрос — и запас под ответ. Именно ограничение окна и цена токенов —
   причина, по которой мы кладём несколько кусков, а не всю базу знаний.
4. **LLM** находит правило в чанке [1], но даты доставки заказа в документах нет —
   это живые данные. Модель отвечает **tool call**: `get_order(1042)`.
5. **Приложение** проверяет права и вызывает функцию, результат (заказ получен 25 дней
   назад) возвращается модели с ролью `tool`.
6. Модель пишет **ответ со ссылками**: «Да: срок возврата — 30 дней с получения [1],
   заказ получен 25 дней назад».
7. **Проверка опоры на источник**:
   - в рантайме: ссылки [id] указывают на реально переданные чанки, цитаты есть в их
     тексте, числа совпадают с результатом функции; можно дополнительно попросить
     дешёвую модель-судью найти неподтверждённые утверждения; если опоры нет —
     честное «не нашёл в документах» вместо выдумки;
   - офлайн: тестовый набор и метрика **faithfulness** (раздел «Оценка качества RAG»),
     а также recall@k для поиска.

**Аналогия.** Хороший консультант: смотрит в регламент (RAG), звонит на склад за
статусом заказа (tool calling), держит на столе только нужные бумаги (контекстное
окно) и в ответе показывает, на какой пункт опирается, — а старший смены выборочно
проверяет его ответы (оценка качества).

## Как ответить на вопросы ментора

> **Вопрос:** что такое эмбеддинг?

- Вектор фиксированной длины, который модель эмбеддингов строит по тексту.
- Похожие по смыслу тексты дают близкие векторы — даже без общих слов.
- Близость меряют косинусным сходством; документы и вопросы кодируют одной моделью.
- Применение: семантический поиск, RAG, кластеризация, рекомендации.

> **Вопрос:** что такое RAG и какую проблему он решает?

- Retrieval-Augmented Generation: сначала найти релевантные куски документов, потом
  сгенерировать ответ по ним.
- Решает: модель не знает ваших и свежих данных и галлюцинирует.
- Даёт ответы по своим данным без переобучения, ссылки на источники, учёт прав доступа.
- Всю базу в промпт не положить — окно, цена, качество.

> **Вопрос:** опиши RAG-пайплайн по шагам.

- Индексация: загрузить и очистить документы → чанкинг → эмбеддинги → векторная БД с
  метаданными.
- Запрос: вопрос → эмбеддинг той же моделью → поиск top-k с фильтрами → (реранкинг) →
  промпт «отвечай по контексту, ставь ссылки» → LLM → ответ с источниками.

> **Вопрос:** зачем нужен чанкинг? Что будет, если чанки слишком большие или маленькие?

- Документ целиком не влезает в окно, а один вектор на большой текст размыт.
- Крупные чанки: размытый поиск, мало чанков в окне, шум, дороже.
- Мелкие: теряется контекст, ответ из обрывков.
- Обычно 300–800 токенов, перекрытие 10–20%, резать по структуре, подбирать по оценке.

> **Вопрос:** что такое векторная БД?

- Хранит векторы с текстом и метаданными и быстро ищет ближайшие к запросу (top-k).
- Использует ANN-индексы (HNSW): почти точный поиск много быстрее перебора.
- pgvector — расширение Postgres, Qdrant — отдельный сервер, Chroma — для прототипов.
- Фильтры по метаданным — в том числе по правам доступа.

> **Вопрос:** когда выбрать RAG, а когда fine-tuning?

- RAG — для знаний: документы, факты, часто меняющиеся данные, нужны источники и права.
- Fine-tuning — для поведения: стиль, формат, узкая задача, короче промпт.
- Начинать с промптинга и RAG; дообучать, если упёрлись в формат, стиль или цену; их
  можно сочетать.

> **Вопрос:** что такое tool calling?

- Модель вместо текста возвращает имя функции и аргументы в JSON по описанию инструментов.
- Вызывает функцию приложение, результат возвращают модели (роль `tool`), она пишет ответ.
- Модель сама код не выполняет: валидация аргументов, права, таймауты — на приложении.

> **Вопрос:** чем агент отличается от обычного вызова LLM?

- Обычный вызов — один запрос, один ответ текстом.
- Агент — LLM в цикле с инструментами: сам выбирает шаги, действует, смотрит на
  результат, продолжает до цели.
- Паттерны: ReAct (мысль → действие → наблюдение) и Plan-and-Execute (план, затем
  выполнение, перепланирование).
- Нужны ограничители: лимит шагов, таймауты, подтверждение опасных действий.

> **Вопрос:** зачем нужны LangGraph и LangChain?

- LangChain — готовые блоки: модели, промпты, загрузчики, сплиттеры, ретриверы, цепочки;
  быстро собрать RAG и сменить провайдера.
- LangGraph — агенты как граф: узлы, общий state, условные переходы, циклы, сохранение
  состояния, человек в контуре.
- Простой сценарий — обычный код; ветвления и циклы — LangGraph.

> **Вопрос:** как оценить качество RAG?

- Тестовый набор реальных вопросов с эталоном и нужным источником.
- Отдельно поиск (hit rate, recall@k, MRR) и ответ (faithfulness, relevance, correctness).
- LLM-as-a-judge по чёткой рубрике + выборочная проверка человеком.
- Любое изменение прогонять на том же наборе; в проде — фидбэк и мониторинг.

> **Вопрос (из урока «LLM»):** помощник должен ответить по документам и вызвать функцию:
> как связаны токены, контекст, RAG и tool calling, и как проверить опору на источник?

- Окно и цена токенов не дают положить всю базу → RAG выбирает несколько чанков.
- Контекст: system-правила + чанки с id + история + вопрос + запас под ответ.
- Живых данных в документах нет → tool call, функцию вызывает приложение.
- Проверка: ссылки [id] на переданные чанки, утверждения сверяются с ними и с
  результатом функции, иначе «не нашёл»; офлайн — faithfulness на тестовом наборе.

## Частые ошибки в ответах

- «Эмбеддинг — это токен» или «эмбеддинги генерирует та же модель, что отвечает».
  Эмбеддинг — вектор смысла целого текста, его строит отдельная модель.
- «RAG — это дообучение модели на документах». RAG ничего не меняет в модели: он
  подкладывает найденное в промпт.
- «Чем больше чанков в контекст, тем лучше». Лишние куски — шум, деньги и риск, что
  модель не заметит нужное.
- «Модель сама вызывает функцию». Модель только просит; вызывает и проверяет права
  приложение.
- «Агент — это любой чат-бот». Агент — цикл с инструментами и решениями модели;
  фиксированный пайплайн агентом не является.
- «Качество RAG проверили на пяти вопросах — работает». Нужен тестовый набор и метрики
  отдельно для поиска и для ответа.
