# RAG, день 3: оценка качества и диагностика

> Цель: вручную оценить выдачу, отдельно проверить ответ и найти первый сломанный
> участок цепочки. **60 минут чтения с вычислениями**, **2–3 часа активного изучения**
> вместе с практикумом. Установка Ragas, запуск LLM-судьи и внешние API не обязательны.

У ассистента «Маяка» уже есть документы, эмбеддинги, поиск, RRF и реранкер. Но слово
«лучше» пока не определено. Пользователь может получить грамотно написанный ответ
по старому регламенту; поиск — найти правильный документ на двадцатом месте; индекс —
идеально воспроизвести геометрию, которая плохо отражает задачу. Одна итоговая оценка
скрывает эти разные причины.

Сегодня разделим четыре вопроса: **есть ли нужный источник в корпусе; находит ли его
поиск; получает ли его генератор; соответствует ли ответ источнику и вопросу**.
Все данные вымышленные. Действующий срок возврата — 45 дней, архивный — 30,
инструкция ERR-4031 касается доступа к рабочему пространству.

## Набор оценки и единица релевантности

**Набор оценки, evaluation set**, — зафиксированные примеры, на которых сравнивают
версии системы. Пример содержит вопрос, разрешённую область корпуса, ожидаемые
основания и критерии хорошего ответа. **Релевантность** — полезность материала для
данного вопроса по выбранным правилам разметки. Это не внутреннее число модели:
эксперт должен объяснить, почему документ даёт нужное основание.

Для вопроса «можно вернуть через 40 дней?» релевантен действующий регламент v2
с условием о состоянии товара. Архивный v1 со сроком 30 дней может быть лексически
очень близок, но не подходит для текущего решения. Для исторического вопроса про
март ситуация меняется. Поэтому разметка зависит от вопроса, даты и прав, а не
просто от темы документа.

**Единица оценки** должна быть определена до счёта. Можно оценивать документы,
чанки или отдельные факты. Если один документ разбит на десять перекрывающихся
чанков, нельзя автоматически считать их десятью независимыми полезными источниками.
При документной оценке дедуплицируем по document_id; при чанковой — явно задаём,
какие фрагменты засчитываются и почему. Правила должны совпадать у сравниваемых систем.

В учебных вычислениях ниже единица — **различимый фрагмент**, дубликатов нет.
Для одного вопроса эксперт нашёл **четыре релевантных фрагмента во всём разрешённом
корпусе**. Поиск вернул три: первый нерелевантен, второй и третий релевантны.
Запишем бинарные метки по порядку выдачи как **[0, 1, 1]**. `1` означает полезный
фрагмент, `0` — бесполезный по нашей инструкции. Нужны не только метки найденного,
но и число всех известных релевантных: без него полноту не посчитать.

Разметка бывает неполной: эксперт мог не проверить весь большой корпус. Тогда
«не размечено» не всегда означает «нерелевантно». Можно объединять кандидатов разных
систем и проверять их вручную, но нужно честно описать охват и ограничение оценки.
Новая система может найти хороший материал вне старой разметки; это повод для аудита,
а не автоматического наказания за новый ID.

### Задание

Два перекрывающихся чанка дословно повторяют правило 45 дней. Можно ли назвать
их двумя найденными основаниями и сравнить с системой, где весь раздел один чанк?

### Ответ

Только если заранее определены сопоставимые правила чанковой оценки. Иначе разбиение
само изменяет знаменатели и даёт ложный выигрыш. Для оценки источников лучше свести
повторы к документу или факту; для поиска чанков — фиксировать разбиение и разметку.

## Precision@k, Recall@k и MRR

**k** — число верхних позиций, которые оцениваем. **Precision@k** — доля релевантных
среди этих результатов. **Recall@k** — доля всех релевантных материалов разрешённого
корпуса, попавших в эти позиции. Связь с общей идеей:
[Precision и Recall](/courses/llm/lessons/ml-classification-metrics#precision-и-recall "Precision измеряет полезность выбранного, Recall — долю найденного среди всего нужного.").
Знаменатели разные, поэтому высокий Precision не гарантирует высокий Recall.

Формулы при фиксированном k и выдаче длины не меньше k:

- `Precision@k = r_k / k`, где `r_k` — число релевантных в первых k позициях.
- `Recall@k = r_k / R`, где `R` — число всех релевантных в корпусе для вопроса.

Для **[0,1,1]**, `k=3`, `r_k=2`, `R=4`:
`Precision@3 = 2/3 ≈ 0.667`, `Recall@3 = 2/4 = 0.5`.
Две трети переданных фрагментов полезны, но нашли только половину всех полезных.
Если смотреть только первое место, Precision@1=0 и Recall@1=0. Для системы,
передающей генератору один чанк, это серьёзный провал, хотя на глубине 3 всё выглядит
приличнее. Поэтому k связывают с реальным потребителем выдачи.

**Reciprocal rank, RR**, — обратная позиция первого релевантного результата:
`RR = 1 / rank_first`. `rank_first` — номер первой полезной позиции, начиная с 1.
В примере первый полезный на месте 2, значит `RR = 1/2 = 0.5`. Если полезного
в оцениваемой выдаче нет, RR принимаем равным 0. Если смотрим только до k,
получаем усечённый вариант; глубину нужно записать.

**MRR, mean reciprocal rank**, — среднее RR по вопросам, а не имя для результата
одного вопроса. Для трёх вопросов с RR `1/2`, `1`, `0`:
`MRR = (0.5 + 1 + 0)/3 = 0.5`. Эта метрика удобна, когда важно как можно раньше
найти хотя бы одно основание. Она не замечает, нашли ли после него остальные три.
Две выдачи `[1,0,0]` и `[1,1,1]` имеют одинаковый RR=1, но разную полноту.

![Один пример выдачи: Precision, Recall, RR и NDCG используют разные знаменатели](/lesson-media/llm/rag-deep-evaluation.svg#1200x720 "Для [0,1,1] и четырёх релевантных в корпусе: P@3=2/3, R@3=1/2, RR=1/2, NDCG@3≈0.531.")

**Короткая выдача.** Если при запросе top-5 вернули только три объекта, договоримся
в этом учебном протоколе считать отсутствующие позиции нерелевантными и делить
Precision@5 на 5. Некоторые инструменты делят на фактически возвращённое число;
числа перестанут совпадать. Не меняйте соглашение задним числом ради красивого отчёта.
Пустая выдача при k>0 даёт Precision@k=0, а Recall=0, если релевантные существуют.

**Не путайте с ANN recall.** Здесь эталон — размеченная полезность. В
[ANN-проверке](/courses/llm/lessons/rag-search-indexes#ann-hnsw-и-ivf "ANN recall сравнивает приближённых соседей с точным поиском по той же геометрии.")
эталон — геометрические соседи exact. Можно иметь ANN recall=1 и Retrieval
Recall@3=0, если сама геометрия поставила нерелевантное выше полезного.

### Задание

В корпусе 4 релевантных фрагмента, выдача `[1,0,1]`. Посчитайте P@3, R@3, RR.
Что изменилось относительно `[0,1,1]`?

### Ответ

P@3=2/3 и R@3=2/4=1/2 не изменились: число полезных одинаково. RR стал 1 вместо
1/2, потому что первое полезное основание поднялось на первое место. Эти метрики
оценивают разные стороны списка, и ни одна не обязана отражать все изменения.

## NDCG и соглашения о полезности

**NDCG, normalized discounted cumulative gain**, — нормализованная накопленная
полезность с уменьшением веса дальних позиций. Она учитывает и порядок, и возможность
разных степеней полезности. Название длинное, но смысл прост: полезное в начале
ценнее полезного в конце; затем результат сравниваем с идеальным порядком для
того же вопроса.

Выберем **явное соглашение**: `gain(rel) = 2^rel − 1`, где `rel` — оценка
релевантности фрагмента, `gain` — его числовая полезность, `2^rel` — два в степени rel.
При rel=0 gain=0, при rel=1 gain=1, при rel=2 gain=3. Последнее говорит: по нашему
соглашению полностью полезный материал ценится в три раза выше частично полезного,
а не в два. Это выбор шкалы, а не природный закон.

**DCG@k** складывает полезности с позиционной скидкой:
`DCG@k = Σ ((2^rel_i − 1) / log2(i + 1))`, где i — позиция от 1 до k,
`rel_i` — её метка, `log2` — логарифм по основанию 2, Σ — сумма вкладов.
На месте 1 знаменатель `log2(2)=1`, на месте 2 — `log2(3)≈1.585`,
на месте 3 — `log2(4)=2`. Чем дальше позиция, тем меньше её вклад.

Для `[0,1,1]`:
`DCG@3 = 0/1 + 1/1.585 + 1/2 ≈ 0 + 0.63093 + 0.5 = 1.13093`.
Теперь строим идеальную выдачу **по всем известным релевантным в корпусе**, а не
переставляем только то, что система уже нашла. Их четыре, значит идеальные первые
три позиции — `[1,1,1]`.
**IDCG@3**, ideal DCG, равен
`1/1 + 1/1.585 + 1/2 ≈ 2.13093`.
Тогда `NDCG@3 = DCG@3 / IDCG@3 ≈ 1.13093/2.13093 ≈ 0.53072`.
Это не 53% вероятности правильного ответа: мы сравнили взвешенную полезность списков.

Если ошибочно построить идеал только из найденных меток `[1,1,0]`, знаменатель
получится меньше и результат будет завышен. Система не должна получать награду
за то, что не нашла материал для идеального сравнения. Список эталонных оценок
и глубина k должны быть одинаковыми для конкурирующих вариантов.

**Градуированная релевантность:** можно задать 0 — бесполезный, 1 — частично отвечает,
2 — даёт полное основание с условиями. Выдача `[2,1,0]` имеет
`DCG@3 = 3 + 1/1.585 ≈ 3.63093`. Перестановка `[1,2,0]` даёт
`1 + 3/1.585 ≈ 2.89279`. Количество ненулевых результатов одинаково,
но более сильное основание в начале получает преимущество.

**Библиотеки могут использовать разные соглашения.** Некоторые принимают готовые
gain как вход и применяют линейную полезность. В частности, `sklearn.metrics.ndcg_score`
использует переданный `y_true` как gain; для воспроизведения выбранной здесь
экспоненциальной схемы на градуированных rel сначала передают `2^rel − 1`.
На бинарных метках разницы нет. Учитывайте также обработку ничьих и усечение k.
Сравнивать результаты двух реализаций нужно на маленьком известном примере.

### Задание

Для `[0,1,1]` коллега получил NDCG@3≈0.693, взяв идеал `[1,1,0]`.
Что проверить прежде, чем объявить его реализацию «другой допустимой формулой»?

### Ответ

Нужно проверить множество эталонных документов. В нашем протоколе в корпусе четыре
релевантных, идеальный top-3 — `[1,1,1]`, поэтому IDCG≈2.13093 и NDCG≈0.53072.
Идеал только по найденным документам меняет задачу и скрывает ненайденные основания.
Сначала согласуем эталон, затем gain, скидку и детали инструмента.

## Что делать, когда релевантных материалов нет

Не каждый вопрос имеет ответ в базе. «Маяк» хранит внутренние регламенты и доступы,
а сотрудник спрашивает прогноз погоды на завтра. Для него число релевантных R=0.
Recall как `найдено/R` не определён, а IDCG=0 делает NDCG неопределённым как 0/0.
Не маскируйте эту ситуацию арифметикой и не присваивайте автоматически идеальную единицу.

В этом учебном протоколе помечаем Recall и NDCG для R=0 как **N/A, не применимо**,
исключаем из среднего этих двух метрик и отдельно публикуем число исключённых
вопросов. Другие протоколы могут назначать ноль, но тогда смешивают полезность поиска
и долю вопросов без ответа; соглашение нужно явно сообщить. RR здесь можно
считать нулевым по определению, однако для оценки продукта полезнее отдельная группа.

Для вопросов без оснований проверяем **корректное воздержание**: система говорит,
что в доступных источниках нет ответа, и не придумывает факт. Это не «ошибка поиска»
в обычном смысле, если нужного документа действительно нет. Отдельно измеряем долю
правильных отказов, ложных ответов и ложных отказов на отвечаемых вопросах. Иначе
можно «улучшить безопасность», отказывая всем, но продукт перестанет быть полезным.

Отсутствие результата тоже требует диагностики. Может отсутствовать сам источник,
может мешать ошибочный фильтр, может не работать поиск, а может пользователь не
иметь доступа. Нельзя обходить авторизацию, чтобы сделать тест отвечаемым. Для
каждого пользователя релевантный корпус ограничивается тем, что разрешено читать.
Ответ «не могу подтвердить по доступным материалам» не должен раскрывать наличие
закрытой инструкции другой команды.

**Порог score** для отказа не выбирают по красивому числу. Высокий cosine может
быть у тематически похожего, но не отвечающего материала; низкий — у короткого
точного кода. Порог проверяют на фиксированном наборе отвечаемых и неотвечаемых
вопросов, при той же модели и обработке. Напоминание:
[score и вероятность](/courses/llm/lessons/ml-classification-metrics#score-вероятность-и-порог "Score не становится вероятностью правильности без проверки и калибровки.").

### Кейс наставника

Команда гордится средним Recall=1: она исключила все вопросы, где ничего не
найдено. Почему такое исключение отличается от R=0?

### Ответ

R=0 — отсутствие релевантного в эталонном разрешённом корпусе. Пустая выдача при
R>0 — настоящий провал поиска и Recall=0, её исключать нельзя. Решение об исключении
принимают по эталону, а не по удобству результата системы.

## Faithfulness, правильность и релевантность ответа

Теперь поисковая выдача оценена, но готовый ответ ещё нет. **Faithfulness,
верность контексту**, в нашей ручной инструкции означает: существенные утверждения
ответа подтверждаются переданным контекстом и не противоречат ему. Это отношение
ответа к контексту, а не универсальная гарантия фактической истины.

**Фактическая правильность** — соответствие действующему проверенному правилу и
условиям задачи. Ответ «возврат возможен в течение 30 дней» может быть faithful
архивному v1, но неправильным для сегодняшнего вопроса, где действует 45.
Обратный случай: модель угадала 45 без источника. Число правильное, но опоры в
переданном контексте нет; доверять такой процедуре нельзя.

**Answer relevance, релевантность ответа**, — отвечает ли текст на заданный вопрос
по выбранной инструкции оценки. Для «что делать при ERR-4031?» длинный точный
рассказ о политике возвратов нерелевантен. **Context relevance, релевантность
контекста**, — насколько переданные фрагменты полезны для решения этого вопроса.
Контекст может содержать нужную инструкцию и ещё девять бесполезных статей;
наличие одной полезной не делает весь набор чистым.

| Ответ и основание | Верность контексту | Фактическая правильность | Ответ на вопрос |
|---|---|---|---|
| «30 дней», контекст — архив v1 | может быть высокой | нет для текущего правила | по теме, но ошибочен |
| «45 дней», контекст не содержит срока | не подтверждена | число может быть верным | требует проверки условий |
| «45 дней при условиях v2», контекст v2 | подтверждена при точной передаче | да, если правило действует | да для вопроса о возврате |
| точный пересказ v2 на вопрос ERR-4031 | может быть высокой | факты о возврате верны | нет |

Чтобы оценить faithfulness вручную, разбейте ответ на проверяемые утверждения.
«Возврат возможен 45 дней, включая использованный товар» — минимум два утверждения:
срок и допустимость использованного товара. Если источник поддерживает только срок,
нельзя назвать весь ответ подтверждённым. Условия и отрицания часто важнее общего
совпадения темы. Ссылку проверяют отдельно: она должна вести к фрагменту, который
поддерживает конкретное утверждение, а не просто к соседнему разделу.

Названия метрик **не задают единственный алгоритм**. В Ragas и других наборах могут
быть разные версии, входы и способы подсчёта: одни требуют эталонного ответа,
другие спрашивают LLM-судью, третьи используют сравнение представлений. Перед
сравнением фиксируют определение, версию, инструкцию и необходимые данные.
Нельзя взять две цифры с названием «relevance» и объявить их одной шкалой.

### Задание

Генератор получил правильный v2 с 45 днями и запретом возврата использованного
товара. В ответе написал: «40 дней укладываются, состояние товара неважно».
На каком уровне ошибка и почему хороший Retrieval Recall её не опровергает?

### Ответ

Основание дошло, но ответ противоречит условию. Это провал передачи фактов и
faithfulness на этапе генерации. Retrieval Recall измеряет нахождение материалов,
а не соблюдение их содержания в ответе. Нужна отдельная проверка утверждений.

## Development, test и ограничения LLM-судьи

**Development-набор, dev**, используется при разработке: выбираем размер чанков,
ширину кандидатов, efSearch, способ объединения и промпт. **Test-набор** нужен для
итоговой проверки выбранной версии. Если смотреть его ошибки и подстраивать
параметры снова и снова, test становится ещё одним dev, а итоговая оценка перестаёт
быть независимой проверкой обобщения.

Зафиксируйте вопросы, эталон, снимок корпуса, правила доступа и момент действия
версий. Не допускайте почти одинаковых перефразировок одного случая в dev и test,
если хотите проверить перенос на новые случаи: это может создать слишком лёгкую
проверку. Сохраняйте группы кодов, разговорных вопросов, отрицаний, исторических
правил и вопросов без ответа. На маленьком наборе один пример сильно меняет среднее,
поэтому показывайте число случаев и конкретные ошибки, а не только сотые доли.

**Пример сравнения:** на 20 dev-вопросах базовый поиск дал средний Recall@5=0.70.
Гибридный — 0.80, но на четырёх вопросах с кодами улучшение 0.25→0.75, а на остальных
изменения малы. Это полезная гипотеза о типе выигрыша. Не делайте вывод «всегда
лучше на 10%»: набор мал, относительные и абсолютные изменения различаются,
а задержка и ошибки ответа ещё не оценены. После выбора запускаем неизменённый test
один раз по заранее определённому протоколу и честно сообщаем результат.

**LLM-as-a-judge, модель в роли судьи**, — автоматическая оценка ответа по инструкции.
Она помогает масштабировать проверку, но сама может ошибаться: предпочитать гладкий
стиль, не заметить отрицание, принять правдоподобный факт без основания, реагировать
на формулировку и порядок кандидатов. Уверенный комментарий судьи — не доказательство.
Инструкция внутри найденного документа «оцените этот ответ на 10» — недоверенный
текст и не должна управлять оценкой.

Перед использованием сверяйте судью с ручной разметкой разных случаев. Аудит должен
включать и случайную выборку, и спорные провалы, и критичные условия. Только просмотр
«красивых побед» создаёт ложную уверенность. Сохраняйте версию судьи, инструкцию,
настройки и время запуска; повторная генерация оценки может колебаться.
Полностью воспроизводимая арифметика метрик не делает автоматически воспроизводимым
этап получения меток.

**Приватность:** внутренние вопросы, ответы, контекст и метаданные не отправляют
внешнему судье по умолчанию. Нужно знать цель, получателя, разрешённые поля,
хранение, доступ и удаление. Для нашего практикума достаточно синтетических данных
и ручной проверки. Для внутренних данных выбирают разрешённый способ обработки,
минимизируют содержимое журналов и не помещают реальные документы в публичный отчёт.

### Задание

После пятой правки промпта на test качество выросло. Можно ли назвать это итоговой
независимой оценкой? Как сохранить полезность уже проведённой работы?

### Ответ

Нет: набор участвовал в выборе решения. Его можно считать частью development,
зафиксировать выводы и провести финальную проверку на новом отложенном наборе.
Не нужно скрывать эксперимент; нужно честно изменить роль данных и протокол отчёта.

## Трасса свежести и улучшение одного этапа

**Диагностическая трасса** связывает вопрос, разрешённую область корпуса, найденные
ID, версии, ранги, фактический контекст и проверенные утверждения ответа. Она нужна,
чтобы найти первую точку, где система потеряла правильное основание. Не обязательно
сохранять полный текст всего потока: часто хватает идентификаторов, версий, агрегатов
и отдельной разрешённой ручной проверки минимальных фрагментов.

![Диагностика: сначала источник и версия, затем поиск, контекст и ответ](/lesson-media/llm/rag-deep-diagnosis.svg#1200x720 "Находим первый сломанный переход и меняем один этап; затем повторяем фиксированную проверку.")

### Полный кейс: правило обновили, ответ остался старым

5 апреля сотрудник спрашивает про возврат через 40 дней. Эталон: v2 действует
с 1 апреля, срок 45 дней при соблюдении условий. Ответ ассистента: «нет, предел
30 дней». Не начинаем с догадки «модель слишком маленькая».

**Шаг 1: источник.** Проверяем, что v2 опубликована, а не существует только черновик.
Если нужное правило не утверждено, поисковая настройка не решит продуктовую неопределённость.
**Шаг 2: индекс.** Есть ли чанки v2, совпадает ли кодировщик, исключена ли v1 из
текущего поиска? Недавний indexed_at у v1 ничего не доказывает.
**Шаг 3: кандидаты.** При тех же правах и вопросе есть ли v2 в exact, ANN,
лексическом и объединённом списках? Так отделяем геометрию от приближения и объединения.
**Шаг 4: контекст.** Дошла ли v2 с условиями в реальный вход генератора?
**Шаг 5: ответ.** Если дошла, какие утверждения расходятся с источником?

Для каждой подтверждённой причины свой минимальный эксперимент. Если v2 не
проиндексирована, исправляем публикацию и проверяем появление версии. Если exact
находит её, а ANN нет, меняем параметр поиска и меряем ANN recall с задержкой.
Если реранкер ставит v2 первой, а сборщик берёт старый исходный порядок, исправляем
сборку. Если контекст верен, проверяем инструкцию, обработку противоречий и ответ,
не перестраивая без причины весь индекс.

**Меняйте один этап за раз.** Если одновременно сменить модель, чанкинг, фильтры
и промпт, улучшение нельзя связать с одной причиной, а ухудшение трудно откатить.
Иногда согласованная миграция требует нескольких изменений сразу, например нового
кодировщика и индекса; тогда это одна явно описанная совместимая версия, которую
сравнивают целиком. Принцип не запрещает обязательные зависимости — он требует
объяснить, какую гипотезу проверяет эксперимент.

### Практикум наставника

Разберите четыре наблюдения и для каждого запишите: первый подтверждённый разрыв,
следующий тест и одно изменение, которое пока делать рано.

1. v2 отсутствует в активном индексе, v1 находится быстро.
2. v2 первая в exact, но не входит в ANN top-10 при тех же векторах и правах.
3. v2 первая после реранкера, но в контекст попали пять повторов v1.
4. v2 с условием в контексте, а ответ обещает возврат использованного товара.

### Ответ

1. Разрыв публикации/индексации. Проверяем импорт и переключение активной версии;
   рано менять реранкер.
2. Разрыв приближённого поиска. Меряем ANN recall и задержку при ширине поиска;
   рано менять генератор.
3. Разрыв сборки контекста. Проверяем использование финального порядка, версии и
   дедупликацию; рано увеличивать размерность эмбеддингов.
4. Разрыв генерации/проверки утверждений. Сравниваем условия источника с ответом;
   рано объявлять, что проблема в отсутствии документа.

### Итоговый проект на бумаге

Составьте 12 вымышленных вопросов: четыре про текущие правила возврата, два про
историческую редакцию, три про ERR-4031 и перефразировки, три без доступных оснований.
Разделите на dev и test **до** выбора настроек. Для каждого определите допустимые
источники, единицу релевантности, эталонные утверждения и корректный отказ.
Для одного отвечаемого случая придумайте выдачу и вручную посчитайте P@3, R@3,
RR и NDCG@3. Для одного неотвечаемого укажите N/A и критерий правильного отказа.
Затем оцените два ответа: гладкий по архивному v1 и короткий по действующему v2.

### Ответ

Содержательное решение фиксирует знаменатели, версию корпуса, права и gain;
не путает RR одного вопроса с MRR, отдельно проверяет верность контексту и актуальную
правильность. На синтетических 12 случаях нельзя доказать производственное качество;
это упражнение на постановку проверяемого эксперимента. После него вы должны уметь
объяснить, каких данных не хватает для следующего решения.

**Связь трёх дней:** первый подготовил актуальные и понятные единицы знания; второй
доставил разрешённые основания с учётом скорости и бюджета; третий сделал качество
измеримым и локализуемым. Задача инженера — назвать наблюдаемую причину и проверку,
а не перечислить максимум названий моделей и баз данных.

### Источники и соглашения

[Ragas: список метрик](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)
показывает, почему нужно проверять конкретную версию определения и необходимые входы;
[scikit-learn: ndcg_score](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html)
— пример соглашения о готовых gain. В этом уроке ручной протокол явно задаёт
экспоненциальный gain, скидку log2(i+1), идеал по корпусу и обработку R=0.
