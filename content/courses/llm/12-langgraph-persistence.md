## Checkpointer сохраняет снимки

**Checkpoint** — сохранённый снимок состояния и сведений о ходе графа. **Checkpointer** — компонент, который пишет и читает эти снимки. **Persistence** означает сохранение информации за пределами отдельного запуска. Оно помогает продолжать диалог или восстанавливаться после остановки.

Это закладка вместе с заполненной карточкой, а не новое знание модели. Checkpoint не обучает LLM и не меняет её веса. Чтобы модель увидела сохранённый факт, приложение должно передать его в следующий запрос.

**Store** — отдельное хранилище данных приложения, например предпочтений пользователя для нескольких диалогов. Checkpointer хранит ход конкретного диалога; store может использоваться между ними. Долговечность обоих зависит от выбранного хранилища.

`InMemorySaver` хранит снимки в RAM, оперативной памяти процесса. Для учебного примера удобно, но после перезапуска память теряется. Хранилище на диске или сервере требует отдельной настройки. Само слово «checkpointer» долговечность не гарантирует.

**Упражнение — 5 минут.** В каком месте хранить незавершённый черновик, а в каком — язык ответов пользователя для разных диалогов? Переживёт ли первый перезапуск с `InMemorySaver`?

```solution
**Решение.** Черновик относится к состоянию процесса и его checkpoint. Язык можно хранить в store с подходящей областью доступа пользователя. `InMemorySaver` перезапуск не переживает; требуется долговечное хранилище. Ни один вариант не меняет веса модели.
```

## Thread отделяет диалоги

**Thread** — последовательность запусков с общей историей состояния. `thread_id` — идентификатор, по которому checkpointer находит эту историю. Один пользователь может вести несколько независимых диалогов.

```python
from langgraph.checkpoint.memory import InMemorySaver

# builder — граф из предыдущего дня; пример только в памяти.
graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "mayak-demo-42"}}
```

Новое обычное сообщение с тем же ID продолжает историю диалога: это новый вход графа. Приостановленный узел требует другого действия — явного **возобновления**, resume. Совпадение ID само по себе не передаёт ответ на запрос подтверждения.

| Вызов | Смысл |
| --- | --- |
| Новый вход, прежний ID | Следующий запуск в том же диалоге |
| Новый вход, новый ID | Другая история |
| `Command(resume=...)`, прежний ID | Ответ на ожидающий `interrupt()` |

![Два диалога имеют разные цепочки снимков](/lesson-media/llm/agents-threads.svg#1200x720 "thread_id выбирает историю состояния; разные идентификаторы не смешивают диалоги")

ID не является паролем. В настоящем приложении сервер проверяет владельца диалога; нельзя давать доступ лишь потому, что клиент знает строку. Сохранять следует только необходимые данные, учитывая срок хранения и удаление истории.

**Упражнение — 5 минут.** Пользователь начал независимое обсуждение заказа 99. Стоит ли повторить ID заказа 42? Достаточно ли отправить «да» обычным сообщением, чтобы продолжить ожидающий узел?

```solution
**Решение.** Для независимой истории нужен другой thread_id, иначе смешаются состояния. Ожидающий interrupt возобновляют через Command(resume=...) с исходным ID и проверенными правами. Обычное сообщение «да» не заменяет протокол возобновления.
```

## Interrupt ждёт решение человека

**Interrupt** — управляемая пауза выполнения. `interrupt(payload)` отдаёт вызывающей стороне данные для согласования; при возобновлении возвращает переданное решение. **Command** — объект управления графом; поле `resume` несёт ответ человека ожидающему узлу.

Человек видит: «Заказ 42; 40 ≤ 45; товар не использован; подготовлен черновик». Возможны согласие, отказ или исправление. До согласия черновик существует в состоянии, но не записан как утверждённый документ.

```python
from langgraph.types import interrupt, Command

def approve(state):
    decision = interrupt({"draft": state["draft"], "order_id": 42})
    # Учебный контракт: принимаем только точное логическое True.
    return {"approved": decision is True}

# Когда граф остановился в approve:
graph.invoke(Command(resume=True), config=config)
```

Это фрагмент: для него в граф добавляют узел `approve`, поле `approved` и переход после согласования. При отказе маршрут идёт в завершение без записи; исправленный текст в полноценном контракте нужно заново проверить и согласовать. Ответ «true» строкой здесь не равен логическому `True`.

![Черновик останавливается перед согласованием](/lesson-media/llm/agents-interrupt.svg#1200x720 "interrupt показывает черновик; Command с тем же thread_id передаёт решение, запись разрешена после проверки")

**Упражнение — 5 минут.** Что вернут `resume=False` и `resume="да"`? Где должен стоять переход к записи?

```solution
**Решение.** В обоих случаях approve вернёт `approved=False`. Условный переход после approve ведёт к записи только при approved=True. При отказе — завершение; для правки нужен отдельный проверяемый контракт, а не догадка по тексту.
```

## Повтор запуска и идемпотентность

При возобновлении узел с `interrupt()` начинает выполнение **с начала**, а не со следующей строки. Поэтому побочный эффект — запись или внешний вызов — до паузы может повториться. Подготовку, согласование и запись полезно разделять.

Небезопасный порядок: «записать утверждённый черновик → interrupt → вернуть результат». Он и записывает до разрешения, и может повторить запись. Безопаснее: «подготовить в состоянии → interrupt → проверить согласие → отдельный узел записи».

Но отдельный узел тоже может повториться после сбоя. Сохранение состояния не обещает **exactly once**, ровно один внешний эффект: запись могла завершиться, а подтверждение о её результате потеряться.

**Идемпотентность** — повтор действия с тем же ключом даёт тот же результат без дубликата. Учебное хранилище утверждённых черновиков использует ключ `order-42:draft-v1`: повтор возвращает уже созданную запись. Версия нужна, чтобы правка не притворялась прежним документом. В реальном хранилище уникальность ключа и запись должны обеспечиваться атомарно, в том числе при гонке.

Разбор сбоя: человек согласился → черновик записан → процесс упал до сохранения результата узла → узел повторился → хранилище нашло тот же ключ → вернуло прежнюю запись. Без ключа возникли бы два документа. Возврат денег этот пример не выполняет.

**Упражнение — 10 минут.** Найди две ошибки: узел сначала добавляет документ в список, затем вызывает interrupt; после перезапуска запись повторяют без ключа. Предложи исправленный порядок и поведение при отказе.

```solution
**Решение.** Первая ошибка — запись до подтверждения. Вторая — повторяемая операция без защиты от дублей. Подготовить черновик только в состоянии, вызвать interrupt, проверить точное согласие и полномочия, затем записать в отдельном узле с устойчивым ключом версии. Отказ завершает процесс без записи. После сбоя повтор с тем же ключом возвращает прежний результат; RAM-словарь показывает идею, но не обеспечивает долговечность и защиту при гонках.
```
