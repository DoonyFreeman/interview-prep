# Reverse proxy и основы конфига

> Цель урока: понять, зачем перед uvicorn ставят nginx, научиться читать любой
> nginx.conf (иерархия `http → server → location`, порядок матчинга) и правильно
> проксировать запросы в Python-бэкенд — с `proxy_pass` и заголовками
> `X-Forwarded-*`, без которых приложение видит «не тот» IP и схему.

## Зачем нужен reverse proxy

**Reverse proxy** — сервер, который принимает запросы клиентов и от их имени
ходит к бэкенду. Клиент видит только прокси; бэкенд спрятан во внутренней сети.
(«Forward proxy» — наоборот, ходит наружу от имени клиента; в вебе почти всегда
речь о reverse.)

Почему uvicorn не выставляют в интернет напрямую:

- **TLS-терминация.** Прокси принимает HTTPS, расшифровывает и передаёт бэкенду
  простой HTTP. Сертификаты, редиректы, HSTS — в одном месте, а не в коде.
- **Статика.** nginx отдаёт файлы (JS/CSS/картинки) в разы эффективнее
  Python-процесса — тот не тратит воркеров на раздачу байтов.
- **Буферизация медленных клиентов.** nginx принимает запрос целиком и быстро
  скармливает его бэкенду, а ответ бэкенда забирает мгновенно и сам медленно
  отдаёт клиенту на плохом канале. Без прокси воркер uvicorn был бы занят всё
  время «капающего» соединения (slow client / slowloris).
- **Единая точка**: лимиты (размер тела, rate limiting), сжатие, логи доступа,
  балансировка на несколько инстансов, аккуратные ошибки при падении бэкенда.

Соседи по нише: **Caddy** — автоматический Let's Encrypt и минимальный конфиг
(наш прод именно на нём), **Traefik** — динамическая конфигурация из label'ов
Docker/Kubernetes. **nginx** — самый распространённый и гибкий; его конфиг —
lingua franca, которую спрашивают на собеседованиях.

**Аналогия.** Ресепшен офиса: посетитель не бродит по кабинетам (бэкендам) —
его встречает администратор: проверяет пропуск (TLS), выдаёт брошюры со стойки
(статика), не пускает толпу разом (лимиты) и знает, кто из сотрудников свободен
(балансировка).

## Структура конфига: http, server, location

Конфиг nginx — вложенные **контексты**. Для веба важны три уровня: `http`
(общие настройки) → `server` (виртуальный хост) → `location` (правила для
путей). Директивы **наследуются вниз**, пока их не переопределили.

```nginx
# /etc/nginx/nginx.conf (упрощённо)
http {                                # общее для всех сайтов
    sendfile on;                      # отдача файлов силами ядра ОС

    server {                          # один виртуальный хост
        listen 80;                    # порт (и IP), который слушаем
        server_name api.example.com;  # какой Host сюда матчится

        location /api/ {              # правила для путей /api/...
            proxy_pass http://127.0.0.1:8000;
        }
        location / {                  # всё остальное
            root /var/www/html;       # отдавать файлы из этой папки
        }
    }
}
```

Как выбирается `server`: по порту из `listen` и по заголовку `Host` против
`server_name`; не совпал ни один — работает **default server** этого порта.

Как выбирается `location` (частый вопрос): **не по порядку в файле** для
префиксов, а по приоритету:

1. `location = /path` — точное совпадение (самый высокий приоритет);
2. `location ^~ /path` — префикс, «дальше regex не смотреть»;
3. `location ~ регэксп` (и `~*` без регистра) — **первый совпавший по порядку
   в файле**;
4. `location /path` — обычный префикс: побеждает **самый длинный**, где бы он
   ни стоял в файле.

```nginx
location /            { ... }   # C: поймает всё остальное (короткий префикс)
location /api/        { ... }   # B: /api/users → сюда (длиннее, чем /)
location = /health    { ... }   # A: ровно /health → сюда, точное совпадение
location ~ \.php$     { ... }   # regex проверился бы раньше префиксов B и C
```

**Аналогия.** Сортировка почты: сначала ящики с точным адресом (`=`), затем
особые инструкции «весь квартал — мне» (`^~`), затем правила по шаблону
(regex, первое подходящее), и лишь потом — самый длинный совпавший район
(префикс). Порядок ящиков на складе (в файле) для префиксов не важен.

## proxy_pass и заголовки

`proxy_pass` пересылает запрос бэкенду. Классическая **ловушка со слэшем**:

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;    # БЕЗ пути: URI передаётся как есть
}                                         # GET /api/users → /api/users

location /api/ {
    proxy_pass http://127.0.0.1:8000/;   # С путём ("/"): префикс location
}                                         # отрезается: /api/users → /users
```

Есть URI (хотя бы `/`) в `proxy_pass` → часть пути, совпавшая с `location`,
**заменяется** этим URI. Нет URI → путь уходит бэкенду без изменений. Из-за
одного слэша FastAPI-роут `/api/users` превращается в несуществующий `/users` —
и наоборот.

Вторая обязательная часть — **заголовки**. Для бэкенда клиент теперь nginx
(127.0.0.1), а исходные данные запроса надо передать явно:

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host              $host;              # исходный Host
    proxy_set_header X-Real-IP         $remote_addr;       # IP клиента
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;  # цепочка IP
    proxy_set_header X-Forwarded-Proto $scheme;            # http или https
}
```

Без них: в логах приложения все клиенты — `127.0.0.1`; `request.url` считает
схему `http`, и сгенерированные приложением redirect/absolute-ссылки ведут на
`http://` вместо `https://`; rate limiting по IP наказывает самого прокси.
Чтобы uvicorn **доверял** этим заголовкам и подставил их в `request.client` /
`request.url`, его запускают с `--proxy-headers` (и `--forwarded-allow-ips`,
если прокси не на localhost). Доверять `X-Forwarded-*` можно только своему
прокси — клиент может прислать их сам и подделать IP.

**Аналогия.** Секретарь пересылает письмо директору, перепечатав конверт. Если
не приложить оригинальный конверт (`X-Forwarded-For/Proto`), директор думает,
что все письма пишет секретарь, и отвечает на его адрес. А слэш в `proxy_pass` —
инструкция «переписать ли адресную строку»: одна лишняя черта — и письмо уходит
в другой отдел.

## Памятка для собеседования

- **Reverse proxy** перед uvicorn: TLS-терминация, статика, **буферизация
  медленных клиентов** (воркеры бэкенда не заняты «капающими» соединениями),
  лимиты/сжатие/логи/балансировка. Альтернативы: Caddy (авто-TLS), Traefik
  (динамика из Docker-labels).
- **Конфиг**: контексты `http → server → location`, директивы наследуются вниз.
  `server` выбирается по `listen` + `server_name` (Host). **Порядок location**:
  `=` точный → `^~` префикс-стоп → `~` regex (первый по файлу) → самый длинный
  обычный префикс (порядок в файле не важен).
- **proxy_pass**: URI в конце (`.../`) **заменяет** совпавший префикс location;
  без URI путь передаётся как есть. Слэш-ловушка: `/api/users` → `/users`.
- **Заголовки**: `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` +
  `uvicorn --proxy-headers`, иначе бэкенд видит IP прокси и схему http.
  `X-Forwarded-*` доверяем только своему прокси.

## Частые ошибки в ответах

- Путать forward и reverse proxy или сводить пользу nginx к «он быстрее».
- Считать, что location выбирается по порядку в файле (для префиксов — по
  длине; порядок важен только среди regex).
- Не знать слэш-ловушку `proxy_pass` — самый частый практический вопрос по nginx.
- Забыть `X-Forwarded-Proto`/`--proxy-headers` и потом удивляться редиректам на
  http и «одинаковым IP» в логах.
- Доверять `X-Forwarded-For` из интернета (клиент подделает IP) — цепочке
  доверяют только от своего прокси.
