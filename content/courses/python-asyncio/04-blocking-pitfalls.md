# Блокирующий код и подводные камни

> Цель урока: разобрать главные практические грабли asyncio — блокировка
> событийного цикла, смешивание sync и async, fire-and-forget задачи и потерянные
> исключения. Именно эти ошибки приводят к «мой async-сервер еле живёт», и про них
> любят спрашивать на бэкенд-собесах.

## Никогда не блокируй событийный цикл

Самое важное правило asyncio: **нельзя выполнять блокирующий или тяжёлый
синхронный код прямо в корутине**. Поскольку всё крутится в одном потоке, любой
блокирующий вызов (`time.sleep`, `requests.get`, тяжёлый цикл, синхронный доступ к
БД) **замораживает весь цикл** — все остальные задачи стоят, пока он не вернётся.

```python
async def handler():
    time.sleep(5)             # КАТАСТРОФА: весь сервер замер на 5 секунд
    requests.get(url)         # блокирующий HTTP — тоже замораживает цикл

async def handler_ok():
    await asyncio.sleep(5)    # уступает цикл — правильно
    await aiohttp_get(url)    # асинхронный HTTP-клиент
```

Правило: в async-коде используйте **асинхронные библиотеки** (`aiohttp`/`httpx`
вместо `requests`, async-драйверы БД, `asyncio.sleep` вместо `time.sleep`).
Симптом нарушения — «сервер тормозит под нагрузкой, хотя async»: где-то блокирующий
вызов держит цикл.

**Аналогия.** Единственный официант (цикл) обслуживает зал. Если его попросить
постоять 5 минут неподвижно (`time.sleep`), весь зал на эти 5 минут остаётся без
обслуживания. Он должен всегда быть в движении, а «ждать» поручать кухне (IO).

## run_in_executor для блокирующего кода

Иногда блокирующий код неизбежен (синхронная библиотека без async-аналога, CPU-
вычисление). Тогда его **выносят в отдельный поток или процесс**, чтобы не держать
цикл, через **`loop.run_in_executor`** или **`asyncio.to_thread`** (3.9+):

```python
# блокирующую функцию — в пул потоков, цикл свободен
result = await asyncio.to_thread(blocking_db_call, arg)

# CPU-bound — в пул процессов
loop = asyncio.get_running_loop()
result = await loop.run_in_executor(process_pool, crunch, data)
```

`to_thread` подходит для **блокирующего IO** (синхронная библиотека ждёт сеть/
диск) — поток отпустит GIL на ожидании. Для **CPU-bound** нужен
`ProcessPoolExecutor` (иначе GIL не даст параллелизма). Так asyncio и «тяжёлый» код
сосуществуют: цикл остаётся отзывчивым, а блокирующая работа идёт в стороне.

**Аналогия.** `to_thread` — официант не чистит картошку сам, а отдаёт её на кухню
(другой поток) и идёт обслуживать зал; когда картошка готова, ему сообщают. Цикл не
простаивает.

## Fire-and-forget и потерянные исключения

Коварная ловушка: создать задачу и **не сохранить ссылку** на неё / не
дождаться. Такие «забытые» задачи могут быть **собраны сборщиком мусора** до
завершения, а **исключения в них потеряются молча**:

```python
asyncio.create_task(background_job())     # ссылку не сохранили — опасно
# если задача упадёт, исключение может быть проглочено;
# задачу может собрать GC до завершения

# правильно: хранить ссылку и обрабатывать результат
task = asyncio.create_task(background_job())
tasks.add(task)                            # держим ссылку
task.add_done_callback(tasks.discard)
```

Связанная проблема — **исключение в задаче всплывает только когда её
`await`-ят** (или через callback). Если задачу не дождались, ошибка может остаться
незамеченной до завершения программы («Task exception was never retrieved»). Лучшее
лекарство — **`TaskGroup`** (3.11+): он держит ссылки, дожидается всех и
пробрасывает ошибки.

**Аналогия.** Fire-and-forget — отправить человека с поручением и забыть про него:
если он попадёт в беду (исключение), вы не узнаете, а то и потеряете его совсем
(GC). Надо держать список отправленных и проверять, кто как вернулся.

## Смешивание sync и async

Итоговые правила безопасного сосуществования:

- **Не вызывайте блокирующий код** в корутине — оборачивайте в `to_thread`/
  executor.
- **Не вызывайте `asyncio.run()`** дважды или внутри уже работающего цикла — он
  создаёт и закрывает цикл, это точка входа верхнего уровня.
- **Не забывайте `await`** у корутин (см. урок про корутины).
- **Async «заразен»**: если функция должна `await`-ить, она и все её вызыватели
  должны быть async. Граница sync↔async проходит через `asyncio.run` (вход) и
  `to_thread`/executor (выход к блокирующему коду).

**Аналогия.** sync и async — два мира с разными «правилами движения». Переход между
ними возможен только через специальные «погранпереходы» (`asyncio.run`,
`to_thread`); пытаться смешать их напрямую — авария на дороге (зависший цикл или
невыполненная корутина).

## Памятка для собеседования

- **Не блокируй цикл**: `time.sleep`/`requests`/тяжёлый sync в корутине замораживают
  весь однопоточный цикл. Используй async-библиотеки (`aiohttp`/`httpx`,
  async-драйверы, `asyncio.sleep`).
- Неизбежный блокирующий код — в `asyncio.to_thread` (блокирующий IO) или
  `run_in_executor` с **ProcessPool** (CPU-bound).
- **Fire-and-forget опасен**: незапомненную задачу может собрать GC, а её
  **исключение потеряется**; держи ссылку или используй **`TaskGroup`** (3.11+).
- Граница sync↔async: вход через `asyncio.run`, выход к блокирующему — через
  executor; async «заразен».

## Частые ошибки в ответах

- Вызывать `requests`/`time.sleep`/синхронный драйвер БД в корутине и не понимать,
  почему «всё висит».
- Не знать про `to_thread`/`run_in_executor` для блокирующего кода.
- Создавать задачи без хранения ссылок и терять их исключения.
- Пытаться вызвать `asyncio.run` внутри работающего цикла или смешивать sync/async
  без границ.
