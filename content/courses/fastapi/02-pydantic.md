# Pydantic: валидация и сериализация

> Цель урока: понять, как FastAPI использует Pydantic для валидации входных данных
> и формирования ответов, что делает `response_model` и почему Pydantic v2 быстрее.
> Это ядро «магии» FastAPI и частая тема: «как у вас валидируются запросы».

## Валидация запроса моделью

**Pydantic-модель** описывает структуру и типы данных. Когда вы аннотируете
параметр-тело такой моделью, FastAPI **сам валидирует** входной JSON: проверяет
наличие полей, типы, ограничения — и при ошибке возвращает **422** с понятным
описанием, не доходя до вашего кода.

```python
from pydantic import BaseModel, Field, EmailStr

class UserCreate(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    email: EmailStr
    age: int = Field(ge=0, le=120)

@app.post("/users")
def create_user(user: UserCreate):     # тело уже провалидировано и приведено
    # сюда попадаем, только если данные корректны
    return save(user)
```

Pydantic не только проверяет, но и **приводит типы** (строку `"30"` к `int`, если
это разумно) и даёт **декларативные ограничения** (`Field(ge=0)`, `EmailStr`).
Главная идея — **валидация на границе системы**: грязные данные извне отсекаются
до бизнес-логики, и внутри вы работаете с гарантированно корректным,
типизированным объектом.

**Аналогия.** Pydantic-модель — это контролёр на входе с чек-листом: пропускает
только тех, у кого все документы в порядке и нужного формата, а остальным сразу
отказывает (422), не пуская внутрь здания (в ваш код).

## response_model и сериализация

**`response_model`** задаёт схему **ответа**: FastAPI прогоняет возвращаемые данные
через эту модель, **сериализует** их в JSON и **фильтрует лишние поля**. Это
критично для безопасности — не дать утечь полям вроде `password_hash`:

```python
class UserRead(BaseModel):
    id: int
    name: str
    email: EmailStr
    # password_hash НЕ включён — не попадёт в ответ

@app.get("/users/{id}", response_model=UserRead)
def get_user(id: int):
    user = repo.get(id)        # объект может иметь password_hash
    return user                # FastAPI отдаст только поля UserRead
```

`response_model` гарантирует, что в ответ попадут **только** объявленные поля, в
правильных типах, и заодно документирует схему ответа в OpenAPI. Частый приём —
**разделять модели**: `UserCreate` (вход, с паролем), `UserRead` (выход, без
пароля), `UserUpdate` (частичное обновление). Это и есть «никогда не отдавать
лишнее наружу».

**Аналогия.** `response_model` — это форма для выдачи справки: что бы ни лежало во
внутренней папке (объект с лишними полями), наружу выдаётся только официальный
бланк с разрешёнными графами. Секретные пометки на бланк не переносятся.

## Валидаторы и Settings

Когда стандартных ограничений мало, есть **кастомные валидаторы**:

- **`@field_validator`** — проверка/преобразование **отдельного поля**.
- **`@model_validator`** — проверка **по нескольким полям** сразу (например,
  «пароль и его подтверждение совпадают», «дата конца после даты начала»).

```python
from pydantic import field_validator, model_validator

class SignUp(BaseModel):
    password: str
    password2: str

    @field_validator("password")
    @classmethod
    def strong(cls, v):
        if len(v) < 8: raise ValueError("too short")
        return v

    @model_validator(mode="after")
    def match(self):
        if self.password != self.password2:
            raise ValueError("passwords differ")
        return self
```

Отдельно — **`pydantic-settings`** (`BaseSettings`): модель для **конфигурации из
переменных окружения** с валидацией и типами. Это стандартный способ конфигурации
12-factor приложений (как `Settings` в этом проекте): env → типизированный
объект настроек.

**Аналогия.** Валидаторы — индивидуальные проверки в анкете: одна сверяет формат
поля (`field_validator`), другая — согласованность нескольких полей между собой
(`model_validator`). `BaseSettings` — та же анкета, но заполняется из окружения
сервера.

## Pydantic v2 и производительность

Важный для собеса нюанс — **Pydantic v2**: его ядро переписано на **Rust**
(`pydantic-core`), что дало **кратный прирост скорости** валидации по сравнению с
v1. Поскольку FastAPI валидирует **каждый запрос**, это заметно влияет на
пропускную способность.

Ключевые отличия v2 (часто спрашивают):

- Скорость (Rust-ядро) — в разы быстрее v1.
- Новые имена: `@field_validator`/`@model_validator` (вместо `@validator`/
  `@root_validator`), `model_dump()`/`model_validate()` (вместо `dict()`/
  `parse_obj()`), `model_config` (вместо класса `Config`).
- Строже и предсказуемее приведение типов.

Понимание, что Pydantic v2 на Rust и почему это важно для FastAPI (валидация на
каждом запросе), — признак, что человек следит за экосистемой.

**Аналогия.** Переход с v1 на v2 — как заменить контролёра-человека на скоростной
автоматический сканер: проверяет тот же чек-лист, но в разы быстрее, что важно,
когда поток посетителей (запросов) огромен.

## Памятка для собеседования

- Pydantic-модель валидирует **тело запроса**: проверка + приведение типов +
  ограничения (`Field(ge=...)`, `EmailStr`); ошибка → **422** до вашего кода.
  Валидация на границе системы.
- **`response_model`** задаёт схему **ответа**: сериализует и **отсекает лишние
  поля** (не утечёт `password_hash`); документирует ответ. Разделять
  Create/Read/Update модели.
- **`@field_validator`** (одно поле), **`@model_validator`** (несколько полей);
  **`BaseSettings`** — конфиг из env с типами.
- **Pydantic v2** — ядро на **Rust**, кратно быстрее v1; новые API
  (`model_dump`/`model_validate`, `field_validator`). Важно, т.к. валидация на
  каждом запросе.

## Частые ошибки в ответах

- Не использовать `response_model` и рисковать утечкой внутренних полей.
- Валидировать данные вручную в теле эндпоинта вместо Pydantic-модели.
- Путать v1 и v2 API (`validator`/`dict` vs `field_validator`/`model_dump`).
- Не знать, что v2 на Rust и почему скорость валидации важна для FastAPI.
