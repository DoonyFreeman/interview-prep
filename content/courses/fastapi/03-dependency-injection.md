# Dependency Injection: Depends

> Цель урока: понять механизм внедрения зависимостей FastAPI — `Depends`,
> под-зависимости, `yield`-зависимости для ресурсов и кэширование в пределах
> запроса. DI — фирменная фича FastAPI и частый вопрос: «как у вас устроена сессия
> БД и текущий пользователь».

## Что такое Depends

**Dependency Injection (DI)** — это способ **объявить, что нужно эндпоинту**
(сессия БД, текущий пользователь, настройки), и позволить FastAPI **самому это
предоставить**. Зависимость — обычная функция; эндпоинт получает её результат через
`Depends`:

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.get("/users/{id}")
def read_user(id: int, db: Session = Depends(get_db)):
    return db.get(User, id)        # FastAPI сам вызвал get_db и передал результат
```

FastAPI при каждом запросе **вызывает зависимость и подставляет** её значение в
параметр. Это убирает дублирование (не открывать сессию в каждом эндпоинте),
делает код **тестируемым** (зависимость легко подменить) и явно описывает
требования эндпоинта. Это прямое воплощение принципа **Dependency Inversion** из
SOLID: эндпоинт зависит от «дай мне сессию», а не создаёт её сам.

**Аналогия.** Depends — как сказать ассистенту «мне для встречи нужны проектор и
кофе»: вы не идёте за ними сами, ассистент (FastAPI) приносит готовое к началу
встречи (эндпоинта). Вы лишь объявляете потребности.

## Под-зависимости

Зависимости могут **зависеть друг от друга**, образуя дерево. FastAPI разрешает
всю цепочку автоматически. Классический пример — «текущий пользователь» зависит от
«токена», который зависит от заголовка:

```python
def get_token(authorization: str = Header(...)):
    return parse_bearer(authorization)

def get_current_user(token: str = Depends(get_token),
                     db: Session = Depends(get_db)):
    user = db.get(User, decode(token))
    if not user:
        raise HTTPException(401)
    return user

@app.get("/me")
def me(user: User = Depends(get_current_user)):   # вся цепочка разрешится сама
    return user
```

Так строят **переиспользуемые слои**: `get_current_user` используется во многих
эндпоинтах, а под ним — `get_token` и `get_db`. Можно вешать зависимости и на
**весь роутер/приложение** (общая проверка для группы эндпоинтов) через
`dependencies=[...]`.

**Аналогия.** Под-зависимости — как рецепт, где для соуса нужен бульон, а для
бульона — овощи: вы просите «соус», а кухня сама готовит всю цепочку снизу вверх.

## yield-зависимости для ресурсов

Зависимость с **`yield`** — это способ дать ресурс **с гарантированной очисткой**:
код до `yield` выполняется как «вход» (открыть сессию/соединение), значение
отдаётся в эндпоинт, а код после `yield` — как «выход» (закрыть), **даже если
эндпоинт упал**. Это аналог контекст-менеджера для DI:

```python
def get_db():
    db = SessionLocal()
    try:
        yield db            # отдаём сессию в эндпоинт
    finally:
        db.close()          # выполнится всегда — после ответа или при исключении
```

Так управляют **сессией БД, соединениями, файлами, транзакциями**: ресурс
открывается на время запроса и гарантированно освобождается после. Это самый
частый паттерн — «сессия на запрос». Важно: код после `yield` выполняется **после
формирования ответа** эндпоинтом.

**Аналогия.** `yield`-зависимость — выдать инструмент под расписку на время работы
и обязательно забрать на выходе (как `with`): что бы ни случилось в кабинете
(эндпоинте), на выходе ресурс сдаётся.

## Кэширование в пределах запроса

Важная деталь: по умолчанию FastAPI **кэширует результат зависимости в рамках
одного запроса**. Если одна и та же зависимость нужна нескольким под-зависимостям
или эндпоинту, она **вызывается один раз**, а результат переиспользуется:

```python
# get_db вызовется ОДИН раз за запрос, даже если её требуют и
# get_current_user, и сам эндпоинт — все получат одну сессию
```

Это удобно (одна сессия БД на весь запрос, а не несколько) и эффективно. Кэш живёт
**в пределах запроса** — в следующем запросе зависимость вызовется заново. Отключить
кэш можно через `Depends(dep, use_cache=False)`, если нужно вызывать каждый раз.
Понимание этого объясняет, почему все слои запроса делят одну сессию/одного
пользователя.

**Аналогия.** Кэш зависимостей — как один общий поднос с кофе на всю встречу:
сколько участников ни попросит, приносят один раз и делят, а не варят кофе заново
каждому. На следующей встрече (запросе) — свежий поднос.

## Памятка для собеседования

- **DI/`Depends`**: объявляешь потребность (сессия, пользователь), FastAPI **сам
  вызывает зависимость и подставляет** результат. Убирает дублирование, даёт
  тестируемость; воплощение Dependency Inversion.
- **Под-зависимости** образуют дерево (current_user → token → header), FastAPI
  разрешает всю цепочку; можно вешать на роутер/приложение.
- **`yield`-зависимости** — ресурс с гарантированной очисткой (до `yield` — вход,
  после — выход, даже при ошибке); паттерн «сессия БД на запрос».
- Результат зависимости **кэшируется в пределах запроса** (вызов один раз, общий
  результат); `use_cache=False` отключает.

## Частые ошибки в ответах

- Открывать сессию/ресурсы вручную в каждом эндпоинте вместо `Depends`.
- Не знать про `yield`-зависимости и гарантированную очистку ресурса.
- Не понимать кэширование в пределах запроса (думать, что зависимость вызывается
  на каждое использование).
- Не связывать DI с тестируемостью (подмена зависимостей в тестах).
