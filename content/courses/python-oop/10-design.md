# Дизайн ООП: SOLID, композиция и паттерны

> Цель урока: подняться с уровня синтаксиса на уровень **проектирования** —
> принципы SOLID, выбор «композиция против наследования» и базовые паттерны.
> На собесе это проверяет, умеете ли вы не только писать классы, но и
> структурировать систему так, чтобы её было легко менять.

## Принципы SOLID

**SOLID** — пять принципов проектирования классов для гибкого, поддерживаемого
кода:

- **S — Single Responsibility** (единственная ответственность): у класса одна
  причина для изменения, он делает что-то одно. Класс, который и парсит, и
  валидирует, и пишет в БД — кандидат на разбиение.
- **O — Open/Closed** (открыт для расширения, закрыт для изменения): новое
  поведение добавляют **расширением** (новый класс/стратегия), не правя
  существующий код.
- **L — Liskov Substitution** (подстановки Барбары Лисков): подкласс должен
  заменять родителя **без сюрпризов** — не нарушать контракт (классический
  антипример: `Square` как наследник `Rectangle`).
- **I — Interface Segregation** (разделение интерфейсов): много узких интерфейсов
  лучше одного «толстого»; клиент не должен зависеть от методов, которые не
  использует.
- **D — Dependency Inversion** (инверсия зависимостей): зависеть от **абстракций**
  (интерфейсов/Protocol), а не от конкретных классов; это основа внедрения
  зависимостей (DI), которое вы видите в FastAPI.

```python
# D: сервис зависит от абстракции хранилища, а не от конкретной БД
class Service:
    def __init__(self, storage: Storage):   # Storage — ABC/Protocol
        self.storage = storage               # легко подменить на mock/другую БД
```

**Аналогия.** SOLID — как правила хорошей планировки дома: у каждой комнаты своё
назначение (S), пристройку делают не ломая стен (O), розетки стандартные, чтобы
любой прибор подходил (D). Нарушишь — каждый ремонт превращается в перестройку.

## Композиция против наследования

Ключевой принцип проектирования: **«предпочитай композицию наследованию»**.

- **Наследование** (`is-a`) — «является»: `Dog is-a Animal`. Сильная связь:
  подкласс зависит от внутренностей родителя, изменения родителя ломают потомков,
  иерархия становится хрупкой. Уместно для настоящих «is-a» отношений.
- **Композиция** (`has-a`) — «содержит»: объект **собирается из** других объектов и
  делегирует им работу. Слабая связь, гибкость: поведение можно менять, подставляя
  другие компоненты в рантайме.

```python
# наследование — жёстко: чтобы поменять способ оплаты, нужен новый подкласс
# композиция — гибко: подставляем стратегию оплаты как зависимость
class Order:
    def __init__(self, payment: PaymentMethod):   # has-a
        self.payment = payment
    def checkout(self, amount):
        self.payment.pay(amount)                  # делегируем
```

Почему композиция чаще лучше: меньше связанность, легче тестировать (подставить
mock), можно менять поведение без переписывания иерархии, нет проблем
множественного наследования. **Миксины** — компромисс: маленькие классы,
добавляющие одну способность через множественное наследование.

**Аналогия.** Наследование — врождённые черты, которые не поменять. Композиция —
сменные инструменты в руках: понадобилось другое — взял другой инструмент, сам не
меняясь. Гибкость второго обычно выигрывает.

## Базовые паттерны проектирования

Паттерны — типовые решения повторяющихся задач. Знать хотя бы базовые:

- **Strategy** (стратегия) — взаимозаменяемые алгоритмы как объекты; подставляются
  через композицию (пример с оплатой выше). В Python часто это просто **функция**,
  переданная аргументом.
- **Factory** (фабрика) — выделенное создание объектов; в Python — `classmethod`-
  фабрики или функция, возвращающая нужный класс.
- **Singleton** (одиночка) — один экземпляр на всё приложение (через `__new__`,
  модуль или DI-контейнер). В Python часто заменяется **модулем** (он и так
  единственный).
- **Observer** (наблюдатель) — объекты подписываются на события и уведомляются при
  изменениях (колбэки, сигналы).
- **Adapter** (адаптер) — обёртка, приводящая чужой интерфейс к ожидаемому.

Важная оговорка для собеса: в Python многие GoF-паттерны **проще**, потому что
функции — объекты первого класса и есть duck typing. Strategy часто = функция,
Singleton = модуль, Factory = функция. Не стоит тащить Java-стиль с классами ради
классов — питоничнее использовать функции и встроенные механизмы.

**Аналогия.** Паттерны — это шаблоны решений, как типовые планировки кухни. Знать
их полезно, но в Python часто есть «встроенная мебель» (функции, модули,
декораторы), и городить полноценный класс-паттерн не нужно.

## Памятка для собеседования

- **SOLID**: Single responsibility · Open/closed · Liskov substitution · Interface
  segregation · Dependency inversion (зависеть от абстракций → основа DI).
- **Композиция (has-a) предпочтительнее наследования (is-a)**: слабее связь,
  гибче, легче тестировать; наследование — для настоящих «is-a». Миксины —
  компромисс.
- Паттерны: **Strategy** (часто просто функция), **Factory** (classmethod/функция),
  **Singleton** (часто модуль), **Observer**, **Adapter**.
- В Python многие GoF-паттерны упрощаются благодаря функциям-объектам и duck
  typing — не тащить Java-стиль ради классов.

## Частые ошибки в ответах

- Перечислить SOLID буквами без понимания смысла каждого (особенно L и D).
- Везде использовать наследование, не зная принципа «композиция важнее
  наследования».
- Реализовывать паттерны в тяжёлом Java-стиле там, где питоничнее функция/модуль.
- Не уметь связать Dependency Inversion с внедрением зависимостей (DI) во
  фреймворках.
