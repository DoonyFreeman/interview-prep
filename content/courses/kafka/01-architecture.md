# Kafka: зачем и как устроена

> Цель урока: понять, какую задачу решает Kafka и чем брокер **событий** отличается
> от очереди **задач**; разобрать её устройство — топики, партиции, оффсеты,
> брокеры и репликацию. Это фундамент: без модели «распределённый лог» невозможно
> осмысленно отвечать ни на один вопрос про Kafka.

## Что такое Kafka и зачем она нужна

**Apache Kafka** — это распределённый **лог событий** (event streaming platform).
Сервисы-**производители** (producers) пишут события в Kafka, а
сервисы-**потребители** (consumers) читают их — каждый в своём темпе, независимо
друг от друга. Kafka развязывает сервисы: заказ создан один раз, а отреагировали
на него хоть пять команд — уведомления, аналитика, склад, антифрод, поиск.

Ключевое отличие от привычной очереди задач (Celery + Redis/RabbitMQ):

- **Очередь задач**: «сделай вот это». Задача адресована исполнителю, после
  выполнения **исчезает** из очереди. Один потребитель на задачу.
- **Лог событий**: «произошло вот что». Событие никому не адресовано; Kafka
  **хранит его** заданный срок (retention, например 7 дней), и **несколько
  независимых** групп потребителей читают один и тот же поток, не мешая друг
  другу. Новый сервис может подключиться и перечитать историю с начала.

```text
Producer (order-service) ──▶ topic "orders" ──▶ consumer group "notifications"
        "заказ #42 создан"        (лог,     ──▶ consumer group "analytics"
                                   хранится) ──▶ consumer group "warehouse"
```

Когда Kafka: событийная интеграция многих сервисов, поток кликов/метрик/логов,
источник для стриминговой обработки, буфер при пиковых нагрузках. Когда она
избыточна: маленький монолит, которому нужно «отправить письмо в фоне» — это
работа Celery (см. концепт «Kafka или Celery» в третьем уроке).

**Аналогия.** Очередь задач — курьерская накладная: одно поручение одному
исполнителю, выполнил — бумажка выброшена. Kafka — газета: издатель напечатал
новость (событие), и сколько угодно подписчиков читают её каждый со своей
скоростью; свежий подписчик может поднять подшивку за неделю.

## Топики, партиции и оффсеты

**Топик** (topic) — именованный поток событий («orders», «payments»). Физически
топик разбит на **партиции** (partitions) — независимые **append-only логи**.
Запись всегда добавляется в конец партиции и получает **оффсет** (offset) —
монотонно растущий порядковый номер внутри партиции.

```text
topic "orders", 3 партиции:
  P0: [0][1][2][3][4] ◀─ producer пишет в конец
  P1: [0][1][2]
  P2: [0][1][2][3]
        ▲
        consumer читает по порядку, запоминая оффсет
```

Три следствия, о которых спрашивают на собеседовании:

- **Партиции — единица параллелизма.** Один консьюмер в группе обрабатывает одну
  партицию (или несколько). 3 партиции → максимум 3 параллельных консьюмера в
  группе; четвёртый будет простаивать.
- **Порядок гарантируется только внутри партиции.** Между партициями порядка
  нет. Поэтому события одного объекта (заказ #42) отправляют с одним **ключом** —
  ключ детерминированно отображается в партицию, и события заказа читаются в
  порядке записи.
- **Чтение не удаляет сообщение.** Консьюмер лишь двигает свой оффсет; данные
  удаляются по **retention** (по времени/размеру), а не по факту прочтения.
  Поэтому один топик могут читать много групп, и поэтому можно «отмотать назад».

Посмотреть на топик глазами администратора:

```bash
# создать топик с 3 партициями
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 3

# описание: партиции, лидеры, реплики
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
```

**Аналогия.** Топик — многотомный журнал регистрации, партиция — отдельный том.
Записи в том вносятся строго по порядку и нумеруются (оффсеты). Читатель ставит
закладку (свой оффсет) в каждом томе; вырвать страницу нельзя — старые тома
просто списывают в архив по сроку (retention).

## Брокеры и репликация

**Брокер** (broker) — один сервер Kafka. Кластер — несколько брокеров, между
которыми распределены партиции всех топиков. Отказоустойчивость даёт
**репликация**: каждая партиция имеет `replication-factor` копий на разных
брокерах.

- У каждой партиции есть **лидер** (leader) — брокер, через который идут **все**
  записи и (по умолчанию) чтения этой партиции. Остальные копии — **фолловеры**
  (followers), они постоянно подтягивают новые записи у лидера.
- **ISR** (in-sync replicas) — множество реплик, не отставших от лидера. Именно
  ISR — кандидаты в новые лидеры.
- **Падение брокера**: контроллер кластера замечает потерю, для каждой партиции,
  где упавший был лидером, **выбирает нового лидера из ISR**, клиенты
  автоматически переключаются. Данные не теряются, пока жива хотя бы одна
  синхронная реплика (и producer писал с `acks=all` — об этом в следующем уроке).

```text
topic "orders", partition P0, replication-factor 3:
  broker 1: P0 (leader)  ◀── запись/чтение
  broker 2: P0 (follower, in-sync)      ┐ ISR
  broker 3: P0 (follower, in-sync)      ┘
broker 1 упал → лидером P0 становится broker 2, клиенты переключились
```

Исторически членство в кластере и выборы координировал ZooKeeper; современная
Kafka использует встроенный протокол **KRaft** (Kafka Raft) — отдельный ZooKeeper
больше не нужен (мы увидим это в docker-compose в третьем уроке).

**Аналогия.** Партиция с репликами — документ и две его заверенные копии в разных
зданиях. Все правки вносит один нотариус (лидер), копии обновляются следом
(фолловеры в ISR). Сгорело здание нотариуса — полномочия передают тому, чья копия
точно актуальна (выбор из ISR), и работа продолжается.

## Памятка для собеседования

- Kafka — распределённый **лог событий**, не очередь задач: события **хранятся**
  (retention) и читаются **многими независимыми группами**; очередь задач — «сделай
  это» одному исполнителю, и задача исчезает.
- **Топик → партиции → оффсеты.** Партиция — append-only лог; оффсет — номер
  записи в партиции. Партиции = параллелизм; **порядок только внутри партиции**
  (события одного объекта — с одним ключом); чтение не удаляет данные.
- **Брокеры и репликация**: у партиции есть **лидер** (через него все записи) и
  **фолловеры**; **ISR** — не отставшие реплики. Брокер упал → новый лидер
  выбирается из ISR. Современная Kafka — **KRaft**, без ZooKeeper.

## Частые ошибки в ответах

- Называть Kafka «очередью» и сравнивать с Celery как одноклассников: у них разные
  модели (события vs задачи) и разные задачи.
- Считать, что сообщение удаляется после прочтения (нет — только по retention) или
  что порядок гарантирован по всему топику (только внутри партиции).
- Не знать, зачем ключ сообщения (маршрутизация в партицию → порядок для одного
  объекта).
- Путать репликацию с партиционированием: партиции — про параллелизм и масштаб,
  реплики — про отказоустойчивость.
- Говорить «Kafka требует ZooKeeper» про современные версии (KRaft).
