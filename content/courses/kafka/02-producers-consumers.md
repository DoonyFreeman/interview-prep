# Производители и потребители

> Цель урока: понять две стороны Kafka-клиента. Producer: как сообщение попадает в
> нужную партицию, что такое `acks` и идемпотентность. Consumer: как группа делит
> партиции, чем опасна ребалансировка, какие бывают семантики доставки и как жить
> с ретраями и «ядовитыми» сообщениями. Это самый спрашиваемый блок по Kafka.

## Producer: ключи, партиции и acks

Producer отправляет запись `(key, value)` в топик. **В какую партицию она
попадёт**, решается так: есть ключ → `hash(key) % партиции` (все события одного
ключа — в одну партицию, порядок сохранён); нет ключа → записи размазываются по
партициям (round-robin/sticky) — максимальная равномерность, но без порядка.

Надёжность записи задаёт **acks** — скольких подтверждений ждёт producer:

- `acks=0` — не ждать вовсе: максимальная скорость, потеря при любой проблеме.
- `acks=1` — подтвердил только лидер: если лидер упал до репликации — запись
  потеряна.
- `acks=all` — подтвердили все ISR-реплики: запись не потеряется, пока жива хоть
  одна синхронная реплика. Стандарт для важных данных.

Ретраи создают вторую проблему: отправка удалась, но ack потерялся → повтор → в
логе **дубль**. Лечится **идемпотентным продюсером** (`enable.idempotence=true`):
брокер по номеру последовательности продюсера отбрасывает повторную запись.
Для пропускной способности producer собирает записи в **батчи** (`linger.ms`,
`batch.size`) — чуть больше задержка, заметно больше throughput.

```python
from confluent_kafka import Producer

producer = Producer({
    "bootstrap.servers": "localhost:9092",
    "acks": "all",               # ждать все ISR-реплики
    "enable.idempotence": True,  # ретраи без дублей в логе
    "linger.ms": 5,              # подкопить батч до 5 мс
})

def on_delivery(err, msg):
    if err is not None:
        log.error("delivery failed: %s", err)  # алерт/метрика, не молчать

# ключ = id заказа → все события заказа в одной партиции, порядок сохранён
producer.produce("orders", key=b"order-42", value=b'{"status": "created"}',
                 on_delivery=on_delivery)
producer.flush()  # дождаться подтверждений (на shutdown)
```

**Аналогия.** `acks` — способ отправки посылки: `0` — бросил в ящик и ушёл, `1` —
получил штамп в отделении (но склад мог сгореть до перевозки), `all` — дождался
подписи получателя. Идемпотентность — трек-номер: даже если курьер приехал дважды,
склад примет посылку один раз.

## Consumer groups и ребалансировка

Консьюмеры объединяются в **группу** (`group.id`). Kafka распределяет партиции
топика между членами группы: **каждая партиция — ровно одному консьюмеру внутри
группы** (один консьюмер может держать несколько партиций). Так группа читает
топик параллельно и без пересечений. Разные группы независимы: у каждой свои
оффсеты, каждая видит весь поток.

```text
topic "orders" (P0, P1, P2), group "billing":
  consumer A ← P0, P1
  consumer B ← P2
добавили consumer C → ребалансировка → A←P0, B←P2, C←P1
консьюмеров больше, чем партиций → лишние простаивают
```

**Ребалансировка** — перераспределение партиций, когда состав группы меняется
(деплой, падение пода, новый инстанс) или консьюмер перестал слать heartbeat.
Её цена: пока идёт ребаланс, группа (в классическом протоколе) **останавливает
обработку** (stop-the-world), а после — возможны повторные сообщения, если
оффсеты не успели закоммититься. Частые «пустые» ребалансы — типичная причина
дёрганой обработки; смягчают их аккуратными таймаутами (`max.poll.interval.ms`,
`session.timeout.ms`), static membership и cooperative-протоколом.

Здоровье консьюмера меряют **лагом** (consumer lag) — разницей между последним
оффсетом партиции и закоммиченным оффсетом группы. Растущий лаг = группа не
успевает; это первый график, на который смотрят в мониторинге Kafka.

**Аналогия.** Группа — бригада на конвейерных лентах (партициях): каждую ленту
разбирает один рабочий. Пришёл новый/ушёл старый — бригадир останавливает цех и
раздаёт ленты заново (ребалансировка): полезно, но во время «планёрки» конвейер
стоит. Лаг — гора неразобранных деталей на ленте.

## Семантики доставки

Семантика — что происходит с сообщением при сбоях. Определяется тем, **когда
консьюмер коммитит оффсет** относительно обработки:

- **At-most-once** («не более раза»): закоммитить **до** обработки. Упали после
  коммита, но до обработки → сообщение потеряно. Допустимо для метрик, не для денег.
- **At-least-once** («не менее раза»): обработать, **потом** коммит. Упали между —
  после рестарта сообщение придёт **повторно**. Стандарт по умолчанию; требует
  **идемпотентного обработчика** (повтор не ломает данные: upsert, уникальный
  ключ операции, проверка «уже обработано»).
- **Exactly-once** («ровно раз»): строго — только внутри экосистемы Kafka
  (транзакции producer + read-process-write, Kafka Streams). Как только результат
  уходит во внешнюю систему (Postgres, HTTP), гарантия превращается в
  **at-least-once + идемпотентность** — и это правильный ответ на собеседовании.

```python
# at-least-once на aiokafka: сначала обработали, потом закоммитили
consumer = AIOKafkaConsumer(
    "orders", group_id="billing",
    enable_auto_commit=False,        # авто-коммит по таймеру = риск at-most-once
    auto_offset_reset="earliest",    # новой группе читать с начала
)
async for msg in consumer:
    await handle(msg)                # handle обязан быть идемпотентным
    await consumer.commit()          # оффсет — только после успешной обработки
```

**Аналогия.** Кладовщик и журнал выдачи. Расписаться до того, как отдал товар, —
at-most-once (сгорел склад — записи есть, товара нет). Отдать, потом расписаться —
at-least-once (не успел расписаться — завтра выдаст повторно, поэтому получатель
должен уметь сказать «уже забирал»). «Ровно раз» без единой кассы (транзакций) не
бывает.

## Порядок, ретраи и DLQ

Три практических следствия партиционированной модели:

- **Порядок.** Гарантирован только внутри партиции → события одного объекта
  отправляй с одним ключом. Больше партиций = больше параллелизма, но порядок
  между ключами никто не обещает. Глобальный порядок = 1 партиция = нет
  параллелизма (почти никогда не нужно).
- **Ретраи консьюмера.** Бесконечно повторять упавшее сообщение нельзя — оно
  «ядовитое» (poison pill) и **блокирует всю партицию** (Kafka читает партицию по
  порядку, следующие сообщения ждут). Нельзя и просто пропустить, если данные
  важны.
- **DLQ (dead letter queue/topic).** Стандартное решение: N быстрых попыток → не
  вышло → сообщение с метаданными ошибки публикуется в отдельный топик
  `orders.dlq`, оффсет коммитится, партиция едет дальше. DLQ мониторят и
  разбирают руками или переигрывают после фикса бага.

```python
MAX_ATTEMPTS = 3

async for msg in consumer:
    try:
        await handle(msg)
    except TransientError:
        if attempts(msg) < MAX_ATTEMPTS:
            await retry_later(msg)          # повтор с backoff
        else:
            await producer.send("orders.dlq", wrap_with_error(msg))
    await consumer.commit()                  # партиция не блокируется
```

**Аналогия.** Лента на почте: если одна посылка не проходит сканер, её после пары
попыток откладывают в ящик «разобрать вручную» (DLQ) и лента едет дальше. Держать
всю ленту ради одной посылки — значит остановить отделение (заблокированная
партиция).

## Памятка для собеседования

- **Producer**: ключ → партиция (`hash(key) % N`), без ключа — round-robin;
  `acks=0/1/all` — скорость vs надёжность (`all` = подтвердили все ISR);
  **идемпотентный продюсер** убирает дубли от ретраев; батчинг (`linger.ms`)
  поднимает throughput.
- **Consumer group**: партиция — одному консьюмеру в группе; группы независимы.
  **Ребалансировка** при изменении состава — пауза обработки + возможные повторы.
  **Lag** — главная метрика здоровья.
- **Семантики**: at-most-once (коммит до обработки, можно терять),
  **at-least-once (обработка → коммит + идемпотентный обработчик — стандарт)**,
  exactly-once — только внутри Kafka; с внешней БД — at-least-once +
  идемпотентность.
- **Ретраи**: ядовитое сообщение блокирует партицию → N попыток → **DLQ-топик** →
  commit → мониторинг и ручной разбор/переигрывание.

## Частые ошибки в ответах

- «`acks=all` значит подтвердили все брокеры кластера» — нет, все **ISR-реплики
  этой партиции**.
- Оставлять `enable_auto_commit=True` и рассказывать про at-least-once: авто-коммит
  по таймеру может закоммитить необработанное (получится at-most-once).
- Обещать exactly-once при записи в Postgres/вызове внешнего API — забывая, что
  это уже at-least-once + идемпотентность.
- Не знать, что ядовитое сообщение блокирует **всю партицию**, и не иметь ответа
  «DLQ» на вопрос «а что с упавшими сообщениями?».
- Думать, что ребалансировка бесплатна, и лечить растущий лаг добавлением
  консьюмеров сверх числа партиций (лишние будут простаивать).
