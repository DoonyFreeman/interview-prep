# Запросы 2.0, Alembic и async

> Цель урока: освоить современный стиль запросов SQLAlchemy 2.0 (`select()`),
> понять роль миграций через Alembic и особенности async-SQLAlchemy. Этот стек —
> ровно то, на чём построен данный проект (FastAPI + async SQLAlchemy), и частый
> предмет вопросов на бэкенд-собесах.

## Стиль запросов 2.0

SQLAlchemy 2.0 унифицировал API: вместо старого `session.query(...)` —
**единый `select()`**, одинаковый для Core и ORM. Запрос строится как Python-
выражение и исполняется через `session.execute()` / `session.scalars()`:

```python
from sqlalchemy import select

stmt = (
    select(User)
    .where(User.age > 18)
    .order_by(User.created_at.desc())
    .limit(10)
)
users = session.scalars(stmt).all()          # список объектов User

# джоины, агрегаты, фильтры — выражениями
stmt = (
    select(User.name, func.count(Order.id))
    .join(Order, Order.user_id == User.id)
    .group_by(User.name)
)
rows = session.execute(stmt).all()           # список строк-кортежей
```

Разница `execute` vs `scalars`: `execute` возвращает строки (`Row`, кортежи
колонок), `scalars` — «разворачивает» первый столбец (удобно, когда выбираете
сущности: `scalars(select(User))` → объекты `User`). Фильтры строятся операторами
над колонками (`User.age > 18`, `User.name.in_([...])`, `.like(...)`).

**Аналогия.** `select()` — это конструктор запроса из кубиков (where, join,
order_by), который собирается в Python и компилируется в SQL. Один и тот же
конструктор для Core и ORM — меньше «двух разных API» в голове.

## Alembic: миграции схемы

Схему БД нельзя менять «руками» в продакшене бесконтрольно — нужны
**версионируемые миграции**. **Alembic** — официальный инструмент миграций для
SQLAlchemy: он хранит **последовательность версий схемы** и умеет применять
(`upgrade`) и откатывать (`downgrade`) изменения.

```bash
alembic revision --autogenerate -m "add orders table"   # сгенерировать миграцию
alembic upgrade head                                      # применить до последней
alembic downgrade -1                                      # откатить на шаг назад
```

Ключевое:

- **`--autogenerate`** сравнивает модели с текущей схемой БД и **черновик**
  миграции генерирует сам. Но его **обязательно проверяют руками** — autogenerate не
  ловит всё (переименования, изменения данных, некоторые constraints).
- Каждая миграция — это `upgrade()` и `downgrade()`; цепочка версий образует
  историю, общую для команды (в git).
- Миграции данных (не только структуры) пишут вручную в теле миграции.

Без миграций изменение моделей рассинхронизируется с реальной схемой — Alembic
делает эволюцию схемы **воспроизводимой и командной**.

**Аналогия.** Alembic — это «git для схемы БД»: каждое изменение структуры —
коммит (ревизия), который можно применить или откатить, и вся команда катит одну и
ту же историю изменений, а не правит БД кто во что горазд.

## Async SQLAlchemy 2.0

SQLAlchemy 2.0 поддерживает **асинхронную работу** (`create_async_engine`,
`AsyncSession`, `await`) — то, на чём построены современные FastAPI-приложения.
Принцип тот же, но с `await` на операциях ввода-вывода:

```python
engine = create_async_engine("postgresql+asyncpg://...")

async with AsyncSession(engine) as session:
    result = await session.execute(select(User).where(User.id == 1))
    user = result.scalar_one()
    await session.commit()
```

Главные отличия и подводные камни:

- Нужен **async-драйвер** (`asyncpg`/`aiomysql`), а не синхронный (`psycopg2`).
- **Ленивая загрузка по требованию не работает** (нельзя сделать неявный IO в
  атрибуте) — обязательны **eager-загрузка** (`selectinload`/`joinedload`) или
  явная подгрузка. Это прямое следствие из урока про связи.
- Всё то же про пул соединений, Session, identity map — но операции IO
  (`execute`, `commit`, `refresh`) идут через `await`.

**Аналогия.** Async-версия — та же машина, но с правилом «на каждом перекрёстке с
БД (запрос, коммит) ставим `await`, уступая дорогу другим». А «незаметно сходить за
связанными данными» (lazy) на ходу запрещено — всё нужное берём заранее.

## Памятка для собеседования

- **2.0-стиль**: единый **`select()`** (вместо `session.query`) для Core и ORM;
  исполнение `session.execute()` (строки) / `session.scalars()` (разворачивает
  сущности). Фильтры — операторами над колонками.
- **Alembic** — версионируемые миграции схемы (`revision --autogenerate`,
  `upgrade`/`downgrade`); autogenerate **проверять руками**; миграции данных —
  вручную. «Git для схемы».
- **Async**: `create_async_engine` + `AsyncSession` + `await` на IO; нужен
  async-драйвер (`asyncpg`); **ленивая загрузка по требованию не работает** —
  обязателен eager/явная загрузка.

## Частые ошибки в ответах

- Использовать устаревший `session.query()` и не знать про `select()` 2.0.
- Путать `execute` и `scalars` (строки vs развёрнутые сущности).
- Полностью доверять `--autogenerate` без ручной проверки миграции.
- В async забыть про async-драйвер или ожидать работающей ленивой загрузки.
