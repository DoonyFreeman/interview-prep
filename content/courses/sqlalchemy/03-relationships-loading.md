# Связи и стратегии загрузки

> Цель урока: понять, как описываются связи между моделями, что такое lazy против
> eager загрузки и как стратегия загрузки порождает или решает проблему N+1. Это
> самый практичный вопрос по SQLAlchemy: «как у вас грузятся связанные объекты и
> как вы боретесь с N+1».

## Описание связей

Связи между таблицами в ORM описываются через **`relationship()`** + внешний ключ.
`back_populates` (или `backref`) делает связь **двунаправленной** — обе стороны
знают друг о друге:

```python
class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    orders: Mapped[list["Order"]] = relationship(back_populates="user")

class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    user: Mapped["User"] = relationship(back_populates="orders")
```

Так выражают **1:N** (как выше), **1:1** (`uselist=False`) и **N:M** (через
`secondary=` — связующую таблицу). **Каскады** (`cascade="all, delete-orphan"`)
управляют тем, что происходит со связанными объектами при удалении/сохранении
родителя (например, удалить заказы вместе с пользователем). Понимание FK +
relationship + cascade — основа моделирования.

**Аналогия.** `relationship` — это «живая ссылка»: у пользователя есть атрибут
`orders`, обращаясь к которому, вы получаете связанные заказы, как будто они
вложены в объект, хотя физически это отдельная таблица, связанная FK.

## Lazy против eager загрузки

Ключевой вопрос: **когда** загружаются связанные объекты.

- **Lazy loading (ленивая)** — связь грузится **в момент обращения** к атрибуту
  (`user.orders` → отдельный SQL-запрос тогда же). По умолчанию в SQLAlchemy
  отношения ленивы. Удобно, но **порождает N+1** в циклах.
- **Eager loading (жадная)** — связанные объекты грузятся **сразу**, вместе с
  основным запросом, заранее. Решает N+1.

```python
# lazy (по умолчанию): обращение к .orders делает запрос «на месте»
user = session.get(User, 1)
user.orders        # ← здесь летит отдельный SELECT

# в цикле lazy = N+1:
for u in session.scalars(select(User)):
    print(u.orders)    # +1 запрос на каждого пользователя
```

Lazy опасна именно своей незаметностью: код выглядит как обычный доступ к атрибуту,
а под ним — скрытые запросы. В async-SQLAlchemy ленивая загрузка вообще **не
работает** «по требованию» (нельзя сделать неявный IO) — там обязателен eager или
явная загрузка.

**Аналогия.** Lazy — заказывать каждое блюдо отдельно, когда до него дойдёт очередь
(много походов официанта). Eager — заказать всё сразу одним заказом. В цикле «по
блюду за раз» официант сбивается с ног (N+1).

## Стратегии eager: selectin, joined, subquery

Eager-загрузку задают через `options(...)` тремя основными стратегиями:

- **`selectinload`** — грузит связанные **вторым запросом** через `IN (...)` по
  собранным id. Обычно **лучший выбор для коллекций (1:N, N:M)**: 2 запроса
  независимо от N, без дублирования строк.
- **`joinedload`** — грузит связанные **тем же запросом через JOIN**. Хорош для
  **1:1 и many-to-one** (один связанный объект); для коллекций даёт **дублирование**
  строк родителя (декартово расширение).
- **`subqueryload`** — через подзапрос; исторически предшественник selectinload,
  сейчас обычно предпочитают selectin.

```python
# коллекция → selectinload (2 запроса, без дублей)
users = session.scalars(
    select(User).options(selectinload(User.orders))
).all()

# один связанный объект → joinedload (один JOIN-запрос)
orders = session.scalars(
    select(Order).options(joinedload(Order.user))
).all()
```

Правило выбора: **`selectinload` для коллекций**, **`joinedload` для «к одному»**.
Это и есть основной инструмент против N+1.

**Аналогия.** `joinedload` — привезти заказ и связанные данные одной машиной
(хорошо, если связанное одно; для списков — лишние дубли в кузове). `selectinload` —
сначала собрать список id, потом одним рейсом привезти все связанные по этому
списку.

## Борьба с N+1 на практике

Сводим в практический алгоритм (перекликается с курсом по SQL):

1. **Заметить N+1** — включить логирование SQL (`echo=True` у engine) и увидеть
   шквал одинаковых мелких запросов в цикле.
2. **Добавить eager-загрузку** нужной стратегией: `selectinload` для списков,
   `joinedload` для «к одному».
3. **Грузить заранее всё, что понадобится** после закрытия сессии (иначе ленивый
   доступ упадёт `DetachedInstanceError` / в async — ошибкой).

Дополнительно: настроить стратегию загрузки можно и на уровне самого
`relationship(lazy="selectin")`, если связь почти всегда нужна. Но злоупотреблять
глобальным eager не стоит — иногда связанные данные не нужны, и лишняя загрузка
тратит ресурсы. Идеал — **загружать ровно то, что нужно конкретному запросу**,
через `options`.

**Аналогия.** Борьба с N+1 — как планирование закупок: посмотреть накладные (логи
SQL), увидеть сто мелких заказов и заменить их одной оптовой поставкой
(eager-загрузка), взяв ровно то, что нужно под задачу.

## Памятка для собеседования

- Связи — `relationship()` + FK; `back_populates` — двунаправленность; `secondary`
  — N:M; `cascade` — поведение при удалении родителя. 1:1 — `uselist=False`.
- **Lazy** (по умолчанию) грузит связь **при обращении** → скрытые запросы и
  **N+1** в циклах; в **async** ленивая загрузка по требованию не работает.
- **Eager** грузит заранее: **`selectinload`** — для коллекций (2 запроса, без
  дублей), **`joinedload`** — для «к одному» (JOIN). Задаётся через `options(...)`.
- Борьба с N+1: логировать SQL → добавить eager нужной стратегией → грузить
  заранее всё, что нужно после закрытия сессии.

## Частые ошибки в ответах

- Не знать, что отношения по умолчанию ленивы и это причина N+1.
- Путать `selectinload` и `joinedload` (коллекции vs «к одному»; дубли строк у
  joined).
- Забыть про неработающую ленивую загрузку в async-SQLAlchemy.
- Глобально включать eager везде, грузя ненужные данные.
