# Session: identity map, unit of work, жизненный цикл

> Цель урока: понять, что Session — это не «соединение», а **рабочая область** с
> identity map и unit of work, и через какие состояния проходит ORM-объект. Это
> самая частая зона путаницы и любимые вопросы: «чем flush отличается от commit»,
> «что такое identity map».

## Session как unit of work

**Session** — это **рабочая область (буфер) для объектов** в рамках одной
транзакции. Она реализует паттерн **Unit of Work**: накапливает все изменения
(добавления, модификации, удаления объектов) и **применяет их в БД разом** при
коммите, в правильном порядке и одной транзакцией.

```python
with Session(engine) as session:
    user = User(name="Аня")
    session.add(user)                  # запланировано к вставке (ещё не в БД)
    user.email = "anya@example.com"    # изменение отслеживается автоматически
    session.commit()                   # все изменения летят в БД одной транзакцией
```

Ключевое: вы **не пишете UPDATE вручную** — Session **отслеживает изменения**
(dirty tracking) загруженных объектов и сама генерирует нужный SQL при flush. Это и
есть «unit of work»: единица работы, которая собирает изменения и атомарно их
фиксирует.

**Аналогия.** Session — как корзина в интернет-магазине: вы кладёте, убираете,
меняете количество (работаете с объектами), и только при оформлении заказа
(`commit`) всё разом уходит на склад одной транзакцией. До этого изменения копятся
в корзине.

## Identity map

**Identity map** — словарь «один объект на одну строку БД» **в пределах Session**.
Если вы дважды запросите строку с одним PK в одной сессии, вернётся **тот же самый
объект Python** (`is`), а не две копии:

```python
u1 = session.get(User, 1)
u2 = session.get(User, 1)
u1 is u2          # True — один объект на строку в этой сессии
```

Зачем это нужно: **согласованность** (нет двух рассинхронизированных копий одной
строки) и **кэш в рамках сессии** (повторный `get` по PK может не идти в БД).
Поэтому изменение объекта видно везде, где на него ссылаются в сессии. Identity map
живёт, пока жива сессия; в новой сессии — новые объекты.

**Аналогия.** Identity map — единая «учётная карточка» сотрудника в рамках одного
рабочего дня (сессии): сколько раз ни спросишь о сотруднике №1, тебе дадут одну и
ту же карточку, а не наплодят дубликатов, которые потом разойдутся.

## flush против commit

Самый частый вопрос про Session:

- **`flush`** — **отправляет накопленный SQL** (INSERT/UPDATE/DELETE) в БД в
  рамках **текущей транзакции**, но **не завершает** её. После flush БД «видит»
  изменения (и присваивает автоинкрементные id), но их ещё можно откатить.
- **`commit`** — делает **flush + завершает транзакцию** (`COMMIT`): изменения
  становятся постоянными и видимыми другим. По умолчанию после commit объекты
  **expire** (помечаются устаревшими) — следующее обращение к их атрибутам
  перечитает данные из БД.

```python
session.add(user)
session.flush()        # INSERT ушёл, user.id уже есть, но транзакция открыта
# ... можно ещё что-то сделать, всё в одной транзакции
session.commit()       # COMMIT — закрепили навсегда
```

flush часто происходит **автоматически** перед запросами (autoflush), чтобы запрос
видел ваши незакоммиченные изменения. Понимание «flush = SQL в транзакцию, commit =
завершить транзакцию» — ключ к контролю над тем, когда и что попадает в БД.

**Аналогия.** flush — отправить черновик документа в общий доступ внутри команды
(видно, но ещё можно отозвать); commit — официально подписать и опубликовать (назад
не вернуть, видно всем).

## Жизненный цикл объекта

ORM-объект проходит через состояния, и их полезно назвать:

- **Transient** — только создан (`User(...)`), не в сессии, нет в БД.
- **Pending** — добавлен в сессию (`session.add`), но ещё не во flush'ен в БД.
- **Persistent** — есть в сессии и в БД (после flush/загрузки); изменения
  отслеживаются.
- **Detached** — был persistent, но сессия закрыта/объект убран; в БД строка есть,
  но связь с сессией потеряна (доступ к ленивым атрибутам упадёт).

```python
u = User(name="x")     # transient
session.add(u)         # pending
session.flush()        # persistent (есть id, в БД в рамках транзакции)
session.close()        # detached — осторожно с ленивой загрузкой
```

Практический смысл: **`DetachedInstanceError`** при обращении к ленивому атрибуту
после закрытия сессии — следствие detached-состояния; лечится загрузкой данных до
закрытия (eager loading) или работой в пределах открытой сессии. `expire`/`refresh`
управляют тем, когда атрибуты перечитываются из БД.

**Аналогия.** Жизненный цикл — как статус посылки: создана (transient), принята в
отделении (pending), в системе доставки с трек-номером (persistent), а после
закрытия сессии — «вне зоны отслеживания» (detached), где о её ленивых деталях уже
не спросишь.

## Памятка для собеседования

- **Session** — рабочая область + **Unit of Work**: копит изменения и применяет
  атомарно при commit; **сама отслеживает** правки объектов (не пишешь UPDATE
  вручную).
- **Identity map** — один объект Python на строку БД в пределах сессии (`u1 is
  u2`); согласованность + кэш сессии.
- **`flush`** — шлёт SQL в текущую транзакцию (id появляются), **не** завершает её;
  **`commit`** — flush + `COMMIT` (постоянно), после него объекты обычно expire.
  Бывает autoflush.
- Состояния: **transient → pending → persistent → detached**;
  `DetachedInstanceError` при ленивом доступе после закрытия сессии.

## Частые ошибки в ответах

- Считать Session «соединением» (это рабочая область над транзакцией).
- Путать flush и commit (flush — SQL в транзакцию, commit — завершить транзакцию).
- Не знать про identity map и думать, что два запроса дадут два объекта.
- Ловить `DetachedInstanceError` и не понимать, что объект перешёл в detached.
