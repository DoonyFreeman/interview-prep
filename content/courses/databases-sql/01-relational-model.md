# Реляционная модель и нормализация

> Цель урока: понять, на чём стоит реляционная БД — таблицы, ключи, связи — и
> зачем нужна нормализация (и когда от неё осознанно отступают). Это база, без
> которой разговор про индексы, JOIN-ы и производительность бессмыслен. На собесе
> просят «спроектируйте схему» и смотрят на ключи и нормальные формы.

## Таблицы, строки, ключи

Реляционная модель описывает данные как **таблицы (отношения)** из **строк
(записей)** и **столбцов (атрибутов)**. Связи между данными выражаются не
вложенностью, а **ключами**:

- **Первичный ключ (Primary Key, PK)** — столбец (или набор), **однозначно
  идентифицирующий строку**; уникален и не NULL. Часто это суррогатный `id`
  (автоинкремент/UUID), а не «естественный» ключ вроде email.
- **Внешний ключ (Foreign Key, FK)** — столбец, **ссылающийся на PK другой
  таблицы**; так выражается связь и обеспечивается **ссылочная целостность** (нельзя
  сослаться на несуществующую строку).
- **Уникальный ключ (UNIQUE)** — гарантирует неповторяемость значений (например,
  email), но в отличие от PK может быть несколько и допускать NULL.

```sql
CREATE TABLE users (
    id    BIGSERIAL PRIMARY KEY,
    email TEXT UNIQUE NOT NULL
);
CREATE TABLE orders (
    id      BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),  -- FK
    total   NUMERIC NOT NULL
);
```

**Аналогия.** Таблица — это картотека, строка — карточка, PK — уникальный номер
карточки. FK — это когда на одной карточке записан номер другой («заказ оформил
клиент №42»), и система не даст сослаться на несуществующий номер.

## Связи: 1:1, 1:N, N:M

Через ключи выражаются три типа связей:

- **Один-к-одному (1:1)** — строке одной таблицы соответствует одна строка другой
  (профиль пользователя). Реже встречается; реализуется FK с UNIQUE.
- **Один-ко-многим (1:N)** — самая частая: у пользователя много заказов. FK
  ставится на стороне «многих» (`orders.user_id`).
- **Многие-ко-многим (N:M)** — студенты и курсы: каждый студент на многих курсах,
  на курсе много студентов. Реализуется через **связующую (junction) таблицу** с
  двумя FK.

```sql
CREATE TABLE enrollments (            -- связующая таблица для N:M
    student_id BIGINT REFERENCES students(id),
    course_id  BIGINT REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)   -- составной PK
);
```

**Аналогия.** 1:N — у мамы много детей, но у ребёнка одна мама (ссылка на маму
хранится у ребёнка). N:M — актёры и фильмы: нужна отдельная ведомость «кто в каком
фильме снялся» (связующая таблица).

## Нормализация (1NF–3NF)

**Нормализация** — приведение схемы к форме, **устраняющей избыточность и
аномалии** обновления. Кратко по нормальным формам:

- **1NF** — атомарные значения: в ячейке одно значение, нет «списков в поле» и
  повторяющихся групп столбцов.
- **2NF** — 1NF + каждый неключевой атрибут зависит от **всего** составного ключа,
  а не от его части.
- **3NF** — 2NF + нет **транзитивных** зависимостей: неключевые атрибуты зависят
  только от ключа, а не друг от друга (если хранить `city` и `city_zip` вместе с
  пользователем, zip зависит от city, а не от пользователя — выносим).

Зачем: без нормализации одни и те же данные дублируются (имя клиента в каждой
строке заказа), и обновление в одном месте оставляет рассинхрон в другом — это
**аномалии вставки/обновления/удаления**. Нормализация хранит каждый факт **в
одном месте**.

**Аналогия.** Нормализация — как вынести повторяющуюся информацию в справочник:
вместо того чтобы в каждом заказе писать полный адрес склада, держим склады в
отдельной таблице и ссылаемся по номеру. Поменялся адрес — правим в одном месте.

## Денормализация: когда дублировать осознанно

Нормализация хороша для **целостности**, но требует **JOIN-ов** при чтении, что
дороже. **Денормализация** — осознанное добавление избыточности (дублирование,
предвычисленные поля) **ради скорости чтения**. Применяют, когда:

- чтений **намного** больше, чем записей, и JOIN-ы стали узким местом;
- нужны агрегаты, которые дорого считать на лету (хранить `comments_count`);
- аналитические/отчётные витрины (OLAP), где скорость запроса важнее чистоты.

Цена — **риск рассогласования**: продублированные данные надо синхронно обновлять
(триггерами, фоновыми задачами), иначе они «разъедутся». Поэтому правило:
**сначала нормализуй, денормализуй только при доказанной проблеме
производительности**, понимая цену.

**Аналогия.** Денормализация — держать копию часто нужного документа на своём
столе, чтобы не бегать в архив (JOIN). Быстро, но если оригинал поменяли, а копию
забыли — будете работать с устаревшими данными.

## Памятка для собеседования

- Таблицы + ключи: **PK** (уникальная идентификация строки), **FK** (ссылка на PK
  другой таблицы → ссылочная целостность), **UNIQUE** (неповторяемость, можно
  несколько/NULL).
- Связи: **1:1** (FK+UNIQUE), **1:N** (FK на стороне «многих»), **N:M** (через
  связующую таблицу с двумя FK).
- **Нормализация** (1NF атомарность → 2NF зависимость от всего ключа → 3NF без
  транзитивных): убирает дублирование и аномалии, хранит факт в одном месте.
- **Денормализация** — осознанная избыточность ради скорости чтения; цена — риск
  рассогласования; применять при доказанной проблеме.

## Частые ошибки в ответах

- Путать PK и UNIQUE или не знать роль FK (ссылочная целостность).
- Не уметь спроектировать N:M (забыть связующую таблицу).
- Перечислять нормальные формы без понимания, какую аномалию каждая устраняет.
- Считать денормализацию «плохой практикой» или, наоборот, денормализовать без
  нужды и без механизма синхронизации.
