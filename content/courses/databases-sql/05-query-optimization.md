# Оптимизация запросов и проблема N+1

> Цель урока: научиться диагностировать и чинить медленные запросы — читать
> `EXPLAIN`, понимать план запроса и узнавать главную боль ORM — проблему N+1.
> «Запрос/страница тормозит, что делать» — практический вопрос, по которому видно
> реальный опыт.

## EXPLAIN и план запроса

СУБД не выполняет SQL «как написано» — **планировщик** строит **план выполнения**,
выбирая, как именно достать данные (перебор, индекс, тип соединения, порядок).
**`EXPLAIN`** показывает этот план, **`EXPLAIN ANALYZE`** — ещё и реально
выполняет запрос с фактическим временем и числом строк.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;
```

Что искать в плане:

- **Seq Scan** (полный перебор) по большой таблице на селективном условии — сигнал,
  что **не хватает индекса**.
- **Index Scan / Index Only Scan** — хорошо, поиск по индексу.
- **тип JOIN** (Nested Loop / Hash Join / Merge Join) — для больших объёмов
  Nested Loop без индекса может быть медленным.
- расхождение **оценки и факта** числа строк (estimated vs actual) — признак
  устаревшей статистики (лечится `ANALYZE`).

Главный навык — не гадать, а **смотреть план**: где время, где seq scan, где
обрабатываются миллионы строк ради десятка нужных.

**Аналогия.** `EXPLAIN` — это маршрут, который навигатор (планировщик) построил до
поездки: видно, поедет ли он по скоростной трассе (индекс) или через все дворы (seq
scan). `ANALYZE` — фактический трек уже проехавшей машины с реальным временем.

## Проблема N+1

**N+1** — самая частая проблема производительности в приложениях с ORM. Возникает,
когда код делает **1 запрос за списком** объектов, а затем **по одному
дополнительному запросу на каждый** объект для связанных данных:

```python
users = session.query(User).all()        # 1 запрос: получить N пользователей
for u in users:
    print(u.orders)                        # +1 запрос НА КАЖДОГО → ещё N запросов
# итого 1 + N запросов вместо одного-двух
```

При 1000 пользователей это **1001 запрос** вместо 1–2 — страница «тормозит», БД
завалена мелкими запросами. Лечение — **загрузить связанные данные заранее**:

- **JOIN / eager loading** — одним запросом с соединением (в SQLAlchemy
  `joinedload`/`selectinload`, в Django `select_related`/`prefetch_related`).
- В чистом SQL — просто `JOIN` вместо цикла запросов.

```python
users = session.query(User).options(selectinload(User.orders)).all()
# теперь 2 запроса (юзеры + все заказы) независимо от N
```

N+1 коварен тем, что в коде он **невидим** (выглядит как обычный доступ к
атрибуту), а проявляется только на данных. Замечать его — важный навык; помогают
логирование SQL и инструменты профилирования запросов.

**Аналогия.** N+1 — сходить в магазин за списком из 100 продуктов, делая **отдельный
поход** за каждым продуктом. Eager loading — взять всё за один-два похода со
списком в руках.

## Типичные приёмы оптимизации

Сводка практических действий, когда «запрос медленный»:

- **Добавить индекс** под условие/соединение/сортировку (проверив план).
- **Не тащить лишнее**: `SELECT` только нужные столбцы (не `SELECT *`), `LIMIT`
  для пагинации; избегать вытягивания миллионов строк в приложение.
- **Чинить N+1** через eager loading / JOIN.
- **Пагинация по ключу (keyset)** вместо `OFFSET` на больших смещениях (`OFFSET
  100000` всё равно перебирает пропускаемые строки).
- **Переписать запрос**: заменить коррелированный подзапрос на JOIN/оконную
  функцию; вынести тяжёлую агрегацию в материализованное представление.
- **Обновить статистику** (`ANALYZE`), чтобы планировщик выбирал верный план.
- **Кэшировать** дорогие, редко меняющиеся результаты (Redis) — но как крайнее
  средство.

Главный принцип: **сначала измерь (EXPLAIN/логи/профайлер), потом оптимизируй**.
Оптимизация «вслепую» часто бьёт мимо.

**Аналогия.** Оптимизация запроса — как ремонт пробок в городе: сначала смотришь,
**где** именно затор (план запроса), а потом расширяешь нужную дорогу (индекс) или
меняешь маршрут (переписать запрос), а не строишь развязки наугад.

## Памятка для собеседования

- Планировщик строит **план**; `EXPLAIN` показывает его, `EXPLAIN ANALYZE` —
  с фактом. Искать **Seq Scan** на селективных условиях (нет индекса), тип JOIN,
  расхождение оценки и факта.
- **N+1** — 1 запрос за списком + по запросу на каждый объект за связями (1+N);
  лечится **eager loading** (`joinedload`/`selectinload`,
  `select_related`/`prefetch_related`) или JOIN. В коде невидим — ловить логами SQL.
- Приёмы: индекс под план, не `SELECT *`, `LIMIT`/keyset-пагинация, переписать
  подзапрос в JOIN/окно, `ANALYZE`, кэш как крайнее средство.
- Принцип: **измерь, потом оптимизируй**.

## Частые ошибки в ответах

- Оптимизировать «на глаз», не смотря `EXPLAIN`.
- Не узнавать проблему N+1 или не знать про eager loading.
- `OFFSET` на больших смещениях для пагинации (перебирает пропускаемые строки).
- `SELECT *` и вытягивание лишних строк/столбцов в приложение.
