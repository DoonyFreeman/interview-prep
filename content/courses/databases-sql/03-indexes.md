# Индексы

> Цель урока: понять, что индекс — это структура для быстрого поиска (обычно
> B-tree), когда он помогает, а когда вредит, и как читать про составные и
> покрывающие индексы. «Как ускорить медленный запрос» почти всегда упирается в
> индексы, поэтому это один из самых практичных вопросов собеседования.

## Зачем нужен индекс и B-tree

Без индекса поиск по условию — это **полный перебор таблицы (sequential scan)**:
O(n). **Индекс** — отдельная структура данных, хранящая значения столбца в
**упорядоченном** виде со ссылками на строки, что превращает поиск в **O(log n)**.

Подавляющее большинство индексов — **B-tree** (сбалансированное дерево): значения
отсортированы, поэтому он эффективен для **поиска по равенству** (`=`),
**диапазонам** (`<`, `>`, `BETWEEN`) и **сортировки** (`ORDER BY`), а также для
префиксного поиска по строкам (`LIKE 'abc%'`).

```sql
CREATE INDEX idx_users_email ON users(email);
-- теперь WHERE email = '...' идёт по индексу (O(log n)), а не перебором
```

**Аналогия.** Индекс — это алфавитный указатель в конце книги. Без него, чтобы
найти упоминание слова, пришлось бы читать всю книгу (seq scan); с указателем вы
сразу прыгаете на нужную страницу (index scan). Указатель занимает место и его надо
обновлять при правках — как и индекс.

## Цена индексов: когда они вредят

Индексы **не бесплатны** — это главный нюанс, который отличает зрелый ответ:

- **Замедляют запись.** При каждом `INSERT`/`UPDATE`/`DELETE` все индексы таблицы
  надо обновлять. Много индексов → медленные модификации.
- **Занимают место** на диске и в памяти.
- **Бесполезны при низкой селективности.** Если столбец имеет мало уникальных
  значений (пол, булев флаг), индекс почти не сужает поиск, и планировщик
  предпочтёт seq scan. Индексы выгодны на **селективных** условиях (мало строк под
  фильтр).
- **Не используются**, если условие «прячет» столбец под функцией
  (`WHERE lower(email) = ...` не возьмёт индекс по `email` — нужен индекс по
  выражению).

Поэтому индексируют **под реальные запросы**, а не «всё подряд». Лишние индексы —
это плата за запись без выигрыша в чтении.

**Аналогия.** Каждый алфавитный указатель ускоряет поиск, но при каждом изменении
книги все указатели надо переиздавать. Сто указателей на тонкую брошюру — больше
возни с переизданием, чем пользы.

## Составные и покрывающие индексы

- **Составной (композитный) индекс** — по нескольким столбцам `(a, b, c)`.
  Критично понимать **правило левого префикса**: такой индекс работает для условий
  по `a`, `(a, b)`, `(a, b, c)`, но **не** для запроса только по `b` или `c`.
  Порядок столбцов в индексе имеет значение.
- **Покрывающий (covering) индекс** — содержит **все** столбцы, нужные запросу
  (в ключе или через `INCLUDE`), так что СУБД отвечает **прямо из индекса**, не
  обращаясь к таблице (**index-only scan**) — это очень быстро.

```sql
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);
-- хорошо для: WHERE user_id = ? [AND created_at > ?]
-- НЕ поможет для: WHERE created_at > ?   (нет левого префикса user_id)
```

Порядок столбцов выбирают так: сначала столбцы с **равенством**, потом —
**диапазон/сортировка**. Понимание левого префикса — частый отсеивающий вопрос.

**Аналогия.** Составной индекс `(фамилия, имя)` — как телефонный справочник: найти
по фамилии (и затем имени) легко, а вот найти всех «Иванов» по **имени**, не зная
фамилии, справочник не поможет — он отсортирован сначала по фамилии.

## Другие типы и практика

Помимо B-tree, есть специализированные индексы (детальнее — в курсе PostgreSQL):
**hash** (только равенство), **GIN** (полнотекст, JSONB, массивы), **GiST**
(геоданные, диапазоны), **BRIN** (огромные таблицы с естественным порядком),
**частичные** (`WHERE` в индексе — индексировать только подмножество),
**по выражению** (`lower(email)`).

Практический цикл оптимизации: найти медленный запрос → посмотреть план
(`EXPLAIN`) → если там seq scan по большой таблице на селективном условии →
добавить подходящий индекс → проверить, что план сменился на index scan. Индексы —
ответ №1 на «запрос тормозит», но добавлять их нужно **прицельно под план запроса**.

**Аналогия.** Тип индекса — как тип указателя: алфавитный (B-tree) для обычного
поиска, тематический (GIN) для «найти все страницы про X внутри текста». Выбирают
под характер вопросов к данным.

## Памятка для собеседования

- Индекс делает поиск **O(log n)** вместо seq scan O(n); по умолчанию **B-tree** —
  хорош для `=`, диапазонов, `ORDER BY`, префикса `LIKE 'abc%'`.
- Цена: **замедляют запись** (каждый INSERT/UPDATE обновляет индексы), занимают
  место, **бесполезны при низкой селективности** и под функцией на столбце.
  Индексировать прицельно под запросы.
- **Составной индекс** работает по **левому префиксу** `(a, b, c)` → годен для
  `a`, `a,b`, не для одного `b`; порядок: равенство раньше диапазона.
- **Покрывающий индекс** содержит все нужные столбцы → **index-only scan** без
  обращения к таблице.

## Частые ошибки в ответах

- Считать индексы бесплатными; не упоминать стоимость записи и низкую
  селективность.
- Не знать правило левого префикса составного индекса.
- Думать, что индекс используется при `WHERE func(col) = ...` (нужен индекс по
  выражению).
- «Навесить индексы на все столбцы» вместо прицельного индексирования под план
  запроса.
