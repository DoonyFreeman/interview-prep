# Транзакции, ACID и уровни изоляции

> Цель урока: понять гарантии ACID, какие аномалии возникают при конкурентном
> доступе и как уровни изоляции их предотвращают. Это сердце надёжности БД и
> глубокий вопрос собеседования: «какие уровни изоляции бывают и что такое грязное
> чтение».

## ACID

**Транзакция** — группа операций, выполняемых **как единое целое**. Гарантии
транзакций описывает аббревиатура **ACID**:

- **A — Atomicity (атомарность)**: транзакция выполняется **полностью или никак**.
  Упала на середине — все её изменения откатываются (`ROLLBACK`). «Перевод денег»
  не оставит деньги списанными, но не зачисленными.
- **C — Consistency (согласованность)**: транзакция переводит БД из одного
  **корректного** состояния в другое, не нарушая ограничений (FK, CHECK, UNIQUE).
- **I — Isolation (изолированность)**: конкурентные транзакции **не видят
  промежуточных** результатов друг друга (степень — по уровню изоляции).
- **D — Durability (долговечность)**: после `COMMIT` данные **сохранены навсегда**,
  даже при сбое питания (обычно через журнал, WAL).

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- обе операции применятся вместе; при сбое между ними — откат обеих
```

**Аналогия.** Транзакция — банковский перевод: атомарность — «или списали и
зачислили, или ничего»; долговечность — «после подтверждения операция не исчезнет,
даже если свет выключат»; изоляция — «другие не видят полузавершённый перевод».

## Аномалии конкурентного доступа

Когда транзакции работают параллельно, без изоляции возникают **аномалии**:

- **Грязное чтение (dirty read)** — транзакция читает **незакоммиченные**
  изменения другой, которые могут откатиться (прочитали «деньги пришли», а перевод
  отменился).
- **Неповторяемое чтение (non-repeatable read)** — одна и та же строка при
  повторном чтении в рамках транзакции **изменилась** (другая транзакция
  закоммитила `UPDATE`).
- **Фантомное чтение (phantom read)** — повторный запрос по условию возвращает
  **новые строки** (другая транзакция вставила подходящие под фильтр).
- **Потерянное обновление (lost update)** — два параллельных `read-modify-write`
  затирают изменения друг друга.

Эти аномалии — то, что уровни изоляции выборочно запрещают, балансируя
**корректность против производительности**.

**Аналогия.** Грязное чтение — поверить черновику, который потом порвали.
Неповторяемое — перечитать абзац, а его уже переписали. Фантом — вернуться к
списку, а там появились новые пункты.

## Уровни изоляции

Стандарт SQL определяет четыре уровня — от слабого к строгому; каждый запрещает
больше аномалий, но обычно дороже:

| Уровень | Dirty read | Non-repeatable | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | возможно | возможно | возможно |
| READ COMMITTED | нет | возможно | возможно |
| REPEATABLE READ | нет | нет | возможно* |
| SERIALIZABLE | нет | нет | нет |

- **READ COMMITTED** — видны только закоммиченные данные; **дефолт в
  PostgreSQL** и многих СУБД. Защищает от грязного чтения.
- **REPEATABLE READ** — стабильный «снимок» данных на время транзакции; в PostgreSQL
  благодаря MVCC он предотвращает и фантомы в большинстве случаев.
- **SERIALIZABLE** — как будто транзакции выполнялись **по очереди**; максимальная
  корректность, но больше блокировок/откатов (сериализационные ошибки, требующие
  ретрая).

Практика: повышают уровень только там, где аномалия реально вредит (финансы,
инвентарь); для большинства запросов хватает READ COMMITTED.

**Аналогия.** Уровни изоляции — степень «отдельной комнаты» для каждого: от
открытого опенспейса (всё видно, дёшево, но мешают) до изолированного кабинета
(никто не помешает, но дорого содержать).

## MVCC и блокировки

Как изоляция реализуется: два подхода.

- **Блокировки (locking)** — транзакция блокирует строки/таблицы, заставляя другие
  ждать. Просто, но снижает конкурентность и грозит дедлоками.
- **MVCC (Multi-Version Concurrency Control)** — каждая транзакция видит
  **согласованный снимок** данных на свой момент; при изменении создаётся **новая
  версия** строки, а старые остаются для тех, кто их ещё читает. Так **читатели не
  блокируют писателей и наоборот** — высокая конкурентность. Это модель PostgreSQL.

Цена MVCC — накопление **старых версий** строк, которые надо периодически чистить
(в PostgreSQL — `VACUUM`/autovacuum, иначе «раздувание» таблиц). Для явной
блокировки строк под изменение есть `SELECT ... FOR UPDATE`.

**Аналогия.** MVCC — как система версий документа: пока один читает версию 5,
другой создаёт версию 6; никто никого не ждёт, каждый видит целостную версию на
момент начала. Потом старые черновики надо убрать в архив (VACUUM).

## Памятка для собеседования

- **ACID**: Atomicity (всё или ничего), Consistency (не нарушать ограничения),
  Isolation (не видеть промежуточное), Durability (после COMMIT — навсегда, WAL).
- Аномалии: **dirty read** (чтение незакоммиченного), **non-repeatable** (строка
  изменилась при повторном чтении), **phantom** (появились новые строки), **lost
  update**.
- Уровни: READ UNCOMMITTED → **READ COMMITTED** (дефолт PG, нет грязного чтения) →
  REPEATABLE READ → SERIALIZABLE (как по очереди). Выше уровень — меньше аномалий,
  дороже.
- **MVCC** (PostgreSQL): версии строк, читатели не блокируют писателей; цена —
  очистка старых версий (`VACUUM`). `SELECT ... FOR UPDATE` для явной блокировки.

## Частые ошибки в ответах

- Назвать ACID буквами без понимания каждой гарантии.
- Путать аномалии (особенно non-repeatable vs phantom) или не знать дефолтный
  уровень (READ COMMITTED).
- Не знать про MVCC и думать, что изоляция — это всегда блокировки.
- Не упомянуть цену SERIALIZABLE (откаты/ретраи) и MVCC (VACUUM/bloat).
