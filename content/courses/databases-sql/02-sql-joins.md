# SQL: JOIN-ы, агрегация, CTE и оконные функции

> Цель урока: уверенно владеть рабочим SQL — типами JOIN-ов, группировкой,
> подзапросами, CTE и оконными функциями. Это ежедневный инструмент бэкендера, и
> на собесе часто дают задачу «напишите запрос», где проверяют JOIN-ы и понимание
> `GROUP BY` vs оконных функций.

## Типы JOIN

**JOIN** соединяет строки таблиц по условию. Типы различаются тем, что делать с
**несовпавшими** строками:

- **INNER JOIN** — только строки, где **есть совпадение** в обеих таблицах.
- **LEFT (OUTER) JOIN** — **все** строки левой таблицы + совпавшие из правой; где
  нет пары — `NULL`. (RIGHT — зеркально.)
- **FULL OUTER JOIN** — все строки обеих таблиц, несовпавшие дополнены `NULL`.
- **CROSS JOIN** — декартово произведение (каждая с каждой).
- **SELF JOIN** — таблица соединяется сама с собой (иерархии: сотрудник →
  руководитель).

```sql
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;   -- все юзеры, даже без заказов (total NULL)
```

Частый вопрос: «найти пользователей **без** заказов» — это `LEFT JOIN ... WHERE
o.id IS NULL` (анти-join). Главное — понимать, INNER теряет несовпавшие строки, а
LEFT их сохраняет: путаница здесь — источник «пропавших» данных в отчётах.

**Аналогия.** INNER JOIN — список пар «гость + его столик» только для тех, кто
реально сел. LEFT JOIN — список всех гостей, и у не севших столик помечен как
«нет» (NULL).

## GROUP BY, HAVING, агрегаты

**Агрегатные функции** (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) сворачивают группы
строк в одно значение. **`GROUP BY`** задаёт, по каким столбцам группировать:

```sql
SELECT user_id, COUNT(*) AS orders_cnt, SUM(total) AS revenue
FROM orders
GROUP BY user_id
HAVING SUM(total) > 1000          -- фильтр ПО ГРУППАМ (после агрегации)
ORDER BY revenue DESC;
```

Критичное различие: **`WHERE` фильтрует строки ДО группировки**, **`HAVING` —
группы ПОСЛЕ агрегации**. Нельзя использовать агрегат в `WHERE` (`WHERE SUM(...)`
— ошибка) — для этого есть `HAVING`. И в `SELECT` при `GROUP BY` можно брать
только столбцы из `GROUP BY` или агрегаты.

Логический порядок выполнения (полезно знать): `FROM → WHERE → GROUP BY → HAVING →
SELECT → ORDER BY → LIMIT`. Поэтому алиас из `SELECT` нельзя использовать в
`WHERE` (он ещё не вычислен), но можно в `ORDER BY`.

**Аналогия.** `GROUP BY` — разложить чеки по клиентам в стопки; агрегат — посчитать
сумму в каждой стопке; `WHERE` — выкинуть лишние чеки до раскладки, `HAVING` —
выкинуть стопки, не дотянувшие до порога, после подсчёта.

## Подзапросы и CTE

Сложные запросы строят из вложенных частей:

- **Подзапрос** — запрос внутри запроса (в `WHERE`, `FROM`, `SELECT`). Бывает
  **скалярный** (одно значение), **в IN** (список), **коррелированный** (ссылается
  на внешний запрос, выполняется построчно — может быть медленным).
- **CTE (Common Table Expression, `WITH`)** — именованный подзапрос «наверху»,
  делающий запрос **читаемым** и переиспользуемым; поддерживает **рекурсию** (обход
  деревьев/графов).

```sql
WITH big_spenders AS (                 -- CTE: называем промежуточный результат
    SELECT user_id FROM orders
    GROUP BY user_id HAVING SUM(total) > 1000
)
SELECT u.name FROM users u
JOIN big_spenders b ON b.user_id = u.id;
```

CTE обычно предпочтительнее громоздких вложенных подзапросов из-за читаемости.
**Рекурсивный CTE** (`WITH RECURSIVE`) решает иерархии: дерево комментариев,
оргструктура, граф связей.

**Аналогия.** CTE — это как дать промежуточному расчёту имя на доске («назовём этих
клиентов крупными»), а потом ссылаться на него, вместо того чтобы каждый раз
переписывать формулу целиком.

## Оконные функции

**Оконные функции** считают агрегат **по группе строк, не схлопывая их в одну** —
в отличие от `GROUP BY`. Каждая строка сохраняется, но получает дополнительное
вычисленное по «окну» значение (`OVER (...)`):

```sql
SELECT
    user_id, total,
    SUM(total)  OVER (PARTITION BY user_id) AS user_total,     -- сумма по юзеру
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY total DESC) AS rn,
    RANK()       OVER (ORDER BY total DESC) AS overall_rank
FROM orders;
```

`PARTITION BY` задаёт группы окна, `ORDER BY` внутри окна — порядок (для
ранжирования и накопительных сумм). Ключевые функции: `ROW_NUMBER`, `RANK`,
`DENSE_RANK`, `LAG`/`LEAD` (соседние строки), `SUM/AVG OVER` (скользящие/
накопительные). Классическая задача «топ-N в каждой категории» решается
`ROW_NUMBER() OVER (PARTITION BY category ORDER BY ...)` + фильтр по номеру.

Главное отличие от `GROUP BY`: **`GROUP BY` уменьшает число строк, оконная функция
— нет** (добавляет столбец к каждой строке). Это частый и любимый вопрос.

**Аналогия.** `GROUP BY` — свести класс к одной строке «средний балл класса».
Оконная функция — оставить всех учеников, но к каждому дописать «средний балл его
класса» и «его место в рейтинге». Строки на месте, контекст добавлен.

## Памятка для собеседования

- JOIN: **INNER** (только совпадения), **LEFT** (все левые + NULL для непарных),
  **FULL**, **CROSS** (декарт), **SELF** (иерархии). «Без заказов» = LEFT JOIN +
  `IS NULL`.
- Агрегаты + **`GROUP BY`**; **`WHERE` фильтрует строки до**, **`HAVING` — группы
  после** агрегации. Порядок: FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT.
- **Подзапросы** (скалярные/IN/коррелированные) и **CTE (`WITH`)** для читаемости;
  `WITH RECURSIVE` — иерархии.
- **Оконные функции** (`OVER (PARTITION BY ... ORDER BY ...)`) считают по группе,
  **не схлопывая строки** (в отличие от GROUP BY): `ROW_NUMBER`, `RANK`,
  `LAG/LEAD`, накопительные суммы.

## Частые ошибки в ответах

- Путать INNER и LEFT JOIN (терять строки без пары).
- Класть агрегат в `WHERE` вместо `HAVING`; путать, что фильтруется до, а что после
  группировки.
- Не знать оконные функции или не видеть разницы с `GROUP BY` (схлопывает строки
  или нет).
- Писать тяжёлые коррелированные подзапросы там, где лучше JOIN/оконная функция.
