# threading: потоки, гонки и блокировки

> Цель урока: понять, когда потоки в Python полезны, что такое гонка данных и
> дедлок, и как их предотвращать примитивами синхронизации. Вопросы про race
> condition и `Lock` — классика; ждут понимания, что GIL **не** делает ваш код
> автоматически потокобезопасным.

## Когда потоки полезны

Модуль `threading` создаёт потоки ОС, разделяющие память процесса. Из-за GIL они
**не ускоряют CPU-bound** код, но **полезны для IO-bound**: пока один поток ждёт
ответа сети/диска (и отпускает GIL), другой работает.

```python
import threading

def worker(url):
    data = requests.get(url).text     # на время ожидания GIL отпущен
    save(data)

threads = [threading.Thread(target=worker, args=(u,)) for u in urls]
for t in threads: t.start()
for t in threads: t.join()            # дождаться завершения всех
```

`start()` запускает поток, `join()` блокирует до его завершения. Потоки разделяют
**общую память**, что удобно (общие структуры данных), но опасно (гонки). Типичные
применения: параллельные сетевые запросы, фоновые задачи, отзывчивый UI.

**Аналогия.** Потоки — это несколько сотрудников в одном кабинете с общими
документами на столе: быстро обмениваются данными, но если двое одновременно
правят один документ — получится каша (гонка).

## Гонки данных (race conditions)

**Гонка данных** — когда результат зависит от **порядка** выполнения потоков,
обращающихся к общим данным. Классический пример — `x += 1` над общей переменной:
эта операция **не атомарна** (чтение → увеличение → запись), и потоки могут
«перебить» друг друга, потеряв обновления.

```python
counter = 0
def increment():
    global counter
    for _ in range(100_000):
        counter += 1          # НЕ атомарно: read-modify-write

# два потока → итог почти наверняка < 200_000: часть инкрементов потеряна
```

Важнейший тезис для собеседования: **GIL НЕ спасает от гонок на уровне вашей
логики**. GIL гарантирует атомарность отдельных байткод-инструкций, но `counter +=
1` — это **несколько** инструкций, между которыми поток может быть прерван.
Поэтому общие изменяемые данные нужно защищать явно.

**Аналогия.** Двое одновременно смотрят на счётчик «10», оба прибавляют 1 у себя в
уме и записывают «11». Должно было стать «12», но стало «11» — одно обновление
потерялось. Это и есть гонка.

## Блокировки и примитивы синхронизации

Чтобы защитить **критическую секцию** (код, работающий с общими данными),
используют **`Lock`** — только один поток может держать его одновременно:

```python
lock = threading.Lock()
def increment():
    global counter
    for _ in range(100_000):
        with lock:            # критическая секция: один поток за раз
            counter += 1      # теперь атомарно на уровне логики
```

Другие примитивы: **`RLock`** (реентерабельный — можно захватить повторно тем же
потоком), **`Event`** (сигнал между потоками), **`Condition`** (ожидание условия),
**`Semaphore`** (ограничить число одновременных доступов), **`queue.Queue`**
(потокобезопасная очередь — **предпочтительный** способ обмена данными между
потоками, не требует ручных блокировок).

**Аналогия.** `Lock` — это ключ от переговорной: кто взял ключ, тот и работает с
общим документом, остальные ждут под дверью. `queue.Queue` — лента-конвейер с
встроенной защитой: класть и брать можно без личных договорённостей.

## Дедлоки

**Дедлок (deadlock)** — взаимная блокировка: потоки навечно ждут друг друга.
Классика — два потока захватывают два замка в **разном порядке**:

```python
# Поток 1: lock_a → ждёт lock_b
# Поток 2: lock_b → ждёт lock_a
# оба ждут навсегда — дедлок
```

Условия дедлока (Коффмана) включают удержание ресурса при ожидании другого и
**циклическое** ожидание. Как избегать: захватывать замки **всегда в одном
порядке**; использовать таймауты (`lock.acquire(timeout=...)`); минимизировать
число одновременно удерживаемых замков; предпочитать высокоуровневые средства
(`queue.Queue`, `concurrent.futures`) ручным блокировкам.

**Аналогия.** Дедлок — двое в узком коридоре, каждый ждёт, пока другой отойдёт, и
никто не двигается. Решение — общее правило «всегда уступаем правому» (единый
порядок захвата), и тупик не возникнет.

## Памятка для собеседования

- `threading` — потоки ОС с общей памятью; из-за GIL не ускоряют CPU-bound, но
  полезны для **IO-bound** (поток отпускает GIL на ожидании). `start()`/`join()`.
- **Гонка данных** — результат зависит от порядка потоков над общими данными;
  `x += 1` не атомарен. **GIL НЕ защищает** составные операции вашей логики.
- Защита критической секции — **`Lock`** (`with lock:`); ещё `RLock`, `Event`,
  `Condition`, `Semaphore`; **`queue.Queue`** — потокобезопасный обмен без ручных
  замков.
- **Дедлок** — взаимное ожидание; избегать единым порядком захвата замков,
  таймаутами, высокоуровневыми средствами.

## Частые ошибки в ответах

- Утверждать, что GIL делает потоки полностью безопасными (он не защищает
  составные операции).
- Не уметь объяснить, почему `x += 1` подвержен гонке (не атомарен).
- Защищать данные «вручную» без `Lock`/`Queue` или захватывать замки в разном
  порядке (дедлок).
- Использовать потоки для CPU-bound, ожидая ускорения.
