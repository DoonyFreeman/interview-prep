# concurrent.futures и выбор инструмента

> Цель урока: познакомиться с высокоуровневым API `concurrent.futures`, который
> единообразно прячет и потоки, и процессы, и собрать итоговое правило выбора
> между потоками, процессами и asyncio. Финальный вопрос темы: «что взять под
> такую-то задачу» — и здесь нужен чёткий, обоснованный ответ.

## Executor и Future

`concurrent.futures` даёт **единый высокоуровневый интерфейс** к пулам потоков и
процессов, скрывая ручное управление. Две реализации:
**`ThreadPoolExecutor`** (потоки, для IO-bound) и **`ProcessPoolExecutor`**
(процессы, для CPU-bound) — с **одинаковым API**, так что переключиться можно
сменой одного класса.

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=8) as executor:
    futures = [executor.submit(fetch, url) for url in urls]
    for fut in as_completed(futures):      # по мере готовности
        result = fut.result()              # значение или проброс исключения

# или просто:
with ThreadPoolExecutor() as ex:
    results = list(ex.map(fetch, urls))    # как map, но параллельно
```

**`Future`** — объект-обещание результата, который посчитается позже:
`result()` (дождаться значения или получить исключение), `done()`, `cancel()`,
`add_done_callback()`. `as_completed` отдаёт futures по мере завершения;
`executor.map` — простой параллельный аналог `map`. Главное преимущество — пул
**переиспользует** воркеров и сам управляет очередью задач.

**Аналогия.** Executor — это бюро с фиксированным штатом исполнителей (`max_workers`)
и окошком приёма заявок. Вы сдаёте задачу (`submit`) и получаете талон
(`Future`); по талону позже забираете результат. Не нужно нанимать/увольнять людей
под каждую задачу.

## Future, исключения и отмена

Важные практические детали работы с `Future`:

- **Исключения не теряются**: если задача упала, исключение всплывёт при вызове
  `fut.result()`. Поэтому результаты нужно забирать — иначе ошибка может остаться
  незамеченной.
- **`map` пробрасывает исключение** при итерации по результатам; порядок
  результатов соответствует порядку входов (в отличие от `as_completed`).
- **Отмена** (`cancel()`) работает только для ещё **не начавшихся** задач; уже
  выполняющуюся отменить нельзя.
- Контекстный менеджер (`with`) гарантирует `shutdown()` — дождаться задач и
  освободить воркеров.

```python
with ProcessPoolExecutor() as ex:           # тот же API, но процессы
    for n, res in zip(inputs, ex.map(crunch, inputs)):
        ...                                  # CPU-bound параллельно на ядрах
```

**Аналогия.** `Future` — квитанция из химчистки: придёте — получите вещь или
узнаете, что её испортили (исключение). Не пришли за квитанцией — и о порче можете
не узнать.

## Итоговое правило выбора

Сводим всю тему в один работающий алгоритм выбора инструмента:

- **IO-bound, много ожидания (сеть, диск, БД)** →
  **`ThreadPoolExecutor`** или **`asyncio`**. Потоки проще встроить в
  синхронный код; asyncio эффективнее при **очень большом** числе одновременных
  ожиданий (тысячи соединений) и меньшем оверхеде, но требует async-кода целиком.
- **CPU-bound, тяжёлые вычисления** → **`ProcessPoolExecutor`** /
  `multiprocessing` (свой GIL у каждого процесса) или **нативные библиотеки**
  (numpy/Cython), отпускающие GIL.
- **Смешанная нагрузка** → комбинируют: процессы для счёта, внутри — потоки/async
  для IO.

```text
IO-bound  + умеренная конкурентность   → потоки (ThreadPoolExecutor)
IO-bound  + тысячи соединений          → asyncio
CPU-bound                              → процессы (ProcessPoolExecutor) / нативный код
```

Главное на собеседовании — не просто назвать инструмент, а **обосновать через
GIL и тип нагрузки**: потоки не ускоряют CPU из-за GIL; процессы дорогие из-за
сериализации, но дают параллелизм; asyncio — однопоточная кооперативная модель,
блестящая для массового IO, бесполезная для CPU.

**Аналогия.** Выбор инструмента — как выбор транспорта: на тяжёлый груз (CPU) —
грузовики (процессы); развезти много мелких писем (IO) — один курьер на велосипеде,
ловко объезжающий пробки (asyncio), или несколько курьеров (потоки).

## Памятка для собеседования

- `concurrent.futures` — единый API к пулам: **`ThreadPoolExecutor`** (IO) и
  **`ProcessPoolExecutor`** (CPU) с одинаковым интерфейсом. `submit` →
  **`Future`**; `map`; `as_completed`.
- `Future.result()` отдаёт значение или **пробрасывает исключение** (забирать
  результаты обязательно); `cancel()` — только для не начавшихся задач; `with`
  делает `shutdown`.
- Выбор: **IO-bound** → потоки или **asyncio** (asyncio — при тысячах соединений);
  **CPU-bound** → процессы/нативный код. Обосновывать через **GIL и тип нагрузки**.

## Частые ошибки в ответах

- Не забирать `Future.result()` и терять исключения задач.
- Считать, что `cancel()` останавливает уже выполняющуюся задачу.
- Брать asyncio для CPU-bound (однопоточный цикл не даёт параллелизма вычислений).
- Называть инструмент без обоснования через GIL и характер нагрузки (CPU vs IO).
