# Потоки и процессы: быстрый практикум

> **12 минут вместе с практикой.** Ты обрабатываешь документы для RAG. Выбери, где ждать, где считать и как собрать результаты без потерь.

## Выбери инструмент по нагрузке

Конкурентность — несколько задач в работе. Они могут по очереди продвигаться на одном ядре. Параллелизм — вычисления идут одновременно, например на разных ядрах. ОС сама переключает потоки. В `asyncio` корутина уступает управление, когда приостанавливается в ожидании.

| Что съедает время | С чего начать |
| --- | --- |
| Ждём ответа от API эмбеддингов. Клиент асинхронный | `asyncio` |
| Ждём сеть, а SDK синхронный | `ThreadPoolExecutor` или `await asyncio.to_thread(...)` в async-сервисе |
| Считаем токены по большим текстам циклом на чистом Python | Пакеты документов в `ProcessPoolExecutor`, если замеры оправдывают накладные расходы |

Потоки разделяют память. У процессов память по умолчанию раздельная. Данные можно передать через `multiprocessing.Queue` или `Pipe`, а большие массивы при необходимости держать в `shared_memory` с явной синхронизацией. У пула `submit()` возвращает `Future`, а `as_completed()` отдаёт задачи по готовности. Вызов `future.result()` возвращает значение или поднимает исключение.

С включённым GIL внутри одного интерпретатора CPython потоки не исполняют Python-байткод одновременно. На многих блокирующих операциях ввода-вывода и в некоторых нативных вычислениях, например в ряде операций NumPy, GIL освобождается. С 3.13 есть отдельная free-threaded сборка. В ней возможно параллельное исполнение Python-кода, хотя некоторые расширения могут снова включить GIL. [Документация CPython](https://docs.python.org/3/howto/free-threading-python.html)

**Посчитай.** Из 10 секунд работы 2 секунды занимает последовательный этап, а 8 секунд делятся поровну на 4 ядра. Сколько займёт идеальный вариант и где предел ускорения?

```solution
На четырёх ядрах получится **2 + 8 / 4 = 4 с**, то есть **2,5×**. Даже при бесконечном числе ядер останутся последовательные 2 секунды, поэтому предел **5×**. Это закон Амдала. На практике запуск процессов и передача данных добавят время.
```

**Запуск процессов.** `spawn` запускает новый интерпретатор, `fork` наследует образ родительского процесса, `forkserver` создаёт дочерние процессы из отдельного серверного процесса. На Windows и macOS обычно используется `spawn`, на Linux с Python 3.14 типичный выбор по умолчанию — `forkserver`. Проверь среду через `multiprocessing.get_start_method()`. Запуск пула защищай `if __name__ == "__main__":`, а функции для воркеров объявляй на уровне модуля. [Методы запуска в Python 3.14](https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods)

## Найди потерянное обновление

Два потока отмечают документы обработанными. Оба читают счётчик, прибавляют единицу и записывают результат. Перед последним шагом предскажи итог.

```execution

  "nodes": ["Поток A", "Поток Б"],
  "steps": [
    {"node": "Поток A", "explanation": "A читает счётчик и запоминает 10. Запись ещё впереди.", "state": {"Счётчик": 10, "Прочитал A": 10}},
    {"node": "Поток Б", "explanation": "Б читает тот же счётчик, пока A ничего не записал.", "state": {"Счётчик": 10, "Прочитал A": 10, "Прочитал Б": 10}},
    {"node": "Поток A", "explanation": "A прибавляет единицу к прочитанному числу и записывает 11.", "state": {"Счётчик": 11, "Прочитал A": 10, "Прочитал Б": 10}},
    {"node": "Поток Б", "explanation": "Б прибавляет единицу к своей копии числа 10 и тоже записывает 11. Второе обновление потерялось.", "state": {"Счётчик": 11, "Прочитал A": 10, "Прочитал Б": 10}}
  ]
}
```

Защити одним общим `Lock` всё действие «прочитать → изменить → записать». Оставь сеть и тяжёлый расчёт снаружи, если это сохраняет согласованность данных. На GIL как на гарантию атомарности составной операции рассчитывать нельзя. Этот пример показывает явное чередование шагов. Один запуск короткого `counter += 1` в конкретной версии CPython может гонку не воспроизвести.

```python
from threading import Lock

lock = Lock()
processed_count = 0

def mark_processed():
    global processed_count
    with lock:
        processed_count += 1
```

| Симптом | Что происходит |
| --- | --- |
| **Deadlock** | A держит замок 1 и ждёт 2. Б держит 2 и ждёт 1. Оба стоят. |
| **Livelock** | Оба освобождают замки и снова пытаются их взять в один и тот же момент. Движение есть, обработанных документов нет. |
| **Голодание** | Одни потоки продолжают работу, один постоянно остаётся без доступа. |

Для двух замков задай единый порядок захвата. Если используешь `acquire(timeout=…)`, освободи уже захваченные ресурсы при выходе и ограничь повторы.

## Передавай работу через очередь

**Производитель → `queue.Queue(maxsize=2)` → потоки-воркеры → результат.** Производитель передаёт документ через `put()`, свободный воркер берёт его через `get()`. Потокобезопасность очереди защищает саму передачу. Передавай неизменяемые данные или отдавай владение объектом воркеру. Если есть пул, воркеры могут возвращать результат через `Future`, а основной поток соберёт итоги.

| Что нужно | Примитив |
| --- | --- |
| Один поток меняет общее состояние | `Lock`. Если тот же поток должен снова захватить тот же замок — `RLock`. |
| На сервис одновременно ходят не больше трёх потоков | `Semaphore(3)`. `BoundedSemaphore` обнаружит лишний `release()`, если счётчик превысит исходное значение. |
| Разослать сигнал «останавливаемся» или дождаться условия над данными | `Event` для сигнала, `Condition.wait_for(predicate)` для условия. |

**Проверь себя.** В очереди уже два документа. Производитель вызывает обычный `put()` в третий раз. Можно ли при этом передать всем воркерам одну сессию БД?

```solution
Третий `put()` ждёт свободного места. Для сессии сначала проверь контракт библиотеки. Например, SQLAlchemy рекомендует **Session на поток**, а **AsyncSession на задачу**. Для ресурса на поток можно передать отдельный экземпляр или использовать `threading.local()` с явной очисткой. Поток в пуле обслуживает много заданий, поэтому его локальные данные могут пережить одно задание.
```
