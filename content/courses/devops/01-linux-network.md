# Linux и сеть для бэкендера

> Цель урока: освоить минимум Linux и сетевых утилит, который реально нужен
> бэкенд-разработчику — процессы, сигналы, права, пайпы, диагностика портов и
> соединений. Эти вопросы проверяют, умеете ли вы жить на сервере, а не только
> писать код.

## Процессы и сигналы

В Linux всё работает как **процессы**, у каждого есть **PID**. Управление
процессами и понимание **сигналов** — база эксплуатации:

- **Сигналы** — способ ОС/пользователя сообщить процессу о событии:
  **`SIGTERM`** (15) — «вежливо завершись» (можно перехватить и корректно закрыть
  ресурсы), **`SIGKILL`** (9) — «убить немедленно» (нельзя перехватить, не даёт
  прибраться), **`SIGINT`** (Ctrl+C), **`SIGHUP`** (часто «перечитать конфиг»).
- Команды: `ps`, `top`/`htop` (что выполняется), `kill <pid>` (послать сигнал, по
  умолчанию SIGTERM), `kill -9` (SIGKILL).

```bash
kill 1234        # SIGTERM — попросить завершиться (graceful)
kill -9 1234     # SIGKILL — убить жёстко (последнее средство)
```

Это **прямо связано с контейнерами**: Docker при остановке шлёт контейнеру
`SIGTERM` и ждёт; приложение должно **обработать SIGTERM** — закончить текущие
запросы, закрыть соединения (graceful shutdown), иначе данные/запросы потеряются.
`SIGKILL` — если не успело за timeout.

**Аналогия.** SIGTERM — попросить сотрудника «закругляйся, доделай и уходи»
(graceful); SIGKILL — выключить рубильник, не дав ничего сохранить. Хороший сервис
реагирует на первое и прибирается.

## Права и файловая система

Linux — многопользовательская система с **правами доступа** на файлы. Каждый файл
имеет владельца, группу и три набора прав: **чтение (r), запись (w), исполнение
(x)** — для владельца / группы / остальных.

```bash
ls -l                  # rwxr-xr-x  владелец=rwx, группа=r-x, остальные=r-x
chmod 644 file         # rw-r--r--  (владельцу запись, остальным чтение)
chmod +x script.sh     # сделать исполняемым
chown user:group file  # сменить владельца
```

Числа: `7=rwx, 6=rw-, 5=r-x, 4=r--`. Это важно для безопасности (не давать лишних
прав, не запускать от **root** без нужды — принцип наименьших привилегий, как
non-root в Docker). Файловая система — единое дерево от `/` (корня); важные места:
`/etc` (конфиги), `/var/log` (логи), `/home`, `/tmp`. Всё — файл (включая
устройства).

**Аналогия.** Права — как замки и ключи на комнатах: владелец, его группа и «все
остальные» имеют разный доступ. Давать всем ключ от всех комнат (`chmod 777`) —
дыра в безопасности.

## Пайпы и работа в шелле

Сила Unix — **композиция мелких утилит** через **пайпы (`|`)**: вывод одной
команды становится входом другой. Так строят обработку текста/логов без скриптов.

```bash
cat access.log | grep "ERROR" | awk '{print $1}' | sort | uniq -c | sort -rn
# прочитать → отфильтровать ошибки → взять IP → посчитать уникальные → топ
```

- **`|`** — пайп (соединить команды), **`>`**/**`>>`** — перенаправить вывод в файл
  (перезапись/дозапись), **`<`** — ввод из файла.
- Базовый набор: `grep` (поиск), `awk`/`sed` (обработка текста), `sort`, `uniq`,
  `wc`, `find`, `tail -f` (следить за логом в реальном времени), `cat`/`less`.

Это **философия Unix**: каждая программа делает одно дело хорошо, а сложное
собирается из простого через пайпы. Для бэкендера это ежедневный анализ логов и
диагностика прямо на сервере.

**Аналогия.** Пайпы — конвейер из насадок: сырьё (вывод) проходит через фильтр,
потом через резак, потом через счётчик. Каждая насадка простая, а вместе они дают
сложную обработку.

## Диагностика сети

Когда «сервис не отвечает», нужны сетевые утилиты:

- **`ss`** (современная замена `netstat`) — какие **порты слушаются**, какие
  соединения открыты: `ss -tlnp` (TCP, listening, с процессами). Ответ на «занят ли
  порт», «слушает ли сервис».
- **`curl`** — отправить HTTP-запрос из консоли: проверить, отвечает ли API,
  посмотреть заголовки/код (`curl -v`, `curl -I`). Главный инструмент проверки
  эндпоинтов.
- **`ping`** (доступен ли хост), **`traceroute`** (маршрут до хоста), **DNS**
  (`dig`/`nslookup` — резолвится ли имя в IP).
- **`telnet`/`nc host port`** — проверить, доступен ли конкретный порт.

```bash
ss -tlnp                       # какие порты слушаются и кем
curl -v http://localhost:8000/health   # проверить эндпоинт
dig example.com                # резолвится ли DNS
```

Типичная диагностика «не подключается»: сервис вообще слушает порт? (`ss`) →
резолвится ли имя? (`dig`) → доступен ли порт снаружи? (`nc`) → что отвечает HTTP?
(`curl`). Это разбивает проблему на слои (DNS → TCP → HTTP).

**Аналогия.** Сетевая диагностика — как проверять, почему не доходит звонок: есть
ли вообще номер (DNS), берут ли трубку на линии (порт слушается), и что говорят,
когда дозвонился (curl-ответ). Проверяешь по слоям, а не гадаешь.

## Памятка для собеседования

- Процессы/сигналы: **SIGTERM** (graceful, перехватываемый) vs **SIGKILL -9**
  (жёсткий, неперехватываемый); Docker шлёт SIGTERM → приложение должно делать
  **graceful shutdown**. `ps`/`top`/`kill`.
- Права: `rwx` для владелец/группа/остальные (`chmod 644`, `+x`, `chown`); принцип
  **наименьших привилегий** (не root зря). ФС — дерево от `/` (`/etc`, `/var/log`).
- **Пайпы** (`|`) — композиция утилит (`grep`/`awk`/`sort`/`uniq`/`tail -f`);
  философия Unix «одна утилита — одно дело».
- Сеть: **`ss`** (порты/соединения), **`curl`** (HTTP), `dig` (DNS), `ping`/`nc`;
  диагностика по слоям DNS→TCP→HTTP.

## Частые ошибки в ответах

- Не знать разницу SIGTERM/SIGKILL и связь с graceful shutdown контейнеров.
- `chmod 777` «чтобы заработало» вместо минимально нужных прав.
- Не уметь проверить порт/эндпоинт (`ss`, `curl`) при диагностике.
- Гадать о причине сетевой проблемы вместо проверки по слоям (DNS/TCP/HTTP).
