# Git: ветки, merge, rebase

> Цель урока: уверенно объяснять модель Git — ветки, разницу merge и rebase,
> отмену изменений (reset/revert) и разрешение конфликтов. Git — ежедневный
> инструмент, и на собесе спрашивают «merge или rebase», «как откатить коммит» —
> ждут понимания, а не заученных команд.

## Модель Git и ветки

Git — **распределённая** система контроля версий: у каждого разработчика **полная
копия истории**. История — это цепочка **коммитов** (снимков состояния), каждый
ссылается на родителя. **Ветка (branch)** — это просто **подвижный указатель** на
коммит, а не «копия файлов».

```text
main:    A───B───C
                  \
feature:           D───E   ← ветка feature указывает на E
```

Создание ветки дёшево (новый указатель), поэтому работают по схеме **feature
branch**: под каждую задачу своя ветка от `main`, потом слияние обратно. `HEAD` —
указатель на текущую позицию. Понимание «ветка = указатель на коммит» снимает
большинство непонимания Git.

**Аналогия.** История коммитов — как сохранёнки в игре, каждая ссылается на
предыдущую. Ветка — закладка, отмечающая, на каком сохранении ты сейчас; завести
новую закладку (ветку) ничего не стоит.

## Merge против rebase

Два способа **объединить** изменения одной ветки в другую — самый частый вопрос:

- **Merge** — создаёт **merge-коммит**, объединяющий истории двух веток. История
  **сохраняется как есть** (видно, что велась параллельная работа), но граф
  ветвится и может стать «ветвистым».
- **Rebase** — **переносит** коммиты ветки поверх другой, переписывая их как будто
  они делались последовательно. История становится **линейной и чистой**, но
  коммиты **переписываются** (новые хэши).

```text
Merge:   ...─C─────M    (M — merge-коммит, обе ветки видны)
              \   /
               D─E

Rebase:  ...─C─D'─E'    (D,E перенесены поверх C, линейно)
```

**Золотое правило rebase**: **не делать rebase публичных (запушенных, общих)
веток** — переписывание истории, которую видят другие, ломает их копии. Rebase —
для **локальной** уборки своих коммитов перед пушем; merge — для объединения общих
веток. Многие команды: rebase для актуализации feature-ветки от main (линейно),
merge (часто squash) для вливания в main.

**Аналогия.** Merge — подшить две папки документов вместе с пометкой «здесь
объединили» (видна история обеих). Rebase — переписать свои черновики набело, как
будто сразу писал по порядку (чисто, но это уже другие листы — нельзя переписывать
то, что другие уже скопировали).

## Отмена изменений: reset и revert

Отменять можно по-разному, и важно не перепутать:

- **`git revert <commit>`** — создаёт **новый коммит**, отменяющий изменения
  указанного. История **сохраняется**, ничего не переписывается — **безопасно для
  общих веток**.
- **`git reset <commit>`** — **сдвигает указатель** ветки назад, «забывая» коммиты.
  `--soft` (оставить изменения в индексе), `--mixed` (в рабочей директории),
  `--hard` (**удалить** изменения — опасно). Переписывает историю — **только для
  локальных** веток.

```bash
git revert abc123      # безопасно отменить коммит в общей ветке (новый коммит)
git reset --hard HEAD~1   # удалить последний коммит ЛОКАЛЬНО (потеря изменений!)
```

Правило: **в общей/запушенной ветке — `revert`** (не ломает чужую историю); в
**локальной** можно `reset`. Ещё полезное: **`cherry-pick`** — перенести
**конкретный коммит** из одной ветки в другую (например, хотфикс).

**Аналогия.** `revert` — дописать в журнал «операция X отменена» (запись о прошлом
осталась). `reset` — стереть последние страницы журнала (история переписана) —
нельзя, если по этим страницам уже работают другие.

## Конфликты и рабочие процессы

**Конфликт слияния** возникает, когда **одни и те же строки** изменены по-разному в
сливаемых ветках — Git не может решить сам и просит выбрать. Конфликт помечается в
файле (`<<<<<<<`, `=======`, `>>>>>>>`); нужно **вручную** отредактировать,
оставив правильный вариант, и закоммитить.

```text
<<<<<<< HEAD
ваш вариант
=======
вариант из другой ветки
>>>>>>> feature
```

**Рабочие процессы (workflows)**:

- **Trunk-based** — короткоживущие ветки, частые слияния в один `main`, флаги фич.
  Подходит для CI/CD и быстрых релизов.
- **Git Flow** — много долгоживущих веток (`develop`, `release`, `hotfix`).
  Сложнее, для релизов «версиями».

Большинство современных команд тяготеют к **trunk-based** (проще, быстрее, меньше
конфликтов от долгих веток). Главное — короткие ветки и частая синхронизация с main
снижают боль от конфликтов.

**Аналогия.** Конфликт — когда два редактора переписали один и тот же абзац
по-разному, и нужно решить, чей вариант оставить. Чем дольше ветки живут порознь
(редко синхронизируются), тем больше таких спорных абзацев накопится.

## Памятка для собеседования

- Git **распределённый**; история — цепочка коммитов, **ветка = указатель** на
  коммит (дёшево). Схема **feature branch**.
- **Merge** — merge-коммит, история сохраняется (ветвисто); **rebase** —
  линеаризует, **переписывает** коммиты. **Не rebase'ить публичные ветки**; rebase
  для локальной уборки, merge для общих.
- Отмена: **`revert`** (новый коммит, безопасно для общих веток) vs **`reset`**
  (сдвиг указателя, переписывает — только локально; `--hard` теряет изменения).
  `cherry-pick` — перенести один коммит.
- **Конфликт** — одни строки изменены по-разному, решать вручную. Workflows:
  **trunk-based** (короткие ветки, CI/CD) vs Git Flow.

## Частые ошибки в ответах

- Не знать золотое правило «не rebase'ить общие/запушенные ветки».
- Путать `revert` (безопасно, новый коммит) и `reset` (переписывает историю).
- Считать ветку «копией файлов», а не указателем на коммит.
- `git reset --hard` на общей ветке или для отмены чужих изменений.
