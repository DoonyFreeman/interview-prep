# Дженерики, Protocol и спецтипы

> Цель урока: освоить продвинутую типизацию — обобщённые типы (TypeVar/Generic),
> структурную типизацию (Protocol) и полезные спецтипы (Literal, Final, NewType).
> Эти инструменты дают точные, переиспользуемые типы; их знание выделяет на собесе.

## TypeVar и обобщённые функции

**Дженерик (обобщённый тип)** позволяет писать код, **работающий с любым типом, но
сохраняющий связь** между входом и выходом. Основа — **`TypeVar`**: переменная
типа, которая «запоминает» конкретный тип на месте вызова.

```python
from typing import TypeVar

T = TypeVar("T")

def first(items: list[T]) -> T:        # вернёт тот же тип, что внутри списка
    return items[0]

first([1, 2, 3])      # mypy знает: вернётся int
first(["a", "b"])     # знает: вернётся str
```

Без дженерика пришлось бы писать `-> Any` (теряя информацию) или дублировать
функцию под каждый тип. `TypeVar` связывает: «что вошло — то и выйдет». Можно
**ограничить** (`TypeVar("T", int, str)` — только эти) или задать **bound**
(`bound=Comparable` — подтипы). В Python 3.12+ есть более лаконичный синтаксис
`def first[T](items: list[T]) -> T`.

**Аналогия.** `TypeVar` — как универсальная форма для отливки, которая
**подстраивается под материал**: зальёшь сталь — получишь стальную деталь, зальёшь
бронзу — бронзовую; форма одна, а тип результата соответствует входу.

## Generic-классы

Свои **контейнеры/классы** делают обобщёнными через `Generic[T]` — тогда тип
содержимого параметризуется при использовании:

```python
from typing import Generic, TypeVar

T = TypeVar("T")

class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list[T] = []
    def push(self, item: T) -> None:
        self._items.append(item)
    def pop(self) -> T:
        return self._items.pop()

s: Stack[int] = Stack()
s.push(1)             # mypy следит: только int
```

`Stack[int]` и `Stack[str]` — один класс, но типизированный по-разному. Так
устроены `list[T]`, `dict[K, V]` в самом языке. Generic-классы дают
**переиспользуемые типобезопасные структуры**.

**Аналогия.** `Generic[T]` — как контейнер с настраиваемой этикеткой: одна и та же
коробка может быть «коробка для int» или «коробка для str», и приёмщик (mypy)
проверяет, что кладёшь правильное.

## Protocol: структурная типизация

**`Protocol`** (PEP 544) задаёт интерфейс **по структуре, а не по наследованию**:
тип подходит, если у него **есть нужные методы/атрибуты**, без явного `class X(...)`.
Это «статический duck typing» (перекликается с курсом ООП).

```python
from typing import Protocol

class Sized(Protocol):
    def __len__(self) -> int: ...

def total_size(items: list[Sized]) -> int:
    return sum(len(x) for x in items)

# любой объект с __len__ подходит — список, строка, своя коллекция,
# БЕЗ наследования от Sized
```

Отличие от ABC: ABC требует **явного наследования** (номинально), Protocol —
только **совпадения формы** (структурно), проверяется mypy. Protocol идеален для
типизации duck typing и **сторонних** классов, которые вы не можете заставить
наследоваться. `@runtime_checkable` добавляет `isinstance`-проверку по наличию
методов.

**Аналогия.** Protocol — объявление «нужен тот, кто умеет считать длину
(`__len__`)»: подходит любой, кто умеет, независимо от «происхождения» (класса) — как
наём по навыку, а не по диплому.

## Literal, Final, NewType

Точечные спецтипы для строгости:

- **`Literal`** — допускает только **конкретные значения**: `Literal["asc",
  "desc"]` — параметр может быть только этими строками (mypy поймает опечатку).
- **`Final`** — **константа**, которую нельзя переприсваивать: `MAX: Final = 100`.
- **`NewType`** — создаёт **различимый подтип** для семантики: `UserId =
  NewType("UserId", int)` — в рантайме это int, но mypy не даст перепутать `UserId`
  с обычным `int` или `OrderId`.

```python
from typing import Literal, Final, NewType

def sort(order: Literal["asc", "desc"]) -> None: ...
sort("up")        # mypy: ошибка, не из допустимых

UserId = NewType("UserId", int)
def get(uid: UserId) -> User: ...
get(5)            # mypy: ошибка — нужен UserId, а не просто int
```

Эти типы делают сигнатуры **самодокументируемыми** и ловят ошибки на этапе
проверки: невалидное значение (`Literal`), случайную перезапись (`Final`),
путаницу одинаковых по представлению, но разных по смыслу id (`NewType`).

**Аналогия.** `Literal` — выпадающий список вместо свободного поля (только
разрешённые варианты). `NewType` — как разные по цвету ключи одинаковой формы:
физически похожи (оба int), но систему не обманешь — от чужой двери не подойдёт.

## Памятка для собеседования

- **`TypeVar`** — обобщённые функции, **сохраняющие связь** вход↔выход (`first(list[T])
  -> T`); можно ограничить/`bound`. **`Generic[T]`** — обобщённые классы
  (типобезопасные контейнеры).
- **`Protocol`** — **структурная** типизация (нужны методы, не наследование);
  «статический duck typing», для сторонних типов; `@runtime_checkable` для
  isinstance.
- Спецтипы: **`Literal`** (только заданные значения), **`Final`** (константа),
  **`NewType`** (различимый подтип — не перепутать `UserId` и `int`). Делают
  сигнатуры строгими и самодокументируемыми.

## Частые ошибки в ответах

- Писать `-> Any` вместо `TypeVar`, теряя связь типов вход/выход.
- Путать Protocol (структурно) и ABC (наследование).
- Не знать про `Literal`/`NewType` для строгих значений и семантических id.
- Думать, что `NewType` создаёт реальный класс (в рантайме это исходный тип).
