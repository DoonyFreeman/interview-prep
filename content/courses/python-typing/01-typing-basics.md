# Основы типизации

> Цель урока: понять, как работают аннотации типов в Python — что они **не влияют
> на рантайм**, как записывать Optional/Union и коллекции. Типизация — стандарт в
> современных проектах (FastAPI, Pydantic), и на собесе спрашивают «что дают
> аннотации» и «как типизировать Optional».

## Аннотации не влияют на рантайм

Главное, что нужно понять: **аннотации типов в Python — подсказки, а не
принуждение**. Интерпретатор их **не проверяет** во время выполнения и **не
приводит** значения по ним. Они нужны для **статических анализаторов** (mypy,
pyright), **IDE** (автодополнение, навигация) и **читаемости**.

```python
def greet(name: str) -> str:
    return "Hi " + name

greet(42)        # в рантайме НЕ упадёт по типу! (упадёт уже на конкатенации)
```

Это «**gradual typing**» (постепенная типизация): можно типизировать часть кода, а
часть оставить без аннотаций — Python всё запустит. Аннотации хранятся в
`__annotations__` и доступны интроспекции, но сам Python ими **не руководствуется**.
Поэтому говорить «Python стал статически типизированным» неверно — он остаётся
динамическим, а типы это **опциональный слой** поверх.

**Аналогия.** Аннотации — как комментарии-указатели на чертеже «здесь должна быть
стальная деталь»: рабочий-чертёжник (mypy) проверит соответствие заранее, но сам
станок (интерпретатор) выточит что подадут, не сверяясь с подписью.

## Базовые аннотации

Аннотируют параметры, возвращаемые значения и переменные:

```python
age: int = 30
name: str = "Аня"
prices: list[float] = [1.0, 2.5]
mapping: dict[str, int] = {"a": 1}
pair: tuple[int, str] = (1, "x")

def total(items: list[int]) -> int:
    return sum(items)
```

С Python 3.9+ для коллекций используют **встроенные дженерики** напрямую
(`list[int]`, `dict[str, int]`), без импорта `List`/`Dict` из `typing` (старый
стиль). Параметризация говорит, **что внутри** контейнера: `list[int]` — список
целых.

**Аналогия.** Базовая аннотация — ярлык на коробке: не просто «коробка» (`list`), а
«коробка с гайками M6» (`list[int]`) — сразу понятно содержимое и не ошибёшься,
что туда класть.

## Optional, Union и None

Очень частый случай — значение, которое **может быть `None`** (нет результата,
необязательный параметр):

- **`X | None`** (3.10+) или **`Optional[X]`** — «X или None».
- **`A | B`** или **`Union[A, B]`** — «одно из нескольких типов».

```python
def find_user(id: int) -> User | None:    # вернёт User или None
    ...

def parse(x: int | str) -> int:           # принимает int или str
    ...

name: Optional[str] = None                 # то же, что str | None
```

Важно: **`Optional[X]` означает именно «X или None», а не «необязательный
параметр»** — это частая путаница. Необязательность задаётся **значением по
умолчанию**, а `Optional` — про допустимость `None` в типе. Современный синтаксис —
`X | None` (PEP 604), читаемее `Optional`. `Any` — «отключить проверку для этого
места» (любой тип), использовать осознанно, т.к. он «заражает» и теряет пользу
типизации.

**Аналогия.** `User | None` — как графа в анкете «телефон (или прочерк, если нет)»:
тип честно говорит, что значения может не быть, и заставляет вас обработать случай
`None`, а не забыть про него.

## Памятка для собеседования

- Аннотации **не влияют на рантайм** (Python их не проверяет/не приводит) — это
  подсказки для **mypy/IDE/читаемости**. **Gradual typing**: типизировать можно
  частично.
- Коллекции (3.9+): встроенные дженерики `list[int]`, `dict[str, int]`,
  `tuple[int, str]` (вместо `List`/`Dict` из `typing`).
- **`X | None`** (3.10+) / **`Optional[X]`** — «X или None» (НЕ «необязательный
  параметр»!); **`A | B`** / **`Union`** — несколько типов; `Any` — отключает
  проверку (осознанно).

## Частые ошибки в ответах

- Думать, что аннотации проверяются в рантайме или приводят типы.
- Считать `Optional[X]` пометкой «необязательный аргумент» (это «X или None»).
- Использовать старый `List[int]` из typing вместо `list[int]` (3.9+) без причины.
- Злоупотреблять `Any`, обнуляя пользу типизации.
