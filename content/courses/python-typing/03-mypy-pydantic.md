# mypy и валидация в рантайме

> Цель урока: понять, что даёт статическая проверка mypy и где проходит граница
> между «типы для проверки» и «валидация данных в рантайме» (Pydantic). Это
> практический срез: статические типы не заменяют валидацию входных данных, и
> наоборот.

## mypy: статическая проверка

**mypy** — статический анализатор: он читает аннотации и **находит ошибки типов
ДО запуска** программы, не выполняя её. Это ловит целый класс багов (передали не
тот тип, забыли обработать `None`, опечатка в поле) на этапе разработки/CI.

```python
def half(x: int) -> float:
    return x / 2

half("10")        # mypy: error — Argument has incompatible type "str"
# программа даже не запускалась, ошибка найдена статически
```

Ключевые идеи:

- **Постепенность**: можно вводить типы инкрементально; нетипизированный код mypy
  по умолчанию пропускает.
- **Строгий режим** (`--strict`) требует аннотаций везде и запрещает неявный
  `Any` — для нового кода полезно.
- **`# type: ignore`** — подавить конкретную ошибку (когда mypy не прав или тип
  сложный); использовать точечно, не как способ «заглушить всё».

Польза mypy растёт с размером проекта: рефакторинг безопаснее (переименовал поле —
mypy показал все места), меньше «глупых» багов. Граница: mypy проверяет **только
то, что видит статически**, и **ничего не делает в рантайме**.

**Аналогия.** mypy — корректор, вычитывающий текст до публикации: ловит
грамматические ошибки заранее. Но он проверяет рукопись, а не то, что реально
скажут вслух на сцене (рантайм) — данные извне он не видит.

## Типы в рантайме

Иногда типы нужны **во время выполнения** — для фреймворков, сериализации,
DI. Инструменты интроспекции:

- **`typing.get_type_hints(obj)`** — получить аннотации функции/класса как словарь
  (с разрешением строковых/отложенных аннотаций).
- **`typing.get_args` / `get_origin`** — разобрать сложный тип: для `list[int]`
  origin = `list`, args = `(int,)`; для `int | None` — достать варианты.

```python
from typing import get_type_hints, get_args, get_origin

def f(x: int, y: list[str]) -> None: ...
get_type_hints(f)            # {'x': int, 'y': list[str], 'return': None}
get_origin(list[int])        # list
get_args(int | None)         # (int, NoneType)
```

Именно на этой интроспекции построены FastAPI и Pydantic: они **читают аннотации в
рантайме** и по ним строят валидацию/документацию. То есть аннотации сами по себе
пассивны, но фреймворк может их **прочитать и использовать**.

**Аналогия.** Интроспекция типов — как прочитать этикетку на детали уже на конвейере
(в рантайме): сам Python этикетку не читает, но робот-сборщик (FastAPI/Pydantic)
читает и действует по ней.

## Типы против валидации (Pydantic)

Критичное разграничение, которое любят на собесе: **статические типы и валидация
данных — разные вещи**.

- **Аннотации + mypy** проверяют **код** на этапе разработки. Но в рантайме, когда
  приходит **внешний JSON**, никакой mypy его не проверит — данные могут не
  соответствовать аннотациям.
- **Pydantic** валидирует **данные в рантайме**: проверяет и приводит входные
  значения к объявленным типам, бросает ошибку при несоответствии. Это нужно на
  **границе системы** (запросы, конфиги, ответы внешних API).

```python
class User(BaseModel):
    id: int
    name: str

User(id="42", name="A")     # Pydantic приведёт "42" → 42 (рантайм-валидация)
User(id="abc", name="A")    # рантайм-ошибка валидации — то, что mypy не поймает
```

Вывод: **mypy — для внутренней корректности кода, Pydantic — для проверки внешних
данных**. Они дополняют друг друга: типы ловят баги программиста, Pydantic — грязные
данные пользователя. Pydantic v2 (ядро на Rust) делает рантайм-валидацию быстрой,
поэтому её не страшно ставить на каждый запрос (см. курс FastAPI).

**Аналогия.** mypy — проверка чертежей инженером в офисе (всё ли логично в проекте).
Pydantic — контроль качества деталей, **физически приходящих** от поставщика на склад
(а вдруг прислали брак). Чертёж может быть верным, но входной материал всё равно надо
проверять.

## Памятка для собеседования

- **mypy** — статическая проверка типов **до запуска**; ловит баги на CI,
  безопасит рефакторинг. Постепенная типизация, `--strict`, точечный
  `# type: ignore`. В рантайме **ничего не делает**.
- Типы в рантайме: **`get_type_hints`**, **`get_args`/`get_origin`** — интроспекция
  аннотаций; на ней построены FastAPI/Pydantic.
- **Типы (mypy) ≠ валидация данных (Pydantic)**: mypy проверяет **код**, Pydantic
  валидирует **внешние данные в рантайме** (приводит/отвергает). Дополняют друг
  друга: баги программиста vs грязный ввод.

## Частые ошибки в ответах

- Думать, что mypy/аннотации проверяют данные в рантайме (нет — это Pydantic).
- Считать, что Pydantic-валидация не нужна, раз есть аннотации и mypy.
- Не знать про интроспекцию типов (`get_type_hints`) как основу FastAPI/Pydantic.
- `# type: ignore` на весь файл вместо точечного подавления.
