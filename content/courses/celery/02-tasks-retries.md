# Задачи, вызов, ретраи и идемпотентность

> Цель урока: научиться определять и вызывать задачи, настраивать ретраи и понять,
> почему **идемпотентность критична** для надёжной обработки. «Что будет, если
> задача выполнится дважды» — ключевой вопрос про распределённые задачи.

## Определение и вызов задач

Задача Celery — функция, помеченная декоратором `@task` (или `@app.task`). Вызывают
её **не напрямую**, а через методы постановки в очередь:

- **`delay(*args)`** — простой способ: `send_email.delay(user_id)`.
- **`apply_async(args=..., ...)`** — то же, но с **настройками** (задержка `countdown`,
  очередь, приоритет, время выполнения `eta`, retry-политика).

```python
@app.task
def send_email(user_id):
    user = get_user(user_id)
    smtp.send(user.email, ...)

# вызов из веба — НЕ send_email(1), а:
send_email.delay(1)                              # поставить в очередь
send_email.apply_async(args=[1], countdown=60)   # выполнить через 60 секунд
```

Прямой вызов `send_email(1)` выполнил бы её **синхронно в веб-процессе** (мимо
Celery) — частая ошибка. Аргументы задачи **сериализуются** (обычно JSON) для
передачи через брокер, поэтому передавать надо **простые данные (id), а не объекты**
(ORM-модели, соединения не сериализуются). Правило: передавай `user_id`, а внутри
задачи загружай объект заново.

**Аналогия.** `delay` — бросить заявку в ящик и уйти; прямой вызов функции — сделать
работу самому на месте (зачем тогда Celery). А в заявке пишут номер заказа (id), а
не везут весь товар (объект) — товар возьмут на складе по номеру.

## Ретраи

Фоновые задачи часто **ненадёжны** (внешний API недоступен, таймаут сети). Celery
умеет **повторять** упавшую задачу — это одна из главных причин его использовать.

```python
@app.task(bind=True, max_retries=3, default_retry_delay=60)
def call_api(self, payload):
    try:
        return external_api.post(payload)
    except TimeoutError as exc:
        raise self.retry(exc=exc)        # повторить (до max_retries раз)
```

Настройки: `max_retries` (сколько раз), `retry_delay`/`countdown` (пауза между),
и важный приём — **экспоненциальный backoff** (`retry_backoff=True`): каждая
следующая попытка ждёт дольше, чтобы не добивать падающий сервис. Можно автоматом
ретраить на определённые исключения (`autoretry_for`). Ретраи превращают
«разовую ненадёжную операцию» в **устойчивую**.

**Аналогия.** Ретрай с backoff — как перезванивать по занятому номеру: не долбить
каждую секунду (добьёшь линию), а ждать всё дольше между попытками, давая шанс
дозвониться.

## Идемпотентность

**Критичнейшая тема.** В распределённых очередях задача **может выполниться больше
одного раза**: воркер упал после работы, но до подтверждения; сработал ретрай;
сообщение доставилось дважды. Поэтому задачи должны быть **идемпотентными** —
**повторное выполнение не должно ломать состояние или дублировать эффект**.

```python
# ПЛОХО: ретрай/дубль спишет деньги дважды
@app.task
def charge(order_id):
    payment.charge(order)          # не идемпотентно!

# ХОРОШО: проверяем, не сделано ли уже
@app.task
def charge(order_id):
    order = get_order(order_id)
    if order.status == "paid":     # уже оплачено — выходим
        return
    payment.charge(order, idempotency_key=order_id)  # ключ идемпотентности
    order.status = "paid"
```

Приёмы идемпотентности: **проверка состояния** перед действием («уже сделано?»),
**ключи идемпотентности** (внешний API не повторит платёж с тем же ключом),
**уникальные ограничения** в БД (повторная вставка упадёт/проигнорируется). Это
прямо связано с «мифом exactly-once» из следующего урока: гарантировать «ровно один
раз» доставку нельзя, поэтому идемпотентность — **обязательное** требование к
задачам.

**Аналогия.** Идемпотентность — как выключатель «выключить свет»: нажал повторно —
ничего не сломалось, свет всё так же выключен. А «снять деньги» без защиты — как
«добавить лампу»: каждое нажатие добавляет новую, и повтор приводит к беде.

## Памятка для собеседования

- Задача — `@task`-функция, вызывается через **`delay()`** / **`apply_async()`**
  (countdown, очередь, eta), **не напрямую** (иначе синхронно в веб-процессе).
  Аргументы **сериализуются** → передавать **id, а не объекты**.
- **Ретраи**: `max_retries`, пауза, **экспоненциальный backoff** (`retry_backoff`),
  `autoretry_for`; превращают ненадёжную операцию в устойчивую.
- **Идемпотентность обязательна**: задача может выполниться **>1 раза** (ретрай,
  падение до ack, дубль). Приёмы: проверка состояния, ключи идемпотентности,
  уникальные ограничения БД.

## Частые ошибки в ответах

- Вызывать задачу напрямую (`task()`) вместо `task.delay()`.
- Передавать в задачу ORM-объекты/соединения вместо id (не сериализуются).
- Не делать задачи идемпотентными, считая, что задача выполнится ровно один раз.
- Ретраить без backoff, добивая падающий сервис.
