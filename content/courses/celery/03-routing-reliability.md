# Маршрутизация, расписание и надёжность

> Цель урока: разобрать управление потоком задач (очереди, приоритеты, расписание
> через beat) и тонкие гарантии надёжности — `acks_late`, visibility timeout и миф
> «exactly once». Это «сеньорная» часть Celery, отличающая тех, кто эксплуатировал
> очереди под нагрузкой.

## Очереди, маршрутизация и приоритеты

По умолчанию все задачи идут в одну очередь, но реальные системы **разделяют**
потоки: быстрые задачи не должны застревать за медленными, у разных задач —
разные требования.

- **Несколько очередей**: например, `emails`, `reports`, `default`. Воркеры
  подписываются на нужные очереди, и можно выделить **отдельные воркеры под тяжёлые
  задачи**, чтобы они не блокировали лёгкие.
- **Маршрутизация** (`task_routes`) — какую задачу в какую очередь направлять.
- **Rate limits** — ограничить частоту задач (не перегружать внешний API).
- **Приоритеты** — поддерживаются (особенно в RabbitMQ), но работают не идеально;
  чаще разделение делают **очередями**, а не приоритетами.

```python
app.conf.task_routes = {
    "tasks.send_email": {"queue": "emails"},
    "tasks.generate_report": {"queue": "reports"},  # тяжёлые — отдельно
}
```

Смысл — **изоляция и контроль**: быстрый отклик для лёгких задач, отдельные ресурсы
для тяжёлых, защита внешних сервисов от перегрузки.

**Аналогия.** Очереди — как разные кассы в супермаркете: экспресс-касса для пары
товаров (лёгкие задачи), обычные для больших тележек (тяжёлые отчёты). Без
разделения человек с одним товаром стоял бы за тем, у кого полная тележка.

## Расписание: Celery Beat

Для **периодических** задач (по расписанию, как cron) есть **Celery Beat** —
отдельный планировщик, который по времени **ставит задачи в очередь**, а выполняют
их обычные воркеры.

```python
app.conf.beat_schedule = {
    "cleanup-every-hour": {
        "task": "tasks.cleanup",
        "schedule": 3600.0,            # каждый час (или crontab(...))
    },
}
```

Применения: ночные отчёты, очистка старых данных, периодическая синхронизация,
напоминания. Важный нюанс эксплуатации: **Beat должен быть запущен в одном
экземпляре** (иначе расписание задвоится) — это единая точка, ставящая
периодические задачи, тогда как воркеров-исполнителей много.

**Аналогия.** Beat — как будильник/диспетчер, который по часам бросает заявки в
общий ящик («пора делать уборку»), а выполняют их свободные сотрудники (воркеры).
Будильник нужен один, иначе уборку запустят дважды.

## acks_late и visibility timeout

Тонкая, но важная механика надёжности:

- **Подтверждение (ack)**: воркер, забрав задачу из брокера, должен её
  **подтвердить**. По умолчанию ack происходит **сразу при получении** — если
  воркер упадёт во время выполнения, задача **потеряется**.
- **`acks_late=True`** — подтверждать **после успешного выполнения**. Тогда при
  падении воркера задача **вернётся в очередь** и выполнится снова (другим
  воркером). Это повышает надёжность ценой возможного **повторного выполнения** —
  отсюда снова требование **идемпотентности**.
- **Visibility timeout** (для Redis-брокера) — время, на которое задача «невидима»
  для других воркеров после выдачи. Если воркер не подтвердил за это время, задача
  снова станет видимой. Слишком маленький timeout → **дубли** (долгая задача ещё
  идёт, а её уже выдали повторно).

```python
@app.task(acks_late=True)        # ack после выполнения → не потеряем при падении
def important_job(): ...
```

**Аналогия.** Ранний ack — расписаться за посылку, ещё не донеся её до двери (упал
по дороге — посылка потеряна, по бумагам «доставлено»). `acks_late` — расписаться
только после фактической доставки: упал — посылку выдадут другому курьеру (но есть
риск, что довезут дважды).

## Миф exactly-once и мониторинг

Главный тезис надёжности: **«exactly once» (ровно один раз) доставки в
распределённых системах гарантировать практически невозможно**. Реальные гарантии:

- **At-most-once** — не более одного раза (можно потерять).
- **At-least-once** — не менее одного раза (можно **продублировать**) — то, что
  даёт Celery с `acks_late`.

Поскольку дубли возможны, **«exactly once» достигается не доставкой, а
идемпотентностью обработки**: at-least-once доставка + идемпотентные задачи =
эффект «как будто ровно один раз». Это и есть правильный ответ на вопрос про
exactly-once.

Мониторинг: **Flower** — веб-панель для Celery (видеть задачи, воркеров, ошибки,
ретраи). Без мониторинга очередь — чёрный ящик: не видно зависших задач, растущих
очередей, падений.

**Аналогия.** Гнаться за «ровно один раз» в доставке — как пытаться гарантировать,
что письмо дойдёт строго один раз через ненадёжную почту. Реально проще принять, что
может прийти дважды (at-least-once), и сделать так, чтобы дубликат не навредил
(идемпотентность) — например, по номеру письма понять «это уже обрабатывали».

## Памятка для собеседования

- **Очереди** разделяют потоки (лёгкие/тяжёлые), `task_routes` маршрутизирует,
  rate limits защищают внешние сервисы; приоритеты слабее разделения очередями.
- **Celery Beat** — планировщик периодических задач (cron-like), ставит их в
  очередь; **запускать в одном экземпляре** (иначе задвоение).
- **`acks_late`** — ack после выполнения (не потерять при падении, но возможен
  **повтор** → идемпотентность); **visibility timeout** мал → дубли.
- **Exactly-once недостижим**: реально **at-least-once** + **идемпотентность** =
  эффект «ровно один раз». Мониторинг — **Flower**.

## Частые ошибки в ответах

- Утверждать, что Celery гарантирует exactly-once доставку.
- Не знать про `acks_late` и его связь с потерей/дублированием задач.
- Запускать несколько экземпляров Beat (задвоение периодических задач).
- Не разделять задачи по очередям (тяжёлые блокируют лёгкие) и не мониторить
  (Flower).
