# Кэширование и сценарии Redis

> Цель урока: разобрать главное применение Redis — кэширование: паттерны
> (cache-aside), стратегии вытеснения, инвалидация и защита от cache stampede.
> «Как вы кэшируете» и «что такое cache-aside» — частые практические вопросы.

## Сценарии применения

Redis закрывает множество задач, где нужна **скорость и временное хранилище**:

- **Кэш** — самое частое: держать результаты дорогих запросов/вычислений рядом с
  приложением.
- **Сессии** — хранилище пользовательских сессий (быстро, с TTL).
- **Rate limiting** — счётчики запросов на пользователя (`INCR` + `EXPIRE`).
- **Лидерборды/рейтинги** — sorted sets.
- **Очереди задач** — lists/streams (брокер для Celery).
- **Распределённые блокировки** — координация между процессами.

Общее у всех — данные **временные или производные**, скорость важнее строгой
надёжности (хотя персистентность есть). Redis не заменяет основную БД, а
**дополняет** её как быстрый слой.

**Аналогия.** Redis — как рабочий стол рядом с архивом (основной БД): то, что нужно
прямо сейчас и часто, держишь под рукой на столе (в RAM), а не бегаешь в архив
каждый раз. Стол не заменяет архив, но ускоряет работу.

## Cache-aside и стратегии записи

Самый распространённый паттерн — **cache-aside (lazy loading)**: приложение само
управляет кэшем.

```python
def get_user(uid):
    cached = redis.get(f"user:{uid}")
    if cached:
        return deserialize(cached)        # cache hit — быстро
    user = db.get_user(uid)               # cache miss — идём в БД
    redis.set(f"user:{uid}", serialize(user), ex=3600)   # кладём с TTL
    return user
```

Логика: **проверить кэш → если нет (miss), взять из БД и положить в кэш с TTL**.
Плюс — в кэш попадает только реально запрашиваемое; минус — первый запрос медленный
(miss), и возможна рассинхронизация с БД. Альтернативы записи:

- **Write-through** — писать в кэш и БД **одновременно** (кэш всегда свежий, запись
  медленнее).
- **Write-behind (write-back)** — писать в кэш сразу, в БД **асинхронно** позже
  (быстро, но риск потери при сбое).

Cache-aside — выбор по умолчанию для чтений.

**Аналогия.** Cache-aside — как заглянуть сначала в записную книжку (кэш), и только
если там пусто — позвонить в справочную (БД) и записать ответ в книжку на будущее.

## Инвалидация и вытеснение

Две вечные проблемы кэша:

- **Инвалидация** — когда данные в БД изменились, кэш **устарел**. Решения: **TTL**
  (само протухнет через время — простой, но возможна короткая рассинхронизация);
  **явная инвалидация** (при изменении данных удалить/обновить ключ —
  точно, но нужно не забыть везде). «В программировании две сложные вещи: инвалидация
  кэша и именование» — это про реальную боль.
- **Вытеснение (eviction)** — память не бесконечна; когда кэш заполнен, Redis по
  политике **`maxmemory-policy`** выкидывает ключи: **LRU** (давно не
  использованные), **LFU** (редко используемые), **TTL-based**, или отказывает в
  записи (`noeviction`). Для кэша обычно `allkeys-lru`.

```text
maxmemory 2gb
maxmemory-policy allkeys-lru     # при заполнении выкидывать давно не нужные
```

**Аналогия.** Инвалидация — следить, чтобы запись в книжке не устарела (вычеркнуть,
когда факт изменился). Вытеснение — стол ограничен: когда заполнился, убираешь то,
чем давно не пользовался (LRU), освобождая место для нового.

## Cache stampede

**Cache stampede (thundering herd)** — опасный сценарий: популярный ключ
**протухает**, и **сразу множество** запросов получают miss и **одновременно
ломятся в БД** за одним и тем же, перегружая её.

Защита:

- **Блокировка/единый пересчёт** — только один запрос пересчитывает значение
  (берёт лок), остальные ждут или отдают старое.
- **Probabilistic early expiration** — обновлять кэш чуть **раньше** TTL с
  вероятностью, размазывая пересчёт.
- **Stale-while-revalidate** — отдавать устаревшее значение, пока в фоне идёт
  обновление.

Понимание stampede и хотя бы одного способа защиты отличает «знаю про кэш» от
«эксплуатировал кэш под нагрузкой».

**Аналогия.** Stampede — как в магазине закончился ходовой товар, и толпа разом
ринулась на склад за ним, создав давку. Защита — пустить за товаром одного
кладовщика (лок), а остальным сказать «сейчас принесём» или отдать что есть.

## Памятка для собеседования

- Сценарии: **кэш**, сессии, **rate limiting** (`INCR`+`EXPIRE`), лидерборды,
  очереди, блокировки. Redis **дополняет** основную БД, не заменяет.
- **Cache-aside**: проверить кэш → miss → взять из БД → положить с TTL. Альтернативы
  записи: **write-through** (синхронно в кэш+БД), **write-behind** (в БД async).
- **Инвалидация**: TTL (само) vs явное удаление ключа. **Вытеснение** при
  `maxmemory`: **LRU**/LFU/TTL (`allkeys-lru` для кэша).
- **Cache stampede** — протух популярный ключ → лавина в БД; защита: лок/единый
  пересчёт, early expiration, stale-while-revalidate.

## Частые ошибки в ответах

- Не знать паттерн cache-aside или путать write-through и write-behind.
- Игнорировать инвалидацию (отдавать устаревшие данные) или не ставить TTL.
- Не знать про политики вытеснения (LRU/LFU) при заполнении памяти.
- Не слышать про cache stampede и способы защиты.
