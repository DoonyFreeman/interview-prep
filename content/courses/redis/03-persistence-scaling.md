# Персистентность, транзакции и масштабирование

> Цель урока: понять, как Redis сохраняет данные на диск (RDB/AOF), как работают
> его «транзакции» и Lua-скрипты, и как Redis масштабируют (репликация, Sentinel,
> Cluster). Это вопросы «теряет ли Redis данные» и «как сделать Redis
> отказоустойчивым».

## Персистентность: RDB и AOF

Хотя Redis держит данные в RAM, он умеет **сохранять их на диск**, чтобы пережить
перезапуск. Два механизма:

- **RDB (snapshot)** — периодический **снимок** всего датасета в один файл.
  Компактный, быстрый рестарт, минимальное влияние на производительность. Минус —
  при сбое **теряются изменения** с момента последнего снимка (например, последние
  5 минут).
- **AOF (Append Only File)** — журнал **каждой записывающей команды**. Надёжнее
  (можно терять максимум 1 секунду при `everysec`), но файл больше и рестарт
  медленнее (проигрывание команд).

```text
RDB:  снимок раз в N минут — компактно, но возможна потеря последних данных
AOF:  лог всех команд — надёжнее, но больше и медленнее восстановление
```

На практике часто **включают оба**: AOF для надёжности + RDB для быстрых бэкапов.
Выбор — это **trade-off надёжность ↔ производительность/размер**. Важно понимать:
Redis **может** быть персистентным, но как кэш его часто гоняют **без**
персистентности (данные восстановимы из БД).

**Аналогия.** RDB — делать фотографию всей доски раз в час (компактно, но что
написали после — потеряется при сбое). AOF — записывать каждое изменение на доске в
блокнот (надёжно восстановить, но блокнот толстый).

## Транзакции и Lua

У Redis есть **транзакции** через `MULTI`/`EXEC`: команды между ними ставятся в
очередь и **выполняются последовательно как единый блок**, без вклинивания других
клиентов (благодаря однопоточности). Но это **не ACID-транзакции** в смысле SQL:
**нет отката** — если команда ошибётся, остальные всё равно выполнятся.

```text
MULTI
INCR counter
INCR counter
EXEC          # обе команды выполнятся атомарно как блок
```

`WATCH` добавляет **оптимистичную блокировку** (отменить транзакцию, если ключ
изменился) — для безопасного read-modify-write.

Мощнее — **Lua-скрипты** (`EVAL`): скрипт выполняется **атомарно целиком** на
сервере, что позволяет реализовать сложную логику «прочитать-проверить-записать» без
гонок и round-trip'ов. Так делают надёжные счётчики, rate limiters, распределённые
локи. Но долгий скрипт **блокирует сервер** (однопоточность!).

**Аналогия.** `MULTI/EXEC` — отдать кассиру список покупок, который он пробьёт
подряд без перерыва (но если один товар без цены — остальные всё равно пробьются,
отката нет). Lua — дать кассиру готовую инструкцию, которую он выполнит целиком, ни
на кого не отвлекаясь.

## Pub/Sub и Streams

Два способа обмена сообщениями:

- **Pub/Sub** — публикация в **канал**, все подписчики получают сообщение **в
  реальном времени**. Но это **fire-and-forget**: если подписчик offline — сообщение
  **потеряно** (нет хранения). Для уведомлений, где потеря допустима.
- **Streams** — append-only **лог** сообщений с хранением, **consumer groups** и
  подтверждениями (ack). Сообщения **не теряются**, можно перечитать, распределить
  между воркерами. Это надёжная очередь (ближе к Kafka).

Выбор: мгновенные эфемерные уведомления → Pub/Sub; надёжная очередь задач/событий →
Streams.

**Аналогия.** Pub/Sub — радиоэфир: кто слушает сейчас — услышит, опоздавшие
пропустят. Streams — записанный подкаст с историей: можно прийти позже, отметить, что
прослушал, и распределить эпизоды между слушателями.

## Масштабирование: репликация, Sentinel, Cluster

Три уровня масштабирования и отказоустойчивости:

- **Репликация** — реплики (read-only копии) синхронизируются с мастером. Дают
  **масштабирование чтения** и резервную копию. Но при падении мастера переключение
  **вручную**.
- **Sentinel** — система **автоматического failover**: следит за мастером и при
  его падении **автоматически** назначает реплику новым мастером. Высокая
  доступность без шардирования.
- **Cluster** — **шардирование**: данные распределяются по нескольким узлам по
  хэш-слотам (16384 слота). Даёт горизонтальное масштабирование **и памяти, и
  пропускной способности** за пределы одного сервера, плюс отказоустойчивость.

```text
Репликация: чтение масштабируется, failover ручной
Sentinel:   авто-failover (HA), данные целиком на каждом мастере
Cluster:    шардирование данных по узлам (масштаб памяти+нагрузки)
```

Выбор: нужно больше **чтения/HA** → репликация + Sentinel; данные **не влезают на
один сервер** или нужна огромная пропускная способность → Cluster.

**Аналогия.** Репликация — копии справочника в разных кабинетах (читать удобно,
оригинал один). Sentinel — дежурный, который при поломке главного справочника сам
назначает главным один из дубликатов. Cluster — разделить огромный справочник по
буквам между зданиями (А-К здесь, Л-Я там).

## Памятка для собеседования

- Персистентность: **RDB** (снимки — компактно, потеря последних данных при сбое)
  vs **AOF** (журнал команд — надёжнее, больше/медленнее); часто **оба**. Как кэш —
  можно без персистентности.
- **`MULTI/EXEC`** — блок команд атомарно, **но без отката** (не ACID); `WATCH` —
  оптимистичная блокировка; **Lua** (`EVAL`) — атомарная сложная логика (долгий
  скрипт блокирует сервер).
- **Pub/Sub** — realtime, fire-and-forget (потеря при offline); **Streams** —
  надёжная очередь с хранением и consumer groups.
- Масштаб: **репликация** (чтение/копия), **Sentinel** (авто-failover/HA),
  **Cluster** (шардирование данных по узлам).

## Частые ошибки в ответах

- Думать, что Redis всегда теряет данные (есть RDB/AOF) или, наоборот, что он
  безусловно надёжен как основная БД.
- Считать `MULTI/EXEC` полноценной ACID-транзакцией с откатом.
- Путать Pub/Sub (теряет при offline) и Streams (хранит, ack).
- Путать Sentinel (failover, данные целиком) и Cluster (шардирование).
