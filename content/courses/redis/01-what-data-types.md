# Redis: что это и типы данных

> Цель урока: понять, почему Redis такой быстрый (in-memory, однопоточный) и какие
> у него структуры данных. Это основа: «почему Redis быстрый» и «какие типы данных
> в Redis» — стартовые вопросы, а понимание однопоточности объясняет многое
> дальше.

## Что такое Redis и почему он быстрый

**Redis** — это **in-memory** хранилище данных типа «ключ-значение», используемое
как кэш, брокер, хранилище сессий. Его скорость (сотни тысяч операций в секунду,
задержки в микросекунды) объясняется тремя вещами:

- **Данные в оперативной памяти**, а не на диске — нет медленных дисковых операций
  на каждый запрос.
- **Однопоточная** модель обработки команд — нет блокировок, переключений
  контекста, гонок; команды выполняются **по одной, атомарно**.
- Эффективные структуры данных и простой протокол.

```text
Redis: всё в RAM + одна команда за раз → предсказуемо быстро
```

**Важное следствие однопоточности**: каждая команда **атомарна** (не прервётся
посередине), но **долгая команда блокирует всё** — например, `KEYS *` на большой
базе или тяжёлый Lua-скрипт остановят обслуживание остальных клиентов. Поэтому
избегают «тяжёлых» команд на проде.

**Аналогия.** Redis — как гениальный кассир-одиночка с идеальной памятью: держит всё
в голове (RAM) и обслуживает по одному, но молниеносно. Минус — если один клиент
займёт его надолго (тяжёлая команда), очередь встанет.

## Основные типы данных

Redis — не просто «строка→строка», а **сервер структур данных**. Ключ —строка, а
значение — одна из структур:

- **Strings** — строки/числа/байты; счётчики (`INCR`), кэш значений, флаги.
- **Hashes** — словарь полей (объект: профиль пользователя как hash).
- **Lists** — связные списки; очереди (`LPUSH`/`RPOP`), стек, последние N.
- **Sets** — множества уникальных; теги, уникальные посетители, операции
  пересечения/объединения.
- **Sorted Sets (ZSet)** — множество с **числовым score**, всегда отсортированное;
  **лидерборды**, очереди с приоритетом, ranged-запросы по score.

```text
SET user:1:name "Аня"          # string
HSET user:1 name "Аня" age 30  # hash (объект)
LPUSH queue task1              # list (очередь)
SADD tags python redis         # set
ZADD leaderboard 100 "player1" # sorted set (лидерборд)
```

Выбор структуры под задачу — ключевой навык: счётчик → string+`INCR`, объект →
hash, очередь → list, уникальность → set, рейтинг → sorted set.

**Аналогия.** Redis — как набор специализированных ящиков: простая полка (string),
ящик с подписанными ячейками (hash), труба-очередь (list), мешок уникальных
жетонов (set), турнирная таблица с очками (sorted set).

## Расширенные структуры и TTL

Помимо базовых, есть специальные:

- **Streams** — append-only лог сообщений (как мини-Kafka): надёжные очереди с
  consumer groups.
- **Bitmaps** / **HyperLogLog** — компактный подсчёт (онлайн-пользователи,
  приблизительное число уникальных за O(1) памяти).
- **Geo**, **Pub/Sub** каналы.

Критичная общая возможность — **TTL (время жизни ключа)**: любому ключу можно
задать срок, после которого Redis **сам его удалит** (`EXPIRE key 3600`,
`SET key val EX 60`). Это фундамент кэширования: данные живут ограниченное время и
автоматически протухают. Без TTL кэш рос бы бесконечно.

```text
SET session:abc "data" EX 1800   # сессия живёт 30 минут, потом исчезнет
TTL session:abc                  # сколько осталось
```

**Аналогия.** TTL — как срок годности на продукте: положил в холодильник (Redis) с
датой, и просроченное само «исчезает». Так кэш не превращается в свалку устаревших
данных.

## Памятка для собеседования

- Redis — **in-memory** key-value хранилище; быстр из-за **RAM + однопоточной**
  обработки (команды атомарны, по одной). **Долгая команда блокирует всё** (`KEYS
  *` — зло на проде).
- Типы: **string** (счётчики/кэш), **hash** (объекты), **list** (очереди),
  **set** (уникальность/операции множеств), **sorted set** (лидерборды,
  приоритеты).
- Спец: **streams** (надёжные очереди), **HyperLogLog**/**bitmaps** (компактный
  подсчёт). **TTL** (`EXPIRE`) — ключи протухают сами; основа кэша.

## Частые ошибки в ответах

- Считать Redis «просто кэшем строка→строка», не зная про структуры данных.
- Не понимать, почему он быстрый (RAM + однопоточность) и чем опасны долгие
  команды.
- Не знать про sorted set для лидербордов/приоритетов или про TTL для кэша.
- Запускать `KEYS *` на проде (блокирует сервер; нужен `SCAN`).
