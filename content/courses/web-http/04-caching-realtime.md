# Кэширование, real-time и форматы API

> Цель урока: разобрать HTTP-кэширование (ETag, Cache-Control), способы реального
> времени (WebSockets, SSE, long polling) и сравнение REST/GraphQL/gRPC. Это
> завершает картину веб-взаимодействия и часто всплывает в вопросах «как сделать
> live-обновления» и «REST или GraphQL».

## HTTP-кэширование

Кэширование избавляет от повторной передачи и генерации неизменившихся данных.
HTTP управляет им заголовками:

- **`Cache-Control`** — главный заголовок: `max-age=3600` (кэшировать N секунд),
  `no-cache` (перепроверять перед использованием), `no-store` (не кэшировать
  вовсе), `private`/`public`.
- **`ETag`** — «отпечаток» версии ресурса. Клиент при повторном запросе шлёт
  `If-None-Match: <etag>`; если не изменилось — сервер отвечает **`304 Not
  Modified`** **без тела**, экономя трафик.
- **`Last-Modified`/`If-Modified-Since`** — то же по времени изменения.

```text
1й запрос:  GET /data → 200 + ETag: "abc"
2й запрос:  GET /data, If-None-Match: "abc" → 304 (тело не передаётся)
```

Слои кэша: **браузер**, **CDN** (раздаёт статику/контент ближе к пользователю),
**обратный прокси**. Главная сложность кэширования — **инвалидация** (когда
сбросить устаревшее); ETag решает её через проверку версии. Кэшируют GET'ы;
небезопасные методы — нет.

**Аналогия.** ETag — как спросить «у меня версия документа abc, поменялось?». Если
нет — «нет, используй свою копию» (304), и курьер не везёт тот же документ заново.
Cache-Control — записка «эта копия годна 1 час».

## Real-time: WebSockets, SSE, long polling

Обычный HTTP — «запрос-ответ», сервер не может **сам** отправить данные клиенту.
Для **реального времени** (чаты, уведомления, котировки) есть подходы:

- **Long polling** — клиент шлёт запрос, сервер **держит** его открытым, пока не
  появятся данные, затем отвечает; клиент сразу запрашивает снова. Просто, работает
  везде, но неэффективно.
- **SSE (Server-Sent Events)** — **однонаправленный** поток сервер→клиент по
  обычному HTTP (`text/event-stream`); сервер шлёт события, соединение держится.
  Идеально для лент новостей, уведомлений, прогресса. Проще WebSockets.
- **WebSockets** — **двунаправленный** постоянный канал поверх одного TCP (после
  HTTP-апгрейда); и клиент, и сервер шлют сообщения в любой момент. Для чатов,
  игр, совместного редактирования.

```text
Long polling: запрос «висит», пока нет данных → ответ → снова запрос
SSE:          один канал сервер→клиент, поток событий (однонаправленно)
WebSocket:    полнодуплексный канал клиент↔сервер (двунаправленно)
```

Выбор: нужен только **сервер→клиент** (уведомления, прогресс) — **SSE** (проще,
поверх HTTP, авто-reconnect); нужен **двусторонний** обмен (чат) — **WebSockets**;
не поддерживается ничего лучше — long polling как fallback.

**Аналогия.** Long polling — звонить в справочную и ждать на линии, пока появится
ответ. SSE — подписаться на рассылку: вам шлют новости по мере появления (в одну
сторону). WebSocket — открытая телефонная линия, где оба могут говорить в любой
момент.

## REST против GraphQL против gRPC

Три парадигмы API, и понимание трейд-оффов ценится:

- **REST** — ресурсы + HTTP-методы, JSON. Просто, кэшируется по HTTP, повсеместен.
  Минусы: **over-fetching** (лишние поля) и **under-fetching** (нужно несколько
  запросов на связанные данные).
- **GraphQL** — **один эндпоинт**, клиент сам описывает, **какие поля** хочет
  получить, одним запросом по графу данных. Решает over/under-fetching, удобен
  фронтенду. Минусы: сложнее кэшировать, риск тяжёлых запросов, своя инфраструктура.
- **gRPC** — бинарный RPC поверх HTTP/2 с **Protobuf**-схемой. Очень быстрый,
  строго типизированный, со стримингом. Идеален для **межсервисного** общения.
  Минусы: не для браузера напрямую, бинарный (труднее отлаживать).

Правило выбора: **REST** — публичные API, простота, кэш; **GraphQL** — богатые
клиенты с гибкими запросами (мобильные/SPA); **gRPC** — внутренняя
высокопроизводительная связь между микросервисами.

**Аналогия.** REST — шведский стол с фиксированными блюдами (берёшь тарелки
целиком). GraphQL — заказ по меню «соберите мне ровно эти ингредиенты одним
блюдом». gRPC — прямая скоростная линия между кухнями ресторанов (сервисами),
говорящими на сжатом профессиональном жаргоне.

## Памятка для собеседования

- HTTP-кэш: **`Cache-Control`** (`max-age`/`no-store`), **`ETag`** +
  `If-None-Match` → **`304`** без тела; слои: браузер/CDN/прокси; сложность —
  **инвалидация**.
- Real-time: **long polling** (держим запрос, fallback), **SSE** (однонаправленно
  сервер→клиент, проще), **WebSockets** (двунаправленный канал). Уведомления →
  SSE; чат → WebSockets.
- **REST** (ресурсы/HTTP, over/under-fetching) vs **GraphQL** (один эндпоинт,
  клиент выбирает поля) vs **gRPC** (бинарный HTTP/2+Protobuf, межсервисный,
  быстрый).

## Частые ошибки в ответах

- Не знать про ETag/304 и роль CDN в кэшировании; недооценивать сложность
  инвалидации.
- Путать SSE (однонаправленный) и WebSockets (двунаправленный); тянуть WebSockets
  туда, где хватит SSE.
- Описывать GraphQL как «замену REST везде», не зная минусов (кэш, сложность).
- Предлагать gRPC для браузерного фронтенда напрямую.
