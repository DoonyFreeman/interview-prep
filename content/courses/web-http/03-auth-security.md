# Аутентификация: сессии, JWT, CSRF, CORS

> Цель урока: разобрать, как веб различает «кто это» — сессии против токенов (JWT),
> и связанные темы безопасности: CSRF и CORS. Это плотная зона вопросов на
> бэкенд-собесе: «сессии или JWT и почему», «что такое CSRF», «как работает CORS».

## Сессии против токенов

Два подхода к аутентификации после входа:

- **Сессии (stateful)**: сервер создаёт **сессию** и хранит её (в памяти/Redis/БД),
  а клиенту отдаёт **session id** в **cookie**. На каждом запросе сервер по id
  находит сессию. Состояние — **на сервере**.
- **Токены (stateless), JWT**: сервер выдаёт **самодостаточный токен**, который
  клиент шлёт в каждом запросе (обычно `Authorization: Bearer`). Сервер
  **не хранит** ничего — проверяет подпись токена. Состояние — **в токене**.

```text
Сессии: cookie(session_id) → сервер ищет сессию в хранилище (stateful)
JWT:    Authorization: Bearer <jwt> → сервер проверяет подпись (stateless)
```

Трейд-офф: **сессии** легко **отозвать** (удалил из хранилища — и всё), но нужно
общее хранилище и оно — точка масштабирования. **JWT** масштабируется без
хранилища (любой сервер проверит подпись), но **трудно отозвать** до истечения
срока (токен валиден, пока не протух). Выбор: сессии хороши для классических
веб-приложений с одним бэкендом; JWT — для API, микросервисов, мобильных клиентов.

**Аналогия.** Сессия — гардеробный номерок: сам по себе пустой, реальная вещь
лежит у гардеробщика (на сервере); потерял номерок — гардеробщик просто
аннулирует. JWT — подписанный пропуск со всеми данными внутри: охране не нужна
картотека, но и «отозвать» уже выданный пропуск до срока сложно.

## Устройство JWT

**JWT (JSON Web Token)** состоит из трёх частей через точку:
`header.payload.signature` (base64url):

- **Header** — алгоритм подписи (`HS256`, `RS256`).
- **Payload** — **claims** (данные): `sub` (кто), `exp` (срок), роли и т.д.
  **Не шифруется**, только кодируется — секреты в payload класть нельзя!
- **Signature** — подпись header+payload секретом; гарантирует, что токен **не
  подделан** и не изменён.

```text
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxIiwiZXhwIjoxNzMwfQ . <signature>
        header                    payload                  подпись
```

Сервер при проверке **пересчитывает подпись** и сверяет `exp`. Критично: JWT
**защищён от подделки** (подпись), но **не от прочтения** (payload читается любым) —
поэтому в нём не хранят пароли/секреты. Для отзыва и долгих сессий используют пару
**access (короткий) + refresh (долгий) токен**: access живёт минуты, refresh
позволяет получить новый access, и его можно отозвать (хранят список/версию).

**Аналогия.** JWT — запечатанный сургучом документ: печать (подпись) подтверждает
подлинность, но текст виден всем, кто возьмёт в руки. Поэтому секреты в него не
пишут.

## CSRF

**CSRF (Cross-Site Request Forgery)** — атака, где вредоносный сайт заставляет
**браузер жертвы** отправить запрос на сайт, где она **залогинена**, используя её
**cookie** (браузер прикладывает cookie автоматически). Так от имени жертвы можно
выполнить действие (перевод денег, смена пароля).

Ключевой момент: CSRF опасен именно для **cookie-аутентификации** (браузер сам
шлёт cookie на нужный домен). Защита:

- **CSRF-токен**: сервер выдаёт случайный токен, который должен прийти в форме/
  заголовке; чужой сайт его не знает.
- **`SameSite` cookie** (`Lax`/`Strict`) — браузер не шлёт cookie в кросс-сайтовых
  запросах. Сейчас основная защита.
- **JWT в заголовке `Authorization`** к CSRF **не уязвим**: браузер не добавляет
  заголовок автоматически (его ставит ваш JS), поэтому чужой сайт не сможет.

**Аналогия.** CSRF — как если бы мошенник прислал вам письмо с кнопкой, которая,
нажатая в вашем залогиненном банке, переводит деньги: банк видит ваши «ключи»
(cookie) и выполняет. CSRF-токен — секретное слово, которого у мошенника нет.

## CORS

**CORS (Cross-Origin Resource Sharing)** — механизм, которым **браузер** решает,
можно ли JS со страницы одного **origin** (схема+домен+порт) обращаться к API
другого origin. По умолчанию действует **Same-Origin Policy** — кросс-доменные
запросы из JS блокируются, **пока сервер не разрешит** их CORS-заголовками
(`Access-Control-Allow-Origin` и др.).

```text
Фронтенд http://localhost:5173  →  API http://localhost:8000
Браузер: разные origin → проверяет CORS-заголовки сервера; нет разрешения → блок
```

Важно понимать: **CORS — это про браузер, а не про безопасность сервера**. Он не
«защищает» API (curl/сервер-сервер CORS игнорируют) — он защищает **пользователя**
от того, чтобы чужой сайт делал запросы к вашему API от его имени из браузера.
Для «непростых» запросов браузер шлёт **preflight** (`OPTIONS`) — спрашивает
разрешение заранее. Настройка CORS (разрешённые origins/методы/заголовки) — частая
боль при разработке SPA+API (как в этом проекте).

**Аналогия.** CORS — это правила пропуска посетителей в зависимости от того, «с
какой улицы» (origin) они пришли: вахтёр-браузер пускает только тех, кого хозяин
(сервер) явно разрешил. Но это правило для «гостей с улицы» (браузера), а не замок
на самой двери (сервер всё равно надо защищать аутентификацией).

## HTTPS и TLS

Всё предыдущее (cookie, токены, пароли) бессмысленно, если данные идут по сети
**в открытом виде** — их перехватят. **HTTPS** — это HTTP поверх **TLS (Transport
Layer Security)**, который даёт три гарантии: **шифрование** (данные нечитаемы для
перехватчика), **целостность** (данные не подменены в пути) и **аутентификацию
сервера** (вы говорите именно с тем сайтом, а не с подставным).

Как устанавливается защищённое соединение (**TLS handshake**, упрощённо):

1. Клиент и сервер договариваются о версии TLS и наборе шифров.
2. Сервер присылает **сертификат** с **публичным ключом**, подписанный
   **удостоверяющим центром (CA)**. Браузер проверяет подпись по списку доверенных
   CA и что сертификат выдан этому домену и не истёк — так подтверждается
   **подлинность сервера**.
3. Через **асимметричную** криптографию (публичный/приватный ключ) стороны
   безопасно согласуют общий **сеансовый (симметричный) ключ**.
4. Дальше весь трафик шифруется **симметрично** (быстро) этим сеансовым ключом.

```text
http://  — данные в открытом виде (пароли, токены видны перехватчику)
https:// — TLS: шифрование + целостность + проверка сертификата сервера
```

Ключевые тезисы для собеседования:

- **Шифруется содержимое** (URL-путь, заголовки, тело, cookie); но **домен (SNI) и
  IP** видны провайдеру — он знает, **с каким сайтом** вы соединились, но не **что**
  передали.
- **Гибрид асимметрики и симметрики**: асимметрия (медленная) — только для обмена
  ключом и проверки сертификата; дальше симметрия (быстрая) — для самих данных.
- Сертификат подтверждает **сервер** (не клиента); доверие строится через цепочку
  **CA**. Бесплатно — Let's Encrypt (как планируется в деплое этого проекта за
  reverse-proxy с TLS).
- **HTTPS обязателен** для любой аутентификации: по HTTP пароли/токены/cookie летят
  открыто.

**Аналогия.** TLS — как договориться о секретном языке перед разговором: сначала вы
проверяете паспорт собеседника (сертификат через CA — точно ли это банк), затем
обмениваетесь шифром так, что подслушивающий не поймёт (обмен ключом), и дальше
говорите на этом языке (симметричное шифрование). Прохожий видит, что вы зашли
именно в банк (домен), но не слышит, о чём вы (содержимое).

## Памятка для собеседования

- **Сессии (stateful)**: id в cookie, состояние на сервере — легко **отозвать**,
  нужно хранилище. **JWT (stateless)**: самодостаточный токен, сервер не хранит —
  масштабируется, но **трудно отозвать**.
- **JWT** = `header.payload.signature`; payload **только кодируется** (читаем, без
  секретов!), подпись защищает от подделки; access+refresh для отзыва/долгих
  сессий.
- **CSRF** — атака через автоматически отправляемые **cookie**; защита: SameSite,
  CSRF-токен. **JWT в заголовке к CSRF не уязвим**.
- **CORS** — **браузерный** механизм допуска кросс-origin запросов из JS
  (Same-Origin Policy + разрешающие заголовки, preflight `OPTIONS`); защищает
  пользователя, **не** заменяет аутентификацию.

## Частые ошибки в ответах

- Думать, что JWT шифруется (он только подписан; payload читается) или хранить в
  нём секреты.
- Не знать трейд-офф «легко отозвать сессию vs масштабируемость JWT».
- Считать, что CORS «защищает API» (это про браузер; сервер защищает auth).
- Не понимать, что CSRF бьёт по cookie-аутентификации, а JWT в заголовке к нему
  устойчив.
