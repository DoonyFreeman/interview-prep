# REST и проектирование API

> Цель урока: понять принципы REST и как проектировать понятный, предсказуемый
> HTTP API — ресурсы, версионирование, пагинацию, формат ошибок. На собесе просят
> «спроектируйте API для X» и смотрят на именование ресурсов и работу со списками.

## Принципы REST

**REST (Representational State Transfer)** — архитектурный стиль для API поверх
HTTP. Ключевые принципы:

- **Ресурсы и их URI**: данные — это **ресурсы** (существительные), адресуемые
  URL. `/users/1/orders`, а не `/getUserOrders`. Действия выражаются **методом**
  (GET/POST/...), а не словом в пути.
- **Stateless**: сервер не хранит состояние клиента между запросами; каждый
  запрос самодостаточен (токен внутри). Это даёт горизонтальное масштабирование.
- **Единообразие интерфейса**: одинаковые правила для всех ресурсов
  (коллекция/элемент, стандартные методы и коды).
- **Представления**: ресурс отдаётся в каком-то формате (обычно JSON); один
  ресурс может иметь разные представления.

```text
GET    /articles            список статей
POST   /articles            создать статью
GET    /articles/42         одна статья
PATCH  /articles/42         обновить
DELETE /articles/42         удалить
GET    /articles/42/comments  вложенный ресурс
```

Главный сдвиг мышления: **существительные + HTTP-методы**, а не глаголы в URL.
Хороший REST-API «угадывается»: зная одну коллекцию, понимаешь все остальные.

**Аналогия.** REST — это библиотека с единой системой адресации: каждая книга
(ресурс) имеет полку (URI), а действия (взять, вернуть) — стандартные операции, а
не отдельная «процедура» под каждую книгу.

## Именование и структура ресурсов

Правила хорошего именования (их любят проверять «спроектируйте API»):

- **Существительные во множественном числе** для коллекций: `/users`, `/orders`.
- **Иерархия для связей**: `/users/1/orders` (заказы пользователя 1).
- **Никаких глаголов в URL** (`/createUser` — плохо; `POST /users` — хорошо).
- **Консистентность**: единый стиль (snake_case или kebab в путях), единая форма
  ответов.
- **Фильтры/сортировка — query-параметрами**: `/orders?status=paid&sort=-created`.

Для действий, не ложащихся на CRUD (например, «опубликовать»), допустимы под-ресурсы
или «действия»: `POST /articles/42/publish` — прагматичный компромисс, когда чистый
REST неудобен. Главное — предсказуемость и единообразие.

**Аналогия.** Именование ресурсов — как адреса в городе с понятной нумерацией:
зная, что дома идут `/улица/дом/квартира`, гость найдёт любую квартиру. Если же
каждый адрес придумывать заново (`getKvartira`), город станет лабиринтом.

## Версионирование

API меняется, а старые клиенты должны продолжать работать — поэтому **версионируют**:

- **В пути**: `/api/v1/users` — самый явный и распространённый.
- **В заголовке**: `Accept: application/vnd.api.v2+json` — чище URL, но менее
  очевидно.
- Реже — в query (`?version=2`).

Принцип: **ломающие изменения** (убрали/переименовали поле, изменили семантику) →
**новая версия**; **обратносовместимые** (добавили необязательное поле) — можно без
версии. Цель — не сломать существующих клиентов. Часто старую версию поддерживают
какое-то время параллельно с новой и объявляют **deprecation**.

**Аналогия.** Версионирование — как издания книги: добавить опечатку в сноску можно
в том же издании (совместимо), но переписать главу — это новое издание (v2), чтобы
у тех, кто ссылался на старое, ничего не «поехало».

## Пагинация, фильтрация, формат ошибок

Реальный API почти всегда отдаёт **списки**, и их нельзя возвращать целиком:

- **Пагинация**: **offset/limit** (`?offset=40&limit=20`) — просто, но дорого на
  больших смещениях; **keyset/cursor** (`?after=<id>`) — стабильнее и быстрее для
  больших данных и «бесконечной ленты».
- **Фильтрация и сортировка** — query-параметрами; возвращать метаданные (общее
  число, ссылки на след./пред. страницу).
- **Единый формат ошибок**: предсказуемая структура (`{"detail": "...",
  "code": "..."}`), корректные статус-коды (4xx/5xx), без утечки внутренних
  деталей/стектрейсов наружу.

```json
GET /orders?status=paid&limit=20&after=1042
{ "items": [...], "next_cursor": "1062", "total": 530 }
```

Дополнительно для надёжного API: **rate limiting** (`429` + заголовки лимита),
**идемпотентность** для небезопасных операций. Хороший дизайн API — это
предсказуемость, единообразие и забота о клиенте (понятные ошибки, разумные
списки).

**Аналогия.** Пагинация — выдавать книги из архива партиями по 20, а не вываливать
весь архив. Cursor-пагинация — закладка «продолжить отсюда», устойчивая, даже если
в архив добавили новые книги; offset — «дай страницы с 40-й», что при изменении
архива может сбиться.

## Памятка для собеседования

- **REST**: ресурсы-**существительные** в URI + действия **методами** (не глаголы
  в пути), **stateless**, единообразие, JSON-представления.
- Именование: множественное число (`/users`), иерархия для связей
  (`/users/1/orders`), фильтры — query; не-CRUD действия — прагматично
  (`/articles/42/publish`).
- **Версионирование**: путь (`/v1/`) или заголовок; ломающие изменения → новая
  версия, совместимые (новое необязательное поле) — без.
- Списки: **offset/limit** (просто) vs **cursor/keyset** (стабильно/быстро);
  фильтры query; **единый формат ошибок** + корректные статусы; rate limiting
  (429), идемпотентность.

## Частые ошибки в ответах

- Глаголы в URL (`/getUser`, `/createOrder`) вместо существительных + методов.
- Не знать разницу offset vs cursor пагинации и проблему offset на больших данных.
- Возвращать списки целиком без пагинации; разнобой в формате ответов/ошибок.
- Ломать совместимость без версионирования; отдавать стектрейсы клиенту.
