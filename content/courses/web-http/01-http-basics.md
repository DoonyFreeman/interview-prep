# HTTP: методы, статусы, идемпотентность

> Цель урока: уверенно владеть основами HTTP — методами, статус-кодами,
> заголовками и понятиями идемпотентности и безопасности. Это ежедневный язык
> бэкендера и обязательный минимум собеседования: «чем PUT отличается от PATCH»,
> «что значит идемпотентный».

## Методы HTTP

HTTP-методы выражают **намерение** операции над ресурсом:

- **GET** — получить ресурс; **не меняет** состояние.
- **POST** — создать ресурс / выполнить действие; **меняет** состояние.
- **PUT** — **полностью заменить** ресурс (или создать по известному URI).
- **PATCH** — **частично обновить** ресурс (только переданные поля).
- **DELETE** — удалить ресурс.

```text
GET    /users/1        → вернуть пользователя 1
POST   /users          → создать нового (id назначит сервер)
PUT    /users/1        → заменить пользователя 1 целиком
PATCH  /users/1        → обновить отдельные поля пользователя 1
DELETE /users/1        → удалить пользователя 1
```

Ключевое различие PUT/PATCH: **PUT заменяет ресурс целиком** (отсутствующие поля
обнуляются/сбрасываются), **PATCH меняет частично**. Путаница здесь — частая
ошибка. Метод — это контракт о намерении, и клиенты/прокси/кэши на него
полагаются.

**Аналогия.** Методы — глаголы для ресурса-существительного: GET «посмотреть», POST
«добавить», PUT «переписать набело», PATCH «исправить пару строк», DELETE
«выбросить».

## Идемпотентность и безопасность

Два свойства методов, которые любят на собесе:

- **Безопасный (safe)** метод **не меняет** состояние сервера: **GET**, HEAD,
  OPTIONS. Их можно вызывать свободно (кэшировать, префетчить).
- **Идемпотентный** метод даёт **тот же результат при повторении**: один или сто
  одинаковых вызовов оставляют сервер в одном состоянии. **GET, PUT, DELETE —
  идемпотентны**; **POST — нет** (повтор создаёт дубликат).

```text
PUT /users/1 {name: "A"}  ×3  → пользователь всё равно {name: "A"} (идемпотентно)
POST /users {name: "A"}   ×3  → три разных пользователя (НЕ идемпотентно)
DELETE /users/1           ×3  → удалён (повтор — уже нет, состояние то же)
```

Почему это важно практически: при **ретраях** (сеть оборвалась, неясно, дошёл ли
запрос) идемпотентные методы можно безопасно повторять. POST повторять опасно —
отсюда паттерн **ключа идемпотентности** (Idempotency-Key) для платежей, чтобы
повтор не создал второй платёж.

**Аналогия.** Идемпотентность — как выключатель «выключить свет»: нажал раз или
десять — свет всё равно выключен (одно состояние). А POST — как «добавить ещё одну
лампу»: каждое нажатие добавляет новую.

## Статус-коды

Статус-коды сгруппированы по первой цифре — знать классы обязательно:

- **2xx — успех**: `200 OK`, `201 Created` (создан ресурс, обычно на POST),
  `204 No Content` (успех без тела).
- **3xx — перенаправление**: `301` (постоянно), `302`/`307` (временно),
  `304 Not Modified` (кэш актуален).
- **4xx — ошибка клиента**: `400 Bad Request`, `401 Unauthorized` (не
  аутентифицирован), `403 Forbidden` (нет прав), `404 Not Found`,
  `409 Conflict`, `422 Unprocessable Entity` (валидация), `429 Too Many
  Requests`.
- **5xx — ошибка сервера**: `500 Internal Server Error`, `502 Bad Gateway`,
  `503 Service Unavailable`.

Частые ловушки: **401 vs 403** (401 — «кто ты?», не залогинен; 403 — «знаю, кто
ты, но нельзя»); **400 vs 422** (общий неверный запрос против ошибки валидации
данных); правильный код на создание — **201**, а не 200. Корректные статусы —
часть хорошего API: клиент по коду понимает, что произошло и можно ли повторить.

**Аналогия.** Класс статуса — как первая цифра ответа справочной: 2xx «всё
сделано», 3xx «идите туда», 4xx «вы что-то не так попросили», 5xx «у нас
сломалось». По первой цифре уже ясно, чья проблема.

## Заголовки и структура запроса

HTTP-сообщение = **стартовая строка** (метод+URL или статус) + **заголовки** +
(опционально) **тело**. Заголовки несут метаданные:

- **`Content-Type`** — формат тела (`application/json`, `multipart/form-data`).
- **`Authorization`** — учётные данные (`Bearer <token>`).
- **`Accept`** — какой формат ответа хочет клиент.
- **`Cache-Control`**, **`ETag`** — управление кэшированием (отдельный урок).
- **`User-Agent`**, **`Content-Length`**, cookies и т.д.

HTTP **stateless**: каждый запрос самодостаточен, сервер не помнит предыдущий
(состояние — в токенах/cookie/БД, не в «соединении»). Это фундамент
масштабируемости: любой запрос может уйти на любой сервер.

**Аналогия.** Запрос — это письмо: на конверте адрес и метод (стартовая строка),
пометки «куда, от кого, формат вложения» (заголовки), внутри — содержимое (тело).
Stateless — каждое письмо понятно само по себе, без «помните, я писал вчера».

## Памятка для собеседования

- Методы: **GET** (читать), **POST** (создать/действие), **PUT** (заменить
  целиком), **PATCH** (частично), **DELETE**. PUT≠PATCH (полная vs частичная
  замена).
- **Safe** (не меняет: GET/HEAD/OPTIONS); **идемпотентный** (повтор = тот же
  результат: GET/PUT/DELETE, **POST — нет**). Важно для ретраев; Idempotency-Key
  для POST.
- Статусы: **2xx** успех (201 на создание, 204 без тела), **3xx** редирект (304
  кэш), **4xx** клиент (401≠403, 400≠422, 429), **5xx** сервер.
- HTTP **stateless**; заголовки несут метаданные (`Content-Type`, `Authorization`,
  `Accept`, кэш).

## Частые ошибки в ответах

- Путать PUT и PATCH (полная vs частичная замена).
- Не понимать идемпотентность или считать POST идемпотентным.
- Путать 401 и 403, 400 и 422; отдавать 200 вместо 201/204.
- Не знать, что HTTP stateless, и думать, что сервер «помнит» клиента между
  запросами.
