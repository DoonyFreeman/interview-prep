# Сеть, тома и переменные окружения

> Цель урока: понять, как контейнеры хранят данные (тома), общаются по сети и
> конфигурируются (env, порты). Это ежедневная практика контейнеризации; вопросы
> «как данные переживают перезапуск» и «как контейнеры видят друг друга» — частые.

## Тома: персистентность данных

Файловая система контейнера **эфемерна**: writable-слой исчезает при удалении
контейнера, поэтому данные БД, загрузки, логи **нельзя** хранить внутри контейнера.
Решение — **тома (volumes)**: хранилище, живущее **вне** жизненного цикла
контейнера.

- **Named volume** — управляется Docker, хранится в его области; **переживает**
  пересоздание контейнера. Для данных БД (как `data/app.db` на named volume в
  планах этого проекта).
- **Bind mount** — монтирует **папку хоста** в контейнер. Удобно для разработки
  (код хоста виден в контейнере, hot-reload) и конфигов.

```bash
docker run -v pgdata:/var/lib/postgresql/data postgres   # named volume — данные БД
docker run -v $(pwd):/app myapp                            # bind mount — код для dev
```

Главный принцип контейнеров — **stateless контейнер, состояние в томе**: сам
контейнер можно убить и пересоздать, а данные на томе сохранятся. Это основа
обновлений и масштабирования.

**Аналогия.** Контейнер — сменный рабочий, который приходит и уходит; том — сейф/
склад, который остаётся на месте. Документы (данные) держат в сейфе, а не в карманах
рабочего, иначе с его уходом они пропадут.

## Сеть контейнеров

Контейнеры общаются через **сети Docker**. Ключевая возможность — в одной
**пользовательской bridge-сети** контейнеры **видят друг друга по имени** (Docker
даёт встроенный DNS): сервис `web` обращается к БД просто по имени `db`, не зная её
IP.

```yaml
# в docker-compose: контейнеры в общей сети находят друг друга по имени сервиса
services:
  web:
    environment:
      DATABASE_URL: postgresql://db:5432/app   # 'db' — имя сервиса, не IP
  db:
    image: postgres
```

**Публикация портов** (`-p 8000:80`) пробрасывает порт контейнера на хост, чтобы
снаружи можно было достучаться. Разделяй: **внутреннее** общение сервисов — по
именам внутри сети Docker (порты наружу публиковать не нужно); **наружу** публикуют
только то, что должно быть доступно извне (веб, прокси). БД обычно **не**
публикуют на хост.

**Аналогия.** Сеть Docker — внутренний телефонный справочник офиса: сотрудники
(контейнеры) звонят друг другу по именам, не зная номеров. Публикация порта — внешняя
линия в город: даёшь её только тем, кому правда нужно общаться с внешним миром.

## Конфигурация: переменные окружения

Контейнеры конфигурируют через **переменные окружения** — это стандарт
**12-factor** («конфиг в окружении, не в коде»). Один и тот же образ работает в
dev/staging/prod, меняясь только переменными.

```bash
docker run -e DATABASE_URL=... -e SECRET_KEY=... myapp
# или --env-file .env  (как GEMINI_API_KEY, JWT_SECRET в этом проекте)
```

Принципы:

- **Образ — неизменяемый артефакт**, конфигурация подаётся снаружи (env), не
  «запекается» в образ.
- **Секреты** (пароли, ключи) — через env/секрет-механизмы, **никогда** в
  Dockerfile или в коде (попадут в слои образа, утекут).
- env-файл (`.env`) удобен для локальной разработки; в проде — секреты оркестратора/
  CI.

Это ровно подход данного проекта: `GEMINI_API_KEY`, `JWT_SECRET`, `CORS_ORIGINS`,
`CONTENT_DIR` инъектируются через env, а контент и код — в образе.

**Аналогия.** Образ — универсальный прибор, env — настройки под розетку конкретной
страны: один прибор работает везде, меняется лишь переходник (конфиг). Секреты —
как PIN: его не печатают на корпусе прибора (в образе), а вводят при использовании.

## Памятка для собеседования

- ФС контейнера **эфемерна** → данные в **томах**: **named volume** (данные БД,
  переживает пересоздание) vs **bind mount** (папка хоста, для dev/конфигов).
  Принцип: **stateless контейнер, состояние в томе**.
- Сеть: в общей bridge-сети контейнеры **видят друг друга по имени** (встроенный
  DNS); внутреннее общение — по именам, наружу **публикуют порты** (`-p`) только
  нужное (БД — нет).
- Конфиг через **env** (12-factor): образ неизменяемый, настройки снаружи;
  **секреты — через env/секреты, не в Dockerfile/коде**.

## Частые ошибки в ответах

- Хранить данные БД внутри контейнера (потеряются при пересоздании) — нужен том.
- Не знать, что контейнеры находят друг друга по имени сервиса в сети Docker.
- Публиковать наружу порты, которые должны быть только внутренними (БД).
- Зашивать секреты в Dockerfile/образ вместо передачи через env.
