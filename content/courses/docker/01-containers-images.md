# Контейнеры и образы

> Цель урока: понять, что такое контейнер (и чем он отличается от виртуальной
> машины), как устроены образы из слоёв и как работает кэш сборки Dockerfile. Это
> фундамент: «контейнер vs ВМ» и «как уменьшить образ» — обязательные вопросы.

## Контейнеры против виртуальных машин

И контейнеры, и **виртуальные машины (ВМ)** изолируют приложения, но
**принципиально по-разному**:

- **ВМ** виртуализирует **железо**: поверх гипервизора работает **полная гостевая
  ОС** со своим ядром. Тяжёлая (гигабайты), медленный старт (минуты), сильная
  изоляция.
- **Контейнер** виртуализирует **ОС**: все контейнеры **делят ядро хоста**, изолируя
  лишь процессы и ресурсы. Лёгкий (мегабайты), мгновенный старт (секунды), но
  изоляция слабее (общее ядро).

```text
ВМ:        [Приложение][Гостевая ОС+ядро] × N  → гипервизор → железо  (тяжело)
Контейнер: [Приложение] × N → общий Docker/ядро хоста → железо        (легко)
```

Изоляция контейнеров строится на двух механизмах ядра Linux: **namespaces**
(изолируют, что процесс **видит** — свои процессы, сеть, файловую систему, имена) и
**cgroups** (ограничивают, сколько ресурсов — CPU, память — процесс **может
использовать**). Контейнер — это, по сути, **обычный процесс хоста** с
namespaces+cgroups, а не отдельная машина.

**Аналогия.** ВМ — отдельный дом с собственным фундаментом и коммуникациями
(гостевая ОС): надёжно изолирован, но дорого строить. Контейнер — квартира в общем
доме (ядро хоста): свои стены и счётчики (namespaces/cgroups), но общий фундамент;
дёшево и быстро, хотя сосед за стеной ближе.

## Образы и слои

**Образ (image)** — неизменяемый **шаблон** для контейнеров (код + зависимости +
окружение). **Контейнер** — запущенный **экземпляр** образа. Ключевое: образ
состоит из **слоёв (layers)** — каждый слой это набор изменений файловой системы.

Каждая инструкция Dockerfile создаёт **новый слой** поверх предыдущего. Слои
**кэшируются и переиспользуются**: если несколько образов основаны на одном базовом
слое, он хранится **один раз**. Контейнер добавляет сверху тонкий **writable-слой**
для изменений в рантайме (исчезает при удалении контейнера — отсюда нужны тома для
данных).

```dockerfile
FROM python:3.12-slim        # слой 1: базовый образ
WORKDIR /app                 # слой 2
COPY requirements.txt .      # слой 3
RUN pip install -r requirements.txt   # слой 4 (тяжёлый)
COPY . .                     # слой 5: код
```

Понимание «образ = слои, контейнер = экземпляр + writable-слой» объясняет и кэш
сборки, и почему данные в контейнере эфемерны.

**Аналогия.** Образ — рецепт-заготовка, слои — как прозрачные плёнки, наложенные
друг на друга (каждая добавляет что-то). Контейнер — готовое блюдо по рецепту, а
изменения во время еды (writable-слой) тарелку покидают, когда её моют.

## Кэш сборки и порядок инструкций

Docker **кэширует слои**: при повторной сборке, если инструкция и её контекст **не
изменились**, берётся готовый слой. Но как только слой **изменился**, **все
последующие** пересобираются заново (кэш «ломается» с этого места вниз).

Отсюда **главный приём оптимизации сборки** — порядок инструкций от **редко
меняющегося к часто меняющемуся**:

```dockerfile
# ПРАВИЛЬНО: зависимости (меняются редко) — ДО кода (меняется часто)
COPY requirements.txt .
RUN pip install -r requirements.txt   # этот тяжёлый слой кэшируется,
COPY . .                              # пока requirements не изменились

# ПЛОХО: COPY . . перед install — любое изменение кода
# инвалидирует кэш и переустанавливает все зависимости каждый раз
```

Если сначала копировать **весь код**, то любое изменение строки кода сбросит кэш и
заставит **переустанавливать зависимости** при каждой сборке — медленно. Поэтому
**сначала зависимости, потом код**. `.dockerignore` (исключить `.git`, `venv`,
кэши) уменьшает контекст сборки и образ.

**Аналогия.** Кэш сборки — как готовить по шагам, сохраняя промежуточные
заготовки: если поменял последний штрих, не переделываешь тесто с нуля. Но если
переставить «замесить тесто» после «украсить», то любое украшение заставит месить
заново.

## Памятка для собеседования

- **ВМ** — своя гостевая **ОС+ядро** (тяжело, сильная изоляция); **контейнер** —
  общее **ядро хоста**, изоляция через **namespaces** (что видит) + **cgroups**
  (сколько ресурсов). Контейнер = процесс хоста, не машина.
- **Образ** — неизменяемый шаблон из **слоёв**; **контейнер** — экземпляр + тонкий
  **writable-слой** (эфемерный → тома для данных). Слои кэшируются/переиспользуются.
- Кэш сборки: изменился слой → пересобираются все ниже. **Сначала зависимости,
  потом код** (иначе переустановка зависимостей на каждое изменение).
  `.dockerignore` уменьшает контекст.

## Частые ошибки в ответах

- Говорить, что контейнер — «лёгкая ВМ», не зная про общее ядро и namespaces/cgroups.
- Путать образ (шаблон) и контейнер (экземпляр); не знать про writable-слой и
  эфемерность данных.
- `COPY . .` перед установкой зависимостей (ломает кэш, медленная сборка).
- Не знать про `.dockerignore` и роль порядка инструкций.
