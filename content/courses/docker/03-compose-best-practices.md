# docker-compose, multi-stage и лучшие практики

> Цель урока: научиться описывать многосервисный стек через docker-compose, делать
> лёгкие образы через multi-stage сборку и знать практики безопасности (non-root,
> секреты). Это «продакшен-готовность» — ровно то, что нужно для деплоя этого
> проекта.

## docker-compose

**docker-compose** описывает **многосервисное приложение** в одном YAML-файле:
сервисы (контейнеры), сети, тома, зависимости — и поднимает всё одной командой
(`docker compose up`). Это стандарт для локальной разработки и небольших
self-hosted деплоев (как планируется здесь).

```yaml
services:
  backend:
    build: ./backend
    env_file: .env
    depends_on:
      db:
        condition: service_healthy      # ждать готовности БД
    ports: ["8000:8000"]
  db:
    image: postgres:16
    volumes: ["pgdata:/var/lib/postgresql/data"]   # данные на томе
    healthcheck:
      test: ["CMD", "pg_isready"]
volumes:
  pgdata:
```

Ключевое: сервисы в одной сети **находят друг друга по имени** (`backend` → `db`);
**`depends_on`** задаёт порядок старта, а с **`healthcheck`** — ждёт реальной
**готовности** зависимости (а не просто запуска контейнера). `healthcheck`
(проверка `/health`, `pg_isready`) — основа надёжного старта и рестарт-политик.

**Аналогия.** docker-compose — как режиссёрский сценарий спектакля: кто на сцене
(сервисы), как связаны (сеть), что у кого в реквизите (тома), кто выходит после кого
(depends_on). Одна команда — и весь спектакль разворачивается.

## Multi-stage сборка

Образы часто раздуты: инструменты сборки (компиляторы, dev-зависимости) не нужны в
рантайме, но попадают в образ. **Multi-stage build** решает это: в одном Dockerfile
**несколько стадий** — в одной собираем, из неё копируем в финальную **только
нужное**.

```dockerfile
# стадия build: ставим зависимости (с инструментами сборки)
FROM python:3.12 AS build
COPY requirements.txt .
RUN pip install --prefix=/install -r requirements.txt

# финальная стадия: только рантайм + готовые зависимости, без мусора сборки
FROM python:3.12-slim
COPY --from=build /install /usr/local      # копируем только результат
COPY . /app
CMD ["uvicorn", "app.main:app"]
```

Результат — **маленький, чистый образ** без компиляторов и кэшей. Для фронтенда
аналогично: стадия сборки (Node + `npm build`) → копируем готовый `dist` в лёгкий
nginx-образ (или, как вариант в этом проекте, отдаём собранный SPA через FastAPI
static). Меньше образ = быстрее деплой, меньше поверхность атаки.

**Аналогия.** Multi-stage — как готовить на большой кухне со всем оборудованием
(стадия build), а на стол подавать только готовое блюдо на чистой тарелке (финальный
образ), не вынося в зал кастрюли и грязную посуду (инструменты сборки).

## Лучшие практики и оркестрация

Практики «правильного» образа и эксплуатации:

- **Маленький базовый образ**: `python:3.12-slim` или distroless вместо полного —
  меньше размер и уязвимостей.
- **Multi-stage** + `.dockerignore` — убрать лишнее.
- **Non-root пользователь**: запускать процесс не от root (`USER appuser`) —
  безопасность (компрометация контейнера не даёт root на хосте).
- **Один процесс на контейнер** — контейнер делает одно дело; несколько сервисов
  → несколько контейнеров.
- **Секреты** через env/секрет-механизмы, не в образе; **тегировать** образы
  версиями, не только `latest` (воспроизводимость).
- **`HEALTHCHECK`** + restart-политика — самовосстановление.

**Оркестрация (обзорно)**: когда контейнеров много и нужны авто-масштабирование,
самовосстановление, раскатка по узлам — приходит **Kubernetes** (или Docker Swarm).
Он управляет **множеством контейнеров на кластере машин**: следит за желаемым
состоянием (нужно N реплик — поддерживает N), делает rolling-обновления, балансирует.
Для маленького self-hosted сервиса (как этот проект) **достаточно
docker-compose** — Kubernetes здесь избыточен.

**Аналогия.** Лучшие практики — техника безопасности на производстве (не от root,
минимум лишнего, версии деталей). Оркестрация (K8s) — автоматизированный завод с
роботами, который сам поддерживает нужное число работающих линий; для маленькой
мастерской (compose) такой завод не нужен.

## Памятка для собеседования

- **docker-compose** — многосервисный стек в YAML (сервисы/сети/тома/`depends_on`),
  поднимается одной командой; **`healthcheck`** + `depends_on: condition` ждёт
  **готовности** зависимости. Сервисы находят друг друга по имени.
- **Multi-stage build** — отдельная стадия сборки → в финальный образ копируем
  **только нужное**: маленький чистый образ без инструментов сборки.
- Практики: маленький базовый образ (slim/distroless), `.dockerignore`,
  **non-root**, один процесс на контейнер, секреты через env, теги-версии,
  `HEALTHCHECK`.
- **Оркестрация** (Kubernetes) — для множества контейнеров на кластере
  (авто-масштаб, самовосстановление); для маленького сервиса хватает compose.

## Частые ошибки в ответах

- Не знать про multi-stage и тащить инструменты сборки в финальный образ.
- Запускать контейнер от root; пихать несколько сервисов в один контейнер.
- `depends_on` без healthcheck и думать, что зависимость уже готова (она лишь
  запущена).
- Считать, что Kubernetes нужен всегда (для малого деплоя достаточно compose).
