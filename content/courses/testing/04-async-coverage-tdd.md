# Async-тесты, покрытие и TDD

> Цель урока: закрыть тему тестирования — как тестировать async-код, что показывает
> и чего не показывает покрытие, и что такое TDD и property-based тестирование. Эти
> вопросы отличают тех, кто «пишет тесты», от тех, кто понимает их смысл.

## Тестирование async-кода

Async-функции нельзя просто вызвать в тесте — их надо **выполнить в событийном
цикле**. Для этого используют **`pytest-asyncio`** (или `anyio`): тест помечается
`async def` и плагин гоняет его в цикле.

```python
import pytest

@pytest.mark.asyncio          # или asyncio_mode=auto в конфиге (как в этом проекте)
async def test_fetch():
    result = await fetch_user(1)     # можно await прямо в тесте
    assert result.id == 1
```

Нюансы: для async-зависимостей мокать через **`AsyncMock`** (возвращает
awaitable); для тестирования ASGI-приложений (FastAPI) — **`AsyncClient` +
`ASGITransport`**, который шлёт запросы в приложение в памяти без сервера (как в
этом проекте). В конфиге `asyncio_mode=auto` избавляет от пометки каждого теста
маркером. Главное — async-тест должен **уметь `await`** тестируемый код, значит сам
быть `async`.

**Аналогия.** Async-тест — как проверять пловца: нельзя проверить технику на суше,
нужен бассейн (событийный цикл). `pytest-asyncio` и наливает этот бассейн вокруг
теста.

## Покрытие кода

**Покрытие (coverage)** — метрика, **какой процент строк/веток** кода выполнился во
время тестов (`pytest-cov`, `coverage.py`). Помогает найти **непротестированные**
участки.

```bash
pytest --cov=app --cov-report=term-missing   # покажет, какие строки не покрыты
```

Критически важный нюанс (его ждут): **высокое покрытие ≠ хорошие тесты**. Покрытие
показывает, что строка **выполнилась**, но **не** что её поведение **проверено**
осмысленным `assert`. Можно иметь 100% покрытия и не поймать ни одного бага, если
тесты ничего толком не утверждают. Поэтому покрытие — **инструмент поиска дыр**, а
не цель сама по себе; гнаться за «100%» вредно (тратишь силы на тривиальный код,
получаешь ложное чувство безопасности). Полезнее покрывать **критичную логику и
граничные случаи**.

**Аналогия.** Покрытие — как отметка «обошёл все комнаты дома». Но «зашёл в комнату»
не значит «проверил, всё ли там в порядке». 100% обхода без проверок — это прогулка,
а не инспекция.

## TDD

**TDD (Test-Driven Development)** — практика, где тест пишется **до** кода, по циклу
**red-green-refactor**:

1. **Red** — написать падающий тест на ещё не реализованное поведение.
2. **Green** — написать **минимальный** код, чтобы тест прошёл.
3. **Refactor** — улучшить код, не ломая тесты.

```text
Red:      test_discount() — падает (функции ещё нет)
Green:    реализовать discount() по-минимуму — тест зелёный
Refactor: причесать код — тесты держат корректность
```

Зачем: тесты пишутся гарантированно (а не «потом»), код сразу **проектируется
тестируемым** (через интерфейсы/DI), тест фиксирует **намерение** до реализации.
TDD — не догма (не везде применим), но понимание цикла red-green-refactor и его
пользы ценится. Родственное — **BDD** (поведение в терминах «given-when-then»,
ближе к бизнес-языку).

**Аналогия.** TDD — как сначала нарисовать мишень, а потом стрелять: ты заранее
определяешь, что считается попаданием (тест), и пишешь код прицельно под него, а не
стреляешь в стену и потом рисуешь круги вокруг попаданий.

## Property-based тестирование

Обычный тест проверяет **конкретные примеры** (`add(2,3)==5`). **Property-based**
(библиотека **`hypothesis`**) проверяет **свойства, которые должны выполняться для
любых входов**, а библиотека **сама генерирует** сотни разнообразных (включая
каверзные) примеров:

```python
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_idempotent(xs):
    assert sorted(sorted(xs)) == sorted(xs)   # свойство для ЛЮБОГО списка

@given(st.text())
def test_encode_decode(s):
    assert s.encode().decode() == s            # round-trip для любой строки
```

Сила в том, что hypothesis находит **граничные случаи**, о которых вы не подумали
(пустой список, огромные числа, спецсимволы), и при падении **минимизирует**
пример до простейшего. Типичные свойства: round-trip (`decode(encode(x)) == x`),
инвариант (`len(sorted) == len(original)`), коммутативность. Это дополнение к
примерным тестам, особенно для парсеров, сериализации, алгоритмов.

**Аналогия.** Примерный тест — проверить замок одним конкретным ключом.
Property-based — заявить «замок должен открываться только правильным ключом» и дать
роботу перебрать тысячи ключей, включая хитрые подделки, чтобы найти дыру.

## Памятка для собеседования

- Async-тесты: **`pytest-asyncio`** (`async def` тест, `asyncio_mode=auto`),
  **`AsyncMock`** для async-зависимостей, **`AsyncClient`+`ASGITransport`** для
  FastAPI в памяти.
- **Покрытие** (`pytest-cov`) — % выполненных строк; находит дыры, но **высокое
  покрытие ≠ хорошие тесты** (строка выполнилась ≠ поведение проверено). Не гнаться
  за 100%.
- **TDD**: red (падающий тест) → green (минимальный код) → refactor; тесты пишутся
  гарантированно, код проектируется тестируемым. BDD — given-when-then.
- **Property-based** (`hypothesis`) — проверка свойств для **сгенерированных**
  входов; ловит граничные случаи (round-trip, инварианты), минимизирует
  контрпример.

## Частые ошибки в ответах

- Не знать, как запускать async-тесты (pytest-asyncio) или мокать async
  (AsyncMock).
- Считать высокое покрытие гарантией качества тестов (строка выполнилась ≠
  проверена).
- Описывать TDD без цикла red-green-refactor или как «обязательную догму».
- Не знать про property-based тесты и их пользу для граничных случаев.
