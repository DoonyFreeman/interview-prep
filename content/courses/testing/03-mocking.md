# Моки: mock, monkeypatch, патчинг

> Цель урока: понять, как изолировать тестируемый код от внешних зависимостей —
> моки, заглушки, `monkeypatch`, и главное правило патчинга «where it's used».
> Вопрос «как вы тестируете код, который ходит в сеть/БД» проверяет владение
> моками.

## Зачем нужны тестовые дублёры

Чтобы тестировать единицу **в изоляции** (быстро, детерминированно), её внешние
зависимости (сеть, БД, время, платёжный API) заменяют **тестовыми дублёрами**.
Терминология (её любят уточнять):

- **Stub (заглушка)** — отдаёт **заранее заданные ответы** на вызовы; нужен, чтобы
  «накормить» код данными.
- **Mock** — заглушка + **запоминает, как его вызывали** (аргументы, число
  вызовов); нужен, чтобы **проверить взаимодействие** («был ли вызван `send` с
  таким аргументом»).
- **Fake** — упрощённая **рабочая** реализация (in-memory БД вместо настоящей):
  ведёт себя правдоподобно, но легче.

```python
# stub: просто возвращает данные
# mock: проверяем, что метод вызвали правильно
# fake: in-memory SQLite вместо PostgreSQL (как в этом проекте)
```

Главное различие mock vs stub: **stub** проверяет **состояние/результат**, **mock**
проверяет **поведение/взаимодействие** (был ли вызов). Это частый уточняющий
вопрос.

**Аналогия.** Stub — манекен с табличкой «отвечаю всегда так». Mock — манекен,
который ещё и ведёт журнал «меня дёрнули 2 раза, вот с какими словами». Fake —
дешёвый, но реально работающий тренажёр вместо настоящего станка.

## unittest.mock и MagicMock

Стандартная библиотека `unittest.mock` даёт **`Mock`/`MagicMock`** — объекты,
которые **притворяются чем угодно**: любой вызванный метод/атрибут существует и
возвращает мок, а вызовы записываются.

```python
from unittest.mock import MagicMock

service = MagicMock()
service.get_user.return_value = {"id": 1}     # задаём ответ (stub-роль)

result = service.get_user(1)
assert result == {"id": 1}
service.get_user.assert_called_once_with(1)   # проверяем вызов (mock-роль)
```

Полезное: `return_value` (что вернуть), `side_effect` (бросить исключение или
вернуть разное на разные вызовы), `assert_called_*` (проверка вызовов). `MagicMock`
дополнительно поддерживает dunder-методы. Для async-кода есть **`AsyncMock`**
(возвращает awaitable).

**Аналогия.** `MagicMock` — актёр-дублёр, готовый сыграть любую роль: что ни
попросишь (`service.anything()`) — он «сыграет», а режиссёр (тест) потом сверит по
записи, правильно ли его о чём просили.

## Патчинг: где, а не что

**`patch`** временно **подменяет** объект в коде на мок на время теста (и
возвращает оригинал после). Главное правило, на котором валятся многие: **патчить
надо там, где имя ИСПОЛЬЗУЕТСЯ, а не где определено** («patch where it's used»).

```python
# app/service.py
from app.api import fetch_data        # импортировали сюда

def process():
    return fetch_data()

# тест: патчим имя в МОДУЛЕ service, а не в api!
@patch("app.service.fetch_data")      # ПРАВИЛЬНО
def test_process(mock_fetch):
    mock_fetch.return_value = {"ok": True}
    assert process() == {"ok": True}
# @patch("app.api.fetch_data") — НЕ сработает: service уже импортировал имя к себе
```

Причина: `from x import y` создаёт **новую ссылку** `y` в модуле-импортёре, и
подменять надо именно её. Это самая частая ошибка с `patch`. `patch` используют как
декоратор, контекст-менеджер (`with patch(...)`) или через фикстуры.

**Аналогия.** Патчить «где используется» — как заменить актёра в конкретном
спектакле (модуле), где он сейчас играет, а не в общем агентстве (где определён):
зрители этого спектакля увидят дублёра, только если заменить его на этой сцене.

## monkeypatch и подмена зависимостей

В pytest есть встроенная фикстура **`monkeypatch`** для безопасной (с
авто-откатом) подмены атрибутов, переменных окружения, словарей:

```python
def test_env(monkeypatch):
    monkeypatch.setenv("API_KEY", "test")          # вернётся после теста
    monkeypatch.setattr("app.config.TIMEOUT", 1)
    monkeypatch.setattr(time, "time", lambda: 12345)  # «заморозить» время
```

`monkeypatch` сам **откатывает** изменения после теста — безопаснее ручного
сохранения/восстановления. Но часто **лучший способ изолировать зависимости — это
дизайн через DI**, а не патчинг: если код получает зависимость как аргумент/через
`Depends`, в тесте её **просто передают другую** (mock/fake), без всякого патчинга.
Так в этом проекте тесты подменяют сессию БД и LLM-клиент через
`dependency_overrides` — чисто и без хрупких patch-путей.

**Аналогия.** `monkeypatch` — временно поменять деталь с гарантией вернуть на место.
Но если механизм спроектирован со сменными модулями (DI), деталь просто вставляют
другую при сборке стенда — патчить ничего не нужно.

## Памятка для собеседования

- Дублёры: **stub** (заданные ответы, проверка состояния), **mock** (записывает
  вызовы, проверка **взаимодействия**), **fake** (упрощённая рабочая реализация,
  напр. in-memory БД).
- **`unittest.mock`**: `Mock`/`MagicMock` (`return_value`, `side_effect`,
  `assert_called_*`), `AsyncMock` для async.
- **patch — «where it's used»**: подменять имя в модуле, который его
  **импортировал/использует**, а не где определено (`from x import y` создаёт новую
  ссылку).
- **`monkeypatch`** (pytest) — подмена с авто-откатом; но **DI часто лучше
  патчинга** (передать другую зависимость / `dependency_overrides`).

## Частые ошибки в ответах

- Не различать mock и stub (взаимодействие vs состояние).
- Патчить «там, где определено», а не «где используется» — мок не сработает.
- Мокать всё подряд вместо проектирования через DI (хрупкие тесты, завязанные на
  реализацию).
- Забывать про `AsyncMock` для async-кода и про авто-откат `monkeypatch`.
