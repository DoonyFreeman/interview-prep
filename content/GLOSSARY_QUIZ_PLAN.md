# Glossary Quiz Plan — тесты на знание терминов (Фаза 5d)

План фичи: внутри раздела «Словарь» можно **пройти тест на знание терминов**,
сгруппированный **по областям знаний** (категориям глоссария). Это план, не
реализация.

Опирается на уже готовую Фазу 5c: 138 терминов P0 в `content/glossary.json`,
таблица `glossary_terms`, публичный `GET /api/glossary`, страница `/glossary`.

---

## Зачем

- Глоссарий сейчас «для чтения» — тест превращает его в **активную проверку**:
  пользователь не просто листает, а проверяет, что реально помнит.
- Естественное продолжение основной идеи сайта (квиз по теории) — но лёгкое,
  быстрое и без затрат на LLM.
- Группировка по категориям = «прокачать конкретную область» (БД, async, сети).

## Куда встаёт в роадмап

**Фаза 5d**, сразу после 5c (раздел уже есть — тест надстраивается над ним).
До Фазы 6 (контент) и Фазы 7 (Docker). Дробится на тонкие срезы (см. ниже):
сначала чисто клиентский MVP без бэкенда, прогресс/LLM — отдельными срезами позже.

## Куда встаёт в архитектуру

Ключевое наблюдение: страница `/glossary` **уже загружает все термины с
определениями**. Значит MVP-тест (multiple-choice) можно собрать **целиком на
клиенте** из этих данных — без новых таблиц, эндпоинтов и без LLM. Это самый
лёгкий и self-hosted-дружелюбный путь, в духе стека.

- Дистракторы (неверные варианты) берём из **других терминов той же категории** —
  они бесплатны и осмысленны (близкие по теме = сложнее и полезнее). Если в
  категории < 4 терминов — добираем из остального глоссария.
- Никакого авторинга вопросов: вопрос генерируется из пары «термин ↔ short_md».

## Рекомендуемый формат: multiple-choice (авто-проверка)

Два типа вопросов для разнообразия (микс):
1. **Определение → термин:** показываем `short_md`, выбрать правильный `term` из 4.
2. **Термин → определение:** показываем `term`, выбрать правильный `short_md` из 4.

Почему MCQ, а не открытый ответ с LLM (для MVP):
- мгновенно, без сети и без расхода квоты Gemini;
- работает офлайн и детерминированно (легко тестировать);
- 138 терминов сами дают качественные дистракторы.

Открытый ответ с оценкой LLM — отдельный **опциональный** срез позже (см. 5d-3):
переиспользует существующий `evaluate`-механизм, где `short_md` играет роль
`reference_answer` («оценивай по базе знаний сайта» — ровно как в уроках).

## Срезы (ordering)

### 5d-1 — MVP: клиентский MCQ-тест (без бэкенда)
- Роуты: `/glossary/quiz` (лендинг: список категорий с числом терминов +
  «Случайный тест по всем») и `/glossary/quiz/:category`.
- Логика генерации (новый `frontend/src/lib/glossaryQuiz.ts`): из массива терминов
  (хук `useGlossary(null, "")`) сэмплируем N вопросов выбранной категории,
  миксуем оба типа, генерим 4 варианта (1 верный + 3 дистрактора-сиблинга,
  перемешанные). Чистые функции → легко покрыть unit-тестами (vitest).
- Компоненты: `QuizRunner` (стейт-машина прогона), `QuizQuestionCard`
  (вопрос + 4 кнопки-варианта), `QuizResult` (итог).
- UX прогона: индикатор «3 / 10», вопрос, 4 варианта; после ответа — подсветка
  верного/неверного и **показ определения термина** (обучающее подкрепление),
  кнопка «Дальше».
- UX итога: счёт (X / N, %), список ошибочных терминов со ссылкой на их карточку
  в `/glossary#<slug>`, кнопки «Пройти заново» и «Только ошибки».
- Параметры: длина теста (10 / 20 / все), выбор категории/всех.
- Точки входа: кнопка «Пройти тест» на странице `/glossary`; на заголовке каждой
  категории — мини-кнопка «тест по разделу».
- i18n: блок `glossaryQuiz.*` в `ru.json`/`en.json`.
- Никаких изменений в backend. Никакого LLM.

### 5d-2 — Прогресс по терминам (нужен бэкенд + auth)
- Новая user-state таблица `glossary_term_stats` (`user_id`, `term_slug`,
  `seen`, `correct`, `last_seen_at`) — по аналогии с `attempts`/`concept_mastery`.
- Эндпоинты: `POST /api/glossary/quiz/result` (записать результат прогона),
  `GET /api/glossary/progress` (агрегаты по категориям: % освоено).
- На странице словаря — индикатор освоенности по категориям; режим «тест по
  слабым терминам» (приоритет тех, где мало `correct`).
- Опционально: лёгкий SM-2-подобный возврат слабых терминов (переиспользовать
  `services/sm2.py`), интеграция в существующую очередь повторений.

### 5d-3 — Опциональный режим «открытый ответ» (LLM)
- «Объясни термин своими словами» → оценка через существующий `llm`-механизм,
  где `short_md` = `reference_answer`. Переиспользует `build_eval_prompt`/клиент.
- Дороже (квота Gemini), поэтому строго опциональный режим, не дефолт.

## Открытые вопросы (решить в начале 5d)
- Длина теста по умолчанию (предложение: 10).
- Тип вопросов: только «определение → термин», или микс обоих (предложение: микс).
- Источник дистракторов: только своя категория, или вся база (предложение: своя
  категория с добором из общей при нехватке).
- Персистить ли результаты сразу (5d-2) или MVP оставить эфемерным (предложение:
  MVP эфемерный, прогресс — отдельным срезом).

## Definition of done (5d-1, MVP)
- `/glossary/quiz` и `/glossary/quiz/:category` работают целиком на клиенте.
- Генератор вопросов покрыт unit-тестами (детерминизм при фиксированном seed).
- Прогон: вопрос → ответ → фидбэк с определением → итог со списком ошибок и
  ссылками на карточки терминов.
- i18n ru/en; вход с `/glossary`; без изменений бэкенда и без LLM.
