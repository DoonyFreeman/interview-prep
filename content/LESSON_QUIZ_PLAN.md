# Lesson tests (MCQ self-check) — план

## Зачем

Сейчас в конце каждого урока есть **один способ проверки** — «собеседование с
нейросетью»: открытый вопрос → свободный ответ → LLM грейдит по материалам урока.
Это сильно, но требует усилий (надо сформулировать развёрнутый ответ), занимает
время и зависит от Gemini (квота/сеть).

Добавляем **второй, лёгкий способ** рядом: **тест с вариантами ответов** (MCQ),
который проверяется **мгновенно на клиенте, без нейросети**. Это:
- быстрый объективный self-check «помню / не помню» после чтения теории;
- разминка перед «настоящим» собеседованием с LLM;
- работает офлайн от LLM (никакой квоты, моментальный фидбэк);
- даёт чёткий числовой результат и список «что повторить».

Принципиально: это **не замена** LLM-собеседованию, а более низкий порог входа.
LLM-квиз — про умение формулировать; тест — про узнавание/вспоминание фактов.

## UX-видение (что увидит пользователь)

На странице урока в карточке «Готов проверить себя?» становится **две дорожки**:

```
┌─ Готов проверить себя? ───────────────┐
│  🎤 Собеседование с ИИ   [основная]    │  ← открытые вопросы, LLM-грейдинг (есть)
│  📝 Пройти тест          [основная]    │  ← MCQ, мгновенно, без LLM (новое)
│  Все вопросы урока        [ghost]      │  ← история открытых вопросов (есть)
│  ✓ Отметить пройденным                 │
└────────────────────────────────────────┘
```

Тест: серия карточек «вопрос + 4 варианта». Тапнул вариант → сразу подсветка
верно/неверно + короткое пояснение + ссылка «к теории» (на якорь концепта) →
«Дальше». В конце — экран результата: `ScoreGauge`, «N из M», список ошибок с
правильным ответом, кнопки «Пройти заново / Только ошибки / К уроку».

На карточке урока после первой попытки — бейдж с последним/лучшим результатом
(«Тест: 8/10»). Это создаёт петлю «прочитал → прошёл тест → увидел пробелы →
вернулся к теории → собеседование с ИИ».

## Тип вопросов

Рекомендация — держать формат узким и качественным, а не «всё подряд»:

1. **Single-choice MCQ (основа, ~80%)** — вопрос + 4 варианта, ровно один верный.
   Универсально, легко авторить, легко грейдить.
2. **True / False (~15%)** — для утверждений-ловушек («GIL есть в любой
   реализации Python — верно?»). Тот же рендер, 2 варианта.
3. **Multiple-correct / select-all (опционально, ~5%)** — «выберите все
   утверждения, которые верны». Усложняет грейдинг и UI — **в v1 не делаем**,
   оставляем на потом.

**Code-output** («что выведет этот код?») — заманчиво для Python, но дорого
авторить и аккуратно рендерить (нужен Shiki внутри варианта). **Откладываем**:
формально это частный случай single-choice, можно добавить позже без смены схемы
(вопрос с markdown-код-блоком в тексте).

Итог v1: **single-choice + true/false**, оба — один и тот же рендер (массив
вариантов + индекс верного).

## Сколько вопросов

Цифры из контента: **20 курсов / 97 уроков / 346 концептов** (≈3.6 концепта на
урок).

- **На концепт:** целимся в **2 MCQ** (один на «вспомнить определение», один на
  «применить/отличить»). Это ~7 вопросов на средний урок и **~690 MCQ суммарно**.
  (Минимум — 1 на концепт; больше 3 — уже перебор для «лёгкого» теста.)
- **Тест урока (по умолчанию):** **все MCQ урока** (≈6–12), вопросы и варианты
  перемешаны. 8–12 вопросов — комфортный размер быстрого чек-теста (1.5–3 мин).
- **Если урок большой** (>14 MCQ): берём случайные ~10, взвешивая по слабым
  концептам (как в глоссарном квизе) — чтобы тест оставался коротким.
- **Тест по курсу («экзамен»):** sample ~15–20 вопросов по всем урокам курса
  (≈1 на концепт), режим без мгновенного фидбэка — фидбэк только в конце. Это
  отдельная сущность на странице курса, делаем **во вторую очередь**.

Юзабилити-принцип: тест урока должен быть **коротким и без конфигуратора** — в
этом его смысл против глоссарного квиза (там полноценные настройки). Максимум —
переключатель «Только ошибки» когда есть статистика.

## Контент-модель и авторинг

### Где живут MCQ
Новый файл на курс — `content/courses/<slug>/tests.json`, по структуре зеркалит
`questions.json`, чтобы сохранить привязку к концепту (для «к теории» и прогресса):

```jsonc
{
  "<lesson_slug>": {
    "<concept_slug>": [
      {
        "id": "what-is-gil-1",          // стабильный id (concept_slug + индекс)
        "type": "single",                // "single" | "boolean"
        "text": "В какой реализации Python живёт GIL?",
        "options": [
          "Только в CPython",
          "В любой реализации Python",
          "Только в PyPy",
          "В стандарте языка Python"
        ],
        "correct": 0,                    // индекс верного варианта
        "explanation_md": "GIL — деталь реализации **CPython**; в Jython/IronPython его нет.",
        "difficulty": 2
      }
    ]
  }
}
```

Markdown — источник истины (как у уроков/вопросов); таблица БД — зеркало,
пересеваемое идемпотентно (на концепт MCQ заменяются целиком, как `questions`).

### Стабильный `id`
В отличие от открытых вопросов (id из БД нестабильны — пересев целиком),
прогресс по тесту надо вести по **авторскому стабильному id** (как глоссарий
ключуется по slug). Поэтому у каждого MCQ — явный `id` (`concept_slug` + индекс),
он переживает пересев и служит ключом статистики.

### Качество (главная сложность — дистракторы)
Хороший MCQ = **правдоподобные, но однозначно неверные** варианты. Это самая
трудоёмкая часть. Подход:
- черновик **с LLM-помощью офлайн** (на этапе авторинга, не в рантайме) из уже
  написанных `reference_answer` концепта;
- **ручная вычитка каждого** — однозначность верного, отсутствие «двух верных»,
  дистракторы из типичных заблуждений, короткое `explanation_md`;
- `explanation_md` + якорь концепта → на экране результата ведём «к теории».

Это не рантайм-генерация: грейдинг по знаниям сайта мы не нарушаем — MCQ
авторятся как контент, ровно как открытые вопросы.

## Бэкенд

Следуем строгой слоистости (endpoint → service → repository → model).

### Модель (`app/models.py`)
Новая таблица-зеркало `mcq_questions`:
```
id            PK
question_id   String, unique, index   # авторский стабильный id (для статистики)
concept_id    FK concepts             # привязка (анкор/курс/урок через концепт)
type          String("single"|"boolean")
text          Text
options       Text (JSON-массив строк)
correct_index Integer
explanation_md Text
difficulty    Integer
order_index   Integer
```
Статистика пользователя `mcq_stats` (как `glossary_term_stats`, ключ — стабильный
`question_id`, не FK, т.к. контент пересевается):
```
id, user_id (FK users CASCADE, index)
question_id   String index            # авторский id MCQ
seen, correct Integer
last_correct  Boolean
last_seen_at  DateTime
UNIQUE(user_id, question_id)
```
> ⚠️ Нет Alembic → добавление таблиц требует пересоздания dev `data/app.db`
> (штатно на раннем этапе). На проде — чистый том, без миграции.

### Пайплайн (`app/content/`)
- `loader.py`: парсит `tests.json` в дата-классы (`McqData`), кладёт в bundle.
- `seed.py`: `_seed_mcq` — на концепт удаляет старые MCQ и вставляет заново
  (wholesale, идемпотентно).
- `registry.py` не трогаем (это про markdown уроков).
- `test_content_integrity.py` дополняем: у каждого концепта (или хотя бы каждого
  урока) есть ≥1 MCQ; `correct_index` в диапазоне; варианты непусты/уникальны;
  `type` валиден.

### Эндпоинты (`app/api/endpoints/quizzes.py` или новый `tests.py`)
- `GET /api/quiz/courses/{course}/lessons/{lesson}/test` → MCQ урока.
- `GET /api/quiz/courses/{course}/test` → выборка по курсу (экзамен, 2-я очередь).
- `POST /api/quiz/test/result` (auth) → массив `{question_id, correct}`, апсертит
  `mcq_stats` (как `POST /api/glossary/quiz/result`), возвращает обновл. прогресс.
- `GET /api/quiz/test/progress` (auth) → агрегаты по урокам/курсам + per-question
  для режима «только ошибки».

### ⚠️ Решение про утечку правильного ответа
Открытые вопросы: `reference_answer` **никогда не уходит до ответа** — это
защищает LLM-грейдинг (иначе нечего проверять). **Для MCQ это правило не
применяется и применяться не должно**: варианты ответа по своей природе уже на
экране, и грейдит не LLM, а сравнение индекса. Чтобы дать **мгновенный фидбэк**
(в этом весь смысл лёгкого теста), сервер отдаёт MCQ **вместе с `correct_index` +
`explanation_md`**, а грейдинг идёт на клиенте — **точно как глоссарный квиз**
(он тоже знает правильные ответы на клиенте и шлёт назад только статистику).

Аудитория приватная (автор + друг), ставок никаких — это инструмент обучения, не
экзамен с защитой от списывания. Поэтому осознанно выбираем мгновенный
клиентский грейдинг. (Для «экзамена по курсу» можно при желании прятать
`correct_index` и грейдить per-POST, но в v1 не усложняем.)

Тест целостности должен проверять, что MCQ-утечка **разрешена** только на
тест-эндпоинтах, а `reference_answer` по-прежнему нигде до ответа не светится.

## Фронтенд

### Переиспользование (важно)
Раннер глоссарного квиза (`GlossaryQuizPage`: кнопки-варианты, подсветка
верно/неверно, прогресс, экран результата со `ScoreGauge`) — почти то же самое,
что нужно тесту урока. Выносим общий компонент **`<McqRunner>`**
(`items: McqItem[]`, режим фидбэка `instant | end`, `onFinish(results)`),
и его используют и глоссарный квиз, и тест урока. Чистые хелперы (shuffle,
scoring, отбор ошибок) — отдельным модулем под vitest, по образцу
`lib/glossaryQuiz.ts`.

### Страницы / маршруты
- `LessonTestPage` — `/courses/:c/lessons/:l/test`. Грузит MCQ урока, прогоняет
  `<McqRunner mode="instant">`, по завершении шлёт `POST /api/quiz/test/result`.
  Экран результата: счёт, ошибки с правильным ответом + `explanation_md` + «к
  теории» (`/courses/:c/lessons/:l#anchor`), кнопки «Заново / Только ошибки / К
  уроку».
- (2-я очередь) `CourseExamPage` — `/courses/:c/test`, `mode="end"`.

### Точки входа
- `LessonPage`: вторая основная кнопка **«📝 Пройти тест»** в карточке действий
  (см. UX-схему выше) + бейдж результата после попытки.
- `CoursePage`: ссылка **«Тест по курсу»** (2-я очередь).
- Уроки без авторских MCQ → CTA теста скрыт (или «скоро»), пока контент не залит.

### Конфиг
Минимум: тест урока без настроек (все вопросы, перемешка). Переключатель «Только
ошибки» — когда есть статистика. Полный конфигуратор как у глоссария **не нужен**
— это анти-фича для «быстрого» теста.

### i18n (`locales/{ru,en}.json`)
Новый неймспейс `lessonTest.*` (title, start, correct/incorrect, explanation,
toTheory, result, retry, retryMistakes, toLesson, score, perfect, scoreBadge,
empty). `lesson.startTest` для кнопки на странице урока.

## Прогресс / мастери

- **v1: тест ведёт свою статистику отдельно** (`mcq_stats`), **не трогает SM-2
  `concept_mastery`**. Причина: SM-2 откалиброван под качество LLM-грейдинга
  открытых ответов; подмешивать «угадал из 4» в ту же шкалу — испортит сигнал.
  Показываем независимый «балл теста» по уроку/курсу.
- **Будущая опция:** верный MCQ может давать слабый положительный сигнал в
  мастери (например, мягкий бонус к ease), но это отдельное решение после v1.

## Тесты

- **vitest:** чистые хелперы раннера (shuffle детерминирован по сид, scoring,
  отбор ошибок, кламп длины, перемешка вариантов сохраняет `correct`).
- **backend pytest:** serve-эндпоинт отдаёт MCQ урока; `result` апсертит
  `mcq_stats` и считает агрегаты; `test_content_integrity` — у каждого урока есть
  MCQ, `correct_index` валиден, варианты уникальны; `reference_answer` по-прежнему
  не утекает на pre-answer эндпоинтах.

## A. Учёт прохождения теста в прогрессе

### A.1 Что сейчас «странно»
- На главном (`CatalogPage` → `StatsHero`) прогресс считается **только по
  концептам** (`lib/progress.ts`: SM-2-мастери + «прочитан урок» + «отвечал на
  открытый вопрос»). Результаты MCQ (`mcq_stats`) там **не участвуют вообще** —
  пройденный тест не двигает ни кольцо, ни статы, ни бар курса. Отсюда ощущение,
  что «не учитывается».
- Бейдж на странице урока показывает `correct/total`, где `correct` = число MCQ,
  у которых **последний** ответ верный, из общего числа. Ответил на 3 из 10, 2
  верно → бейдж `2/10` (выглядит как «2 балла из 10», хотя это 2 из 3). Мутно.

### A.2 Семантика «лучшего балла» (важно — чтобы не геймилось)
- Балл прогона = `верных / всего вопросов в прогоне`.
- **В «лучший балл» урока засчитываем только ПОЛНЫЙ прогон** (отвечены все MCQ
  урока). Прогон в режиме «только ошибки» (3 из 10) — НЕ полный, поэтому его
  100% не должны фальшиво поднимать лучший балл. Определяем полноту **на сервере**:
  если множество присланных slug == все slug урока → полный прогон.
- «Пройден» = `best_score ≥ 80`. Состояния урока: **не начат** (нет результатов) /
  **начат** (есть попытки, best < 80) / **пройден** (best ≥ 80).

### A.3 Бэкенд
**Новая таблица `lesson_test_results`** (per-user, per-lesson; ключ строковый —
`course_slug`+`lesson_slug`, как и остальная «переживающая пересев» статистика):
```
id, user_id (FK users CASCADE, index)
course_slug  String index
lesson_slug  String index
attempts     Integer   # число полных прогонов
last_score   Integer   # 0..100, последний полный прогон
best_score   Integer   # 0..100, лучший полный прогон
last_at      DateTime
UNIQUE(user_id, course_slug, lesson_slug)
```
`passed` не храним — выводим на чтении (`best_score >= 80`), порог в одной
константе (`TEST_PASS_THRESHOLD = 80`).
> ⚠️ Это **новая таблица** → `create_all` создаёт её и на существующем томе
> (в отличие от добавления колонки). Пересоздавать БД не нужно.

**`mcq_stats` оставляем** как есть (per-вопрос: seen/correct/last_correct) — для
будущего кросс-сессионного «только ошибки» и покрытия. Роли разводим явно:
`lesson_test_results` = балл/прохождение урока (для бейджа и дашборда),
`mcq_stats` = пер-вопрос (для разбора/ошибок).

**`POST …/test/result`** (`services/lesson_test.record_results`):
1. как и сейчас — апсертит `mcq_stats` по каждому присланному вопросу;
2. **новое**: если присланные slug покрывают все MCQ урока (полный прогон) —
   считает `score = round(100 * correct/total)`, апсертит `lesson_test_results`
   (`attempts += 1`, `last_score = score`, `best_score = max(best, score)`,
   `last_at = now`). Полный прогон детектим по `set(posted) >= all_lesson_slugs`.
3. возвращает расширенный `LessonTestProgressOut`.

**`GET …/test/progress`** (per-lesson) — расширяем ответом:
`{ total, answered, correct, attempts, last_score, best_score, passed }`
(`total/answered/correct` оставляем для совместимости, но бейдж переедет на
`best_score`/`passed`).

**Новый `GET /api/quiz/tests/overview`** (auth) — агрегат для дашборда:
```jsonc
{
  "total": 10,        // уроков, у которых есть MCQ (по всем курсам)
  "passed": 3,        // из них пройдено (best >= 80) у этого юзера
  "started": 5,       // начато (есть попытки)
  "courses": [
    { "slug": "python-core", "total": 10, "passed": 3, "started": 5 }
  ]
}
```
Сервис: множество «уроков с MCQ» получаем join-ом `McqQuestion → Concept →
Lesson → Course` (так оно само растёт по мере 9.2); затем `lesson_test_results`
юзера накладываем, считаем passed/started. Курсы без MCQ в `courses` не попадают
(в пилоте это только `python-core`).

**Схемы (`schemas.py`)**: расширить `LessonTestProgressOut`; добавить
`TestsCourseOverviewOut` + `TestsOverviewOut`.
