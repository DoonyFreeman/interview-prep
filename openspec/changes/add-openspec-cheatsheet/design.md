# Design

## Context

`CheatsheetsPage.tsx` уже показывает общий PDF и условный вход в личную шпаргалку резюме. В `origin/master` эндпоинт `backend/app/api/endpoints/cheatsheets.py` для личного PDF использует `get_current_user`, `has_account_bound_token` и `services/private_hr.py` для сверки `user.id`, `email`, `created_at` с серверным манифестом; PDF сверяется по SHA-256. Статика Vite и FastAPI не обеспечивает такую проверку. Проверенный общий PDF — 19 страниц.

## Goals / Non-Goals

**Goals:** переиспользовать серверную привязку и стиль каталога, сохранить исходные байты отдельного PDF, отделить персональный сборник от публичного.

**Non-Goals:** публичный ридер, новая схема пользователей, изменение общих сборников или инфраструктуры CI/CD.

## Decisions

1. **Привязка к записи аккаунта, не к нику или роли admin.** Оператор проверяет учётную запись владельца в приложении; манифест на приватном томе привязывает её к `user.id`, email и `created_at`. Не записывать настоящие идентификаторы и хеши приватных файлов в репозиторий. Legacy-сессия без account-bound токена должна заново войти. Ошибка или отсутствие привязки закрывает доступ по умолчанию.
2. **Серверные маршруты вместо скрытой статической ссылки.** Предусмотреть `GET /api/cheatsheets/my-openspec` с двумя флагами доступности и два фиксированных маршрута скачивания `.../pdf` и `.../bundle.pdf`. У анонимного запроса нет доступа; у другого аккаунта или legacy-сессии флаги ложны, PDF-ответы — 404. Каждый PDF проверяется независимо, после аутентификации и привязки. Приватные ответы не кэшировать (`Cache-Control: private, no-store`, `Vary: Authorization`); успешная загрузка — `application/pdf`, `Content-Disposition: attachment`, `nosniff`, фиксированное имя файла. Не принимать имя файла или ID владельца из запроса. Интерфейс использует авторизованный API-клиент и скачивание blob; нет общего кэша доступности между сессиями, при смене пользователя старые действия не показываются.
3. **Два файла и манифест на существующем приватном томе.** Хранить их в отдельном подкаталоге вне static с режимами 0700/0600 и владельцем приложения. Общие поля владельца и читаемость JSON проверять строго: их ошибка закрывает оба скачивания. Поля OpenSpec `original_sha256`, `bundle_sha256` и `common_sha256` проверять независимо; отсутствующий, некорректный по типу/формату или несовпадающий хеш делает недоступной только зависимую загрузку. Не ослаблять модель владельца или проверки других личных PDF. Выдавать ровно проверенные байты с ограничением размера. При обновлении атомарно заменить файлы, затем манифест; несовпадение закрывает соответствующее скачивание. Не выводить пути, содержимое или метаданные владельца в HTTP-ошибки и логи.
4. **Персональный сборник готовить офлайн.** На вход взять действующий общий PDF из той же версии, что выкатывается, и исходное вложение из приватной папки. Сохранить порядок и закладки общего PDF; после его страниц добавить OpenSpec с отдельной закладкой на первую из шести новых страниц. Не импортировать активные действия и вложения исходного документа в сборник. Отдельный PDF выдавать байт-в-байт после офлайн-проверки именно тех байтов, чей хеш будет записан в манифест. Проверка должна разобрать структуру документа, включая все уровни закладок, а не ограничиваться ключами каталога и страниц; не выполнять действия и не открывать ссылки при проверке. Отклонять активное содержимое и непроверяемую структуру до записи результата, сохраняя обычные внутренние закладки. Пассивный C2PA-манифест исходника не переносить в сборник. При обновлении общего набора оператор пересобирает личный PDF: проверка версии общего файла в манифесте отключает устаревший личный сборник, не отключая исходный OpenSpec.
5. **Изолированная реализация.** Продолжить в существующем worktree на отдельной ветке. Сверить свежий `origin/master`. Прежние правки публичного реестра, тестов и Markdown — черновик отменённого варианта, не часть нового релиза. Убрать только собственные черновики после сверки diff; не переносить посторонние рабочие изменения. Не синхронизировать черновой PDF обратно в `frontend/public`.

## Risks / Trade-offs

- Ошибочно выбран аккаунт → привязка по подтверждённой записи и проверки с чужим аккаунтом, совпадающим ником и legacy-токеном.
- Раскрытие через статику, кеш, сборку или Git → staging-проверка, неизменность публичных PDF, `private, no-store`, синтетические fixtures и отдельный доверенный канал доставки.
- Устаревший или неполный набор → независимая проверка формата и значения хешей, отключение только затронутой загрузки.
- Действие вне каталога и страниц → проверять вложенные закладки до подготовки оригинала и сборника. Не переписывать исходник, если проверка не пройдена.

## Migration Plan

Миграции БД не нужны. После отдельного разрешения: коммит по scope → PR в `master` → штатный GitHub Actions/GHCR deploy. После успешной выкатки оператор приватно передаёт файлы вне Git/CI и привязывает манифест к подтверждённой записи владельца. Проверить `/health`, обе личные загрузки владельцем, отсутствие кнопок и PDF у другого пользователя, неизменность публичных сборников. При сбое приватной части сначала отозвать доступ, убрав её манифест из активного пути; при сбое приложения — штатный revert или предыдущий рабочий образ с разрешения оператора. Не восстанавливать и не заменять БД или том для отката этого change. Уже скачанные копии отозвать нельзя.

**Decision Map:** пользователь запускает Apply отдельно; оператор подтверждает запись аккаунта и приватное провижининговое действие. Push, merge и production-операции выполняются только с явными полномочиями. Секреты, токены и реальные данные аккаунта не требуются для планирования.
